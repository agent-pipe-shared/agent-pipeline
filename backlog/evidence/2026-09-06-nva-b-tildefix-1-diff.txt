    fix(guard-lifecycle-ready): reject a leading `~` in a read argument
    
    A path-taking argument starting with `~` was admitted as "inside the
    project root" by every read-scope containment lane: the shell expands
    `~` to an absolute home-directory path before argv assembly, but the
    guard's parser treated the literal, nonexistent `~...` string as a
    path segment and walked its ancestors up to root, calling it safe.
    Confirmed live: `cat ~/.ssh/id_rsa`, `rg x ~/.ssh | head -n 5`, and
    `cat ~root/x` were all admitted.
    
    rawReadCandidatePath() (guard-lifecycle-ready.mjs) now returns a
    sentinel absolute candidate (`sep` + the literal value) for a leading
    `~`, which fails containment deterministically without touching the
    filesystem while still self-matching when re-added as its own
    extraRoots entry by the single-command/git-pipeline self-lift
    widening -- preserving the shortcut those callers need to route the
    refusal to GUARD-READ-SCOPE-OUTSIDE-ROOT instead of silently falling
    through to unconditional admission. This one function also covers the
    cat-pipeline and git-pipeline lanes, which reuse it.
    
    approvedReadPath() (guard-command-grammar.mjs, the rg-to-rg/rg-to-head
    bounded pipeline lane) carries an independent one-line twin of the
    same check, returning false unconditionally -- that lane's governing
    branch always denies with an existing code once containment fails, so
    it needs no self-referential-match trick.
