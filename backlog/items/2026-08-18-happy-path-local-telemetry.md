# Add local telemetry for happy-path timing and turn/tool-call counts

## Description

Tool-call and human-turn explosion only became visible after the fact,
through manual transcript forensics. There was no built-in mechanism to
detect this during a run itself.

## Triggering situation

From a greenfield happy-path test report, pipeline version
0.6.0+codex.20260818162535.96cf805, test repo Rune_Test1_Codex_060_52,
full report at docs/pipeline-greenfield-happy-path-handover.md in that
test repo. Cites Section 9, item P2-2 ("Happy-Path-Telemetrie").

## Affected artifact

new local telemetry recorder, feature lifecycle instrumentation.

## Proposal

The pipeline should record locally, per feature: time to durable input;
time to PRD; time from approval to implementation; tool calls per phase;
human handoffs; guard denials and retries; signature attempts; and
review-lane success.

Acceptance test: a local completion report automatically shows whether
happy-path SLOs were met, without exporting any content or private data.

## Design proposal (Wave-4 prep), 2026-08-18

*Prep material for PO triage, not a decision — a Triage section, if/when added, records the actual PO decision. Generated by a Workflow-dispatched read-only design pass (dispatch NVA-W4-DESIGN-happy-path-local-telemetry-design-options) grounded in the current repo state.*

**Problem (restated):** The backlog item (backlog/items/2026-08-18-happy-path-local-telemetry.md) asks for a new local, non-exporting telemetry recorder tied to feature-lifecycle events -- time to durable input, time to PRD, approval-to-implementation, tool calls per phase, human handoffs, guard denials/retries, signature attempts, review-lane success -- plus an automatic local completion report comparing a run against happy-path SLOs. It traces to Section 9 / P2-2 of an EXTERNAL test repo's handover report (Rune_Test1_Codex_060_52, not present in this checkout -- could not be read, so I'm relying only on the item's own prose for that source). The 'Affected artifact' field is deliberately vague ('new local telemetry recorder, feature lifecycle instrumentation') -- it names no concrete files, so I grounded the analysis in what actually exists today by reading the real integration points: plugins/pipeline-core/scripts/pipeline-state.mjs (activeFeature/phase state machine), plugins/pipeline-core/scripts/usage-ledger.mjs (existing read-only, local, transcript-based token telemetry), templates/costs.md and telemetry/costs.md (existing manual per-session cost/turn ledger, MP-20/MP-21), and .claude/guard-override.log.jsonl (existing but partial guard-event log).

**Options:**

1. **Build the full recorder as proposed (item's own Proposal)** — Implement a new local telemetry component that instruments the full feature lifecycle end to end: phase-transition timestamps (durable-input -> PRD -> approval -> implementation), per-phase tool-call/turn counts, human handoff counts, guard denial/retry counts, signature-ceremony attempt counts, and review-lane (Critic) pass/fail outcomes -- culminating in an automatic local completion report that states whether SLOs were met, with an explicit no-export/no-content guarantee. Impact: Gives the PO/Elephant a machine-generated, per-feature dashboard at close instead of manual transcript forensics (the exact gap the triggering incident exposed). Directly answers the open dispatch-bootstrap-cost item's own stated blocker (backlog/items/2026-08-17-...disproportionate.md: 'a real measurement pass needs actual dispatch instrumentation and telemetry, which a read-only triage pass cannot produce'). Tradeoffs: Touches several distinct, non-trivial subsystems: (1) pipeline-state.mjs's activeFeature.phase enum today only has two values, 'design' and 'implementation' (confirmed at lines ~4142 and ~4902) -- there is no 'durable-input' or 'PRD' phase marker and no phase-transition history log, so two of the six requested timing metrics need new schema fields plus matching updates across the ~6 existing pipeline-state*.test.mjs files; (2) guard denials are NOT currently logged anywhere durable -- .claude/guard-override.log.jsonl only records successful GG-rule overrides, not the (much more common) denial case -- so this sub-scope means adding new append-logs inside guard-git.mjs/guard-testpath.mjs/guard-devplan.mjs/human-guard-override.mjs, which is security-adjacent hook code; a sibling open item from the same day (backlog/items/2026-08-18-guard-devplan-and-guard-testpath-have-no-bash-write-lane.md) explicitly says changes to that same guard family 'deserve a dedicated dispatch with real design latitude, not a rushed same-session patch.' Largest, riskiest, most valuable option.
2. **Minimal version: extend existing local telemetry instead of building a new recorder** — Don't build a new component. (a) Add a phase-transition history array with ISO timestamps to activeFeature in pipeline-state.mjs (small, additive schema change) so 'time in phase' and 'approval-to-implementation' become derivable; (b) extend usage-ledger.mjs's existing --row mode (or add a sibling script reusing its already-built, already-audited transcript-parsing code) to also surface turn count and tool-call count per session/subagent -- it already walks every assistant record in the local JSONL transcripts, so tool_use blocks are already in hand, just not counted yet; (c) explicitly defer guard-denial/retry and signature-attempt counting to a follow-on item, since no append-log for denials exists yet and building one means editing the same guard hooks the sibling 2026-08-18 item already flagged as needing its own dedicated design pass. Impact: Delivers the timing and tool-call/turn-count half of the acceptance test relatively cheaply, reusing infrastructure that is already local-only, read-only, and content-free by construction (usage-ledger.mjs's own documented discipline). Does not deliver an automatic pass/fail-vs-SLO completion report or the guard/signature metrics -- so the item's acceptance test as literally written would not be fully met by this option alone. Tradeoffs: Cheaper and lower-risk, but is a partial implementation dressed as a full item close -- would need its own honest re-scoping of the acceptance criteria (drop or explicitly re-defer the guard-denial/signature/review-lane metrics) rather than claiming the item is done. Two separate follow-on items would then need to exist and be tracked (guard/signature telemetry; SLO report format), which adds backlog bookkeeping overhead.
3. **Defer/merge into Sprint Alfred rather than opening standalone Pipeline work** — Don't triage this as independent Wave-4 work at all. The 2026-08-17 dispatch-bootstrap-cost item (backlog/items/2026-08-17-goldfish-critic-dispatch-bootstrap-token-cost-is-disproportionate.md) was itself reassigned to Sprint Alfred on 2026-08-18 specifically because its own rationale says a fix needs 'actual dispatch instrumentation and telemetry.' That is substantially the same underlying capability this item wants (per-phase/per-dispatch tool-call and turn counting), approached from a different angle (happy-path SLOs vs. bootstrap-cost breakdown). Re-scope this item's Decision to 'merge into Sprint Alfred's telemetry foundation work' rather than dispatching a second, independently-designed instrumentation effort. Impact: Avoids building two overlapping local-telemetry mechanisms under two different names in the same release window, and lets one dispatch design a single instrumentation layer that serves both consumers (SLO reporting here, cost-breakdown there). Costs a delay: this item's acceptance test doesn't ship until Sprint Alfred picks it up. Tradeoffs: Requires the PO/Elephant to actually confirm Sprint Alfred is the right home and that the two items' needs are compatible enough to share one design (plausible from what I read, but not verified against Sprint Alfred's own scope doc, which I did not read in this pass). Risks the item quietly stalling if Sprint Alfred's queue is long -- 'merged into a queue' can become a soft reject if not tracked with its own checkpoint.

**Recommendation:** A hybrid of Option B and Option C: do the minimal, low-risk extension of usage-ledger.mjs and pipeline-state.mjs's phase history now (cheap, reuses already-audited read-only/no-export infrastructure, and directly unblocks the open 2026-08-17 dispatch-bootstrap-cost item's stated blocker), but explicitly fold the guard-denial/retry and signature-attempt telemetry sub-scope into Sprint Alfred rather than building it standalone here -- that sub-scope touches the same guard-hook family (guard-git.mjs/guard-testpath.mjs/guard-devplan.mjs/human-guard-override.mjs) the sibling 2026-08-18 item already flagged as needing a dedicated design pass, so building it twice under two uncoordinated backlog items is the real risk to avoid. Re-scope the acceptance test accordingly (timing + tool-call/turn counts + a simple local report now; guard/signature/review-lane metrics as a named Sprint Alfred follow-on) rather than accepting the item's full six-metric acceptance test as one atomic close.

**Risks/dependencies:** 1) The item's cited source (docs/pipeline-greenfield-happy-path-handover.md, Section 9/P2-2, test repo Rune_Test1_Codex_060_52) lives in an external repo not present in this checkout -- I could not verify the original finding's exact wording or severity beyond the backlog item's own paraphrase. 2) pipeline-state.mjs's activeFeature.phase enum is currently exactly {'design','implementation'} with an F1 history noting a prior writer/reader schema-drift bug already fixed once for this exact field -- any change adding phase values or a transition-history array needs care and a full re-run of the existing pipeline-state*.test.mjs suite (6 files touch phase/approval semantics directly). 3) Direct scope overlap with backlog/items/2026-08-17-goldfish-critic-dispatch-bootstrap-token-cost-is-disproportionate.md (reassigned to Sprint Alfred 2026-08-18) -- both want dispatch/phase-level tool-call instrumentation; triaging this item without cross-referencing that one risks duplicated design work. 4) Direct hook-family overlap with backlog/items/2026-08-18-guard-devplan-and-guard-testpath-have-no-bash-write-lane.md (open, same day, explicitly deferred pending its own design pass) -- any guard-denial-logging sub-scope of this item touches the identical files. 5) Whatever design ships must preserve the no-content/no-export discipline usage-ledger.mjs already establishes (path-free output, reads local transcripts only, never writes/exports); the acceptance test's 'without exporting any content or private data' language should be checked against that existing precedent rather than re-derived from scratch. 6) CLAUDE.md's own recently-learned lesson about signature-ceremony request files (.git/agent-pipeline/human-guard-overrides/requests/) being byte-identity-sensitive means any future signature-attempt telemetry must be strictly read-only and never run mid-ceremony.
