# PO key and trust anchor as one-time machine onboarding task

## Description

In the feature-plan gate, two keys had to be created, an identity
corrected, and a trust anchor manually committed. This forced manual
setup work into what should be a routine plan-approval flow.

## Triggering situation

Greenfield happy-path test report, pipeline version
0.6.0+codex.20260818162535.96cf805, test repo Rune_Test1_Codex_060_52; see
docs/pipeline-greenfield-happy-path-handover.md in that test repo,
Section 9, item P1-7.

## Affected artifact

PO key setup flow, trust anchor materialization, plan-approval gate.

## Proposal

When signature mode is active, the first pipeline onboarding should check
early whether a machine-wide configured PO authority already exists. If
it exists, its public anchor is materialized in a controlled way. If it
does not exist, there is exactly one separate setup ceremony with an
explicit name prompt. Local, reversible plan approvals must not
unnecessarily depend on this push infrastructure.

Acceptance test: the first real push requires only the passphrase; no key
setup and no manual JSON/git step occurs during the feature flow.

## Triage (filled in by the Elephant of the next Pipeline session)

- **Decision:** Accepted — hybrid: one shared detection helper (machine plane → local PO authority → materialization snippet) used by both this item's onboarding-time guidance and `full-push-preflight-before-signature`'s trust-anchor check; the onboarding-time guidance itself is this item's actual deliverable.
- **Rationale:** PO 2026-08-18 accepted the analyst's recommendation as-is.
- **Assignment (if accepted):** Nova Wave 4 implementation, coordinate the shared helper with `full-push-preflight-before-signature` (ideally one dispatch, to avoid building the helper twice).
- **Date:** 2026-08-18


## Design proposal (Wave-4 prep), 2026-08-18

*Prep material for PO triage, not a decision — a Triage section, if/when added, records the actual PO decision. Generated by a Workflow-dispatched read-only design pass (dispatch NVA-W4-DESIGN-po-key-trust-anchor-onboarding) grounded in the current repo state.*

**Problem (restated):** Backlog item pipeline.po-key-trust-anchor-onboarding (backlog/items/2026-08-18-po-key-trust-anchor-onboarding.md) reports that during a greenfield happy-path test (source is docs/pipeline-greenfield-happy-path-handover.md in an EXTERNAL test repo not present in this checkout, Section 9 item P1-7 -- I could not read it directly and rely only on the item's own summary), the operator had to create two keys, correct a recorded identity, and manually commit a trust anchor before the first real push could go through -- friction the item wants folded into a one-time machine onboarding step instead of ad hoc rediscovery during the feature-plan gate.

Grounding in the actual code (the item's 'Affected artifact' names 'PO key setup flow, trust anchor materialization, plan-approval gate' loosely rather than exact paths, so I traced the real components):

1. Trust-anchor materialization: `project/critical-human-proof.json` is GS-2 gate-strength protected (plugins/pipeline-core/hooks/guard-gate-strength.mjs lines 84-87) -- an agent can NEVER Edit/Write it directly, by design ('An agent that can weaken its own gate has no gate', same file lines 4-16). The only routes in are a genuine human hand-edit+commit outside the session, or the audited human-guard-override (HGO) signed-capability ceremony (plugins/pipeline-core/lib/human-guard-override.mjs). ADR-0056 decision 7 (docs/adr/0056-push-approval-mode.md lines 176-196) already states the anchor is public data and 'committing it costs nothing' -- the cost is entirely the ceremony/discovery friction, not secrecy.

2. Key creation: `plugins/pipeline-core/scripts/po-human-approval.mjs`'s `setup` subcommand (lines ~910-976) is already idempotent -- rerunning it against an existing key/authority at the resolved directory is a no-op, and there is already a built-in name-correction path (lines 938-949, the 'existing PO authority record predates --human-name' upgrade branch) plus an explicit identity-mismatch refusal (lines 951-962) rather than silent overwrite. Key-directory resolution already has a 4-tier precedence (explicit --directory > this repo's own repo-scoped store > machine-scoped plane's poKeyDirectory > $PIPELINE_PO_APPROVAL_DIRECTORY env, lines 424-473), following the PO-KEYDIR-01(A) 2026-08-11 decision (backlog/items/2026-08-10-po-key-directory-default-should-be-repo-scoped-not-machine-wide.md) that deliberately made the DIRECTORY default repo-scoped, not machine-wide -- this item's ask must not be read as reopening that decision; it targets the ANCHOR artifact, not the directory setting.

3. Onboarding already has a 'once per machine' push-approval guidance step (`collectPushApprovalPreferenceAction`, plugins/pipeline-core/lib/project-onboarding-v3.mjs lines 3960-4010) that fires only when the machine plane (`~/.agent-pipeline/machine.json` via machine-plane.mjs) has never been written, walks the PO through creating a key in their own terminal, and tells them to record the choice into pipeline.user.yaml and the machine plane -- but it explicitly, by design, never touches `project/critical-human-proof.json` (comment lines 3979-3985: 'Deliberately does NOT write pipeline.user.yaml, machine.json, or a key directory itself'). So even after a machine-wide key exists and is recorded, EVERY subsequent project on that machine still needs its own from-scratch discovery and manual GS-2 edit to materialize a trust anchor -- nothing today reads the machine plane's already-known authority and offers to propagate its public digest into a new project. That gap is real and is the actual mechanism behind the item's complaint.

4. Plan approval (`submit-plan`/`approve-plan` in plugins/pipeline-core/scripts/pipeline-state.mjs, backed by `poGateAuthority`/`validatePoGateAuthorityForRepository` in plugins/pipeline-core/lib/po-gate-authority.mjs) has ZERO references to keys, signatures, openssl, or trust anchors anywhere in po-gate-authority.mjs -- plan approval today does NOT depend on the push-signing infrastructure. The item's sentence 'Local, reversible plan approvals must not unnecessarily depend on this push infrastructure' is therefore already true in the current code and should be read as a preserve-this-invariant constraint on the fix, not as a description of an existing bug.

A closely related sibling item from the SAME source report (backlog/items/2026-08-18-full-push-preflight-before-signature.md, P0-4 in the same Section 9) proposes a new 'plan-push coordinator' whose atomic preflight explicitly includes 'a valid trust anchor with external key-directory binding' -- meaning trust-anchor detection logic is about to be built twice unless the two items are coordinated.

**Options:**

1. **A. Detect-and-guide at onboarding: reuse the machine plane, propose materialization, single named ceremony** — Extend the existing 'once per machine' onboarding guidance (project-onboarding-v3.mjs's collectPushApprovalPreferenceAction and its neighbors) with a new detection step that: (1) reads the machine-scoped plane's poKeyDirectory and, if a valid local PO authority record already exists there, computes its public key digest and hands the PO a ready-to-use trustAnchors snippet plus the exact one-line commit (or HGO ceremony) command to add it to THIS project's project/critical-human-proof.json; (2) if no machine-wide authority exists yet, folds the --human-name prompt into the guidance text up front so the ceremony is framed and run once, rather than discovered mid-ceremony as a second call. Impact: For a PO who already has a machine-wide key (the common repeat-project case), a fresh repo's push route becomes usable after one proposed, pre-composed edit instead of the operator rediscovering the file's shape and the GS-2 escape route from scratch. For a genuinely first-time machine, the 'two keys created' friction goes away because the name is asked before the ceremony starts rather than causing a failed first attempt. Tradeoffs: Cannot remove the human step entirely -- GS-2 is a deliberate, unliftable protection (guard-gate-strength.mjs's own stated purpose), so the acceptance test in the item's own Proposal ('no manual JSON/git step occurs') is not fully achievable without weakening that guard, which nothing here proposes. Touches project-onboarding-v3.mjs, a very large and heavily diff-shape-disciplined file (per its own extensive doc comments), so review cost is nontrivial. Must be built as a shared detection helper rather than inline, so it can be reused by the sibling P0-4 push-preflight coordinator without duplicating anchor-lookup logic -- otherwise the two items diverge on what counts as 'a valid trust anchor.'
2. **B. Minimal version: surface-only guidance text, no new detection state or name-prompt restructuring** — Add a small, non-mutating addition to the existing onboarding guidance: if the machine plane's poKeyDirectory resolves to a directory with an existing local authority record, print the exact trustAnchors JSON and the exact command to commit it; otherwise, change nothing about the ceremony itself. No new 'once per project' state, no restructuring of the name-prompt flow. Impact: Removes only the 'operator didn't know this existed / didn't know the file's shape' cost. The number of manual/ceremony steps stays exactly what it is today for a first-time machine (still discoverable as a failure mid-ceremony if --human-name is omitted, since that path is untouched). Tradeoffs: Does not address the 'two keys had to be created' or 'identity corrected' parts of the triggering situation at all -- only the trust-anchor rediscovery cost. Much smaller diff and much lower risk to review/land, and does not touch the identity/name-prompt code path at all, so it can't regress po-human-approval.mjs's existing (working) mismatch/upgrade logic. A reasonable first slice if Wave-4 wants to de-risk before committing to the fuller Option A.
3. **C. Defer/fold into the sibling P0-4 push-preflight coordinator instead of a separate onboarding change** — Decline a standalone onboarding-time fix and instead let trust-anchor detection be built once, inside the 'plan-push coordinator' that backlog/items/2026-08-18-full-push-preflight-before-signature.md (P0-4, same source report) already proposes, which explicitly lists 'a valid trust anchor with external key-directory binding' among its atomic preflight checks. Impact: Zero new onboarding-time surface for this item specifically; the anchor-detection logic gets built exactly once instead of twice, inside a component the PO is already being asked to triage separately. Tradeoffs: P0-4's coordinator is scoped to run 'before the subject digest is generated' -- i.e. at push time, not at project setup. This item's own Proposal explicitly asks for the check to happen 'early' in 'the first pipeline onboarding,' which is a materially earlier and different moment; a PO who never approaches push until much later in a feature would still hit the same rediscovery gap at that point, just wrapped in a preflight failure message instead of surfaced proactively. Also leaves this item unscheduled behind an item that is itself still 'open' with no assignment.

**Recommendation:** A hybrid of A and C: accept the item, but scope its implementation to a single shared helper function (read machine plane -> resolve local PO authority -> compute the trustAnchors materialization snippet) that BOTH this item's onboarding-time guidance and the sibling P0-4 push-preflight coordinator call, rather than building either in isolation. Land the onboarding-time guidance addition (Option A) as the actual deliverable for this item, since it is the only one of the three that satisfies the 'early, at onboarding' half of the item's own Proposal that P0-4 does not cover -- but rewrite the item's acceptance test before assignment: 'no manual JSON/git step occurs' is not achievable without weakening GS-2 (guard-gate-strength.mjs's whole point is that this file cannot be agent-written), so the realistic acceptance criterion is 'at most one pre-composed, copy-pasteable human step, proposed automatically, with the ceremony's human-name requirement never causing a failed first attempt.' If Wave-4 wants a smaller, faster-landing slice first, Option B is a safe, low-risk subset that can ship before the full Option A/C coordination lands.

**Risks/dependencies:** 1. Direct implementation dependency: this item's detection helper and P0-4's push-preflight coordinator both need the same 'does a valid machine-wide/project trust anchor exist' answer -- sequence or co-design them so the logic isn't written twice and doesn't drift (P0-4 is itself unassigned/open, so this item may need to either wait for it or be built first and then have P0-4 reuse it). 2. Do not let this item's fix regress PO-KEYDIR-01(A)'s 2026-08-11 decision that the KEY-DIRECTORY default is repo-scoped, not machine-wide (backlog/items/2026-08-10-po-key-directory-default-should-be-repo-scoped-not-machine-wide.md) -- this item is about the trust-ANCHOR artifact (public key digest committed into project/critical-human-proof.json), a different thing from where the private key lives, and the two must not get conflated in the dispatch. 3. Preserve the confirmed-true invariant that submit-plan/approve-plan (po-gate-authority.mjs) never gain a dependency on signature-key infrastructure -- any implementation that routes trust-anchor materialization through the plan-approval gate itself would be a regression the item's own text explicitly warns against. 4. Whatever 'controlled way' Option A's materialization step uses (a shown manual diff+commit, or the existing HGO signed-Edit ceremony) must go through the existing audited GS-2 escape routes only -- guard-gate-strength.mjs's design rationale is explicit that no new bypass may be added for this file. 5. The item's only cited evidence is a summary inside this backlog item itself; the underlying handover doc (docs/pipeline-greenfield-happy-path-handover.md) lives in an external test repo (Rune_Test1_Codex_060_52) not present in this checkout, so the exact sequence of 'two keys, an identity corrected' could not be independently verified beyond what the current code plausibly explains -- worth asking the source session for the literal transcript/commands if precision matters before scoping a dispatch.
