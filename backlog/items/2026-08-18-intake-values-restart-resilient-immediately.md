# Make intake values (git author, language, profile) restart-resilient immediately after being answered

## Description

Git author, language, and profile were answered by the PO before a
restart, but were asked again after the restart. The proposed change is
to persist the PO's answers into a private, restart-resilient intake
state as soon as the PO responds. Git identity can either be set
immediately at the repository-local level, or held safely in this state
until the first commit.

## Triggering situation

From a greenfield happy-path test report for pipeline version
0.6.0+codex.20260818162535.96cf805, test repo Rune_Test1_Codex_060_52,
full report at docs/pipeline-greenfield-happy-path-handover.md in that
test repo. Section 9, item P1-4.

## Affected artifact

intake flow; project-onboarding-v3.mjs; restart barrier.

## Proposal

Persist each PO-answered intake value (git author, language, profile)
into a private, restart-resilient intake state as soon as it is answered,
with git identity either set immediately repository-locally or held
safely in this state until the first commit.

Acceptance test: no mandatory question that has already been answered is
asked again after a restart.

## Design proposal (Wave-4 prep), 2026-08-18

*Prep material for PO triage, not a decision — a Triage section, if/when added, records the actual PO decision. Generated by a Workflow-dispatched read-only design pass (dispatch NVA-W4-DESIGN-intake-values-restart-resilient-immediately) grounded in the current repo state.*

**Problem (restated):** Git author, language, and profile are each answered by the PO through a `collect-input` ask inside `project-onboarding-v3.mjs`, but none of the three answers is written anywhere durable before the command that actually consumes it runs (git config for author identity is deliberately deferred per a 2026-08-17 PO decision; language is only consumed via kickoff's `--language` flag; profile only via `pipeline-state.mjs submit-plan --profile`). A restart between "PO answers" and "value gets used" wipes the answer from conversational memory, so the same mandatory question gets asked again, which is the concrete P1 finding from the Rune greenfield happy-path report.

**Options:**

1. **Full parity with restart-barrier** — Build one new persisted intake-state module for all three fields, reusing codex-onboarding-runtime.mjs's private-directory and CAS/generation/ticket discipline verbatim. Impact: Satisfies the acceptance test for all three fields in one coherent, maximally-audited place. Tradeoffs: Replicates CAS/ticket machinery designed to guard runtime-executable drift across a Codex restart -- a threat model that doesn't apply to a PO's typed string; heavier to build and review than the problem requires.
2. **Targeted minimal hybrid** — Lean on git config's existing restart-resilience for identity (already re-probed live by unresolvedAuthorIdentityKeys(), but kept in the 'hold, don't set until first commit' branch per the 2026-08-17 PO decision) and add one small, machine-plane.mjs-style atomic-write JSON file (temp-then-rename, no CAS) for language + profile + the held identity value, in the same private onboarding directory codex-onboarding-runtime.mjs already resolves. Impact: Same acceptance-test guarantee as the full option, with a much smaller new-code surface because it copies the lighter existing pattern instead of the heavier one. Tradeoffs: Still requires a new schema/module and wiring at three call sites; the 'held' identity value still needs the same file as language/profile, so scope is nearly identical to Option A -- the savings are in implementation weight, not field coverage.
3. **Defer to the SS6 bootstrap-question taxonomy** — Do not build new persisted state now; close or defer this item, pointing at machine-plane.mjs's own comment that language (and this class of 'ask once, persist forever' questions) is already earmarked for a later, comprehensive bootstrap-question design (SS6). Impact: Zero new code now; the PO keeps re-answering the same questions after every restart until SS6 ships. Tradeoffs: Contradicts a fresh, concrete P1 field report with real, recurring PO cost; SS6 has no committed timeline in anything read, so this is an open-ended deferral, not a bounded wait.

**Recommendation:** Option B (targeted minimal hybrid), with one hard constraint: keep git identity in the 'hold, do not set until first commit' branch exactly as the 2026-08-17 closed item settled -- do not let the implementer 'simplify' by switching to setting git config immediately, since that would relitigate a recent, explicit, PO-tested decision rather than extend it. Concretely: one small machine-plane.mjs-pattern atomic-write file (not the restart-barrier's CAS/ticket apparatus, which guards a different threat) in the private onboarding directory codex-onboarding-runtime.mjs already resolves, storing gitAuthorName/gitAuthorEmail/language/profile the instant each is answered, consulted by all three existing collect-input call sites before they re-ask.

**Risks/dependencies:** Must not repurpose resume-hint.json (explicitly non-authoritative and discardable -- using it as the source of truth reintroduces the exact bug). Whoever implements this must read the full 2026-08-17 git-identity item before touching collectAuthorIdentityAction()'s guidance again. Conceptually overlaps the deferred SS6 bootstrap-question taxonomy referenced in machine-plane.mjs -- worth a Triage note that this is a narrow field-scoped slice, not a substitute, so a future SS6 pass doesn't have to unwind a conflicting mechanism. New private-state file must not collide with codex-onboarding-runtime.mjs's existing files (restart-barrier.json, current-readback.json, tickets/, .writer-lock) in the same directory.

**Estimated complexity:** medium
