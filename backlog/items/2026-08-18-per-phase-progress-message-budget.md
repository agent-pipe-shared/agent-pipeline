# Limit session progress messages to one start and one completion per phase

## Description

Internal pipeline movements were surfaced to the user as many separate
progress messages. This adds unnecessary noise to the human-facing turn
stream, obscuring the signal of what actually needs the PO's attention.
Routine internal readbacks were not being distinguished from messages
that genuinely required visibility.

## Triggering situation

From a greenfield happy-path test report, pipeline version
0.6.0+codex.20260818162535.96cf805, test repo Rune_Test1_Codex_060_52,
full report at docs/pipeline-greenfield-happy-path-handover.md in that
test repo. Cites Section 9, item P2-1 ("Status- und Turn-Budget").

## Affected artifact

session progress messaging conventions.

## Proposal

Limit progress messaging to at most one short start message and one short
completion message per phase. Additional messages are only sent when a
human decision is needed, a real blockage occurs, or a step's runtime
exceeds 60 seconds; routine readbacks stay internal.

Acceptance test: no additional PO turn is generated between intake and
PRD approval, and none between approval and the result.

## Triage (filled in by the Elephant of the next Pipeline session)

- **Decision:** Accepted — new `roles/elephant.md` rule (EL-3x): one start + one completion message per lifecycle phase, exceptions for a real decision/blockage/step >60s; anchor "phase" to `operating-model.md` §4's 8-phase list, treat the 60s threshold as a soft heuristic.
- **Rationale:** PO 2026-08-18 accepted the analyst's recommendation as-is; triage jointly with `transactional-readbacks-not-status-cascades` since both were flagged as related noise sources.
- **Assignment (if accepted):** Nova Wave 4 implementation.
- **Date:** 2026-08-18


## Design proposal (Wave-4 prep), 2026-08-18

*Prep material for PO triage, not a decision — a Triage section, if/when added, records the actual PO decision. Generated by a Workflow-dispatched read-only design pass (dispatch NVA-W4-DESIGN-per-phase-progress-message-budget-wave4-design-options) grounded in the current repo state.*

**Problem (restated):** Backlog item backlog/items/2026-08-18-per-phase-progress-message-budget.md (Wave-4, priority P2-1, sourced from the Rune Codex 0.6.0 greenfield happy-path handover, an EXTERNAL test-repo doc not present in this checkout) proposes capping the Elephant's PO-facing progress chatter to one short start message and one short completion message per lifecycle phase, with exceptions for real decisions/blockages/>60s steps. 'Affected artifact' in the item is stated only as the vague phrase 'session progress messaging conventions' -- it names no concrete file. I confirmed there is no existing single convention document that already enforces a per-phase message cap: the closest governing rule today is roles/elephant.md EL-17 (PO communication contract, section 7, lines ~243-251), which covers decision-question formatting, action-request framing, and a phase-start orientation block, but says nothing about capping routine progress narration mid-phase. operating-model.md section 4 (lines 87-122) defines the 8 lifecycle phases (Bootstrap, Intent/triage, Spec/readiness, Human plan gate, Dispatch, Verify, Critic, Close) that 'per phase' would have to map onto; its only nearby existing rule (lines 107-113) is about the Elephant tolerating an ABSENT early progress message from a dispatched Goldfish worker -- a different concern (orchestration patience toward a subagent) from this item's concern (how much the Elephant itself narrates to the human PO). A closely related sibling Wave-4 item, backlog/items/2026-08-18-transactional-readbacks-not-status-cascades.md (P1-8, same source report, higher priority), targets a more mechanical/tooling-level version of the same noise problem: coordinator commands (pipeline-state.mjs) triggering redundant separate status/continuity/handover readback calls after one mutation, proposing a single consolidated readback object instead. The two items overlap in spirit (reduce redundant round-trips/messages) but operate at different layers -- one is about CLI tool output shape, this one is about the Elephant's own chat narration cadence -- and should probably be triaged with that overlap made explicit rather than independently. I also found a directly relevant prior investigation, backlog/items/2026-08-10-happy-path-turn-and-wall-clock-cost-is-not-externally-defensible.md, whose 2026-08-18 forensic time-accounting pass (a full phase-by-phase transcript audit of a real happy-path session) found the actual dominant wall-clock costs were CLI-syntax rediscovery subagents, Critic-round friction, and push-approval-chain failures -- NOT a proliferation of Elephant progress messages to the PO. That pass did not measure PO-facing message COUNT/noise at all (a distinct axis from wall-clock cost), so it neither confirms nor refutes this item's premise, but it is evidence that if the goal is to cut the ~2h happy-path cost, this item is not where the time actually goes -- its value case is specifically signal-to-noise for the human reading along, not raw wall-clock savings.

**Options:**

1. **Adopt the item's own proposal as a new elephant.md rule (EL-3x)** — Add a new numbered MUST rule to roles/elephant.md section 7 (alongside EL-17), stating the exact budget from the item: at most one short start message and one short completion message per lifecycle phase (the 8 phases in operating-model.md section 4), with explicit exceptions for (i) a genuine human decision needed, (ii) a real blockage, (iii) a step whose runtime exceeds 60 seconds. Reference the phase list in operating-model.md section 4 explicitly so 'phase' has one canonical meaning, not an ad hoc one per session. Keep EL-17's existing rules (decision-question formatting, orientation block) unchanged and complementary. Impact: PO reads a much quieter turn stream: internal tool calls, readback confirmations, and routine sub-steps within a phase (e.g. multiple pipeline-state.mjs inspections during Dispatch) stay in the Elephant's own working context and never surface as separate chat turns, unless one of the three exceptions fires. The item's own acceptance test becomes directly checkable: no PO turn is generated between intake and PRD approval, none between approval and result, for a normal run. Tradeoffs: A rule stated only in prose is easy to under-observe in practice -- nothing mechanically enforces the cap the way guard-lifecycle-ready.mjs enforces shell-command shape; adherence depends on the Elephant self-policing each turn, the same failure mode that produced EL-17 in the first place (ad hoc adoption, later formalized after incidents). Also introduces a judgment call the rule cannot fully specify: what counts as 'a real blockage' or a step whose duration is genuinely unknown-until-tried, which risks either over-suppression (PO loses visibility into a stall) or the rule being quietly ignored under time pressure. Requires deciding whether the 60-second threshold is even measurable by the Elephant in a chat-only session (it usually has no wall-clock instrumentation on its own narration).
2. **Minimal version: silence-by-default only for identified noisy sub-cases, no blanket per-phase cap** — Instead of a general one-start/one-completion budget for every phase, target only the concrete noise sources actually named in the sibling P1-8 item and this item's own Description -- 'routine internal readbacks' (status/continuity/handover queries after a mutation) -- and fold the fix into the sibling transactional-readbacks item's readback-consolidation work rather than adding a second, overlapping rule. No new elephant.md rule at all; instead a narrower addition to EL-17 or a short note cross-referencing the consolidated-readback behavior once P1-8 ships. Impact: Removes the most concrete, already-diagnosed noise source (readback cascades) without committing to a blanket numeric budget across all 8 lifecycle phases, some of which (e.g. Dispatch, which can span a long async Goldfish run) may legitimately need more than one PO-visible touchpoint. Avoids maintaining two overlapping rules for what is largely the same underlying complaint. Tradeoffs: Under-delivers relative to the item's own acceptance test, which explicitly wants zero additional PO turns across two named phase boundaries (intake-to-PRD-approval, approval-to-result) -- a readback-only fix does not guarantee that, since an Elephant can still generate multiple prose progress updates that are not readback calls at all. Effectively defers/narrows this item rather than accepting its proposal as written; would need the PO's explicit sign-off that the narrower scope satisfies the original complaint, since the source report treated P2-1 and P1-8 as two distinct findings, not one.
3. **Defer: fold into a future PO-facing UX/telemetry pass instead of a standalone Wave-4 acceptance** — Mark the item accepted-in-principle but not scheduled standalone; revisit it together with backlog/items/2026-08-18-happy-path-local-telemetry.md and the still-open 2026-08-10 turn/wall-clock-cost investigation once that investigation's recommended fixes (CLI-rediscovery defect class, push-approval friction, commit-bundling rework) are actually implemented -- on the reasoning that message-count noise is a second-order polish item (correctly P2, the lowest Wave-4 priority tier) compared to the P0/P1 items already queued from the same report. Impact: No immediate elephant.md change; the PO's attention and the next dispatch slot go to higher-priority Wave-4 items first. Lets the pipeline avoid designing a message-budget rule twice if the local-telemetry item ends up wanting to instrument message counts anyway, which could make the eventual rule better-informed. Tradeoffs: Leaves the actual PO complaint (noisy turn stream obscuring signal) unaddressed for however long the deferral lasts, on an item that is cheap to fix now (a prose rule addition, not code) -- deferring a small, well-scoped, low-risk item mainly to sequence it after unrelated larger items has low benefit and a real cost (PO keeps experiencing the noise every session until it lands). Given the PO's own stated preference elsewhere in this repo's memory ('PO wants decisions made now, not deferred' -- resolve and execute the same session), an open-ended defer cuts against established PO preference unless there's a concrete blocking dependency, which I did not find one of.

**Recommendation:** Accept the item's own proposal (Option 1), but implement it as a single elephant.md rule that explicitly cross-references and gets triaged in the same PO conversation as the sibling P1-8 item (transactional-readbacks-not-status-cascades) rather than in isolation -- the two are the same underlying complaint (cascading, redundant PO-visible chatter) surfaced at two different layers (chat narration vs. CLI readback shape) from the same source report, and triaging them separately risks either duplicate rule text or a gap between them. Concretely: adopt Option 1's rule text nearly verbatim, but (a) anchor 'phase' explicitly to the operating-model.md section 4 lifecycle list so there's no ambiguity, (b) treat the 60-second threshold as a soft heuristic rather than a literally measured one, since the Elephant has no built-in wall-clock instrumentation on its own narration, and (c) note in the Triage 'Rationale' that this rule is complementary to, not a substitute for, whatever P1-8 ships for coordinator-command readback consolidation. This is small, cheap, low-risk, and directly actionable without new tooling -- there is no reason to defer it (Option 3) given no blocking dependency was found, and narrowing it (Option 2) would leave the item's own acceptance test unmet.

**Risks/dependencies:** 1) Overlap with P1-8 (transactional-readbacks-not-status-cascades): both items came from the same source report and address related noise; triage them together or note the relationship explicitly, otherwise risk drafting two rules that either conflict or leave a gap between 'chat narration' and 'tool readback' noise. 2) The item's source evidence (docs/pipeline-greenfield-happy-path-handover.md, Section 9, item P2-1) lives only in the external test repo Rune_Test1_Codex_060_52, not in this checkout -- I could not independently read the original observation, only the backlog item's own paraphrase of it; the Triage should note this provenance limitation. 3) No enforcement mechanism exists or is proposed for this rule (unlike, e.g., guard-lifecycle-ready.mjs for shell commands) -- it relies on Elephant self-discipline the same way EL-17 does, so its real-world compliance rate is unverifiable except by later Critic/PO review of session trajectories; consider whether EL-17's existing 'Check' pattern (a Critic reviewing session trajectories flags violations) should be extended to cover this new rule too. 4) The related, higher-priority 2026-08-10 turn/wall-clock-cost item's own forensic pass found progress-message count was NOT among the actual dominant cost drivers in the one session it audited -- so this item should be triaged on its own merits (signal-to-noise for the PO reading along) rather than folded into that cost-reduction effort's success metric, to avoid setting an expectation this change won't deliver (it improves readability, not wall-clock time).
