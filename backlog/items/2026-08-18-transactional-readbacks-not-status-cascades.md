# Transactional readbacks instead of status cascades

## Description

Many writes each triggered separate status, continuity, and handover
queries. This produced redundant, cascading inspection calls instead of a
single consolidated result.

## Triggering situation

Greenfield happy-path test report, pipeline version
0.6.0+codex.20260818162535.96cf805, test repo Rune_Test1_Codex_060_52; see
docs/pipeline-greenfield-happy-path-handover.md in that test repo,
Section 9, item P1-8.

## Affected artifact

coordinator command readback shape, pipeline-state.mjs.

## Proposal

Coordinator commands should return, after an atomic mutation, one bound
overall readback covering state, continuity, handover, candidate, and
next action. Additional individual inspections should only be necessary
in case of drift.

Acceptance test: the normal plan-approval transition requires at most one
mutating action and one overall readback.

## Triage (filled in by the Elephant of the next Pipeline session)

- **Decision:** Accepted — add a single consolidated read-only `inspect` subcommand (reusing the existing richer-subcommand JSON pattern), paired with a documentation update to the dispatch templates so it's actually adopted. Not the full 14-writer bundle.
- **Rationale:** PO 2026-08-18 accepted the analyst's recommendation as-is.
- **Assignment (if accepted):** Nova Wave 4 implementation. Coordinate with `per-phase-progress-message-budget` so the new payload stays a tool-result, not echoed into chat.
- **Date:** 2026-08-18


## Design proposal (Wave-4 prep), 2026-08-18

*Prep material for PO triage, not a decision — a Triage section, if/when added, records the actual PO decision. Generated by a Workflow-dispatched read-only design pass (dispatch NVA-W4-DESIGN-transactional-readbacks-not-status-cascades) grounded in the current repo state.*

**Problem (restated):** Backlog item pipeline.transactional-readbacks-not-status-cascades (P1-8 from the external Rune greenfield happy-path report, not reproducible in this checkout) claims that pipeline-state.mjs mutating commands each trigger separate follow-up status/continuity/handover inspection calls instead of returning one consolidated result. I read the item file in full and grepped/read the named artifact, plugins/pipeline-core/scripts/pipeline-state.mjs (5972 lines; harness/scripts/pipeline-state.mjs is a 20-line re-export shim onto it, not a second implementation). The claim is well-grounded in the actual code, though the item's own framing ('coordinator commands') is slightly imprecise -- there is no single uniform contract today: roughly half the mutating subcommands (approve-plan L5120-5183, submit-plan L4939, set-phase L4900, set-feature L4867, close-feature L5587, discard-feature L5717, approve-push L5370, approve-deploy L5797, consume-deploy L5857, revoke-plan L5277) emit only a one/two-line human-readable console.log confirmation and exit 0/2 -- e.g. approve-plan's entire success output is "Plan approved by..." plus a static "Next: implementation writes remain refused..." hint, no structured state. Meanwhile a different family of subcommands (continuity-result-rebind ~L3084-3133, continuity-result-bootstrap ~L3531-3594, continuity-result-case-migration ~L3283-3287, materialize-push-threat-model, PO-authority rebind ~L4743-4792) already emit rich structured JSON with plan/postimage/authorityResult/resume shapes -- so the codebase already has the payload machinery, just not applied uniformly. Separately, every phase/approval-changing mutation calls syncNextActionDocs -> syncStateMdNextAction (onboarding-continuity.mjs L3435) as a best-effort side effect that rewrites docs/state.md's "## Next action" section on disk -- but does not return that content to the caller, so the caller re-reads the file to see it. And continuity/candidate/handover status live in genuinely separate scripts (plugins/pipeline-core/scripts/continuity-status.mjs, resume-hint.mjs, project-onboarding-v3.mjs's inspect path) that a coordinator session calls independently. So "many writes each trigger separate status/continuity/handover queries" is an accurate description of the current shape, even though I could not read the external test-repo evidence itself (docs/pipeline-greenfield-happy-path-handover.md lives in test repo Rune_Test1_Codex_060_52, not this checkout, and the item says so explicitly).

**Options:**

1. **Bundle the full readback into every mutating writer's return value (the item's literal proposal)** — Change all ~14 terminal-status mutating subcommands in pipeline-state.mjs (approve-plan, submit-plan, set-phase, set-feature, close-feature, discard-feature, approve-push, approve-deploy, consume-deploy, revoke-plan, seal-plan-approval, plan-legacy-v2-revocation-recovery, bind-plan-spec, clear-deploy) to emit one structured JSON object on success -- state + continuity + handover-doc pointer + candidate/release status + next action -- instead of a plain console.log line, matching the shape the richer subcommands (continuity-result-rebind etc.) already use. Impact: A coordinator session gets everything in the single mutating call itself; zero follow-up calls are structurally possible for the happy path. Satisfies the acceptance test with headroom (0 separate readback calls, not 'at most one'). Tradeoffs: Touches ~14 call sites plus their existing tests (pipeline-state.test.mjs, pipeline-state-inspection-contract.test.mjs, plus whatever downstream scripts/docs parse today's plain-text confirmations, e.g. syncNextActionDocs callers and any harness scripts grepping for 'Plan approved by'). Every failed mutation would also need a defined payload shape (there is no successful postimage to report on a 'return 2' error path). Bloats every write's response even when the caller doesn't need it -- in tension with the sibling P2-1 item (per-phase-progress-message-budget) which explicitly wants routine internal readbacks to stay off the human-facing stream, and with guardrails/token-budget.md's existing concern about per-dispatch token cost. Largest surface area of the three options.
2. **One new consolidated read-only 'inspect' command, mutating writers stay terse** — Add a single new subcommand (e.g. pipeline-state.mjs inspect, or extend continuity-status.mjs) that returns the full bound snapshot -- state, continuity, handover-doc content/pointer, candidate/release status, computed next action -- in one JSON call, superseding the need to separately invoke continuity-status.mjs, resume-hint.mjs, and a docs/state.md re-read. Mutating commands keep their current terse confirmation but each success/failure message points at the new inspect command by name. Update harness/session-bootstrap.md and the Goldfish/Elephant/Critic dispatch templates to call it exactly once after a state-changing transition instead of the current ad hoc multi-tool cascade. Impact: Collapses N separate inspection tool calls into 1, directly satisfying the item's acceptance test as literally worded ('at most one mutating action and one overall readback' -- one mutation call + one inspect call = two total, matching 'at most'). Mutating write-path output contracts and their tests are untouched, so this is far less invasive to existing call sites. Failure paths are handled uniformly too, since inspect can be called regardless of whether the preceding mutation succeeded. Tradeoffs: Doesn't eliminate the second call the way option 1 does -- a coordinator that forgets to call inspect, or that still calls the old separate scripts out of habit, gets no structural protection; the discipline still has to be documented and followed rather than being unconditionally true of the API shape. Requires deciding what 'candidate' status means precisely (this repo doesn't currently expose a first-class 'candidate' concept from pipeline-state.mjs itself -- it's assembled from release-version-plan.mjs/release-preflight.mjs/check-release-state-consistency.mjs) and building that aggregation, which is new integration work, not just a repackaging of an existing field.
3. **Documentation/discipline fix only -- no code change to pipeline-state.mjs** — Treat this as a process-discipline gap like the 2026-08-18 're-verify inherited still-open claims' rule already added to this file's CLAUDE.md: add a rule to harness/session-bootstrap.md / docs/operating-model.md stating the intended call budget explicitly (one mutating action, at most one status/continuity/handover check) and rely on the coordinator session to follow it, without touching pipeline-state.mjs's output shape or building a new inspect surface. Impact: Near-zero implementation cost; ships this session if the PO wants something on record immediately. No new code, no new tests, no risk to existing 14 call sites. Tradeoffs: Doesn't fix the underlying cause: today's terse commands (approve-plan et al.) genuinely do not expose structured state, so a documentation-only rule gives the coordinator nothing concrete to call once even if it wants to comply -- it would still have to fall back to reading docs/state.md or running continuity-status.mjs, i.e. the exact cascade being complained about. This option only works if paired with at least a pointer to an existing single source of truth; as a pure no-code option it is likely to reproduce the same P1 finding on the next greenfield test.

**Recommendation:** Hybrid built from options 2 and 3, not option 1: add the single consolidated read-only inspect surface (option 2) rather than bundling full state into all ~14 mutating writers. This satisfies the item's own acceptance test as worded ("at most one... and one overall readback"), reuses the JSON-payload machinery this codebase already has for the richer subcommands (continuity-result-rebind, PO-authority rebind) instead of inventing a second shape, and avoids retrofitting output contracts and tests across every terminal-status writer. Pair it with the documentation change from option 3 (session-bootstrap.md and the Goldfish/Elephant/Critic dispatch templates each get an explicit "one mutation, one inspect call" line) so the new surface is actually adopted rather than left as an unused alternative next to the old scattered scripts. Do not adopt option 1 outright -- its cost (touching every terminal mutating command's contract, defining a failure-path payload shape that doesn't exist today, and working against the sibling P2-1 item's "routine readbacks stay internal" intent) is disproportionate to what option 2 already buys.

**Risks/dependencies:** Overlaps two sibling Wave-4 items from the same source report and same triage batch, worth resolving together rather than independently: pipeline.per-phase-progress-message-budget (P2-1, backlog/items/2026-08-18-per-phase-progress-message-budget.md) wants routine internal readbacks kept OFF the human-facing turn stream -- a design here must keep the new inspect payload as an internal/tool-result artifact, not something echoed verbatim into chat, or the two items will conflict; pipeline.universal-human-command-renderer (P0-3, backlog/items/2026-08-18-universal-human-command-renderer.md) is about a different rendering path (human-executable HGO commands) but shares the same "coordinator output shape" theme and the same source document, so triaging both in the same session avoids two separate design passes over related code. There's also a real dependency on guardrails/token-budget.md's TB-01/TB-04 concerns and the standing PO/memory note that dispatch bootstrap cost is already too high (50k-150k tokens/dispatch) -- any consolidated payload should be sized deliberately (e.g. omit full handover-doc text, include only its path/hash/section) rather than assumed free. "Candidate" status is not currently a first-class field inside pipeline-state.mjs's own state; wiring it into a consolidated readback means integrating release-version-plan.mjs / check-release-state-consistency.mjs, which is genuinely new plumbing, not a relabeling exercise. Finally, the item's own evidence (docs/pipeline-greenfield-happy-path-handover.md) lives only in the external test repo Rune_Test1_Codex_060_52 and could not be read from this checkout, so the PO or whoever ran that test should confirm the exact call sequence observed before final scoping -- my grounding is from reading the actual pipeline-state.mjs behavior, not from the cited report.

**Estimated complexity:** medium
