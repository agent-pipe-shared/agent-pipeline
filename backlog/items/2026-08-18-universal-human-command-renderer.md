# Introduce a universal renderer for human-executable commands

## Description

Two HGO (Human-Gated Operation) commands failed because of visual line
wraps in the middle of a path. The safe, bounded copyCommand renderer was
only adopted consistently at a later point in the workflow.

## Triggering situation

Observed during the greenfield happy-path test of pipeline version
0.6.0+codex.20260818162535.96cf805 in test repo Rune_Test1_Codex_060_52;
see Section 9, item P0-3 of the full report at
docs/pipeline-greenfield-happy-path-handover.md in that test repo.

## Affected artifact

HGO command rendering path; any coordinator emitting a human-executable
command.

## Proposal

Every pipeline action that a human must execute externally should deliver
exclusively structured executable/argv data plus a tested
copyCommand.posix|powershell|cmd rendering; agents must not freely format
such commands themselves.

Acceptance test: all generated handoff commands work after copy/paste in
a 72-column terminal, and no path or digest can be split apart by UI
wrapping.

## Design proposal (Wave-4 prep), 2026-08-18

*Prep material for PO triage, not a decision — a Triage section, if/when added, records the actual PO decision. Generated by a Workflow-dispatched read-only design pass (dispatch NVA-W4-DESIGN-universal-human-command-renderer) grounded in the current repo state.*

**Problem (restated):** The backlog item (backlog/items/2026-08-18-universal-human-command-renderer.md) reports that during an external greenfield test, two HGO commands failed after copy/paste because a human-executable command line-wrapped mid-path/mid-digest in the terminal, and that the safe copyCommand renderer was 'only adopted consistently at a later point in the workflow.' Its 'Affected artifact' field is vague ('HGO command rendering path; any coordinator emitting a human-executable command'), and its cited evidence (Section 9/P0-3 of docs/pipeline-greenfield-happy-path-handover.md) lives in an external test repo not present in this checkout, so the specific failing commands could not be directly verified. However, reading the actual code confirms the underlying claim independently and more precisely than the item states it: a tested, bounded (72-column), three-shell (posix/powershell/cmd) renderer already exists -- boundedOpaqueCopyCommand() in plugins/pipeline-core/lib/project-onboarding-v3.mjs:1884-1903, with a real bash-eval round-trip test (po-human-approval.test.mjs:2047, 'GF-105') -- and is correctly used at 2 sites (po-human-approval.mjs:802; codex-pretool-guard.mjs:236 via commandDisclosureFields()). But at least 3 other sites that print a human-executable HGO ceremony command still build it ad hoc with plain template strings and no bounded/multi-shell rendering: guard-lifecycle-ready.mjs's humanOverrideRoute() (lines 409-431) -- which I triggered live, twice, in this exact session, producing the identical 'Human override available...' guidance with a long absolute script path and a 64-hex request-sha256 inline; guard-testpath.mjs (lines 265-286), a near-byte-identical duplicate of the same logic; and human-guard-override.mjs, the central library backing both, which has zero occurrences of copyCommand/boundedOpaqueCopyCommand anywhere and in one branch (HGO-EXTERNAL-PROJECT-BOUNDARY, lines 1414-1429) discloses only a toolInputSha256 with no literal command at all -- the exact same gap-shape as the already-fixed-twice GF-059/2026-08-17 finding. So the item's title ('introduce a universal renderer') slightly overstates the gap: the renderer exists; what's missing is consistent adoption plus something that stops future sites from reintroducing ad hoc formatting, which is exactly what happened at least 3 times already (GF-059's original site, its missed sibling closed 2026-08-18, and now these).

**Options:**

1. **A -- Full mandate: forbid ad hoc formatting everywhere, add an enforcement check** — Implement the item's literal proposal: every human-executable-command site must emit only {executable, argv, command, copyCommand}; extend boundedOpaqueCopyCommand (or wrap it) to cover multi-step ceremonies (plan -> prepare-authorization -> emit-signature-digest -> authorize-by-signature is 3-4 separate commands, not the single string the primitive takes today); migrate guard-lifecycle-ready.mjs, guard-testpath.mjs, and human-guard-override.mjs's uncovered action shapes onto it; then add a repo-wide structural check (grep/AST-based, alongside harness/scripts/check-doc-contracts.mjs-style checks) that fails verify if a file builds a 'human must execute this' string without routing through the shared renderer. Impact: Closes the 3 confirmed live gaps for good, and -- unlike a one-off code fix -- makes a 4th recurrence structurally impossible rather than merely unlikely, which matters given this exact class of drift (one site fixed, a structurally identical sibling missed) has already happened twice in this repo's own history (GF-059, closed 2026-08-17 item). Tradeoffs: Real design latitude required for the multi-step-ceremony question (bounding a sequence of related commands, not one line) -- not a trivial call-site swap. Touches the central human-guard-override.mjs library, so needs care and its own regression tests per site (mirroring the pattern the two prior closed items already used). Also duplicates scope already claimed, and deliberately deferred to Sprint Alfred, by the open item 2026-08-02-unified-human-authorization-ux.md, whose remaining scope explicitly includes 'an adoption check that prevents new one-off human-approval UX from being introduced' -- building a second, differently-named enforcement mechanism here risks two parallel governance layers for the same problem.
2. **B -- Minimal: finish adopting the existing renderer at the known sites, no new enforcement** — Route guard-lifecycle-ready.mjs's humanOverrideRoute(), guard-testpath.mjs's duplicate logic, and human-guard-override.mjs's uncovered action shapes (including the toolInputSha256-only HGO-EXTERNAL-PROJECT-BOUNDARY branch) through boundedOpaqueCopyCommand(), exactly mirroring the fix pattern the two already-closed sibling items used (2026-08-10-push-approval-signature-commands-also-line-wrap.md; 2026-08-17-cross-repository-boundary-guidance-still-omits-the-literal-command.md). No new lint/contract check; no claim of 'universal' coverage. Impact: Closes the concrete, demonstrated defect class (the actual line-wrap failure the item reports, which I reproduced independently against this repo's own code) with a small, low-risk diff using a proven, twice-successful pattern. Also satisfies the item's stated acceptance test (72-column bound, no path/digest split) directly, since that bound is already built into boundedOpaqueCopyCommand. Tradeoffs: Leaves the item's own acceptance criterion ('agents must not freely format such commands themselves') structurally unenforced -- nothing stops a 4th site from reintroducing the same ad hoc string-template pattern next sprint, which is exactly the failure mode that produced this item and its predecessor twice already.
3. **C -- Merge into Sprint Alfred's already-deferred adoption-check scope** — Treat this item as evidence/detail for 2026-08-02-unified-human-authorization-ux.md rather than a separate initiative: fold the 3 concrete sites found here into that item's still-open 'remaining scope' list (which already names an adoption-enforcement check as unbuilt, deferred 2026-08-17 to Sprint Alfred), and either close this item as a duplicate-scope cross-reference or keep it open only long enough to land Option B's narrow code fix now, with the enforcement mechanism explicitly left to Alfred. Impact: Avoids tracking the same architectural gap ('one-off human-approval/command UX creeps in') under two different backlog IDs with two different names, which would otherwise cost a future session time reconciling them (as already happened once this session block, per the 2026-08-18 backlog item on inherited stale claims). Tradeoffs: If deferred wholesale with no immediate code fix, a demonstrated, live-reproducible defect (not just an external test report -- I triggered it twice in this exact repo this session) ships unfixed into whatever follows 0.6.0. Pure deferral without at least the narrow fix is hard to justify given how cheap and precedented Option B is.

**Recommendation:** Hybrid of B and C: accept the item now, but rescope its Triage decision text to make the split explicit. (1) Do the narrow fix immediately -- route guard-lifecycle-ready.mjs's humanOverrideRoute(), guard-testpath.mjs's duplicate block, and human-guard-override.mjs's uncovered action shapes through the existing, already-tested boundedOpaqueCopyCommand(), exactly the pattern used twice successfully already (2026-08-10 and 2026-08-17 closed items). This is small, low-risk, and closes a defect I independently reproduced live against this exact repo, not merely the external test's word for it. (2) Do NOT build a second, separately-named 'universal renderer + adoption check' mechanism under this item's identity -- register the structural/enforcement half (stop future sites from reintroducing ad hoc formatting) as a contribution to 2026-08-02-unified-human-authorization-ux.md's already-deferred Sprint Alfred scope, which explicitly wants exactly that. This keeps the fix proportionate to what's actually broken today while not losing the systemic point.

**Risks/dependencies:** Dependency: 2026-08-02-unified-human-authorization-ux.md (open, remaining scope deferred to Sprint Alfred 2026-08-17) already owns the 'adoption check that prevents new one-off human-approval UX' ask -- triaging this item without cross-referencing that one risks two divergent governance mechanisms for the same problem, or the PO being asked to decide the same architectural question twice under different names. Design risk within the narrow fix itself: boundedOpaqueCopyCommand() takes one command STRING; the HGO ceremonies at the affected sites are 3-4 sequential commands (plan -> prepare-authorization -> emit-signature-digest -> authorize-by-signature), so the fix needs either N separate bounded renderings (one per step, each labeled) or a small primitive extension -- not a single trivial call-site swap, though still far smaller than inventing new infrastructure. Process risk: this is the third occurrence of the identical drift shape (a bounded/safe-disclosure fix landing at one site while a structurally identical sibling site is missed) after GF-059 (2026-08-09) and its 2026-08-17 follow-up -- worth flagging to the PO as a pattern, not a one-off, when deciding whether Option A's structural check is worth doing sooner rather than deferring to Alfred.

**Estimated complexity:** medium
