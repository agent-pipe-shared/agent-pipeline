# Atomic PRD approval without PRD mutation

## Description

The gate requires a marker to be written into a PRD that is already bound
and therefore no longer editable. This creates a contradiction: the
approval mechanism demands a write to an artifact whose immutability the
binding step itself is supposed to guarantee. There is currently no
separate, atomic way to record PO acknowledgement without touching the
bound PRD.

## Triggering situation

Observed during a greenfield happy-path test of pipeline version
0.6.0+codex.20260818162535.96cf805 in test repo Rune_Test1_Codex_060_52;
documented as Section 9, item P0-2 of the full report at
docs/pipeline-greenfield-happy-path-handover.md in that test repo.

## Affected artifact

PO-Gate, pipeline-state.mjs, Promotion-History, guard-apply-patch.mjs.

## Proposal

Store the PO acknowledgement separately in the pipeline state instead of
writing a marker into the PRD. approve-plan should accept the confirmed
PRD/spec digest and the human attribution, and atomically perform
acknowledgement, plan approval, history update, and phase transition in
one step, so that no comment ever needs to be written back into the PRD
afterward.

Acceptance test: after exactly one chat approval, a bound greenfield
feature transitions into implementation without any HGO, reopen-design,
rebind, or signature step, and continuity is immediately valid.

## Triage (filled in by the Elephant of the next Pipeline session)

- **Decision:** Accepted — extend the existing `po-authority-rebind` family with an acknowledge-plan/apply pair (real fix), done alongside the cheap promotion-admission-check extension — not the full merge-into-one-step option, which stays a separate, explicit future PO product decision.
- **Rationale:** PO 2026-08-18 accepted the analyst's recommendation as-is.
- **Assignment (if accepted):** Nova Wave 4 implementation.
- **Date:** 2026-08-18


## Design proposal (Wave-4 prep), 2026-08-18

*Prep material for PO triage, not a decision — a Triage section, if/when added, records the actual PO decision. Generated by a Workflow-dispatched read-only design pass (dispatch NVA-W4-DESIGN-atomic-prd-approval-without-mutation) grounded in the current repo state.*

**Problem (restated):** Backlog item `pipeline.atomic-prd-approval-without-mutation` claims the PO-approval gate demands a marker be written into a PRD that a prior "bind"/"promotion" step has already frozen, with no atomic, non-mutating way to record PO acknowledgement. This is grounded, not stale: `plugins/pipeline-core/lib/po-gate-authority.mjs` defines `PO_GATE_PRD_ACKNOWLEDGEMENT_MARKER = "<!-- po-plan-acknowledged: content-sound-and-spec-consistent -->"` (line 68) and requires it, exactly once, physically inside the PRD text, whenever `submit-plan`/`approve-plan`/`bind-plan-spec` call `poGateAuthority()` with expected digests (`requireAcknowledgement` gate, lines 776-798). Its own repair text says plainly (lines 149-151, 169-171): "If a kickoff promotion has already bound this PRD, do not add that line in place... there is no sanctioned way to add the marker to an already-bound PRD today." A near-identical failure (for the sibling `po-language`/`technical-spec-sha256` markers) was already diagnosed and fixed as backlog item `2026-08-08-a-promotion-freezes-a-prd-the-po-gate-will-reject.md` (closed 2026-08-11, commit `fb918b86`) by making `kickoff promote plan` check those two markers at admission time, before the PRD's bytes freeze (`onboarding-continuity.mjs` `promotionArtifacts()`, lines 4082-4121). That admission check was never extended to the acknowledgement marker (confirmed: zero references to it in `onboarding-continuity.mjs`), so a greenfield kickoff can be promoted/bound without it and then unavoidably hit `PO-GATE-PRD-ACKNOWLEDGEMENT-MISSING` with no sanctioned exit — the exact scenario the new item's acceptance test (one chat approval, no HGO/reopen-design/rebind/signature) is written against. Two of the item's four named "Affected artifact" entries don't hold up on inspection: `guard-apply-patch.mjs` is a generic Codex `apply_patch`-to-per-file-guard translator with zero PRD-specific logic (confirmed by full read), and no file literally named "Promotion-History" exists — the real enforcement lives in `guard-lifecycle-ready.mjs`'s `boundAuthorityDocumentPath()`/`AUTHORITY_DOCUMENT_BOUND_CODE` (lines 465-557) and the marker logic in `po-gate-authority.mjs`, neither of which the item names.

**Options:**

1. **Adopt the item's proposal as-is: move acknowledgement into state, merge approval + phase transition** — Retire the PRD-file `po-plan-acknowledged` marker and the code paths that check it. Extend `approve-plan` to accept a confirmed PRD/spec digest plus `--by` attribution and, in one atomic writeState transaction, record acknowledgement, approval, history, and the design->implementation phase transition -- exactly as the item's Proposal and acceptance test describe. Impact: Fully removes the marker-in-a-bound-PRD dead end: one chat 'approved' plus one command takes a bound feature straight into implementation, with zero PRD writes at any point in the flow. Tradeoffs: Reverses two decisions the current code makes deliberately, not accidentally: (1) the acknowledgement marker's own comments (po-gate-authority.mjs:164-167) frame it as the PO's own physical proof of having read the document -- replacing it with `--by` attribution alone repeats the 'a pure UI dialog as approval' alternative ADR-0021 explicitly rejected ('verworfen; "freigegeben" ist ein Gate, kein UI-Mechanismus'), and echoes the ADR's own addendum risk ('gate held != gate fulfilled'); (2) merging phase-transition into approve-plan removes the explicit, commented separation 'approval and implementation-start are separate deliberate acts' (pipeline-state.mjs:5181). Both reversals are legitimate but should be an explicit PO call, not a side effect of a defect fix. Largest blast radius of the three options: new state schema, retired guard logic, broader test surface.
2. **Extend the existing rebind-family precedent to cover acknowledgement (targeted fix)** — Keep the PRD-file marker and the approve/implement separation as they are. Give a bound PRD a sanctioned, transactional, PO-attributed route to acquire the acknowledgement marker after binding, by extending the existing `po-authority-rebind-plan`/`po-authority-rebind-apply` machinery (pipeline-state.mjs ~4313-4720: lock file, journal, fsync, atomic rename, already built and tested) with an equivalent acknowledge-plan/apply pair, or a widened rebind that also accepts the acknowledgement marker as a target. This is literally Direction 5 of the closed 2026-08-08 item ('give the authority family a recovery that covers the pre-approval state'), never carried out. Impact: Closes the dead end -- a bound-but-unacknowledged feature gets a typed, audited way out -- while preserving both of the deliberate properties Option 1 would remove: the PO's own hands touch the file, and approval stays a separate act from implementation-start. Tradeoffs: Does not meet the item's literal 'one chat approval, one step' acceptance test -- still a distinct command (plan, then apply) and still a governed physical write, just no longer an unrecoverable one. New command surface to design, document, and test, though it has a direct template to follow in the existing rebind test suite.
3. **Close the cheaper, higher-confidence half first; defer/re-scope the rest** — Before any state-machine work, extend the kickoff-promotion admission-time check in `onboarding-continuity.mjs` `promotionArtifacts()` to also validate the acknowledgement marker's presence, mirroring exactly the fix already shipped for the language/spec markers (lines 4082-4121) -- same pattern, third marker. Re-file this item explicitly as a recurrence of the closed 2026-08-08 item rather than an independent one, and defer the harder post-bind-review case (PO reads and marks the PRD only after promotion) to a later Wave. Impact: Near-zero-cost, immediately prevents new greenfield sessions from reaching the frozen dead end in the common ordering (PO reviews before promotion); reuses a pattern already proven and accepted once. Tradeoffs: Doesn't help when PO review genuinely happens after promotion -- which ADR-0021's own EL-19 flow (approve just before the first implementation dispatch) suggests may be the normal case, since promotion typically happens once design is otherwise finished. Likely just relocates the same dead end for a real fraction of sessions rather than eliminating it -- a stopgap, not a structural fix.

**Recommendation:** Recommend Option 2 as the real fix, with Option 3 done alongside it as a cheap immediate mitigation -- not Option 1 as filed. The gap is real and reproducible in current code (not a stale claim), but the item's own Proposal silently reverses two things the codebase currently does on purpose: ADR-0021's explicit rejection of "a pure UI dialog as approval," embodied in the acknowledgement marker's requirement that the PO physically edit the PRD, and the deliberate separation of plan-approval from implementation-start (pipeline-state.mjs:5181). Those are worth a PO decision each, not a default folded into a bug-shaped fix. Option 2 closes the actual dead end using a pattern this codebase already built and trusts (the po-authority-rebind family) without touching either deliberate design choice, and it directly completes Direction 5 of the closed sibling item rather than opening new design surface. Pair it with Option 3 (extend the promotion admission check, exactly like the already-shipped fix for the other two markers) as a same-day, near-zero-cost belt-and-suspenders step that prevents most sessions from ever reaching the state Option 2 has to recover from. If the PO wants the full "one chat word, one step" experience the item's acceptance test describes, that's a legitimate ask but should be raised and decided as its own explicit product call (effectively Option 1), separately from closing this defect.

**Risks/dependencies:** Duplicate/overlap risk: this item is best triaged as a recurrence of the CLOSED defect `2026-08-08-a-promotion-freezes-a-prd-the-po-gate-will-reject.md` (fixed 2026-08-11, `fb918b86`) for a third marker (`po-plan-acknowledged`, added later per `2026-08-07-a-promoted-feature-can-never-pass-the-plan-gate.md`) that was never brought under the same admission-time check -- Wave-4 should link/cross-reference both rather than triage this as fully independent, and whoever implements should re-read that closed item's Direction 1/2/5 before starting. Related open items in the same subsystem worth checking for overlap before assigning: `2026-07-25-po-gate-authority-receipt-readback.md`, `2026-07-25-po-gate-authority-path-canonicalization.md`, `2026-08-05-critical-human-proof-not-wired-to-push-and-prd-gates.md`, `2026-07-19-po-gate-worktree-authority.md`. Dependency: any implementation of Option 2 must reuse the exact lock/journal/fsync transaction pattern already built for `po-authority-rebind-plan/apply` (pipeline-state.mjs ~4313-4720) rather than inventing a parallel one, and must route through -- not around -- `guard-lifecycle-ready.mjs`'s `boundAuthorityDocumentPath()`/`AUTHORITY_DOCUMENT_BOUND_CODE` (lines 465-557), which is the actual current enforcer of "no direct edit to a bound PRD" and already names the sanctioned reopen-design/rebind route in its own refusal text. ADR-0021 (PRD-PO-Gate) is still explicitly "provisional, never formalized" -- if the PO does want the full Option 1 merge later, that's a natural piece to fold into ADR-0021's eventual formalization pass rather than a standalone patch. Correct the item's "Affected artifact" list when it's assigned: point at `plugins/pipeline-core/lib/po-gate-authority.mjs` and `plugins/pipeline-core/lib/onboarding-continuity.mjs` (the files that actually carry this logic) rather than `guard-apply-patch.mjs` (confirmed unrelated) and a "Promotion-History" file that does not exist under that name.
