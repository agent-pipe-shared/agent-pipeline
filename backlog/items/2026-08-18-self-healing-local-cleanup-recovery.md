# Auto-execute reversible, local, fully-typed cleanup recoveries without PO prompt

## Description

The PO had to select a recommended attended-host-recovery for local,
private cleanup metadata. Recoveries that are reversible, local, and
fully typed should be executable autonomously within the consent already
granted to the pipeline; only data loss, external effects, or genuine
policy choices should remain a human decision.

## Triggering situation

From the greenfield happy-path test report for pipeline version
0.6.0+codex.20260818162535.96cf805 in test repo Rune_Test1_Codex_060_52,
docs/pipeline-greenfield-happy-path-handover.md, Section 9 item P1-5.

## Affected artifact

session-cleanup-recovery.mjs, cleanup recovery planner.

## Proposal

Reversible, local, and fully-typed cleanup recoveries should be executed
autonomously under the already-granted pipeline consent; only data loss,
external effects, or genuine policy choices remain human decisions.

Acceptance test: an orphaned cleanup descriptor is repaired automatically,
and the PO sees at most a completion note, not a selection question.

## Triage (filled in by the Elephant of the next Pipeline session)

- **Decision:** PO's own modified design (neither offered option as-is): full auto-execute across ALL SIX recovery kinds (not just the non-composite bind-orphan/retire-orphans subset) — but every file the auto-recovery touches must first get a `.bak` backup copy written before modification, as a rollback safety net replacing the human-confirmation gate.
- **Rationale:** PO 2026-08-18 — accepted the broader automation across all six recovery kinds but paired it with a cheap, purely mechanical safety net (pre-modification backup) instead of relying on a human checkpoint; addresses the analyst's caution about the riskiest composite kind and the two related open defects in the same subsystem without needing a human in the loop.
- **Assignment (if accepted):** Nova Wave 4 implementation — `session-cleanup-recovery.mjs`'s planner: set `requiresConfirmation: false` across all recovery kinds, and add a `.bak` write of each touched file immediately before its recovery action executes. Backup naming/location and any old-backup cleanup policy is left to the implementing dispatch's own design — not further specified by the PO.
- **Date:** 2026-08-18


## Design proposal (Wave-4 prep), 2026-08-18

*Prep material for PO triage, not a decision — a Triage section, if/when added, records the actual PO decision. Generated by a Workflow-dispatched read-only design pass (dispatch NVA-W4-DESIGN-self-healing-local-cleanup-recovery) grounded in the current repo state.*

**Problem (restated):** Backlog item `2026-08-18-self-healing-local-cleanup-recovery.md` proposes that `plugins/pipeline-core/lib/session-cleanup-recovery.mjs` (the cleanup-recovery planner) auto-execute recoveries it classifies as "reversible, local, and fully-typed" instead of stopping to ask the PO to pick a recovery. I read the full 1604-line file plus its two callers (`plugins/pipeline-core/scripts/session-cleanup.mjs` CLI wiring and `plugins/pipeline-core/lib/project-onboarding-v3.mjs`'s `partialCleanupRecoveryResult`) to ground the analysis in the actual code, not the item's prose.

What the code actually does: `planSessionCleanupRecovery()` inspects the private onboarding-session-cleanup binding and produces one of several typed plan shapes depending on binding status (`bound`, `unbound`, `closed-bound`, `closed-unbound`, `closed-receipt-invalid`, `design-unbound`). For every "ready" plan it builds via `readyRecoveryPlan()` (line 641) — covering `bind-orphan`, `retire-orphans`/`retire-externally-archived-orphans`/`retire-mixed-orphans`, `retire-orphans-release-lost-binding` (a crash-safe composite with its own journal+lock machinery, lines 456-639), `release-lost-binding`, `release-closed-feature`, and `quarantine-private-receipt` — the resulting `applyAction` unconditionally sets `mutation: true, requiresConfirmation: true` (lines 664-665), regardless of how tightly typed/digest-bound the plan is. `project-onboarding-v3.mjs`'s `partialCleanupRecoveryResult()` (line 1261) surfaces that `applyAction` as a lifecycle `nextAction` with `status: "partial"` — this is the mechanism that turns into "the PO had to select a recovery" during bootstrap.

Important nuance found in the code, not just the item's framing: there is already a PRECEDENT of ungated auto-execution in the same file. The ordinary `cleanup-required` and `release-ready` next-actions (closure already observed as `active`/`closed` with no ambiguity, lines 839-856 and 978-987) already ship with `requiresConfirmation: false`. So the codebase already distinguishes "routine, unambiguous progress" (no confirmation) from "recovery" (always confirmation) — the item's ask is to move more cases from the second bucket into something like the first, not to invent the pattern from scratch. A source comment at lines 749-751 also documents a deliberate policy choice ("The legacy V1 owner case is therefore a Human-only, digest-bound recovery rather than an automatic cleanup") — i.e. the original author already considered and rejected blanket auto-recovery for at least one sub-case, on ambiguity grounds specific to that case, not carelessness.

I also found two related, currently-open defects in the same file/mechanism family (`backlog/items/2026-08-09-kickoff-promotion-cleanup-readback-has-no-in-session-recovery.md`, `backlog/items/2026-08-08-the-scratch-cleanup-mechanism-exists-but-no-event-calls-it.md`) documenting live bugs and half-wired paths in this exact cleanup/recovery subsystem, which matters for risk-sizing any change here.

**Options:**

1. **Full auto-execute (the item's own Proposal, as written)** — Remove the `requiresConfirmation: true` gate from every `readyRecoveryPlan()` output across all six recovery kinds (`bind-orphan`, `retire-orphans*`, `retire-orphans-release-lost-binding`, `release-lost-binding`, `release-closed-feature`, `quarantine-private-receipt`), and change `partialCleanupRecoveryResult()` in project-onboarding-v3.mjs to call `applySessionCleanupRecovery(..., activate: true)` directly whenever `planSessionCleanupRecovery` returns status `ready`, only falling back to a PO question if apply itself fails or `plan-human-recovery`'s decision-required path is reached (which is unaffected, since it only fires when NO typed plan exists). Impact: The PO stops seeing any confirmation prompt for any of the six typed recovery kinds, including the composite `retire-orphans-release-lost-binding` (the most consequential one — it retires potentially multiple session descriptors AND releases a private binding pointer in one crash-safe transaction) and `quarantine-private-receipt` (moves aside a receipt that failed integrity validation, i.e. discards forensic evidence of what happened, even though it's typed as recoverable). Meets the acceptance test literally: an orphaned descriptor is repaired with at most a completion note. Tradeoffs: Removes the human checkpoint uniformly, including on the one recovery kind (`retire-orphans-release-lost-binding`) whose implementation complexity (dedicated journal schema, lock schema, writer-identity byte-for-byte script/manifest verification) signals the original author treated it as unusually risky to get wrong — that safety engineering defends correctness/atomicity of the write, not whether a human should have vetoed it first. Also silently overrides the deliberate 'Human-only, digest-bound recovery' policy documented in the source comment at line 749-751 for the ambiguous multi-descriptor case, without re-examining whether that rationale still holds. No config knob — PO cannot get the old behavior back per-project without a code change.
2. **Scoped auto-execute: only the genuinely low-ambiguity subset** — Auto-execute only the two recovery kinds that are single-fact, non-composite, and match the file's own existing no-confirmation precedent in shape: `bind-orphan` (exactly one active descriptor, unambiguous single owner) and `retire-orphans` (pure crash residue, no external-archive complexity, no binding release attached). Leave `retire-externally-archived-orphans`, `retire-mixed-orphans`, `retire-orphans-release-lost-binding`, `release-lost-binding`, `release-closed-feature`, and `quarantine-private-receipt` gated exactly as today. Impact: Covers the item's own acceptance-test example ('an orphaned cleanup descriptor is repaired automatically') directly, since bare orphan retirement is the common case a crashed session leaves behind. The PO still confirms anything that touches a private binding release, an external-archive proof, or a failed-integrity receipt — the cases with either compound state changes or an already-documented ambiguity precedent. Tradeoffs: Doesn't fully satisfy the item's broader Proposal text ('reversible, local, and fully-typed... should be executed autonomously' as a general rule) — a PO or future session could reasonably ask 'why only these two out of six typed kinds.' Requires a real, if small, code change: splitting `readyRecoveryPlan()`'s `applyAction` construction by `recovery` kind, and adding a matching branch in `partialCleanupRecoveryResult()` to actually invoke `applySessionCleanupRecovery` for the allow-listed kinds. Line is a judgment call the PO would still need to bless once, even though individual future incidents wouldn't need per-incident confirmation.
3. **Defer / minimal: keep the gate, reduce friction some other way** — Don't change `requiresConfirmation` at all this wave. Instead (a) leave it as project-wide standing config, mirroring the `gates.push_approval` precedent (ADR-0056) already in this codebase — e.g. a `gates.cleanup_recovery_confirmation: auto|ask` setting in `pipeline.user.yaml` that a PO sets once per project rather than per incident — or (b) simply defer the item, since two related, currently-OPEN defects in this exact cleanup/recovery family (kickoff-promotion revision-check bug, scratch-cleanup wiring gaps) suggest the underlying planner still has edge cases worth shaking out under human observation before removing the last checkpoint. Impact: No behavior change to the recovery flow itself in this wave (option a still requires wiring a new config read-path, so it's not literally zero-effort, but the risky mutation-execution code path is untouched). The PO keeps visibility into every recovery until the sibling defects are closed and more real-world incidents have been observed. If (a) is chosen, the PO gets the same one-time-consent shape the item's own Proposal invokes ('consent already granted to the pipeline') without hand-editing gate code — consistent with how the repo already solved an analogous problem for push approval. Tradeoffs: Does not satisfy the item's acceptance test in this wave; the PO would still see a selection prompt on the next orphaned-descriptor incident. If deferred outright, the friction the greenfield tester (source: Rune happy-path handover, P1-5) flagged persists into the next greenfield run. Config-toggle option (a) adds a new manifest surface to document and test, and needs its own default-value decision (default to `ask` to stay conservative, or `auto` to match the item's intent — itself a policy call for the PO).

**Recommendation:** Hybrid of options 2 and 3(a): implement the scoped auto-execute (bind-orphan + retire-orphans only) as the mechanical change, but gate it behind a one-time project-level consent setting rather than hard-coding it on — e.g. `gates.cleanup_recovery_auto_apply: [bind-orphan, retire-orphans]` (or a simple boolean covering just those two kinds) in `pipeline.user.yaml`, following the exact pattern ADR-0056 already established for `gates.push_approval`. This directly answers the item's own framing ('consent already granted to the pipeline') with a mechanism the repo already has precedent for, rather than inventing a new always-on behavior. It satisfies the acceptance test (orphan descriptor repaired with at most a completion note) for the common crash-residue case without touching the composite `retire-orphans-release-lost-binding` path, the external-archive paths, or `quarantine-private-receipt` — all of which either have documented complexity signaling deliberate risk-awareness, or (per line 749-751) an explicit prior 'stay human' policy decision that this triage pass has not re-examined and should not silently overturn. Leave `release-closed-feature` and `release-lost-binding` gated too, pending a separate look — they read as lower-risk than the composite path but weren't specifically named in the item's own acceptance test and don't need to be bundled into this decision.

**Risks/dependencies:** Two concrete dependencies/risks surfaced by reading the surrounding code and backlog, neither mentioned in the item itself:

1. `backlog/items/2026-08-09-kickoff-promotion-cleanup-readback-has-no-in-session-recovery.md` (status: open, re-triaged 2026-08-17) documents a live, confirmed bug in the SAME cleanup/recovery subsystem family — `kickoffPromotionCleanupRecoveryPlanCore()` in `onboarding-continuity.mjs` hard-codes a revision check that structurally excludes a project's first, ordinary kickoff→promotion, landing it in a dead-end 'recovery-unavailable' state with a candidate that cannot even execute in-session. This is a different function than `planSessionCleanupRecovery`, but it's the escape hatch `planSessionCleanupRecovery`'s own non-typed branches (`closed-recovery-unavailable`, `orphan-recovery-unavailable`) fall through to. It's evidence this recovery-planning family has real, recently-discovered edge-case bugs — a reason to keep the scope of any auto-execute change narrow and to not treat 'fully-typed, therefore safe' as self-evidently true without testing.

2. `backlog/items/2026-08-08-the-scratch-cleanup-mechanism-exists-but-no-event-calls-it.md` (status: open, partially executed, remaining points deferred to Sprint Alfred) documents that a SIBLING mechanism in this identical file (`bindScratchDescriptor`/`retireOrphanScratchDescriptors`, lines 1447-1597) shipped with green tests but no live caller wiring it into bootstrap for a long stretch — a documented pattern in this exact file of 'the mechanism exists, nothing invokes it correctly yet.' Worth checking, before committing effort to this item, whether the caller wiring for whichever recovery kinds get auto-executed is itself fully live and tested end-to-end (not just unit-tested), given that history.

3. This item's own 'Affected artifact' pointer (`session-cleanup-recovery.mjs`) is accurate for the TYPED, ready-plan confirmation friction (the actual scope of a fix), but the phrase in the item's Description — 'select a recommended attended-host-recovery' — matches the vocabulary of a DIFFERENT, adjacent escape-hatch mechanism (`session-cleanup.mjs plan-human-recovery`, backed by `onboarding-continuity.mjs`, surfaced via `cleanupHumanRecoveryAction()` in `project-onboarding-v3.mjs`), which is reached only when `planSessionCleanupRecovery` could NOT construct a typed plan at all. That escape hatch is explicitly untyped/unprovable by design and is out of scope for 'fully-typed' auto-execution — whichever session picks this item up should confirm, if possible, which of the two mechanisms the source greenfield report (Section 9, P1-5, in the external test repo not present in this checkout) actually observed, since it changes what 'fixing this' means.

## Implementation status, 2026-08-19 (NOT closed — reopened after Critic FAIL)

Implemented, not accepted: all six typed cleanup-recovery kinds now
auto-execute (requiresConfirmation: false) with a .bak pre-mutation
backup safety net. Commit: 3d5fda6d. A companion fix
(9d8cd787, unrelated commit's fixture regression) is unrelated to this
item's own correctness.

An independent Critic review (task W4-CRITIC-2C, opus/max route,
security-class-mandated) returned FAIL after a full 10-category hunt
(a prior attempt truncated with zero output and had to be retried):

- **F1 (major, unresolved):** `partialCleanupRecoveryResult()` now
  performs the recovery in-line and, on success, falls through to
  return a `ready` lifecycle result built from the PRE-recovery
  `continuity` object — nothing re-observes continuity after the
  mutation. Three of the six kinds (`release-lost-binding`,
  `release-closed-feature`, and the release half of the composite)
  mutate portable State and return a fresh `stateSha256`/`mutated`
  flag from the underlying call that the caller never re-reads. A
  caller trusting the returned `ready` result gets digests the same
  call just invalidated.
- **F2 (major, unresolved, QG-11):** two of the six kinds
  (`quarantine-private-receipt`, and both
  `retire-externally-archived-orphans`/`retire-mixed-orphans` via
  `backupExternalRetirementManifest`) have ZERO test coverage, and
  every fail-closed branch of the new `.bak` helpers is untested.
  The external-retirement path is the only one of the six that
  deletes a pre-existing file it did not create — the single kind
  where the `.bak` net most directly replaces the removed human gate
  — and its backup helper silently returns `null` on a missing
  source with no caller checking the result. (The Critic separately
  verified the actual path-reconstruction logic IS correct today by
  direct trace — the finding is the absence of a test pinning it, not
  a present bug.)
- **F3 (minor):** the commit's claim "all fail closed on a symlink or
  non-regular-file source" is false for two of the three backup
  helpers (`backupBeforeMutation` uses `existsSync`, which follows
  symlinks and returns false — silently skipping, not failing closed,
  on a dangling symlink; `backupOnboardingPrivateState` silently
  `continue`s past non-regular entries instead of refusing). Residual
  risk is bounded by an independent downstream fail-closed check, but
  the security claim in the commit message does not hold as written.
- **F4 (minor):** a bare `catch {}` in the new apply path discards the
  typed failure code and replaces it with one generic message — the
  human escalation path (the safety valve replacing the removed gate)
  now gets strictly less diagnostic information than before.
- **F5 (minor, QG-06):** the external-manifest path convention is
  disclosed as deliberately duplicated/un-exported rather than pinned
  by any test — a future change to the source convention would
  silently disable that kind's safety net.
