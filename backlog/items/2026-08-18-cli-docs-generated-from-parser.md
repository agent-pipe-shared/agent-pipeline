# Generate CLI usage docs from parser definitions and cover them with contract tests

## Description

The --dir documentation and the flagless CLI drifted apart from each
other over time, meaning documented usage no longer matched actual
command behavior.

## Triggering situation

From a greenfield happy-path test report, pipeline version
0.6.0+codex.20260818162535.96cf805, test repo Rune_Test1_Codex_060_52,
full report at docs/pipeline-greenfield-happy-path-handover.md in that
test repo. Cites Section 9, item P2-3 ("Dokumentation und CLI aus einer
Quelle").

## Affected artifact

CLI usage documentation generation, push/recovery command docs.

## Proposal

Usage examples should be generated from the CLI parser definitions or
from tested fixtures, and every command form shown in the docs should run
in a contract test.

Acceptance test: all documented push and recovery commands are validated
in CI as argv fixtures against the real parser.

## Design proposal (Wave-4 prep), 2026-08-18

*Prep material for PO triage, not a decision — a Triage section, if/when added, records the actual PO decision. Generated by a read-only design pass (dispatch NVA-W4-DESIGN-cli-docs-generated-from-parser) grounded in the current repo state.*

**Problem (restated):** `docs/push-release-flow.md` (359 lines, 8 fenced command examples covering `pipeline-state.mjs`, `po-human-approval.mjs`, `po-approval-gate.mjs`, `guard-human-override.mjs`) is hand-authored prose describing exact CLI invocations, and it has already drifted from the real CLI at least once: `plugins/pipeline-core/scripts/pipeline-state.mjs:5946` carries a reactive patch to its own `--help` text — "The project directory comes from CLAUDE_PROJECT_DIR, or the current working directory. There is no `--dir` flag." — added specifically because agents/docs assumed a `--dir` flag that never existed. `pipeline-state.mjs` (5,972 lines, 46 subcommands in `PIPELINE_STATE_COMMANDS`) parses flags with a hand-rolled loose `parseFlags(argv)` (any `--x value` pair, silently accepted) plus a stricter `parseExactFlags` used only for a subset of CAS-bound commands (`pipeline-state.mjs:2525-2551`); there is no single declarative per-command flag/type schema to generate docs *from*. `po-human-approval.mjs` is closer to a schema (a fixed `Set` of known flag names plus a `KNOWN_COMMANDS` list, `po-human-approval.mjs:403-482`) but validation logic and error text are still imperative and hand-written, not declarative. There is no existing generator; there is, however, existing precedent for **fixture-argv-against-real-parser** tests in this exact codebase (`plugins/pipeline-core/scripts/pipeline-state-result-case-migration.test.mjs` and `pipeline-state-result-rebind.test.mjs` already build `argv` and invoke the exported `run()`).

**Options:**

1. **Generate docs from a declarative parser schema (the item's own Proposal)** — retrofit `pipeline-state.mjs` and the `po-*` scripts with a per-command declarative flag/type/help definition, generate `--help` text and doc snippets from it, and contract-test every documented example. Impact: docs structurally cannot drift from the parser again, for every command, going forward. Tradeoffs: requires rearchitecting the flag handling of a 5,972-line file with 46 hand-tuned, incident-scarred commands (security-sensitive ones like `approve-push` use the deliberately closed `parseExactFlags`) — real regression risk in guardrail/push-approval code paths, large surface, and it duplicates ground already accepted-and-deferred to **Sprint Nightwing** under "Product experience: onboarding, configuration, documentation" (`backlog/items/2026-08-09-agents-read-the-pipelines-source-because-nothing-describes-its-interface.md`, whose own Direction 2 is literally "`--help` on the operator-facing scripts"). Complexity: **large**.
2. **Contract-test the existing docs as argv fixtures, no generation** — extract the documented command examples from `docs/push-release-flow.md` into fixtures and assert each one at least parses/validates against the real exported `run()`/`runHumanApproval()` (reusing the exact pattern already in `pipeline-state-result-*.test.mjs`), failing CI on drift instead of catching it reactively (as the `--dir` comment shows happened once already). Impact: closes the acceptance-test half of the item cheaply; would have caught the actual observed `--dir` incident. Tradeoffs: docs stay hand-maintained — a human/agent must still remember to update prose when a flag changes; the test only covers commands actually harvested into fixtures, not the full parser surface. Complexity: **small–medium**.
3. **Minimal: subcommand-existence lint only** — grep each fenced command block in `docs/push-release-flow.md` for its subcommand token and check it's a member of `PIPELINE_STATE_COMMANDS` / `KNOWN_COMMANDS`. Impact: near-zero cost, catches "renamed/removed command" drift. Tradeoffs: would **not** have caught the actual `--dir` incident (a phantom flag, not a missing command) — the loose `parseFlags` silently accepts unknown flags, so this option misses the demonstrated failure mode. Complexity: **small** (trivial, weaker guarantee).

**Recommendation:** Option 2, narrowly scoped to `docs/push-release-flow.md`'s push/recovery examples (matching the item's own "Affected artifact"), reusing the `plan()`/`invoke()` fixture pattern already established in `pipeline-state-result-case-migration.test.mjs`. Decline Option 1 for Nova Wave 4 — it's a rearchitecture of guardrail-adjacent CLI code that duplicates scope already accepted for Sprint Nightwing, and Nova is closing out toward 0.6.0. Option 3 alone is too weak given the specific incident that motivated this item.

**Risks/dependencies:** This item substantially overlaps two already-closed items' explicitly-left-open follow-ups: `backlog/items/2026-08-09-push-approval-skill-reference-predates-adr-0061.md` Direction 2 ("a test or generation step that asserts the skill reference names every subcommand `po-human-approval.mjs --help` actually reports... remains genuinely open") and its own cross-reference `2026-08-07-lifecycle-guard-does-not-know-the-human-signing-commands.md` ("the same drift class"). Before dispatching, the PO should decide whether this 2026-08-18 item supersedes/consolidates those, or whether it's an unintentional re-filing — running three parallel backlog entries for the same fix is a coordination cost, not three fixes. Also note the precedent at `backlog/items/2026-08-16-guard-lifecycle-allowlist-should-derive-from-the-onboarding-cli-table.md` (closed 2026-08-18): "derive from the CLI's own table" was recently done successfully there, but only for one narrow declared property on one list — it is evidence a narrowly-scoped derivation works, not evidence that full doc generation across `pipeline-state.mjs`'s 46 commands is proportionate right now.

**Estimated complexity:** small (for the recommended Option 2, bounded to `docs/push-release-flow.md`)
