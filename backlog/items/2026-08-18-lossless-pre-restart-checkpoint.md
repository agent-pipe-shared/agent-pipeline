# Lossless pre-restart checkpoint for material intake input

## Description

Material input is currently only compressed into a strongly limited
resume card before a forced restart. This means substantive user-supplied
input can be lost or degraded across a restart boundary, since the resume
card is not designed to carry it losslessly.

## Triggering situation

From a greenfield happy-path test report for pipeline version
0.6.0+codex.20260818162535.96cf805, test repo Rune_Test1_Codex_060_52; see
Section 9, item P0-1, full report at
docs/pipeline-greenfield-happy-path-handover.md in that test repo.

## Affected artifact

resume-hint.mjs, project-onboarding-v3.mjs, kickoff design flow, restart
barrier.

## Proposal

Before a restart barrier is activated, if material input is present, a
durable, sanitized source-evidence file must be written; the resume card
should thereafter reference only that file's path and SHA plus the intake
decisions already answered. Alternatively, a new private kickoff-intake
artifact with the same bindings could be introduced.

Acceptance test: a PO supplies at least 10 KB of structured input,
answers intake questions, and restarts; the following session must be
able to produce a complete, content-equivalent design-input.md without
the input being re-pasted, and language, profile, git author, and
already-answered design decisions must not be asked again.

## Design proposal (Wave-4 prep), 2026-08-18

*Prep material for PO triage, not a decision — a Triage section, if/when added, records the actual PO decision. Generated by a Workflow-dispatched read-only design pass (dispatch NVA-W4-DESIGN-lossless-pre-restart-checkpoint-design-options) grounded in the current repo state.*

**Problem (restated):** Item backlog/items/2026-08-18-lossless-pre-restart-checkpoint.md (source: Rune happy-path handover, P0-1) claims that substantive PO-supplied material input (e.g. a large requirements paste) can be lost or degraded across a forced restart because the only carry-forward mechanism, the resume card, is not designed to hold it losslessly. I verified this against the actual code: plugins/pipeline-core/lib/resume-hint.mjs is explicitly 'Non-authoritative, discardable context for a brief session restart' (line 2), capped at RESUME_HINT_MAX_BYTES=4096 total (line 9) with MAX_FIELD_BYTES=480 per field (line 13), and its four/five keys (intent/scope/constraints/questions, +optional progress) are short single-line distilled strings, not raw material -- validText() forbids multi-line content, secrets, opaque tokens, code fences, URLs, paths, command lines (lines 47-67, 121-125). It has no field shaped to hold 10KB+ of pasted requirements. Separately, project-onboarding-v3.mjs's kickoff goal collection is capped even tighter: KICKOFF_GOAL_MAX_BYTES=160 bytes (plugins/pipeline-core/lib/onboarding-continuity.mjs:84), used by collectGoalAction()/collectAuthorIdentityAction() (project-onboarding-v3.mjs ~L1951, L3936-3946). No 'source-evidence' or equivalent durable-material-capture concept exists anywhere in lib/ or docs/ (grep found zero hits). So the item's factual premise holds: today there is genuinely no artifact that losslessly carries PO material input across a restart boundary; the item is not fabricated or already solved.

Critically, this item is NOT standalone. It is one of three sibling items filed from the exact same Rune report section (Section 9): backlog/items/2026-08-18-fresh-repo-onboarding-intake-first-transaction.md (P0-0, same priority tier as this item) already proposes, as step (2) of a broader 'atomic bootstrap-from-intake coordinator', to 'losslessly save already-delivered material input into a private intake checkpoint' -- i.e. exactly this item's proposal, but embedded inside a much larger onboarding-reordering redesign (steps 1-6: consent+missing-values, lossless checkpoint, bundled intake questions, single-transaction PRD/spec generation, authority binding only after, provisional-kickoff elimination). backlog/items/2026-08-18-intake-values-restart-resilient-immediately.md (P1-4) is adjacent but distinct: it's about persisting already-ANSWERED intake decisions (git author, language, profile) immediately, not about the raw unstructured material paste this item targets. All three items share 'Affected artifact: project-onboarding-v3.mjs' and 'restart barrier'. Wave-4 triage must not decide this item in isolation from P0-0 -- doing so risks either duplicate design work or building a narrow checkpoint mechanism that P0-0's broader transaction redesign would have to rip out and replace.

**Options:**

1. **Minimal bolt-on: sanitized source-evidence file + resume-card pointer** — Implement the item's own Proposal narrowly and in isolation: before any restart-barrier activation while material input is pending, write a durable sanitized evidence file (e.g. project/intake-evidence/<sha>.md or similar, git-trackable or gitignored-but-persistent) capturing the raw PO material verbatim (after the same secret/shape sanitization resume-hint.mjs already does), plus already-answered intake decisions. Extend resume-hint.mjs's schema with a new optional field carrying {path, sha256} pointing at that file, instead of trying to fit the material into the existing 480-byte fields. Kickoff/onboarding flow reads the evidence file back on resume to reconstruct design-input.md. Impact: Directly closes the P0-1 acceptance test: a PO's 10KB+ paste survives a forced restart without re-pasting, and answered intake decisions aren't re-asked (for the material-input dimension only). Adds one new file format/schema (versioned, needs its own validator akin to resume-hint's, its own secret-shape filtering, its own size ceiling) and one new write/read call site pair. Tradeoffs: Built and shipped independently of P0-0, this creates two competing 'private intake checkpoint' concepts if P0-0 is later accepted and implements its own step-2 checkpoint as part of the larger transaction reorder -- likely requiring a second migration/rework pass. Doesn't address P0-0's actual complaint (provisional authority created before intake is durably captured) or P1-4's complaint (already-answered git author/language/profile re-asked) -- a PO could still hit two of the three related bugs in the same restart even after this ships alone. Net new surface: another sanitization filter to keep in sync with resume-hint.mjs's (duplication risk unless factored into a shared module).
2. **Fold into P0-0's atomic bootstrap-from-intake coordinator** — Decline to design this item separately. Accept it as satisfied-by-reference into fresh-repo-onboarding-intake-first-transaction (P0-0), whose step (2) already specifies 'losslessly save already-delivered material input into a private intake checkpoint' as one stage of a single atomic transaction (consent+missing-values -> lossless checkpoint -> bundled intake questions -> single-transaction PRD/spec generation -> authority binding only after -> no/staging-only provisional kickoff artifacts). Close this item as a duplicate/subsumed sub-requirement and route its acceptance test into P0-0's spec as one of P0-0's own acceptance criteria. Impact: One coherent onboarding redesign instead of two independently-evolving mechanisms touching the same restart barrier and the same project-onboarding-v3.mjs surface. The lossless-checkpoint acceptance test (10KB input, restart, content-equivalent design-input.md, no re-ask) becomes a checkable sub-case of P0-0's own acceptance test, which is already stricter (also requires no generic kickoff commits, no reopen/rebind, no HGO, no continuity repair). Tradeoffs: P0-0 is a large, six-step onboarding-flow reorder (provisional-authority timing, kickoff promotion, lifecycle publication order) -- materially bigger in scope, risk, and review surface than the narrow checkpoint mechanism alone. If P0-0 stalls, gets deferred, or is descoped in Wave-4 triage, this item's concrete PO-facing pain (lost paste) ships later or not at all, even though it could have been fixed standalone in a fraction of the time. Makes this item's own triage outcome fully dependent on a separate, not-yet-triaged item's fate -- a process risk if P0-0 triage happens in a different session/pass.
3. **Defer / no separate action pending P0-0 triage** — Mark this item's Decision as deferred rather than accepted-standalone or subsumed: hold it open, do no design or implementation work yet, and revisit once P0-0 (fresh-repo-onboarding-intake-first-transaction) is itself triaged and its scope for Wave-4 is settled. Record the dependency explicitly in this item's Triage so a later session doesn't re-litigate the P0-0 relationship from scratch. Impact: Zero implementation risk taken this wave; avoids committing to either the narrow-file schema (Option A) or the six-step reorder (Option B) before the PO has actually decided P0-0's fate. Costs nothing to reverse later. Tradeoffs: Leaves a P0-priority, PO-validated real bug (confirmed by reading the actual 4096/480/160-byte caps in resume-hint.mjs and onboarding-continuity.mjs) unaddressed for at least one more triage cycle, on an item the PO's own test report flagged P0. Given CLAUDE.md's explicit instruction to re-verify inherited 'still open' claims and the memory note that the PO wants decisions made now rather than deferred ('machen oder verwerfen'), pure deferral without at least scoping a fallback is likely to be rejected by the PO outright unless paired with a concrete next step (e.g. 'decide together with P0-0 in the same triage pass').

**Recommendation:** Hybrid of Options A and B, sequenced rather than exclusive: triage P0-0 (fresh-repo-onboarding-intake-first-transaction) and this item in the SAME Wave-4 pass, back-to-back, because they name the same affected artifacts (project-onboarding-v3.mjs, restart barrier) and P0-0's own step (2) is a verbatim restatement of this item's Proposal. If the PO accepts P0-0's broader reorder, close this item as subsumed with an explicit cross-reference (Option B) rather than building a competing mechanism. If the PO defers or descopes P0-0 (six-step reorder is large and touches provisional-authority timing, a materially riskier surface than a checkpoint file), accept THIS item standalone and implement the minimal bolt-on (Option A) -- it is small, additive (new optional resume-hint field + one new sanitized evidence-file schema, following resume-hint.mjs's existing sanitization/schema-versioning pattern almost mechanically), and delivers the PO-validated P0-1 acceptance test on its own without waiting on the larger redesign. Do not decide this item in a vacuum without at least reading P0-0's current Triage status in the same session (per CLAUDE.md's re-verify-before-dispatch rule) -- the two are not independent despite living in separate files.

**Risks/dependencies:** 1) Direct scope overlap with P0-0 (fresh-repo-onboarding-intake-first-transaction) as shown above -- both name project-onboarding-v3.mjs and 'restart barrier' as affected artifact, and P0-0 step 2 textually restates this item's Proposal. Triaging them independently/out of order risks duplicate or conflicting implementations. 2) Partial overlap with P1-4 (intake-values-restart-resilient-immediately): different payload (raw material paste vs. already-answered discrete fields: git author/language/profile) but the same restart-barrier mechanism and same file (project-onboarding-v3.mjs) would likely need touching for both -- worth at least noting in the same triage pass to avoid two separate goldfish dispatches editing overlapping code regions. 3) Any new evidence-file schema should reuse resume-hint.mjs's existing sanitization primitives (FORBIDDEN_SHAPES, secretAssignment, opaqueToken, MAX_FIELD_BYTES discipline) rather than reimplementing secret-filtering from scratch -- diverging filters is a known source of security drift. 4) This item and its two siblings all derive from a single external test report (docs/pipeline-greenfield-happy-path-handover.md in test repo Rune_Test1_Codex_060_52, which I could not read -- it lives outside this checkout) -- the item's own text is the only available account of what P0-1 actually observed; I could not cross-check against the raw report. 5) The batch of roughly 35 other 2026-08-18-dated backlog items in this repo suggests a large Wave-4 triage session is already underway/planned; sequencing (which items get triaged in what order, whether P0-0 and P0-1 land in the same PO conversation) is itself a process decision the PO should make, not something this analysis can force. 6) Implementation of either Option A or Option B touches project-onboarding-v3.mjs (4814 lines) and the restart-barrier machinery, which per CLAUDE.md's own guardrail notes is an area with documented HGO-signature-binding fragility (statusSha256 drift) -- any dispatch here should be scoped carefully and reviewed by Critic per the self-application rule.
