# Separate implementation-complete from PO-accepted in the final status

## Description

The result was reported as done even though browser verification and an
independent Critic review were missing. The completion status needs to
distinguish these states rather than collapsing them into a single
"done".

## Triggering situation

From the greenfield happy-path test report for pipeline version
0.6.0+codex.20260818162535.96cf805 in test repo Rune_Test1_Codex_060_52,
docs/pipeline-greenfield-happy-path-handover.md, Section 9 item P1-6.

## Affected artifact

completion/acceptance status model, final report format.

## Proposal

The completion status should separate: implementation complete;
automated verify passed; independent review passed/deferred;
manual/browser-based checks passed/pending; PO acceptance open/confirmed.
A push may still happen on explicit request even with documented pending
items, but must not be described as fully accepted.

Acceptance test: when a browser is missing, the status honestly reads
"browser verification pending" and the PO receives a clear local startup
instruction before the push ceremony.

## Triage (filled in by the Elephant of the next Pipeline session)

- **Decision:** Accepted — hybrid: keep GF-09's existing report shape, add a glossary distinction between "implementation complete" and "PO-accepted", one new handover marker value, a hard rule against saying "done" while checks are open, require GF-09's Open-items section to name outstanding review/manual checks by category.
- **Rationale:** PO 2026-08-18 accepted the analyst's recommendation as-is.
- **Assignment (if accepted):** Nova Wave 4 implementation.
- **Date:** 2026-08-18


## Design proposal (Wave-4 prep), 2026-08-18

*Prep material for PO triage, not a decision — a Triage section, if/when added, records the actual PO decision. Generated by a Workflow-dispatched read-only design pass (dispatch NVA-W4-DESIGN-explicit-final-acceptance-gate) grounded in the current repo state.*

**Problem (restated):** The backlog item (backlog/items/2026-08-18-explicit-final-acceptance-gate.md) reports that in a Rune/Codex 0.6.0 greenfield happy-path test (external repo, report not present in this checkout — confirmed by a `find` for docs/pipeline-greenfield-happy-path-handover.md returning nothing), a result was reported as fully 'done' even though browser verification and an independent Critic review had not actually happened. The item's own diagnosis: the completion/acceptance status model collapses several genuinely different states ('implementation complete', 'verify passed', 'review passed/deferred', 'manual/browser checks passed/pending', 'PO acceptance open/confirmed') into one binary done/not-done, so a partially-checked result can misreport as fully accepted.

Grounding in the actual repo: the closest existing status model is the '🟡-Merge v2' scheme in templates/handover.md (lines 78-84) — a 3-value marker (✅ done / 🟡 human verification pending / 🔄 in progress) on docs/state.md's work-package table, with a MANDATORY rollback-anchor requirement for any 🟡 row. This is a partial precedent for exactly what the item wants (a state short of full acceptance that still doesn't block merge), but it is a single flat marker, not a multi-dimensional model — it cannot distinguish 'Critic skipped' from 'browser check pending' from 'PO hasn't looked yet'. Separately, roles/goldfish.md §6 (GF-09) defines the Goldfish's own six-section completion report (DoD results / evidence / changed files / deliberately-not-changed / deviations / open items) with a three-valued per-DoD-check status (passed/failed/not verifiable) — this is honest at the per-check level already, but nothing in operating-model.md's lifecycle (§4 step 8 'Close') or glossary (§10) defines a distinct terminal PO-acceptance state that a Goldfish/Elephant report rolls up into; grep across roles/goldfish.md, roles/critic.md and docs/operating-model.md for 'browser' returns nothing — there is currently no vocabulary anywhere in the core rules for a browser/manual-verification checkpoint, confirming the gap the item names. docs/push-release-flow.md governs push *authorization* (signature ceremony, who may push) and is a separate, already-well-specified mechanism; the item explicitly does not want to block push, only to stop mislabeling it as 'accepted'.

**Options:**

1. **Full five-facet status model (the item's own proposal)** — Adopt the item's proposal essentially as written: extend the completion/acceptance vocabulary to five independently-tracked facets — implementation complete; automated verify passed; independent review passed/deferred; manual/browser checks passed/pending; PO acceptance open/confirmed — and require every 'final' report (Goldfish GF-09 report, Elephant handover to docs/state.md, and any pre-push summary) to state all five explicitly rather than collapsing them into one status word. Push may still happen with facets open, but the report accompanying it must name which ones are. Impact: Every closing report and every docs/state.md status-table row gains a small fixed structure (5 named fields) instead of one word. The PO always sees, at a glance, exactly which gates a candidate has and has not cleared before deciding to push or accept. Closes the exact failure mode from the trigger report: an implementation-complete-but-unverified result can no longer read as plain 'done'. Tradeoffs: Touches multiple normative surfaces at once: roles/goldfish.md GF-09 (report format, currently capped at ~1000 tokens/40 lines — a 5-facet block adds to that budget), templates/handover.md's Status table (currently one ✅/🟡/🔄 marker column), and docs/operating-model.md §4 step 8 / §10 glossary (needs a normative definition of the five facets and their terminal states). Five facets for every dispatch, including trivial Rigor-0 ones, risks becoming ceremony that gets rubber-stamped rather than read — the same failure mode this item is trying to fix, one level up. Needs explicit reconciliation with the existing 🟡-Merge v2 marker so the two don't drift into two competing status vocabularies.
2. **Minimal fix: one added state, no new taxonomy** — Instead of five facets, add exactly one new terminal value to the existing vocabulary: keep the Goldfish/Elephant report format as-is (already honest per-check via GF-08/GF-09's passed/failed/not-verifiable), but forbid the word 'done'/'complete' as a final characterization anywhere a review or manual check is outstanding — require 'implementation complete, PO acceptance pending: <named open item>' as the only acceptable phrasing in that case, and extend templates/handover.md's marker legend with one more explicit value (e.g. 🟠 'implementation complete, acceptance pending') distinct from 🟡 (human verification pending, i.e. spot-check style) so the two don't get conflated. Impact: Fixes the exact reported symptom (reporting 'done' when it wasn't) with a wording/vocabulary rule plus one new marker value, not a new report schema. Low implementation surface: one glossary entry, one handover-marker addition, and a phrasing constraint added to roles/goldfish.md GF-09 and the Elephant's close-step guidance (operating-model.md §4 step 8). Tradeoffs: Doesn't produce the fully itemized five-facet visibility the trigger report implicitly wants (a reader still has to go find out *what* is pending, not see it broken out by category at a glance). Relies on prose discipline ('never say done when X is pending') more than the first option's structural forcing function — a report format that merely forbids a word is more easily drifted from than one with named required fields.
3. **Defer — fold into the adjacent full-push-preflight item** — Do not create a new standalone status-model change. Recognize this item as one symptom of a broader honesty-at-the-push-boundary gap already covered by the same 2026-08-18 batch (backlog/items/2026-08-18-full-push-preflight-before-signature.md proposes a plan-push coordinator that validates preconditions atomically before the signature ceremony) and defer this item, folding its acceptance-status requirement into that coordinator's scope as one more precondition it must report on. Impact: Avoids two overlapping efforts touching the same push/acceptance boundary from different angles in the same wave. Concentrates the fix at the mechanical layer (the preflight coordinator) rather than the reporting layer. Tradeoffs: The two items are not actually the same shape: full-push-preflight is about a coordinator validating clean-HEAD/remote/verify-path preconditions mechanically before a push signature, while this item is about report vocabulary and honesty in ordinary Goldfish/Elephant completion reporting — most 'done but not verified' claims happen long before any push ceremony starts (e.g., mid-session status updates, docs/state.md rows). Deferring this item into that one risks losing the reporting-layer fix entirely if that item's scope stays narrowly mechanical, and delays a cheap, well-scoped fix for an unrelated reason.

**Recommendation:** A hybrid of options 1 and 2: take option 2's minimal shape as the actual implementation (extend the existing GF-08/GF-09 per-check honesty and the templates/handover.md marker legend with one clearly-named 'implementation complete, PO acceptance pending' state, and a hard rule against characterizing a result as 'done' while review/manual checks are open), but borrow option 1's five named categories as the *content* of what goes into that state's 'named open item(s)' rather than building five separate always-present fields. Concretely: keep GF-09's existing six-section report and 🟡-Merge v2's existing marker column, but (a) add explicit glossary terms in operating-model.md §10 for 'implementation complete' vs 'PO-accepted' as distinct lifecycle states, matching §4 step 8's Close step language, (b) require GF-09's 'Open items' section and the Elephant's close-step summary to name outstanding review/manual/browser checks by category when present (reusing the item's five-facet vocabulary as a checklist to consult, not five mandatory fields to fill even when empty), and (c) add the acceptance test from the item almost verbatim: when a browser is unavailable, the report must say 'browser verification pending' plus give the PO a local startup instruction before any push ceremony. This gets the honesty fix with a small, bounded surface (glossary + one marker + one phrasing rule + one Open-items content requirement) instead of a five-field schema imposed on every report regardless of size, while still directly satisfying the item's stated acceptance test. I would not defer/reject this — the underlying gap (grep for 'browser' returns nothing anywhere in roles/ or docs/operating-model.md) is real and the trigger incident is concrete and recent (this session's own date), and the fix is cheap relative to the honesty cost of 'reported done but wasn't' recurring (roles/goldfish.md GF-08 already names this as 'the documented main failure mode (P4)' for a different context — under-verification — so this item is the same failure mode one layer up, at the acceptance-reporting layer, and the Pipeline has already invested in the analogous per-check fix once).

**Risks/dependencies:** 1) Overlaps but is not a duplicate of backlog/items/2026-08-18-full-push-preflight-before-signature.md (same 2026-08-18 batch, same trigger report family) — that item is a mechanical pre-signature coordinator, this one is a reporting/vocabulary fix; both touch the push boundary and should be triaged with awareness of each other so they don't produce two independent, inconsistent 'is this really done' checks. 2) Touches roles/goldfish.md GF-09, whose report is already token-capped (~1000 tokens/40 lines) and whose format changes have caused truncation regressions before (per GF-09-D's own history note about 'seven long dispatches... ended with a fragment... instead of their report') — any addition to the mandatory report shape needs to stay inside that budget or risks reintroducing truncation. 3) templates/handover.md's 🟡-Merge v2 marker legend is referenced by a HARD RULE (mandatory rollback anchor per 🟡 row) — adding a new marker value must not silently exempt it from or conflict with that rollback-anchor requirement. 4) The item's own named trigger document (docs/pipeline-greenfield-happy-path-handover.md, Rune test repo Rune_Test1_Codex_060_52) is external and not present in this checkout, so the Wave-4 triage is working from the item's own summary of that report, not the primary source — worth flagging to the PO that independent confirmation of the trigger incident (beyond this item's paraphrase) hasn't been possible from within this repo. 5) No conflicting or duplicate backlog item was found proposing the same five-facet acceptance model; this is a net-new gap, not already covered elsewhere in the 2026-08-18 batch.

**Estimated complexity:** small
