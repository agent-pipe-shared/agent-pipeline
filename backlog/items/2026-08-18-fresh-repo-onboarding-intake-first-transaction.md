# Recut fresh-repo onboarding as an intake-first transaction

## Description

Onboarding currently creates provisional project, kickoff, and lifecycle
authority before the concrete PO input has been fully and durably captured.
The later, normal processing of that input then invalidates the
self-created pre-state and triggers an unnecessary repair cascade. The
onboarding flow needs to be reordered so that authority is only bound
after the input is durably captured, not before.

## Triggering situation

From a greenfield happy-path test report on pipeline version
0.6.0+codex.20260818162535.96cf805, test repo Rune_Test1_Codex_060_52; full
report at docs/pipeline-greenfield-happy-path-handover.md in that test
repo, Section 9, item P0-0.

## Affected artifact

project-onboarding-v3.mjs, kickoff promotion, resume hint, pipeline-state
initialization, authority binding, restart barrier, and greenfield guards.

## Proposal

Introduce a dedicated atomic bootstrap-from-intake coordinator for fresh
repositories, structured as: (1) capture pipeline consent and any
still-missing required values once; (2) losslessly save already-delivered
material input into a private intake checkpoint; (3) ask any open design
questions in one bundled round and add the answers to the same checkpoint;
(4) from that checkpoint, generate the durable design source plus initial
PRD/spec in a single transaction; (5) only then bind the finally-generated
artifacts as authority and publish the lifecycle; (6) either avoid
provisional kickoff artifacts entirely, or keep them strictly as unbound,
replaceable staging data. Runtime setup and a technically necessary
restart may occur within this transaction, but not before a lossless
checkpoint exists and not with any publicly effective partial binding.

Acceptance test: an empty repository receives at least 10 KB of
requirements in the first message; after consent, one bundled intake
answer, and a forced restart, exactly one durable design source and one
consistent initial authority state are produced; there must be no generic
kickoff commits, no repeated mandatory questions, no reopen/rebind, no
HGO, and no continuity repair.

## Design proposal (Wave-4 prep), 2026-08-18

*Prep material for PO triage, not a decision — a Triage section, if/when added, records the actual PO decision. Generated by a Workflow-dispatched read-only design pass (dispatch NVA-W4-DESIGN-fresh-repo-onboarding-intake-first-transaction) grounded in the current repo state.*

**Problem (restated):** backlog/items/2026-08-18-fresh-repo-onboarding-intake-first-transaction.md (P0-0, from the Rune greenfield happy-path handover, Section 9) says onboarding currently binds provisional project/kickoff/lifecycle authority BEFORE the PO's actual requirements input is durably captured, and that the later real input then invalidates that self-created pre-state, triggering an unnecessary repair cascade. I read the item in full plus every file named under 'Affected artifact' that actually exists.

Grounding in the real code (all in plugins/pipeline-core/): project-onboarding-v3.mjs exists in two places -- scripts/project-onboarding-v3.mjs (336-line CLI wrapper, argv parsing + subcommand dispatch table) and lib/project-onboarding-v3.mjs (4814 lines, the actual state machine: v4Inspection, planLifecycle/applyLifecycle, the kickoff/kickoff-promote entry points at lines 4713-4814). The kickoff/promotion mechanics themselves live one file over, in lib/onboarding-continuity.mjs (~5300 lines).

The item's central claim is concretely true and precisely locatable: KICKOFF_GOAL_MAX_BYTES = 160 (onboarding-continuity.mjs:84) -- 'kickoff' captures only a 160-byte single-line 'goal' string (collectGoalAction(), project-onboarding-v3.mjs:1943-1962) and from that writes a PROVISIONAL pipeline-state.json, calibration, PRD, spec, handover and continuity-history (applyOnboardingKickoff, onboarding-continuity.mjs:4734) -- exactly the 'provisional project, kickoff, and lifecycle authority' the item describes, built from far less than the PO's real >=10KB of requirements. Only later does 'kickoff promote' (planOnboardingKickoffPromotion/applyOnboardingKickoffPromotion, onboarding-continuity.mjs:4494/5000) take the real --prd-path/--spec-path/--design-input-path and mark the provisional PRD+spec superseded (KICKOFF_SUPERSESSION_BASENAME = 'SUPERSEDED.md', onboarding-continuity.mjs:167) while the provisional directory itself is NOT removed (comment at line 164: 'The provisional kickoff PRD and Spec are not removed at promotion: they are named superseded'). The 'repair cascade' the item complains about is not hypothetical: a chain of prior incidents from exactly this two-phase (kickoff-then-promote) design already exists in the backlog -- 2026-08-07-a-promoted-feature-can-never-pass-the-plan-gate.md, 2026-08-08-a-permitted-edit-drops-the-session-into-an-unrecoverable-readiness-class.md, 2026-08-08-no-design-to-implementation-handover-exists.md, and 2026-08-09-the-promotion-supersedes-the-handover-and-leaves-it-saying-otherwise.md (this exact one: the promotion superseded the provisional PRD/spec but the canonical handover kept pointing at the now-superseded provisional anchor -- a resuming session was misdirected by the very artifact meant to prevent that). onboarding-continuity.mjs also carries a 15-stage crash-injection harness (KICKOFF_FAULT_STAGES, lines 182-198: prd-temp-fsync, prd-rename, ..., state-directory-fsync) built specifically to make the provisional-then-promote transaction crash-safe -- real engineering already sunk into hardening the CURRENT two-phase shape.

Two other backlog items were opened on 2026-08-18 from the SAME report section (Section 9) as narrower slices of the same finding: 2026-08-18-lossless-pre-restart-checkpoint.md (P0-1: the resume card that survives a forced restart is destructively lossy) and 2026-08-18-intake-values-restart-resilient-immediately.md (P1-4: answered intake values like git author/language/profile get re-asked after a restart). Grounding for P0-1's claim: resume-hint.mjs (comment at line 2: 'Non-authoritative, discardable context for a brief session restart') caps the whole card at RESUME_HINT_MAX_BYTES = 4096 across just four base keys (intent/scope/constraints/questions, each field capped at MAX_FIELD_BYTES = 480) -- nowhere near enough to losslessly carry 10KB+ of PO material across the restart the onboarding flow itself forces (restartAction(), project-onboarding-v3.mjs:1983-2003, driven by a restart-required status reachable mid-onboarding). This P0-0 item's own Proposal step (2) -- 'losslessly save already-delivered material input into a private intake checkpoint' -- is essentially a restatement of P0-1's proposal, and step (1) -- 'capture ... any still-missing required values once' -- substantially overlaps P1-4's proposal. I did not find any file matching the item's other named artifacts ('restart barrier' as a distinct module -- it is a set of functions/state inside project-onboarding-v3.mjs and codex-onboarding-runtime.mjs, not a separate file; 'greenfield guards' likewise names a behavior area, not a locatable file) so those two nouns in 'Affected artifact' are areas of the existing files above, not separate artifacts.

**Options:**

1. **Build the full atomic bootstrap-from-intake coordinator (the item's own Proposal)** — Implement the six-step transaction exactly as proposed: consent+missing-values once, a lossless private intake checkpoint, one bundled design-question round appended to that checkpoint, a single transaction generating design source + initial PRD/spec from the checkpoint, authority binding only after that, and either no provisional kickoff artifacts at all or strictly unbound/replaceable staging data -- restart/runtime-init allowed inside the transaction but never before a lossless checkpoint exists and never with a publicly effective partial binding. Impact: For a fresh-repo PO: one consent, one bundled question round, one forced restart at most, and the acceptance test's guarantee (no generic kickoff commits, no repeated mandatory questions, no reopen/rebind, no HGO, no continuity repair) holds by construction. For the codebase: this replaces the current two-phase kickoff -> kickoff-promote model with a one-phase model, which means retiring or fundamentally repurposing the KICKOFF_SUPERSESSION_BASENAME/supersession machinery, re-deriving crash-safety guarantees currently expressed as the 15-stage KICKOFF_FAULT_STAGES fault-injection harness for a new transaction shape, and re-threading every v4Inspection status (kickoff-required, restart-required, ready, etc.) and every CLI subcommand in ONBOARDING_SUBCOMMANDS that currently assumes the kickoff/promote split. Tradeoffs: Large surface: touches project-onboarding-v3.mjs (both files), onboarding-continuity.mjs, resume-hint.mjs, codex-onboarding-runtime.mjs's restart-barrier code, and the guard-lifecycle-ready.mjs allowlist that derives from ONBOARDING_SUBCOMMANDS -- essentially every consumer named in 'Affected artifact'. This is not a bug fix on top of stable ground; it is a rearchitecture of machinery that has already absorbed four prior repair-cascade incidents (2026-08-07 x2, -08, -09) and has purpose-built crash-safety tests. It needs its own spec/ADR-weight design pass (does 'kickoff' as a CLI verb survive at all? what happens to in-flight/old provisional-kickoff repos on upgrade -- a migration path is required) before implementation, not a direct dispatch from this backlog item's Proposal prose.
2. **Do the minimal version: accept the two narrower 2026-08-18 siblings, defer the full coordinator** — Implement only 2026-08-18-lossless-pre-restart-checkpoint.md (durable sanitized intake-evidence file before any restart barrier fires, referenced by path+SHA from the resume card) and 2026-08-18-intake-values-restart-resilient-immediately.md (persist each answered intake value -- git author/language/profile -- to restart-resilient private state as soon as it's answered). Leave the kickoff/promote two-phase authority-binding shape untouched. Merge this P0-0 item into those two per backlog's documented 'merged-into' convention rather than tracking it as separate accepted work. Impact: Directly closes the P0-1 and P1-4 acceptance tests (no re-pasting >=10KB material after a restart; no re-asking language/profile/git-author) with much smaller, independently reviewable changes confined mostly to resume-hint.mjs and the intake-collection call sites in project-onboarding-v3.mjs. It does NOT close this item's own acceptance test: provisional kickoff commits, the kickoff-promote supersession/repair path, and authority binding before durable capture all remain exactly as today -- the 'repair cascade' this item names stays possible, just less likely to be triggered by restart-related data loss specifically. Tradeoffs: Cheap and low-risk, but it is a genuine scope reduction, not a smaller version of the same fix: it treats the symptom (data lost/re-asked across a restart) rather than the item's actual root claim (authority is bound too early, before durable capture, full stop -- restart or not). A PO reading only 'accepted' against this item's id would be misled about what was actually delivered; the Decision text needs to say explicitly that P0-0 itself was NOT implemented, only its two narrower siblings were.
3. **Scope the coordinator down: kickoff writes only unbound staging data, promotion stays the sole authority-binding transaction** — A middle design: keep the existing two-call CLI shape (kickoff, then kickoff-promote) but change what 'kickoff' is allowed to write. Today applyOnboardingKickoff (onboarding-continuity.mjs:4734) writes real pipeline-state.json/calibration/PRD/spec/handover/history from a 160-byte goal -- i.e. it already binds authority. Instead, kickoff would write ONLY into a private, explicitly-unbound staging area (no pipeline-state.json write, no handover, no history entry); promotion would remain the one and only place authority gets bound, but its intake (design-input-path/prd-path/spec-path, already a joint atomic target per PROMOTION_TARGET_KEYS) would be fed from the durable staging checkpoint instead of requiring the PO to hand-author files ahead of time. Impact: Removes the 'self-created pre-state' the item names -- there is no provisional pipeline-state.json to supersede or repair, because kickoff never wrote one -- while reusing promotion's already-atomic, already-fault-tested commit path as the SINGLE binding transaction the item's Proposal step (4)-(5) actually asks for. The supersession/SUPERSEDED.md machinery becomes unnecessary and can be deleted rather than repurposed. Tradeoffs: Still touches both onboarding files and the v4Inspection status machine (kickoff-required's contract with callers changes: it no longer implies a bound state exists), and still needs the lossless-checkpoint and restart-resilient-answers pieces from option 2 as prerequisites -- so it does not avoid that work, it builds on it. Smaller blast radius than option 1 (no new one-phase transaction type to invent; reuses promotion's existing atomicity) but still a real behavioral change to a load-bearing status contract, and needs its own design pass to enumerate every caller that currently treats a post-kickoff 'kickoff-required' -> apply as having produced durable state.

**Recommendation:** Hybrid of options 2 and 3, sequenced rather than merged in one shot. Accept and implement the two narrower 2026-08-18 siblings first (lossless-pre-restart-checkpoint, intake-values-restart-resilient-immediately) as the immediate P0/P1 fix -- they are small, close two of the three concrete failure modes from the same triggering report, and are safe to build without touching the authority-binding state machine. For THIS item (P0-0), do not dispatch implementation straight from its Proposal prose: defer it with a stated condition -- a dedicated design pass (spec-weight, since it changes v4Inspection's status contract and the kickoff/promote CLI shape) to choose between option 1 (full one-phase coordinator, largest rewrite) and option 3 (kickoff demoted to unbound staging only, promotion stays the sole binder, smallest change that still satisfies the item's actual root claim). My own lean, once that design pass happens, is option 3: it fixes the exact defect named (authority bound before durable capture) by reusing machinery this repo has already built and hardened through four prior incidents (promotion's atomic multi-target commit, its fault-injection discipline) rather than inventing a new transaction shape from scratch. Track this item's status as open/deferred with that condition in the Triage Decision text, not accepted outright and not silently merged into the siblings, since its acceptance test (no reopen/rebind, no continuity repair) is strictly broader than either sibling's.

**Risks/dependencies:** 1) Direct proposal-overlap risk: this item's own Proposal steps (2) and (1) are near-duplicates of the P0-1 and P1-4 sibling items' proposals respectively -- triaging all three independently risks either duplicate implementation or three separate PO decisions on what is actually one piece of work at two granularities. Recommend triaging P0-1 and P1-4 first/together, then revisiting this item's Decision in light of what they actually deliver.
2) Regression risk on existing hardening: any change to applyOnboardingKickoff's write set interacts with the 15-stage KICKOFF_FAULT_STAGES crash-injection tests (onboarding-continuity.mjs) and with the four already-fixed repair-cascade bugs (2026-08-07 x2, -08, -09 backlog items) -- a design pass for option 1 or 3 must explicitly re-derive crash-safety for the new write shape, not assume the old fault-injection tests still cover it.
3) Guard/allowlist coupling: ONBOARDING_SUBCOMMANDS (project-onboarding-v3.mjs:62-86) is the single source hooks/guard-lifecycle-ready.mjs derives its automated-invocation allowlist from (GUARDDERIVE-1, referenced in-file). Any new or removed subcommand from a coordinator redesign needs a guard-side pass, not just a library change, or automated dispatches will be silently blocked/misrouted.
4) Migration/back-compat: any repo already onboarded under the current two-phase model (with a live provisional-then-superseded kickoff directory) needs an explicit compatibility story under whichever option is chosen -- none of the three options as scoped address existing installations, only fresh repos, and the item's own acceptance test is fresh-repo-only.
5) No conflicting prior PO decision found: grep of docs/state.md turned up no existing 'Wave-4' or item-specific mentions, so this triage is starting clean, not overriding a standing decision.

**Estimated complexity:** large
