# Unify verify evidence path between producer and push guard

## Description

The verify evidence producer and the guard consumer used different file
paths (verify.json vs. verify-latest.json) for the same evidence
artifact. This mismatch means a default verify run does not necessarily
produce the file the push guard actually reads, creating a silent gap
between evidence generation and evidence consumption.

## Triggering situation

Observed during a greenfield happy-path test of pipeline version
0.6.0+codex.20260818162535.96cf805 in test repo Rune_Test1_Codex_060_52,
documented in docs/pipeline-greenfield-happy-path-handover.md (in that
test repo), Section 9, item P0-5.

## Affected artifact

verify.mjs (evidence producer), guard-push.mjs, critic-packet-preflight.mjs,
documentation.

## Proposal

Introduce a shared export, VERIFY_EVIDENCE_DEFAULT_PATH, imported by the
producer, the push guard, the Critic preflight, and the documentation, so
all four consistently reference the same evidence path. The producer
should use this path by default; free/custom paths should only be
permitted for additional (supplementary) evidence, not as a substitute
for the default.

Acceptance test: invoking verify with no flag, using the default
settings, must produce exactly the file that the push guard consumes.

## Design proposal (Wave-4 prep), 2026-08-18

*Prep material for PO triage, not a decision — a Triage section, if/when added, records the actual PO decision. Generated by a Workflow-dispatched read-only design pass (dispatch NVA-W4-DESIGN-canonical-verify-evidence-path) grounded in the current repo state.*

**Problem (restated):** The backlog item (backlog/items/2026-08-18-canonical-verify-evidence-path.md) reports that a greenfield happy-path test of pipeline 0.6.0+codex build hit a producer/consumer path mismatch for verify evidence: 'verify.json vs verify-latest.json'. Reading the actual current source confirms a real, narrower version of this gap: this repo's own self-application script (harness/scripts/verify.mjs:112) hardcodes evidence/verify-latest.json and needs no flag. But the script that CONSUMER projects actually use, plugins/pipeline-core/scripts/verify-evidence-producer.mjs, takes a REQUIRED --out flag with NO default at all (line 172: `if (!value['--out']) fail('VEP-USAGE', ...)`) -- the caller must type the exact path themselves every time. Meanwhile the two real hardcoded consumers of the canonical path are plugins/pipeline-core/hooks/guard-push.mjs:1610 (`checkEvidenceFreshness('evidence/verify-latest.json')`, inside a large TP-3-protected file) and plugins/pipeline-core/scripts/push-prepare.mjs:307 (same literal string) -- each holding its own independent string literal, not a shared constant. The only place the correct value 'evidence/verify-latest.json' is currently communicated to a human/agent running the producer is a hand-typed comment string embedded in the manifest text project-onboarding-v3.mjs seeds for fresh consumers (lines 963-964, 999) -- documentation, not enforcement. IMPORTANT CORRECTION to the item's own 'Affected artifact' list: plugins/pipeline-core/scripts/critic-packet-preflight.mjs, read in full, contains NO hardcoded verify-evidence path at all -- it only declares a generic REFERENCE_KINDS set including the string 'evidence' and accepts caller-supplied evidence references. The real second hardcoded consumer that should be in scope instead is push-prepare.mjs, which the item's proposal omits entirely. Any dispatch built from the item's literal Proposal text as-is would target one file (critic-packet-preflight.mjs) that has nothing to fix and would miss one file (push-prepare.mjs) that does.

**Options:**

1. **A. Item's own proposal as written: shared VERIFY_EVIDENCE_DEFAULT_PATH export + restrict custom --out to supplementary-only** — Add a shared exported constant (new small lib module, e.g. lib/verify-evidence-path.mjs), import it in verify-evidence-producer.mjs (as the default when --out is omitted), guard-push.mjs, push-prepare.mjs, and the project-onboarding-v3.mjs seeded manifest text. Additionally change verify-evidence-producer.mjs semantics so a caller-supplied --out that differs from the default is only accepted as ADDITIONAL/supplementary evidence (e.g. for critic-dispatch-preflight's generic --evidence list), never as a substitute that guard-push/push-prepare will ever look at. Impact: Closes the failure class completely and by construction: a bare `verify-evidence-producer.mjs` invocation with no --out (or the seeded onboarding command) always produces exactly what guard-push and push-prepare read; a consumer can no longer accidentally SUBSTITUTE a differently-named file for the canonical one and have it silently ignored by the push gate. Tradeoffs: Requires touching guard-push.mjs, a large (1800+ line), TP-3-protected, self-application-critical file -- per this repo's own guardrail history this carries real process cost (careful review, possibly an HGO ceremony for the protected region, corresponding guard-push.test.mjs updates). It also invents a new 'supplementary vs substitute' policy distinction that has no existing home in the schema or in critic-dispatch-preflight.mjs's generic --evidence contract -- that distinction needs its own short design decision (what does a 'supplementary' evidence file actually unlock downstream?) rather than being silently bundled into what looks like a pure refactor. Larger surface than strictly needed to satisfy the item's own acceptance test.
2. **B. Minimal fix: default --out to the canonical constant, leave override freedom as-is** — Add the same small shared constant, but only change verify-evidence-producer.mjs so --out defaults to it when omitted (no new restriction on supplying a different --out). Update guard-push.mjs and push-prepare.mjs to import the constant instead of their independent literal strings, purely as a drift-prevention refactor, with no behavior change to those two files. Impact: Directly satisfies the item's own stated acceptance test ('invoking verify with no flag ... must produce exactly the file the push guard consumes') -- a default/no-flag invocation of the producer is now provably correct. Eliminates the two-literal duplication that let the two hardcoded consumers silently diverge from each other in the future, at near-zero behavioral risk since guard-push.mjs's own logic is untouched, only the string source. Tradeoffs: Does not stop a consumer (human or agent) from still hand-typing a wrong custom --out path and being just as silently unread by guard-push as today -- it only fixes the DEFAULT-path case, which is exactly the failure mode the greenfield report actually hit, but leaves the broader 'free path' risk open. Smaller footprint: one new tiny constant file, one default-parameter change, two import swaps, plus their existing test suites (verify-evidence-producer.test.mjs, guard-push.test.mjs, push-prepare.test.mjs) updated to assert against the shared constant instead of a repeated literal.
3. **C. Defer / documentation-only: rely on the already-seeded onboarding comment** — Treat this as already substantially mitigated: project-onboarding-v3.mjs already seeds the exact correct command (`verify-evidence-producer.mjs --out evidence/verify-latest.json`) into every fresh consumer project's manifest comments (lines 963-964, 999). Do not touch code this wave; ask the reporting session for the exact command it actually ran before committing to a code fix, and re-triage next wave with that evidence. Impact: Zero engineering cost this wave. Preserves the status quo where the SEEDED path is already correct for anyone who follows the onboarding-generated manifest text verbatim. Tradeoffs: Weak given what was actually found: the report is P0-priority from a live greenfield run on today's date (0.6.0+codex.20260818...), the seeded comment is documentation with zero code enforcement, and this repo's own CLAUDE.md explicitly distrusts 'the doc already covers it' as a substitute for a mechanical guarantee. Also does not resolve the concrete duplication risk already found live in the code (two independent literal strings in guard-push.mjs and push-prepare.mjs) which is a defect regardless of the onboarding-comment mitigation. Only defensible as a deliberate 'gather more evidence first' half-step, not as a final resolution.

**Recommendation:** Hybrid of B, explicitly scoped down from A: ship the minimal safe-default fix (one shared constant, verify-evidence-producer.mjs defaults --out to it, guard-push.mjs and push-prepare.mjs import the same constant instead of their independent literals) THIS wave -- it is small, satisfies the item's own acceptance test exactly, and removes the live literal-duplication risk I found in the actual code. Defer option A's 'restrict custom --out to supplementary-only' semantics to a follow-on item rather than bundling it here -- that is a real policy question (what a 'supplementary' evidence file means for critic-dispatch-preflight's generic --evidence contract) that deserves its own short design pass, not a silent scope-add onto what should be a narrow, low-risk fix touching a TP-3-protected file. Before dispatching: correct the item's 'Affected artifact' list -- drop critic-packet-preflight.mjs (verified to hold no hardcoded evidence path at all) and add plugins/pipeline-core/scripts/push-prepare.mjs (verified to hold its own independent 'evidence/verify-latest.json' literal at line 307, the item's proposal currently misses this file entirely).

**Risks/dependencies:** 1) guard-push.mjs is a large, TP-3-protected, self-application-critical file (per CLAUDE.md's guard-testpath discipline) -- even a pure literal-to-constant swap there should go through the same careful-edit discipline this repo already applies to that file, and its own test suite (guard-push.test.mjs) must be updated in the same commit. 2) The item's 'Affected artifact' list is inaccurate as written (see problemRestated) -- re-verify the corrected file list before building any dispatch briefing from it, per this session's own re-verify-before-dispatch discipline. 3) I could not confirm from this repo alone whether the reporting greenfield session (external repo Rune_Test1_Codex_060_52, out of this checkout's read/write scope) actually ran the onboarding-seeded correct command and still hit a mismatch, or ran something else -- worth a quick clarifying read of that repo's handover doc (read-only, it is an external project repo) before finalizing scope, since it would confirm whether the seeded-comment mitigation (already in project-onboarding-v3.mjs) was bypassed or was simply not present yet in the build under test. 4) No blocking dependency found on other open backlog items from the recent git log (item-hash-rescope-amendment, managed-onboarding-success-contract, guard-devplan/guard-testpath no-bash-write-lane item) -- these look unrelated to verify-evidence pathing.
