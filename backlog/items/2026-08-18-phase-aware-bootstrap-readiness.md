# Phase-aware bootstrap readiness check for pre-implementation verify

## Description

The greenfield design requires verify availability even though verify is
only permitted to be configured in the implementation phase. This creates
a false requirement during earlier phases, where no verify contract can
legitimately exist yet.

## Triggering situation

From a greenfield happy-path test report (pipeline version
0.6.0+codex.20260818162535.96cf805, test repo Rune_Test1_Codex_060_52),
full report at docs/pipeline-greenfield-happy-path-handover.md in that
test repo. Section 9, item P1-1.

## Affected artifact

bootstrap readiness check, pipeline-start-preflight.mjs.

## Proposal

Before the implementation phase, bootstrap should accept an explicit
status of verify-pending-initial-scaffold. This state is honest but
non-blocking. At the atomic phase transition into implementation, real
calibration becomes mandatory.

Acceptance test: an empty project reaches design-ready status without a
fake verify and without a guard denial; before the first implementation
commit, a real verify contract must exist.

## Design proposal (Wave-4 prep), 2026-08-18

*Prep material for PO triage, not a decision — a Triage section, if/when added, records the actual PO decision. Generated by a Workflow-dispatched read-only design pass (dispatch NVA-W4-DESIGN-phase-aware-bootstrap-readiness) grounded in the current repo state.*

**Problem (restated):** The greenfield/consumer-project bootstrap protocol (harness/session-bootstrap.md Step 5, 'Project gates available?', lines 202-206) unconditionally demands that the project's verify script 'exists and is basically runnable' before any write work, and on failure 'treat like F4 (STOP for write work...)'. This fires even in a genuinely pre-implementation project (design/PRD-only, no code yet), where no legitimate verify contract can exist. The item's own acceptance test wants an empty project to reach a 'design-ready' status without a fake verify and without a guard denial, while a real verify contract becomes mandatory only at the atomic transition into the implementation phase.

**Options:**

1. **Item's own proposal: new 'verify-pending-initial-scaffold' calibration status** — Add a new, explicit, honest calibration/bootstrap status (verify-pending-initial-scaffold) that Step 5 accepts as non-blocking before implementation. Wire the atomic mandatory-verify check into the ALREADY-EXISTING implementation-phase transition: pipeline-state.mjs's `set-phase --phase implementation` subcommand, which calls `enterPlanImplementation()` in plugins/pipeline-core/lib/plan-spec-state-v2.mjs:657-671. I read that function in full: today it checks only `lifecycle.status === 'approved'` and `activeFeature.phase === 'design'` -- it performs NO verify-script check at all, so this is a clean, currently-empty hook point to add one. Impact: Bootstrap Step 5 gains a third outcome (today it only has 'verify OK' vs 'missing -> F4 STOP'). A greenfield session can write specs/PRDs during design phase without a fake verify script or a STOP. The real enforcement moves to a single, already-atomic, already-guarded state transition (set-phase implementation), so 'no fake verify before, mandatory real verify at the transition' becomes a code-level guarantee, not just documented discipline. Tradeoffs: Touches three layers: (1) calibration/status vocabulary (new value, needs a home -- operating-model.md's calibration field sketch it references at 'docs/operating-model.md §8' is itself stale, that section is 'Operating shapes', not a field sketch, so this change would also need to fix or relocate that pointer), (2) harness/session-bootstrap.md Step 5 + the mandatory confirmation-line format (Step 6, lines 214-229) which would need a new defined addition, (3) plan-spec-state-v2.mjs's enterPlanImplementation, which is itself protected/tested state-machine code (pipeline-state.test.mjs), so any change there needs its own test coverage and possibly a signed maintenance-window edit given this repo's TP-class protections on Pipeline plugin source. Medium-sized, multi-file, touches a tested state machine.
2. **Minimal fix: reuse the existing activeFeature.phase field instead of inventing a new status** — pipeline-state.mjs already tracks activeFeature.phase in {'design','implementation'} (see e.g. pipeline-state.mjs lines 4900-4936, 4108-4243). Instead of a new calibration status, make Step 5's STOP conditional on that existing field: no active feature yet, or phase === 'design' -> missing verify is expected and non-blocking (log it, don't STOP); phase === 'implementation' -> missing/uncallable verify remains a hard STOP exactly as today. No new schema value, no new confirmation-line variant beyond reusing the phase already being read. Impact: Same practical outcome for the acceptance test (empty/design-phase project writes proceed without a fake verify or a denial) but with a much smaller footprint: Step 5's text changes, and the enforcement point is the read of an already-existing field rather than a new one. A project that never calls set-feature (truly no lifecycle tracking) needs an explicit default -- treating 'no activeFeature' as equivalent to 'design/pre-implementation' is the natural default but must be stated, not left implicit, or it quietly disables the check forever for projects that skip the feature lifecycle machinery. Tradeoffs: Cheaper and lower-risk than option A because it adds a read, not a new write/status. But it doesn't independently strengthen the implementation-phase gate the way A's explicit hook into enterPlanImplementation does -- that half of the fix (a real, mandatory, atomically-enforced verify check at the design->implementation transition) is still worth doing on its own merits even under this option, since enterPlanImplementation currently checks nothing about verify at all regardless of which option is chosen.
3. **Reject/defer: downgrade Step 5 to advisory-only, no phase logic** — Simplest possible change: turn Step 5's STOP into a warning-only note in all cases (drop the 'treat like F4' STOP entirely), relying on human/Elephant judgment and the existing F4 read-only fallback for a truly missing calibration file. No phase tracking, no new status. Impact: Immediately unblocks the greenfield case with a one-line doc edit to session-bootstrap.md. But it also removes the STOP for projects genuinely past the design phase with a broken verify script -- exactly the failure mode Step 5 was written to catch ('without a runnable verify, the evidence duty can't be fulfilled... this should surface at session start, not at task end', session-bootstrap.md line 205). Tradeoffs: Cheapest option but reintroduces a known problem for mid-lifecycle projects rather than solving the actual pre-implementation/post-implementation distinction. Only defensible as a stopgap, or folded into option B by scoping the downgrade specifically to the pre-implementation case (which is what B already does more precisely).

**Recommendation:** Recommend a hybrid built mostly from Option B with Option A's enforcement half: (1) reuse the EXISTING activeFeature.phase field (no active feature, or phase='design' -> missing verify is expected/non-blocking; phase='implementation' -> unchanged hard STOP) rather than inventing a new calibration status -- this is the minimal change that satisfies the acceptance test and needs no new schema vocabulary or confirmation-line variant; AND (2) separately, and regardless of (1), add an actual verify-existence/callability check into enterPlanImplementation() (plan-spec-state-v2.mjs:657) so the design->implementation transition -- which is already the one atomic, state-machine-enforced moment in this codebase -- becomes the place a real verify contract is mechanically required, not just documented as a bootstrap-protocol step nobody enforces today. Also correct the item's 'Affected artifact' line before assigning work: pipeline-start-preflight.mjs (the file actually named) only resolves plugin-distribution identity/version (SCHEMA pipeline.start-preflight.v1) and contains zero verify-contract or phase logic -- I read it in full. The real affected artifacts are harness/session-bootstrap.md Step 5 (lines 202-206) and, for the enforcement half, plugins/pipeline-core/lib/plan-spec-state-v2.mjs's enterPlanImplementation plus pipeline-state.mjs's set-phase subcommand (lines 4900-4936).

**Risks/dependencies:** 1) Sequencing with backlog/items/2026-08-18-fresh-repo-onboarding-intake-first-transaction.md (id pipeline.fresh-repo-onboarding-intake-first-transaction): same source report (Rune P0-0, higher priority than this item's P1-1), and its proposal introduces its own 'design-ready'-shaped checkpoint/authority-binding transaction for fresh repos.
