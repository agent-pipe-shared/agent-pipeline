# Push preflight checks are missing before signature (remote, threat model, verify path)

## Description

The remote, threat model, and verify path were only corrected after or
between signatures, rather than being validated beforehand. There is no
atomic preflight step that verifies all push-relevant preconditions
before the subject digest is generated and the signature command is
offered.

## Triggering situation

From a greenfield happy-path test run of pipeline version
0.6.0+codex.20260818162535.96cf805 in test repo Rune_Test1_Codex_060_52;
full report at docs/pipeline-greenfield-happy-path-handover.md in that
test repo, Section 9, item P0-4.

## Affected artifact

push approval flow; plan-push coordinator (new); guard-push.mjs.

## Proposal

Introduce a plan-push coordinator that, before generating the subject
digest, atomically checks: a clean and unchanged HEAD; a safe, existing
remote name; remote URL and auth readback; target-ref shape and branch
non-existence; a versioned threat model; canonical candidate-bound verify
evidence; and a valid trust anchor with external key-directory binding.
Only a fully green plan may render the signature command.

Acceptance test: a new feature branch is published with exactly one
signature and one push attempt; a URL given instead of a remote name, or
an incorrect evidence path, is rejected before the passphrase prompt.

## Triage (filled in by the Elephant of the next Pipeline session)

- **Decision:** Accepted — minimal preflight extension of `prepare-push-subject` (trust-anchor + evidence-freshness + clean-tree checks), PLUS (per the PO's `phase-aware-bootstrap-readiness` decision, same session) a verify-contract-existence check as the actual hard gate for a missing/broken verify script. Network-dependent remote/branch-existence checks split into a separate follow-up item pending a PO decision on branch-non-existence semantics.
- **Rationale:** PO 2026-08-18 accepted the analyst's minimal-preflight recommendation, and separately decided (via `phase-aware-bootstrap-readiness`) that THIS is where the verify-existence hard block belongs, rather than at the design→implementation transition.
- **Assignment (if accepted):** Nova Wave 4 implementation. Also share the trust-anchor detection helper with `po-key-trust-anchor-onboarding` rather than duplicating it (see that item's Triage).
- **Date:** 2026-08-18


## Design proposal (Wave-4 prep), 2026-08-18

*Prep material for PO triage, not a decision — a Triage section, if/when added, records the actual PO decision. Generated by a Workflow-dispatched read-only design pass (dispatch NVA-W4-DESIGN-full-push-preflight-before-signature) grounded in the current repo state.*

**Problem (restated):** Backlog item backlog/items/2026-08-18-full-push-preflight-before-signature.md (P0-4 from the Rune greenfield happy-path report) says push-relevant preconditions -- remote, threat model, verify path -- are only discovered wrong AFTER or BETWEEN signatures, not validated atomically BEFORE the subject digest is generated and the signature command is offered. I read the item in full and the two files it names under Affected artifact plus the flow doc it implies. Grounding: `guard-push.mjs` (plugins/pipeline-core/hooks/guard-push.mjs, ~1800 lines) is real and does exactly what the item implies -- it checks evidence freshness, security completeness, and forCommit/remote/destination approval binding, but ONLY at actual `git push` time (Layer 5), i.e. strictly after the human has already signed (Layer 2+3). A 'plan-push coordinator' does NOT exist anywhere in the repo (confirmed by find) -- it is genuinely proposed-new, not misnamed. docs/push-release-flow.md corroborates the item's complaint end to end: it documents 6 layers, states 'Verify has to run *before* the approval' as a prose-only 'Ordering rule...interim workflow measure', and separately documents that the external-signing-directory trust-anchor comparison ('Finding the right external directory... A mismatch fails closed with CRITICAL-PROOF-TRUST-ANCHOR-MISMATCH') is a MANUAL human step today. I traced CRITICAL-PROOF-TRUST-ANCHOR-MISMATCH into pipeline-state.mjs (verifyCriticalHumanProof, ~lines 2779-2787): that check exists in code, but is only invoked inside `approve-push` (Layer 4, run by the agent AFTER the human has already signed at Layer 3) -- so a wrong external key directory is only caught after the private key/passphrase ceremony has already been spent, exactly the waste the item describes. I also found a partial, already-shipped precursor: `pipeline-state.mjs prepare-push-subject` (~lines 5528-5585) is a READ-ONLY subcommand that already computes --subject-sha256 from the SAME inputs approve-push later verifies, and it already validates remote-name shape (regex `^[A-Za-z0-9._-]{1,80}$`, which would already reject a URL like `https://...` or `git@host:owner/repo.git` -- so the item's own acceptance-test clause 'a URL given instead of a remote name... is rejected before the passphrase prompt' is ALREADY satisfied by existing code, independent of any new coordinator), destination-ref shape, candidate resolvability, and threat-model artifact existence+hash. What it does NOT check: working-tree cleanliness/HEAD drift, verify-evidence freshness, remote existence/reachability/auth, destination-branch non-existence on the remote, or the external signing-directory trust-anchor binding -- all real, current gaps matching the item's Proposal. I also found a directly analogous, already-fixed bug in a sibling ceremony: backlog/items/2026-08-08-a-maintenance-window-signature-is-voided-by-an-unrelated-file-write.md (closed) hit the exact 'signature spent, then discovered useless' failure for Guard Maintenance Window, fixed via an IDEMPOTENT re-prepare (same signed digest survives a benign intervening write/commit within scope) rather than only a preflight gate -- the push/authorize-critical ceremony has no equivalent idempotency today (grepped po-human-approval.mjs: no reusable-prepared-request logic exists there, unlike GMW's `reusablePreparedRequest()`), so it remains MORE exposed to wasted-signature drift than GMW now is.

**Options:**

1. **Full atomic plan-push coordinator (the item's own Proposal)** — Build the new subcommand the item describes: before rendering the authorize-critical command, atomically check (1) clean/unchanged working tree and HEAD, (2) remote exists + URL/auth readback (e.g. a timeout-bounded `git ls-remote`, mirroring the 7s BatchMode SSH check guard-push.mjs already uses for anonymous-public-push calibration), (3) destination-ref shape and branch non-existence via that same ls-remote call, (4) threat-model artifact (reuse resolvePushThreatModelArtifact, already exists), (5) canonical candidate-bound verify evidence (extract guard-push.mjs's existing evidence-freshness check (a) into a shared lib function both this coordinator and guard-push.mjs call, so the two never drift), (6) trust-anchor binding against --directory (reuse the exact comparison verifyCriticalHumanProof already does at pipeline-state.mjs ~2783-2787, just invoked pre-signature instead of only at approve-push). Only an all-green plan prints the ready-to-copy authorize-critical command; any red finding blocks it and reports every reason together (matching guard-push.mjs's own 'collect all failures, report together' doctrine). Impact: Closes the full failure class the item names: a bad remote, stale evidence, wrong external key directory, or a not-yet-committed threat model can no longer reach the human passphrase prompt at all. Extends the existing prepare-push-subject/authorize-critical pattern rather than replacing it, so it fits ADR-0061's one-command shape for the human side. Tradeoffs: Largest option: new network-dependent checks (git ls-remote / SSH) inside what has been a purely local, deterministic gate so far -- needs careful offline/timeout/auth-failure handling to avoid becoming its own new failure mode (a flaky network now blocks a signature it previously would have allowed). 'Branch non-existence' is ambiguous as literally stated: enforced as a blanket precondition it would wrongly refuse the ordinary case of a SECOND push to a feature branch already pushed once this sprint -- the item's own acceptance test only exercises the first-push-of-a-new-branch case, so this needs an explicit scoping decision before implementation, not just an implementation. Does not by itself add GMW-style idempotent re-prepare, so a benign unrelated commit landing between a green plan and the actual signature can still void the signature (the same class of bug 2026-08-08's now-closed GMW item hit and fixed differently).
2. **Minimal preflight: extend prepare-push-subject with the cheap, non-network checks** — Instead of a new coordinator concept, harden the ALREADY-SHIPPED prepare-push-subject in place: add working-tree-clean + HEAD-matches-candidate, verify-evidence freshness (reusing the same check guard-push.mjs already implements, factored into one shared helper), and trust-anchor binding against --directory (reusing the exact comparison already in verifyCriticalHumanProof, just called earlier). Explicitly defer the network-dependent remote-existence/auth-readback and branch-non-existence checks to a follow-up item once their semantics (does 'branch non-existence' apply only to first-ever pushes of a branch?) are decided. Update push-release-flow.md's prose 'Ordering rule' section to point at running this hardened command as the literal first step of Layer 2, replacing prose-only guidance with a real gate for the two costliest failure modes. Impact: Closes the highest-cost gap (a wrong external signing directory, which burns the actual private-key/passphrase ceremony -- the single most expensive mistake in this flow per the doc's own description of Layer 3) and the most commonly-hit one (stale verify evidence) without touching network/DNS/SSH inside a gate. Reuses three functions that already exist for this exact purpose rather than inventing new mechanics, so the diff stays small and low-risk in a security-tier code path. Tradeoffs: Does not fully satisfy the item's literal acceptance test's second clause fully (it DOES cover the incorrect-evidence-path case, but not the remote/branch half of the Proposal), so the item cannot be marked fully closed against its own stated Proposal without a follow-up. Two ceremony failure classes (bad remote, branch already exists) remain discoverable only at actual git-push time, same as today, just for a narrower set of mistakes than before this change.
3. **Defer: turn the doc's existing 'Ordering rule' prose into an explicit checklist, no new code** — Ship nothing mechanical this wave. Convert push-release-flow.md's already-existing but purely advisory ordering-rule paragraph into a numbered, copy-paste preflight checklist (run prepare-push-subject; cat evidence/verify-latest.json and eyeball commit+exitCode; git ls-remote <remote> <destination>; sha256sum the external directory's po-public.pem against project/critical-human-proof.json's trustAnchor) that the agent is instructed to run and paste output of before constructing authorize-critical. Impact: Ships immediately, zero implementation risk, no new attack surface in a security-tier script. Tradeoffs: Not fail-closed -- relies on session discipline exactly like the doc's current 'Ordering rule...interim workflow measure' language already does, and that class of prose-only rule has already failed once at real cost in this exact repo: CLAUDE.md's own hard-rule entry on tree mutation during an outstanding HEAD-bound PO command was added specifically because a prose expectation was violated live and burned a passphrase entry. A defer here is likely to be revisited rather than genuinely closed, and does not touch the trust-anchor gap, which is the costliest one found during this analysis.

**Recommendation:** Option 2 (the minimal/incremental preflight), not Option 1 as literally proposed, and not Option 3. Extend prepare-push-subject now with the three checks that are cheap, deterministic, reuse code that already exists for this exact purpose, and close the costliest failure mode found during this analysis (a wrong external signing directory silently burning the human's private-key ceremony, currently only caught by verifyCriticalHumanProof AFTER the signature is already produced) plus the most commonly hit one (stale verify evidence). Explicitly split off the remote-existence/auth-readback and branch-non-existence checks into a separate follow-up item rather than blocking this slice on them -- they are genuinely new capability (network calls inside a gate) with an unresolved semantics question (does 'branch non-existence' wrongly refuse a routine second push to an already-pushed feature branch?) that deserves its own triage rather than being decided implicitly inside this implementation. Note for the PO: the item's own acceptance-test clause about a URL-instead-of-remote-name being rejected is already true today (prepare-push-subject's existing remote regex rejects it), so accepting this item does not need to re-solve that part.

**Risks/dependencies:** 1) Scoping risk on 'branch non-existence': the item's Proposal states it as a flat precondition, but a literal reading breaks the ordinary case of pushing a second commit to a feature branch already on the remote -- needs a PO decision on intent (new-branch-only vs. every push) before any implementation of that specific check, in either option. 2) Adjacent, distinct gap found in the same area, not this item: backlog/items/2026-08-18-push-approval-general-mode-lane-does-not-bind-remote-or-destination.md -- guard-push.mjs's chat/standing-approved lane checks only forCommit, never remote/destination (this repo runs in signature mode so it isn't exposed, but a project on chat/standing-approved mode is). Worth triaging in the same Wave-4 pass since both are about push-binding correctness, but they are independent fixes in different files/lanes. 3) Residual drift-voids-signature risk even after this item ships: unlike Guard Maintenance Window (which got an idempotent-reuse fix in backlog/items/2026-08-08-a-maintenance-window-signature-is-voided-by-an-unrelated-file-write.md, closed 2026-08-18), the push/authorize-critical ceremony has no equivalent -- a benign unrelated commit landing between a green preflight and the actual signature still voids it under the documented 'ordering rule'. Worth flagging as a natural follow-up reusing the GMW fix pattern, not something either option here solves. 4) Several other 2026-08-18-dated items touch the same signature-ceremony surface (hgo-signature-ceremony-requires-more-human-steps..., pipeline-author-repair-signature-mode-never-actually-admits-the-edit) -- worth triaging as one batch given the shared blast radius (po-human-approval.mjs / pipeline-state.mjs critical-action code), to avoid three separate dispatches touching the same security-tier file in the same wave.
