## 1. Findings

### F-A · The "already refused" justification inverts the design's own execution order

- **Gap.** §7.3 (`specs/sprint-phoenix-epic/design/gmw-hgo-evidence-intake-into-the-human-ledger.md:772-777`) grounds the byte-identity set on: "`expiresAtEpochMs` is the signed `subject.expiresAtMs` itself — `min(signed, installedAtMs + MAX_WINDOW_TTL_MS)` cannot select the clock term at install, because `GMW-EXPIRY-TOO-FAR` (`guard-maintenance-window.mjs:443-445`) **already refused** every request whose signed bound exceeds `nowMs + MAX_WINDOW_TTL_MS` … The bound that actually bounds the lift is therefore still compared byte for byte, **and it is a signed value**." (§4's row at `:289` makes the same move, hedged with "in practice".) But `GMW-EXPIRY-TOO-FAR` lives inside `installGuardMaintenanceWindow`, which the same document calls only at §7.4 step (d) (`:876-883`), *after* the `requested`/`granted` appends at steps (b)/(c). AC-1 (`:1466-1468`) states the order normatively ("appends … **before the window record exists**"), and §7.4 step (e) (`:882-883`) exists precisely because install can throw *after* the appends. At the moment the ledger value is built and committed, that check has refused nothing.
- **Risk (minor).** For a PO-signed subject whose `expiresAtMs` exceeds install-time `nowMs + MAX_WINDOW_TTL_MS` — the exact case `plugins/pipeline-core/lib/guard-maintenance-window.mjs:424-445` was written to block, so not hypothetical inside this project's own threat surface — the committed `validity.expiresAtEpochMs` is the **clock** term `installedAtMs + MAX_WINDOW_TTL_MS`, not the signed bound, falsifying "it is a signed value". Two consequences: the portable ledger can carry a `granted` record whose bound is unsigned and clock-derived (later revoked via step (e)); and in that corner (b)'s byte-identity on `expiresAtEpochMs` can only match between two honest racers by millisecond coincidence, so the adoption branch is once again coincidence-decided — the defect class this delta removes everywhere else. Capability is **not** widened: `min()` can never exceed the signed bound, install throws, step (e) appends `revoked`, and no window arms. The defect is in the soundness of the justification, not in the mechanism.
- **Evidence.** Design `:772-777` and `:289` versus `:876-883`, `:1466-1468`, `:882-883`; `plugins/pipeline-core/lib/guard-maintenance-window.mjs:443-445` (the check, inside `installGuardMaintenanceWindow`, whose signature is at `:383`) and `:456` (`const installedAtMs = nowMs;`). Not caught by the gate that ran: `node harness/scripts/check-doc-contracts.mjs` validates links/anchors only.
- **Spec reference.** H-AC-04 ("validity" as a required binding dimension, `specs/sprint-phoenix-epic/acceptance.md:148-150`) — this sentence is the stated reason one half of `validity` may be treated as a signed constant inside the identity check; internal inconsistency with §7.4/AC-1/§8.1 of the same normative design.

No blocker or major finding.
