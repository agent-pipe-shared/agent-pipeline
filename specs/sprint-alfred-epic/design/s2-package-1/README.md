`verify.mjs`) are in an accepted registry and are NOT wrong. Anchors, all read this session:

- The checker builds its entry list from the three `verify.mjs` arrays (`check-verify-suite-registration.mjs:434-457`)
  AND from `harness/verify-suites.json` (`:459-485`); an UNREGISTERED finding fires only when a file is in neither
  (`:565-580`). Its header text says "registered in verify.mjs" (`:1-3`) but the code accepts both.

  with its `caseCompletion`, into `TEST_SUITES` (`harness/scripts/verify.mjs:910-927`).

  (`check-verify-suite-registration.mjs:468-473`); `verify.mjs` entries do not. `clone-hook-readiness-tests` is registered
  in the JSON (`harness/verify-suites.json:1303-1315`), which is why the two new `clone-hook-readiness` / hook-refresh
  suites have no related neighbour in `verify.mjs`; they were appended at the end of the array instead.
- Case-completion policy lives INLINE in the registration entry (`verify.mjs` entry, or the JSON entry,
  `check-verify-suite-registration.mjs:340-360`; `verify.mjs:926`). `harness/config/verify-case-completion.v1.json`
  is not where a policy is written: it is a separate disposition list (`required` / `legacy-process-only`) keyed by
  suite name + path (`check-verify-case-completion.mjs:15,477-511`; its entry for `clone-hook-readiness-tests` is
  `verify-case-completion.v1.json:179-181`). The checker only demands an inline policy for suites listed there as
  `required` (`:587`) and the `registerTestCaseCompletion` protocol in their source (`:598-600`). A suite not listed
