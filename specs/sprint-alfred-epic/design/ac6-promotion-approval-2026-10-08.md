## 2. Seams [D]

- Evaluator: `evaluatePromotionEvidence({ baseline, poApproval } = {})`, `interruption-receipts.mjs:511`. `baseline` is the exact bytes (string) of the tracked file, `poApproval` is `{ baselineSha256 }`, elapsed time is never an input (`:507-509`). Returns `unavailable` (non-string baseline, unparseable JSON, window/coverage not plain objects, window start/end not objects, empty coverage: `:512-519`), `report-only` (any coverage value `unknown` `:520`, a null window value `:521`, no matching approval `:523`) or `calibrated-pass` (`:523`).
- Matching rule: sha256 of the UTF-8 bytes of the baseline text (`:522`) must equal `poApproval.baselineSha256` by `===`, and `poApproval` need only be a plain object (`:523`). Nothing else is checked: no signature, no attribution, no mode, no window/scope binding. Consequence [C-inference from `:522-523`]: today any party that can build the object, an agent included, reaches `calibrated-pass`; the "approval" is a bare digest claim, weaker than ADR-0056 `chat` (which at least carries `--by` and a mode label). The existing pin `{ baselineSha256: digest }` -> `calibrated-pass` is `interruption-receipts.test.mjs:51-53`; the ruling-22 pins are `:71-88`.
- Baseline writer: `writeBaseline(root, aggregate, ports)` `report-interruptions.mjs:450-465`. Fields `window`, `coverage`, `registrySha256`, `limitations` (always `[]`: the aggregate has no `limitations` key, `:455`; AC6-F2), `generatedAt` (`new Date().toISOString()`, `:456`); no `scope` today. Path `<root>/telemetry/interruption-baseline.json` (`:458-459`); temp file then `renameSync` (`:460-463`); bytes `JSON.stringify(baseline, null, 2)` plus a trailing newline (`:462`), which is exactly what the digest covers. Called only from `main` when `--write-baseline` is set (`:489`). Aggregate source of `window`/`coverage`/`registrySha256`: `interruption-receipts.mjs:500-501`.
- Consequence of `generatedAt` inside the digested bytes [C-inference]: any rewrite of the baseline, even with identical measurements, changes the digest and voids a recorded approval. This is correct (an approval attaches to bytes) and must be stated to the PO.
- Platform [D]: the receipt store needs the Linux ext backend, so a Windows host records no receipts and can never produce a baseline (N9, `po-open-questions-2026-10-07-night.md:25`). The baseline is a tracked file (ruling 15 `:95`), so a Windows host can still read it. Untested risk [C]: `core.autocrlf` checkouts would turn the LF bytes into CRLF and change the digest; the reader must fail closed on that (case 17).
- Push approval route [D]: `gates.push_approval` in `pipeline.user.yaml`, `signature` default, `chat` alternative (ADR-0056 `docs/adr/0056-push-approval-mode.md:32-51`); every unreadable or unrecognised state resolves to `signature` (`:53-58`); `chat` keeps commit binding, attribution and a self-declaring mode label (`:60-70`) but "is an attribution record, not proof of a human" (`:72-80`). In `signature` mode the guard admits "not a record - a verified signature", rebuilt from what it observes and checked against committed trust anchors (`:132-141`); a mutable working-tree state file is deliberately not believed (`:143-151`); the anchor is read from the governing session, not from the target repository (`:189-198`). This repository's anchor set is empty, so the proof means "a well-formed Ed25519 key outside the repository signed", not a named identity (`:273-297`); "this guard family bounds agents, not humans" (`:299-306`).
- Flow [D]: the human part is one command, `po-human-approval.mjs authorize-critical`, which builds the request and signs that exact object in one invocation (`docs/push-release-flow.md:151-167`); consuming the proof into state, `pipeline-state.mjs approve-push --proof-request --proof-authority --proof`, is "ordinary agent work" (`:448-464`). Its `--destination` accepts only `refs/heads/*` (`:459-461`), so the push subject cannot be reused for a promotion; a new action kind is needed.
- Precedent for a fifth action kind [D]: ADR-0056 follow-up of 2026-08-11 gave `feature-package-reconcile` the same signature/chat shape under its OWN key `gates.reconcile_approval`, "not an overload of `gates.push_approval`", reading only the already-committed trust anchors and NOT adding a kind to `requiredKinds` (`docs/adr/0056-push-approval-mode.md:237-259`). Code: `GATE_APPROVAL_MODE_KEYS` and its comment "Extending this table is how a future action kind gets the identical fail-closed mode logic" (`plugins/pipeline-core/lib/critical-human-proof-policy.mjs:34-54`); the injected approval check and its default (`plugins/pipeline-core/scripts/pipeline-state.mjs:8398-8450`, `:8569-8590`, record under `featurePackageReconcileApproval.lastApproved` `:8664`).

## 3. The three options, evaluated [C]

Constraints used. K1 authentic: in `signature` mode an agent cannot manufacture the approval (ADR `:132-151`). K2 bound: to the exact baseline bytes, and visibly to window, coverage, scope and limitations. K3 fail closed: unreadable, unrecognised or absent never reaches `calibrated-pass` (ADR `:53-58`). K4 self-declaring: the record says what backed it (ADR `:68-70`). K5 Windows first-class: a host that cannot write a baseline reports `unavailable`, not an error. K6 small protected-surface growth. K7 acceptance 23 evidence column: a promotion check that reads the baseline exists, and an explicit PO approval is possible.

- A - signed promotion record (Ed25519, same route as the push approval): meets K1-K4 and K7. Cost: a new action kind and subject in the ceremony, a consume verb, a reader, an anchor check; the PO signs once per promotion decision, and again after any baseline rewrite.
- B - chat-mode attribution record governed by `gates.push_approval`: meets K2-K3/K7 only as attribution (K1 fails by ADR `:72-80`, accepted there for pushes). As briefed it fails a stated constraint: one action kind owns one key (ADR `:90-91` for the conflict rule, `:243-250` for the reconcile precedent), and here `gates.push_approval` is `signature`, so B collapses into A in this repository while a consumer project on `chat` for pushes would silently get chat-clearable calibration promotions. The mode shape is reusable, the key is not.
- C - no promotion path in 0.7.0 (report-only, `calibrated-pass` unreachable by design): meets K1-K6 trivially, but fails K7 unless the PO amends acceptance 23, whose evidence column asks for a promotion check that reads the baseline; and as long as the exported evaluator accepts a bare digest (`:523`) `calibrated-pass` is reachable by construction from any future caller. Even C therefore needs the reader (section 4, slice F3) reporting `report-only` with a typed reason.
- Recommendation [C]: A, in a slice order where C is the stopping point. The reader lands first and, with no record present, reports `report-only` with `APR-RECORD-MISSING`: that shipped state IS option C. If the signing slices do not pass Critic review before the candidate, ship C and document it (N12's own fallback, `po-open-questions-2026-10-07-night.md:28`). A is a superset of C, so no work is thrown away. B is not a separate path: a later `chat` variant is one table entry plus an own key `gates.promotion_approval` (ADR `:243-250`; table `critical-human-proof-policy.mjs:47-54`), explicitly out of 0.7.0 (open choice 3).

## 4. Contract for A [C]

Principle: rebuild, do not believe (ADR `:134-151`). The record file is a mutable working-tree file; authenticity comes from re-verifying the detached proof against a subject REBUILT from the baseline the reader actually loaded, on every read.

- Schema `pipeline.interruption-promotion-approval.v1`, file `telemetry/interruption-promotion-approval.json`, exact fields, no others (unknown keys -> `APR-RECORD-INVALID`):
  - `schema` (the string above);
  - `kind`: `"interruption-promotion"` (the ceremony action kind; cross-kind replay of a push proof is refused);
  - `mode`: `"signature"` (only value accepted in 0.7.0);
  - `by`: attribution name, as `approve-push --by`;
  - `approvedAt`: ISO-8601 UTC;
  - `subject`: `{ baselineSha256, registrySha256, window: { start, end }, coverage, scope, limitations }`, copied from the baseline for human-readable display at signing time (`scope`, `limitations` opaque JSON as the baseline stores them after AC6-F2); `baselineSha256` is sha256 over the exact baseline bytes (`interruption-receipts.mjs:522`);
  - `subjectSha256`: sha256 of the canonical JSON of `subject` (repo `canonical` helper, signature to confirm at slice start); this is the digest the key holder signs inside the ceremony request;
  - `proof`: the detached-proof material exactly as `approve-push` stores it for its route (request, authority reference, signature; shape read at slice start from `po-human-approval.mjs`).
- Location [C]: tracked beside the baseline, `telemetry/interruption-promotion-approval.json`; one file, latest decision, git history is the audit trail. Rejected: `.git/agent-pipeline/` private state (not reviewable, per clone, and this repository runs on two machines). A new protected path is NOT recommended and not needed: deleting, replacing or forging the record can only downgrade to `report-only` (fail closed), never promote, because the reader re-verifies the proof. Therefore no signed-package route is needed for the record path itself.
- Writers [C]:
  - Signing act: human-only, never agent-run. The existing `po-human-approval.mjs authorize-critical` ceremony (`push-release-flow.md:151-167`) with the new kind `interruption-promotion`; the signing key lives outside the repository.
  - `scripts/interruption-promotion.mjs subject --root <root>`: READ-ONLY. Loads the baseline, refuses an ineligible one (evaluator with a self-matching approval must give `calibrated-pass`, else `APR-BASELINE-NOT-ELIGIBLE` / `APR-SCOPE-FILTERED`), prints the subject and `subjectSha256` for the PO to sign. Nothing is written.
  - `scripts/interruption-promotion.mjs record --root <root> --by <name> --proof-request --proof-authority --proof`: the consume step, analogous to `approve-push` (`push-release-flow.md:448-464`). It verifies the proof against the rebuilt subject and only then writes the record atomically (temp + rename, as `report-interruptions.mjs:460-463`). It is agent-runnable like `approve-push`: it adds no authority, it only caches a human-made proof that the reader re-verifies. It never creates a proof, and a missing or invalid proof writes nothing. Alternative for the PO: require a human-run `record` too; this buys nothing under re-verification (open choice 2).
  - `report-interruptions.mjs --write-baseline` is unchanged by this note (AC6-F2 owns its fix) and never writes the record.
- Reader [C]: new `lib/interruption-promotion.mjs` exporting `checkInterruptionPromotion({ root, deps })`. Steps: (1) read `telemetry/interruption-baseline.json` as exact UTF-8 text (no re-serialisation); (2) read the record if present (regular file, size bound, no symlink); (3) read trust anchors from the governing session, not from `root` (ADR `:189-198`); (4) rebuild the subject from the baseline and compare to the record's `subject` and `subjectSha256`; (5) verify `proof` over the rebuilt `subjectSha256` and the kind; (6) only on success call `evaluatePromotionEvidence({ baseline, poApproval: { baselineSha256 } })`; otherwise call it with no approval so the evidence-quality verdict is still reported. Returns `{ status, code, baselineSha256, mode }`. The evaluator stays a pure predicate and is NOT edited (its pins stay valid); authentication lives in the reader, and a static test makes the reader its only production importer (case 15), closing the "bare digest" path structurally.
- Production caller [C]: `report-interruptions.mjs --promotion-status --root <root>` (read-only; the "promotion check that reads the baseline" of acceptance 23). Any future B1/D2 threshold consumer must call `checkInterruptionPromotion`, never the evaluator. Handling per result: `calibrated-pass` -> consumers may treat the threshold as calibrated, `mode` shown; `report-only` -> thresholds advisory only, the typed code is printed; `unavailable` -> no usable baseline (missing, invalid, or a host that cannot produce one), the code is printed. All three exit 0 as data; argument errors exit 2 as today (`report-interruptions.mjs:471-474`).
- Typed codes (prefix `APR-`), status in parentheses:
  - `APR-BASELINE-MISSING` (unavailable); `APR-BASELINE-INVALID` (unavailable);
  - `APR-BASELINE-NOT-ELIGIBLE` (report-only: coverage not exactly `receipts`/`followup` measured, null or inverted window, ruling 22); `APR-SCOPE-FILTERED` (report-only/refusal, ruling 23);
  - `APR-RECORD-MISSING` (report-only); `APR-RECORD-INVALID` (shape, schema, unknown keys, symlink, oversize);
  - `APR-MODE-UNSUPPORTED` (`chat` or any other mode); `APR-SUBJECT-MISMATCH` (baseline bytes, registry, window, coverage, scope or limitations differ from what was signed, including a CRLF-converted baseline);
  - `APR-PROOF-INVALID` (bad or foreign-key signature, wrong kind, malformed); `APR-ANCHOR-UNRESOLVED` (trust policy unreadable from the governing session); `APR-IO`.
- What is protected [flag]: (a) registering the new suite in `harness/verify-suites.json` is TP-13: a stop condition for a Goldfish, it rides the signed-package Verify-registration slice (`0.7-execution-order.md:102`); (b) the new ceremony kind in `po-human-approval.mjs` and any anchor handling are guardrail-class code: Critic path, and the MP-07 higher-capability route at `max` applies to slice F2; (c) `project/critical-human-proof.json` `requiredKinds` is NOT touched (reconcile precedent, ADR `:253-257`); the committed anchors are read only; (d) no new protected path for the record (see Location). `hooks.json` and guard files stay untouched. If the PO wants the record itself protected, that is a signed-package edit, not an agent edit.

## 5. Test list (fixture roots only: `mkdtemp` repo roots, in-test Ed25519 keypair, injected anchors and clock; no real key, home or ceremony touched)

Prerequisite: the AC6-T2 pins and the AC6-F2 fix (rulings 22/23) land first, because the baseline gains `scope` and `limitations` there and the subject copies them. Then: test-only dispatch (file `plugins/pipeline-core/lib/interruption-promotion.test.mjs`, red against a stub, cases 1-17); then fix slices.

1. missing baseline -> `unavailable`, `APR-BASELINE-MISSING`, nothing created.
2. invalid baseline (not JSON; JSON without plain window/coverage) -> `unavailable`, `APR-BASELINE-INVALID`.
3. eligible baseline, no record -> `report-only`, `APR-RECORD-MISSING` (this is option C's shipped state).
4. eligible baseline + valid signed record -> `calibrated-pass`, `mode: "signature"`, digest echoed (positive control).
5. baseline changed by one byte after signing (e.g. a rewritten `generatedAt`) -> `report-only`, `APR-SUBJECT-MISMATCH`.
6. table-driven: record `subject` differs from the loaded baseline in each of registry, window start, window end, coverage, scope, limitations -> `APR-SUBJECT-MISMATCH`, never `calibrated-pass`.
7. proof: key outside a non-empty anchor set -> `APR-PROOF-INVALID`; empty anchor set + well-formed key -> verified (ADR `:273-297` posture, stated in the test name); corrupted signature -> `APR-PROOF-INVALID`.
8. forged record written by hand: `mode: "chat"` or unknown mode -> `APR-MODE-UNSUPPORTED`; missing mode -> `APR-RECORD-INVALID`; a record with only `{ baselineSha256 }` -> `APR-RECORD-INVALID`.
9. record shape: wrong schema, extra keys, symlink, oversize, non-UTF-8 -> `APR-RECORD-INVALID`; none reaches `calibrated-pass`.
10. ruling 22 through the reader: valid signed record over an ineligible baseline (coverage `estimated`, extra or missing coverage key, null or inverted window) -> `report-only`, `APR-BASELINE-NOT-ELIGIBLE`.
11. `subject` verb: ineligible or scope-filtered baseline refused (`APR-BASELINE-NOT-ELIGIBLE` / `APR-SCOPE-FILTERED`); eligible prints the subject and `subjectSha256`; the tree is byte-identical afterwards (read-only).
12. `record` verb: valid proof -> record written atomically at the exact path, readable by the reader; invalid proof -> `APR-PROOF-INVALID`, nothing written, an existing record preserved; re-recording the same proof is idempotent; failure of the temp or rename step leaves no partial file (`APR-IO`).
13. anchor source: a nested fixture repository carrying its own anchor file does not satisfy the check; anchors come from the governing root only -> `APR-ANCHOR-UNRESOLVED` / `APR-PROOF-INVALID` (ADR `:189-198`).
14. cross-kind replay: a valid push proof presented as a promotion proof -> `APR-PROOF-INVALID`.
15. static: `evaluatePromotionEvidence` has exactly one production importer, the reader; the record path is written only by the `record` verb; the new modules contain no drive-letter, `.gemini` or `homedir` literal; `harness/scripts/check-consumer-safe-paths.test.mjs` passes.
16. CLI: `report-interruptions.mjs --promotion-status` prints the three statuses for fixtures of cases 1, 3, 4; exit 0; read-only; on a host with no baseline it is `unavailable` with `APR-BASELINE-MISSING`, not an error (N9).
17. line endings: a CRLF-converted copy of an otherwise approved baseline -> `APR-SUBJECT-MISMATCH` (fail closed, no crash); a fixture asserts the repository pins LF for `telemetry/interruption-baseline.json` (attribute rule, to confirm at slice start).

Fix slices after the test-only dispatch (red -> green; a fix dispatch never edits test rows, ruling 14 `0.7-execution-order.md:91-93`):

## 6. Open choices for the PO (non-blocking, recommendation first)

1. Option: A staged so that C is the stopping point (recommended) vs C now vs A in one piece.
2. Record verb: agent-runnable consume step like `approve-push` (recommended; the reader re-verifies) vs human-run `record`.
3. Mode: `signature` only in 0.7.0, `chat` later under its own `gates.promotion_approval` key (recommended; ADR `:243-250`) vs `chat` now vs overloading `gates.push_approval` (rejected).
4. Limitations: non-empty `limitations` allowed but copied into the signed subject so the PO signs knowingly (recommended; ruling 22 does not make them a gate) vs a non-empty list blocks promotion.
5. Rewriting the baseline after approval: allowed, voids the approval by digest (recommended; fails closed) vs `--write-baseline` refuses to overwrite an approved baseline.
6. Record shape over time: one latest record, history in git (recommended) vs an append-only list.
7. Contradictions: none found between the briefed context files and the Critic record. Unverified: whether the ruling 22/23 fixes (AC6-T2, AC6-F2) have landed; this note assumes they land before F1.
