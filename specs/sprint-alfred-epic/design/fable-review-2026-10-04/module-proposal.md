## Executive summary

1. The plugin has **two files that are the Pipeline**: `hooks/guard-lifecycle-ready.mjs` (7,057 lines, 18 distinguishable responsibilities, 3 non-test importers, imports 8 CLI scripts) and `scripts/pipeline-state.mjs` (12,377 lines, 36 responsibilities, a 2,382-line `run()` dispatcher, ~45 imports). Every R1–R5 workstream has to edit both; that is why every fix round produces follow-on defects (`confirmed` sizes; causal claim `hypothesis`, consistent with the 10 operator hotfixes clustering on these two files plus `lib/architecture-design.mjs` and the design-course coordinator).
2. Below them sit four more giants that no agent can hold in context: `lib/onboarding-continuity.mjs` (8,774), `lib/project-onboarding-v3.mjs` (7,467), `lib/human-guard-override.mjs` (4,871), `hooks/guard-push.mjs` (2,566); plus 14 modules between 1,000 and 2,600 lines (Section 1).
3. **Duplication is systemic, not incidental**: ≈190 local `sha256/digest/canonicalJson/canonical` definitions, ≈75 private `fsyncDirectory/writeAtomic/writeExclusive/publishExclusive` implementations with at least two different win32 error-tolerance lists, 12 independent lock implementations, ≈215 `exactKeys/isObject/readJson` validators, 4 copy-safe command renderers (Section 3, all `confirmed` by `rg` definition counts). The same name carries three different semantics (`digest` = hash | SHA-256 format check | namespaced hash), so consolidation must go by semantics, never by name.
4. **Dependency direction is inverted at the top**: the guard hook imports eight `scripts/*.mjs` CLI entry points (`guard-lifecycle-ready.mjs:44-56`), and a plugin script imports through the source-only harness shim (`scripts/phoenix-authority-revision.mjs:5` → `harness/scripts/pipeline-state.mjs`), which the current fitness model forbids (`pipeline-core.allowedDependencies: [schemas]`). No lib imports a hook (`confirmed` by import-edge probe) — the inversion is hooks→scripts and scripts→scripts, fixable by moving the imported exports into libs.
5. Recommended stage order (effort S/M/L; "IC" = coherent intermediate-candidate boundary):
   - **S1 (M, IC)** shared primitives behind facades (digest, fs-atomic, closed-shape, path-containment, lock) — serves R4 directly (K3-10/K3-13 live in those duplicates).
   - **S2 (L, class-high, IC)** split `guard-lifecycle-ready.mjs` into a ≤500-line hook facade + 10 `lib/guard/*` lane modules; the command catalogue (R1) and the read policy (R2) each become ONE small module with ONE contract.
   - **S3 (L, class-high, IC)** split `pipeline-state.mjs` into facade + store + continuity + verbs + PO-authority + feature-package + closed-evidence, with a `commands` table that R1's catalogue consumes (one source for emitted and admitted argv).
   - **S4 (M)** `human-guard-override.mjs` → ceremony modules (R3). **S5 (M)** `guard-push.mjs` → push-policy libs (R3). **S6 (L)** onboarding/continuity by lifecycle stage, folding the session-cleanup triplication (R5, recovery). **S7 (S–M)** legacy deletion batch. **S8 (S)** map/fitness re-cut into ≥8 governed modules (D2–D4).
6. Top consolidate/delete wins (estimated net lines removed): shared primitives CD-1…CD-5 ≈ 2,000; legacy branches inside the state writer CD-6 ≈ 400 (incl. a project-specific recovery bridge that expires on 2026-10-31 by its own constant); `--legacy-v1` design-course route CD-7 ≈ 1,000 (`hypothesis` size); session-cleanup triplication CD-10 ≈ 800 (`hypothesis`); renderers CD-11 ≈ 250. Confirmed-class total ≈ 3,000 lines; with hypothesis-class items up to ≈ 5,000.
7. Two live R2 defects were hit during this read-only dispatch and belong in R2's reproduction list (end of Section 3): an in-root `wc -l` with a glob operand, and one with a non-existent in-root path, are both refused as `GUARD-READ-SCOPE-OUTSIDE-ROOT` (spec §21.2: "No in-root target yields GUARD-READ-SCOPE-OUTSIDE-ROOT").

## 2. Split proposals (MP-n)

Design rules applied to every split (doctrine §2): one responsibility per module; the public contract is the list of exported functions with inputs/outputs; **hooks depend on `lib/`, `lib/` never on `hooks/` or `scripts/`, `scripts/` are thin argv facades over `lib/`**; the existing entry file stays as a facade so `hooks.json` (TP-4) and every documented command path are unchanged; existing behavioural suites keep running against the facade, new unit suites land per lane.
