# Claude latest-family contract research

## 1. Goal and decision
As of 2026-10-01, official Claude Code docs define family aliases as the latest/recommended model for a provider and say aliases update over time. This is useful automatic alias movement, but it is **not** a verifiable guarantee of the newest selectable model for a particular installed account. Provider type, Claude Code version, organization restrictions, allowlists, environment/settings overrides, and routing may affect selection. Thus AC06/07/11/13's strict installed-account “latest” contract remains unproven; do not qualify Claude family automation on alias documentation alone.

## 2. Primary documentation and scope
- [Claude Code model configuration](https://code.claude.com/docs/en/model-config): `opus`/`sonnet` are described as latest; documentation says aliases point to the recommended version for the provider and update over time. Its provider table currently lists Anthropic API Opus 5.5/Sonnet 5.5; Claude Platform on AWS Opus 5.5/Sonnet 4.6; Bedrock and Google Agent Platform Opus 5.5/Sonnet 4.5; Microsoft Foundry Opus 4.6/Sonnet 4.5. This is a docs snapshot/provider mapping, not account inventory or selectable-release ordering. It explicitly allows full IDs to pin a version.
- The same page documents allowlists/denials and says a restricted family alias may resolve to the newest version that organization permits. This can be older than the alias's usual provider target. Exact pins can also be blocked by managed policy.
- [Claude Code CLI reference](https://code.claude.com/docs/en/cli-usage): `--model` accepts alias or full name; `--effort` accepts low/medium/high/xhigh/max/ultracode, with availability depending on model. This establishes a request interface, not effective effort.
- [Effort documentation](https://platform.claude.com/docs/en/build-with-claude/effort): effort is supported only on named models and levels vary by model; it is a behavioral signal, not a strict token budget. The docs establish supported request settings, not a response field attesting effective effort.
- [Claude Code model configuration: checking the current model](https://code.claude.com/docs/en/model-config): for JSON/stream-json output, the startup warning is suppressed and docs direct readers to `modelUsage` in the result message for the actual model. The warning/check discussion also documents automatic model remapping and restrictions.
- [Agent SDK cost and usage](https://code.claude.com/docs/en/agent-sdk/cost-tracking): `modelUsage` is a result-message map from model names to per-model token/cost totals; it includes subagent work. It is a usage breakdown, not a model catalogue or latest guarantee. No effort field is documented.

## 3. Alias, version, and legacy-pin findings
The docs support this guarantee: at the documented Claude Code version, a family alias resolves according to provider defaults/recommended version, and alias targets may change across Claude Code releases. They do **not** define numeric family-version parsing/order or guarantee every available account release is discoverable. No numerical version grammar should be inferred from these aliases. The provider table above is the only concrete mapping reported here; it is not evidence that those versions are currently selectable under this host's account.

Explicit version selection is documented through a full model name (and the `ANTHROPIC_DEFAULT_OPUS_MODEL` / `ANTHROPIC_DEFAULT_SONNET_MODEL` variables). This is a legacy-version pin request, not proof the old ID remains selectable. Managed restrictions can block IDs; provider/account confirmation or a successful usage observation is still needed for local selectability. No separate API-key catalogue may stand in for the installed Claude Code account.

## 4. Effort and runtime evidence
Claude Code exposes requested effort via `--effort`; legal values depend on the model. The CLI docs do not document a result field for effective effort. Therefore producer evidence can bind the exact argv/requested effort and verify the returned concrete model ID, but cannot claim observed/effective effort from the current native contract. Unknown effective effort must stay unknown; effort support in public docs does not prove this exact account/runtime honored the request.

Official docs call `modelUsage` the actual model evidence to inspect when JSON warnings are suppressed, and describe its keys as model names used for per-model accounting. A successful isolated alias probe with exactly one key can establish a host-observed concrete model ID for that call. It says nothing about the newest selectable family version, catalogue completeness, or provider attestation. Multi-model usage, fallback, or subagents can produce multiple keys; do not collapse those to a unique launch identity. Cost-tracking docs describe aggregate usage (including subagents) rather than per-invocation identity. No stable native result schema/field for effective effort was found in the bounded official-documentation search.

## 5. Executable verification and unresolved contract
An executable producer can record trusted executable/version and provider context, exact alias/model and effort arguments, process result, and the returned `modelUsage` key(s); it can reject errors, missing/ambiguous IDs, unknown family/version classification, or postlaunch ID mismatch. Existing repository alias observation is explicitly one-call host evidence, “not provider-attested”; its own source inventory agrees that it has no observed effort or latest catalogue.

To qualify installed-account latest-family automation, the producer still needs either a complete authenticated installed-account catalogue with release/selectability/effort metadata, or an independently verified provider contract that binds the alias to the numerically newest selectable release for this exact provider/account scope and remains valid at launch. Official documentation provides neither contract. Concrete postlaunch ID comparison can validate what ran against a selected ID, but cannot by itself establish that selection was latest. Effective effort remains unavailable from the documented result contract. No live/native qualification was performed or claimed.
