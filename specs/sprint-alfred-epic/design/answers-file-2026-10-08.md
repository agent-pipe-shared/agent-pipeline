## 3. Contract [C] - answers to the three open questions, then the rest

**Q1 Digest algorithm and where recorded.** Recommended: SHA-256, lowercase hex, over the raw file bytes (BOM included), identical to `--text-file-sha256` and `--plan-sha256`. Flag `--answers-file-sha256 <64 hex>` is OPTIONAL and means "refuse unless the file's digest equals this"; mismatch refuses with a typed code. The computed `{sha256, byteLength}` is always echoed in the command output (`answersFile` object). Recording in the durable checkpoint is NOT recommended for v1: the answers themselves are already durable and content-addressed there, so the file digest would only add transport provenance and would need a checkpoint-schema change in the hot `lib/onboarding-continuity.mjs`. Optional later slice F8, decided after reading the `designQuestions` entry shape (only if an additive optional field is admitted). "With digest" in SPEC:1836 is satisfied by verification plus echo.

**Q2 Onboarding and design course, or design course only.** Recommended: design course only, i.e. exactly the two commands that carry `--answers-json` today (`intake-design-questions-apply`, `-replace`). SPEC says "wherever `--answers-json` is"; the grep shows that is these two. Onboarding consent has no answers payload; its multi-line material already uses `--text-file`. Rejected: adding the flag to `intake-consent-apply` (no value, widens the guard surface).

**Q3 Missing / unreadable / oversize / non-UTF-8 behaviour.** Recommended: reuse the reader, with an additive options object so existing callers keep their codes and cap bit-for-bit. For the answers route the codes carry their own prefix, never `INTAKE-CAPTURE-TEXT-FILE-*` (wrong flag name in the message):
- `INTAKE-ANSWERS-FILE-INVALID` (empty/NUL path, or NUL byte in the content: parity with published `rejectNul`), `-MISSING` (ENOENT; new, because the capture route folds it into unreadable), `-UNREADABLE` (not a regular file, symlink leaf, read error), `-OUTSIDE-ROOT`, `-TOO-LARGE`, `-INVALID-UTF8`, `-DIGEST-INVALID`, `-DIGEST-MISMATCH`.
- CLI level: `INTAKE-DESIGN-ANSWERS-AMBIGUOUS` (both `--answers-json` and `--answers-file`), `INTAKE-ANSWERS-FILE-DIGEST-WITHOUT-FILE`.
- Every refusal is a non-zero exit with the code in the JSON error and the checkpoint untouched. Malformed JSON stays the apply function's refusal exactly as for inline (do not add a second parser verdict).

**Path rules.** Repository-relative, resolved against `--root`, as `--text-file` (`scripts/project-onboarding-v3.mjs:118-133` comment). An absolute path is accepted only if it physically resolves inside the root (this falls out of `:24-30` for free); nothing machine-specific is recorded or echoed beyond the path as given. Symlink leaf refused (existing rule). Home for the file: `scratch/` (guard-devplan exempt prefix; agent-obligations section 3), written by the agent once, then passed by path. Size bound: 65,536 bytes, equal to the published `answersJson` `maxBytes` (`lib/project-onboarding-v3.mjs:2864`); 30,720 bytes (R5-3) passes with 2x margin. Implementation: additive `maxBytes` option on the reader (stat first, then read), default stays 1,000,000.

**Arguments and shapes.** For both commands: `requiredValueOneOf: ["--answers-json","--answers-file"]`, `optionalValue: ["--answers-file-sha256"]`, `required: ["--activate"]`, `requiredValue: ["--root"]`. Guard validators: `"--answers-file": nonEmptyTrimmedNotFlag`, `"--answers-file-sha256": isHexDigest`.

**Published action.** Keep `applyAction` and the `answersJson` input unchanged (consumers: `scripts/measure-fresh-repo-onboarding-turns.mjs:113-114`, `scripts/project-onboarding-e2e.test.mjs:1239,1311`). Add a sibling `fileApplyAction` (argv with a fixed scratch path constant, as `intakeCaptureAction` does at `lib/project-onboarding-v3.mjs:2743,2789-2807`) and put one sentence in the guidance: use the file route whenever the answers contain a newline or exceed a few KB.

**Guard admission - protection check.** `lib/guard/sanctioned-args-onboarding.mjs` is NOT in the TP table (TP-1..TP-13 per `templates/prompts/agent-obligations.md` section 2; none matches `lib/guard/`), so no signed package and no human override is needed. It is a guardrail surface all the same: that slice is class GUARDRAIL (MP-07 higher-capability route at `max`, critical Critic path T1). The working tree currently carries other uncommitted edits under `lib/guard/` (`evaluate.mjs`, `env-dump-lane.mjs`); `sanctioned-args-onboarding.mjs` itself was not dirty at dispatch, but re-check `git status` before the slice. Ordering matters: add the validators (F3) BEFORE the shape-table change (F2'), because a table flag without a validator may be admitted unvalidated or refused (unread, see section 2).

**Language asked once.** The value lives in one place, `checkpoint.values.language` (set by consent, projected by `onboarding-later-language.mjs`). Recommended mechanism, three parts: (a) the intake-path nextAction for `design-questions-pending`/`ready-to-generate` states the confirmed language in its guidance (builder `intakeDesignQuestionsAction(root, runner)` gets a `language` parameter read from the checkpoint; if the caller has no checkpoint access, the `v4Inspection` projection exposes `confirmedLanguage` and the builder reads that - decide after reading the builder's caller); (b) `kickoff-design.md:74-84` gains a precondition: "if a consent receipt/checkpoint already holds a language, use it and do not ask the operator-facing question"; (c) the hosted-project document-language question (`:86-99`) is a different question and stays (recommended; open question 1). "Asked once" is then testable as: after consent, no emitted intake-path action asks for the operator-facing language, and the docs say so.

1. Reader regression: default call keeps the 1,000,000 cap and the `INTAKE-CAPTURE-TEXT-FILE-*` codes unchanged (pin before F1).
2. `maxBytes: 65536`: a 30,720-byte file, and a 65,536-byte file, are accepted; 65,537 bytes -> `INTAKE-ANSWERS-FILE-TOO-LARGE` decided from `stat` before any read.
3. Windows shapes: UTF-8 BOM and CRLF variants of the same JSON both parse after decoding; `sha256` equals the digest of the raw bytes (BOM included); NO BOM in the returned text.
4. Non-UTF-8 bytes (lone `0xFF`) -> `-INVALID-UTF8`; NUL inside the content -> `-INVALID`; NUL in the path -> `-INVALID`.
5. Paths: missing -> `-MISSING`; directory -> `-UNREADABLE`; leaf symlink -> `-UNREADABLE` (skip with a recorded reason when the host refuses `symlinkSync`, as on unprivileged Windows); `..` escape, absolute outside the root, the root itself -> `-OUTSIDE-ROOT`; absolute inside the root -> accepted.
6. Digest: matching accepted; mismatch -> `-DIGEST-MISMATCH`; uppercase/short/non-hex -> `-DIGEST-INVALID`.
7. Error identity: each refusal is an `Error` whose `.code` equals its message (the reader's `refuse` shape, `:9-11`), so CLI output carries the code.
8. Parse/CLI: `--answers-file <p>` accepted for both commands; `--answers-file-sha256` without `--answers-file` -> `INTAKE-ANSWERS-FILE-DIGEST-WITHOUT-FILE`; `--answers-json` plus `--answers-file` -> `INTAKE-DESIGN-ANSWERS-AMBIGUOUS`; neither -> usage error; flag-shaped or empty value rejected; usage text (`:353` area) lists the new flags.
9. Shape closure: both design-question shapes carry the `requiredValueOneOf` pair and the optional digest; every flag named in any shape has an entry in the guard validator map (consistency test, so the table and the map cannot drift again).
10. R5-3 end-to-end: temp repo in `design-questions-pending`; a 30,720-byte pretty-printed, multi-line, non-ASCII answers file, in LF and CRLF variants, applied via `--answers-file` -> status `applied`, output echoes `{sha256, byteLength}`, the checkpoint equals what the same answers give inline; `-replace` follows the same rules as inline `-replace` (including "second round with different answers is refused", `intake-generate-design.md:54`).
11. Each Q3 refusal through the real CLI: non-zero exit, code in the JSON error, checkpoint bytes unchanged.
12. Published action: the `intake-design-questions-required` nextAction keeps `applyAction`, the `answersJson` input and `maxBytes` unchanged and ADDS `fileApplyAction`; update the pinned argv expectations (`lib/project-onboarding-v3.test.mjs:9214-9217,9395-9398`) additively. (The Windows argv limit cannot be reproduced portably; this case pins the routing instead.)
13. Guard (`hooks/guard-lifecycle-ready.test.mjs`): `intake-design-questions-apply --root R --answers-file scratch/a.json --activate` admitted with and without `--answers-file-sha256 <64 hex>`; refused: uppercase/short digest, flag-shaped value, duplicate flag, both `--answers-json` and `--answers-file`, `--answers-file-sha256` alone.
14. Language reuse: consent with `--language de` -> the following design-course nextAction states `de` (no `collect-input` asking for a language) and the generated PRD carries `<!-- po-language: de -->` (regression pin of `onboarding-continuity.mjs:6798`).
15. Asked once: for every intake-path state (`collecting`, `design-questions-pending`, `ready-to-generate`, `generated`) no emitted nextAction input asks for an operator-facing language once consent holds one.
16. Doc/emitter consistency (R5-1 style): `kickoff-design.md` contains the "recorded consent language is not re-asked" rule; `intake-generate-design.md:54` documents the file route with the same flag names the shape table emits.
17. Static: the new code has no drive-letter or home-directory literal; `harness/scripts/check-consumer-safe-paths.test.mjs` passes.
