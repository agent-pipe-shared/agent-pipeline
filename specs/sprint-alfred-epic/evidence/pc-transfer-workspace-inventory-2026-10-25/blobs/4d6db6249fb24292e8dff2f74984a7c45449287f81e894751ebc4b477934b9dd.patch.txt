+# Native-Windows counted results, 2026-10-22
+
+Engineering evidence from a measurement slice (ALF-K30). It is not an independent Critic review and not PO acceptance. No product
+code, test or pin was changed to produce it. Commit measured: `b02abaa78ef0e6ff41b0375c1d88e9ad12a60eba` (branch feat/sprint-alfred).
+
+## How it was measured
+
+- Native Windows: the WSL session reaches the Windows node (v24) through interop. A clone is made on the Windows drive with
+  `--no-hardlinks` (hardlinks fail across devices) and each suite is run ALONE as
+  `cmd.exe /c "cd /d <native Windows clone> && node --test <suite path with backslashes>"`, stdin closed, default Windows temp root.
+- Linux comparison: the same suite, `node --test <suite>` in a clone on the WSL filesystem, TMPDIR set to a private directory outside every git repository.
+- Counts are taken from the Node test runner summary (tests / pass / fail / cancelled / skipped / todo). Raw per-suite logs were kept outside the repository.
+- Per-suite time limit: 25 minutes on Windows, 15 minutes on Linux. A suite that hit the limit is recorded as TIMEOUT and is NOT a measured result.
+- Suites run strictly one at a time, but this machine was shared with other agents, and the suites that timed out on Windows left their
+  child node processes running (they could not be stopped from this session), so durations are upper bounds and later Windows runs may have been slowed.
+- The native Windows clone sits directly under a top-level directory on a non-system drive that was created from WSL. Its ancestor ACLs were not inspected or hardened.
+  Several failures below depend on ancestor or temp-root ACL assessments and may be an effect of that location (see classification).
+
+## Selection
+
+288 test files outside `specs/` mention `process.platform`, `win32`, a HOST-LIMITATION marker, "native Windows", or carry "windows" in the file name.
+They were ordered: backlog-named native-Windows pins and files with Windows in the name first, then files with a HOST-LIMITATION or "native Windows" marker,
+then the rest by number of win32 mentions; the guard-lifecycle-ready, worktree-lifecycle, passive-read-policy, human-guard-override, verify-journal and
+po-human-approval suites were deferred to the end because of their run time. The run was stopped on the tool budget, so only the head of that order was measured.

+## Summary
+
+- 77 of the 288 candidates were started; 74 have a result on both platforms. Never started: 211 (see "Not measured").
+- Native Windows: 17 suites red with 76 failing cases in total; 57 suites green; 3 TIMEOUT (guard-lifecycle-ready, onboarding-continuity, pre-commit-hook-install).
+- Linux (WSL2): every measured suite green (0 failing cases); 1 TIMEOUT (onboarding-continuity, 15 minutes, so slow on both platforms, not Windows-specific).
+- Several suites that exercise native-Windows behaviour pass with a typed skip on Linux (for example windows-authority-ancestors-above-repository-are-human-controlled: 8 skipped on Linux, 8 pass on Windows).
+- The reverse also occurs and deserves a look: some suites skip on Windows what Linux runs, for instance worktree-process-start (0 pass / 2 skipped on Windows, 2 pass on Linux),
+  design-workflow-package-v2 (2 skipped on Windows), sign-intent-bare-openssl-spawn-searches-the-working-directory-on-windows (3 of 4 skipped on Windows), security-scanner-diagnostics (15 of 24 skipped on Windows).
+- The guard-lifecycle-ready suite did not finish within 25 minutes on Windows, so the 60-failure figure of backlog item
+  `pipeline.guard-suite-fails-60-tests-on-native-windows` is still not re-measured at this commit. The Linux baseline for it is in
