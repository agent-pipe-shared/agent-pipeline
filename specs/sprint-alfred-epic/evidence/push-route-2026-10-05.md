## 1. What push-prepare requires for Verify evidence

- Source: `evidence/verify-latest.json` (`plugins/pipeline-core/lib/verify-evidence-path.mjs:22`), read from the
  PRIMARY worktree of the git common dir (`plugins/pipeline-core/scripts/push-prepare.mjs:454-457`, used at :605-607).
- It is NOT private state and NOT tracked: `/evidence/` is gitignored (`.gitignore:52`). It is a plain JSON
  file; no MAC, signature or private-receipt check at consumer side.
- Binding checked (`push-prepare.mjs:174-218`): file readable, `exitCode === 0` (:181), `commit === HEAD`
  (:182; otherwise only a valid release-promotion envelope can bridge, :183-212), and
  `verifyEvidenceSatisfiesBoundary(data,"push")` (:215).
- That predicate (`plugins/pipeline-core/lib/verify-selection.mjs:159-172`): selection hash self-consistent
  (:136-157), `selection.candidateCommit === evidence.commit`, `exitCode 0`; for push accepts
  `mode "release"` with full execution, or `mode "push"` with `unmatchedPaths` empty or a complete full fallback (:165-167).
- Clean tree is required of the candidate at production time: producer refuses/records dirty
  (`plugins/pipeline-core/scripts/verify-evidence-producer.mjs:142-146, 317-333`) and re-checks commit+tree after the run
  (:416-419). Tree and commit are written into evidence (:446-448). push-prepare itself also demands a clean
  tree (`push-prepare.mjs:98-107`). NOTE: the working tree currently has a modified tracked file
  (`plugins/pipeline-core/scripts/codex-isolated-critic-protected-preimage.v1.json`); it must be committed or reverted first.
- The push-time guard re-applies the same contract (`plugins/pipeline-core/hooks/guard-push.mjs:2060-2093`) plus, for an
  `impacted` run, that `selection.baseCommit` is a strict ancestor of the pushed commit (:2094-2102).
- Import/attest route: none exists as such, but nothing in the consumer-side checks (above) ties the file to the
  machine that produced it. Evidence generated by the producer in a separate native-Linux clone checked out at the
  SAME commit, with a clean tree, carries the identical `commit`/`tree`/`selection` and would pass both
  `push-prepare.mjs:174-218` and `guard-push.mjs:2060-2093` if copied to `evidence/verify-latest.json` of this checkout.
  This is an inference from the checks read, not a documented/supported route (no doc in `docs/push-release-flow.md:40-160`
  mentions it). It also bypasses the intent of "run against this checkout"; PO should decide whether that is acceptable.
- Producer command shape (`push-prepare.mjs:157-163`): `node <plugin-root>/scripts/verify-evidence-producer.mjs --root <repo> --mode push --base <verified-base> --out evidence/verify-latest.json`;
  a `--prepare` step first generates a consumer adapter that must be reviewed and committed (:160-162).
  Push mode also refuses if a blocking gate lacks its git-level backstop (`verify-evidence-producer.mjs:264-266`;
  pre-push hook is currently ABSENT per bootstrap preflight observation).
- Scope of push mode: impacted-selection (`verify-selection.mjs:80-134`): a subset when `--base` is a strict ancestor and
  every changed path is classified; full when base missing/invalid, paths unclassified, or suite unclassified. Default base
  is `HEAD^1` (`verify-evidence-producer.mjs:154`), which would give a narrow, honest-but-thin run for a docs-only tip; an
  honest push run for the whole branch needs `--base` = last pushed/verified ancestor, which likely falls back to full.
  Suite count: not determined (registry is `harness/verify-suites.json`, not read).

## 2. Constraints

- Journal directory is fixed at `<git-common-dir>/agent-pipeline/verify/runs/<runId>`
  (`plugins/pipeline-core/scripts/verify-journal.mjs:188-191, 347, 1087`), created with mode 0700 (:140) and then
  checked: on non-Windows `(mode & 0o077) !== 0` throws `VERIFY-JOURNAL-DIRECTORY-NOT-PRIVATE` (:133). No override,
  env var or alternate directory parameter exists (`gitCommonDir` is derived from the repo, `verify-evidence-producer.mjs:377, 474`).
  Hence a DrvFs `/mnt/<drive>` checkout cannot work; a clone on native ext4 inside WSL is the only Linux-side shape.
- On win32 the check is an ACL assessment instead (:130-132), so native Windows is not blocked by this, only by the host-stability rule (PO memory).

## 4. Ranked routes (signature push of the branch)

Matrix applicability: all routes are Claude-runner; WSL/Windows noted per route; own-repo only (consumer repos unaffected). Codex/Antigravity cells not evaluated.

1. **Linux-clone Verify, copy evidence (needs PO acceptance of the unsupported import).**
   Steps: (a) agent/PO: commit or revert the dirty tracked file so HEAD is final; (b) PO in WSL: `git clone` this repo's local path to
   native ext4 (e.g. under the WSL home), checkout candidate commit; (c) there run `verify-evidence-producer.mjs --mode push --base <last-pushed-ancestor> --out evidence/verify-latest.json` (plus `--prepare`/adapter commit first if demanded, which changes HEAD and requires redoing the clone at the final commit); (d) copy the file into this checkout's `evidence/`; (e) agent: `push-init.mjs ... --base --candidate` (read-only report); (f) PO attended terminal: printed `authorize-critical` (signature); (g) agent: `approve-push` then `git push`, commit nothing in between.
   Time: Verify wall time unknown (full run likely tens of minutes up to hours; not measured) + about 15 min ceremony. Risks: evidence copy is unattested; wrong HEAD after any further commit invalidates it; pre-push hook absent may trigger `VEP-UNBACKED_GATE` (`verify-evidence-producer.mjs:264-266`) so install via `pre-push-hook-install.mjs --install` first; security evidence may be needed too (:604-610); `.git/` of the clone is separate so receipts do not transfer (not needed).
2. **Run the producer in WSL against a native-ext4 CLONE, then push FROM the clone** (avoids the copy).
   Same as 1 but the whole ceremony (push-init, authorize-critical, approve-push, push) runs in the clone; needs the PO operator key/machine plane reachable from WSL (`push-prepare.mjs:317-333`) and pipeline state (active feature) present in the clone. Higher setup risk; cleaner provenance. Not verified feasible.
3. **Native Windows full Verify:** ruled out by the host-stability rule (PO memory), no code path blocks it.
4. **WSL on `/mnt/<drive>` checkout:** blocked at `verify-journal.mjs:133`, no override.
5. **None-fully-feasible-unattended tonight:** the signature ceremony is human-only (`docs/push-release-flow.md:80-88`); routes 1/2 are only feasible if the PO is present for steps (b) to (f). Verify duration is the unmeasured risk against the 06:30 target.
