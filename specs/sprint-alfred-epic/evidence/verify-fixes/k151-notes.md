## Why Option C cannot be delivered as briefed
1. No hook point inside codex-critic-host.mjs. The only host.mjs functions that run around the launch are `consumeNativeCriticPreparedContext` (before the reservation: baseline taken there would still miss the product's writes) and `recordNativeCriticPreparedExecution` / `captureNativeCriticPreparedReturn` (after the child has finished: a baseline taken there would hide any child write, i.e. the weakening the briefing forbids). The instant "after the product's reservations, before the child starts" lies inside `launchHeldCriticFamilyRoute` / `entry.launchModelFamilyInvocation` (session-route.mjs and lib/model-family-invocation.mjs, outside the briefed scope; the latter is kernel-adjacent). CCH136 calls `launchHeldCriticFamilyRoute` directly, CCH137 via `invokeCodexNativeCriticHost`; neither passes through a host.mjs seam between reservation and child start.
2. The baseline must survive to finalize in a different module instance. CCH136 (and CCH137) finalize with a context rebuilt by `createNativeCriticPreparedContextFactory().reconstruct()` from files on disk (`<prepared>.family-invocation`, `.family-consumed`, `.family-execution`). The in-memory `preparedFamilyContexts` entry of the launching module is not available there. A baseline value therefore has to be persisted. The existing custody (`pipeline.critic-family-native-custody.v1/v2`) is validated with `exactKeys`, so adding the value means a persisted-format change; only a brand-new sidecar file avoids touching an existing format, but it would still be a new persisted artifact written from code outside host.mjs. This is the briefing's stop condition (persisted receipt/return format).
3. Receipt semantics: `validateReceiptSemantics` (host.mjs ~1921-1922) requires `receipt.state.before` and `receipt.state.after` both to equal `prepared.bindings.protectedBefore`. With a post-reservation baseline the true `after` candidate hash differs from `protectedBefore`, so the receipt would either fail its own semantic check or have to record a value that is not the observed state. Fixing that needs a change to receipt content/semantics.
4. CCH137 contradicts the briefing. Test lines ~3299-3303 (pre-finalize assertion) compare the live candidate fingerprint with `prepared.bindings.protectedBefore` and `assert.fail` on any difference. `protectedBefore` is fixed at prepare (before the reservation) and "stays as it is" per the briefing, so CCH137 cannot go green without either editing that expectation (forbidden: "do not edit the CCH136/CCH137 expectations") or moving `protectedBefore` itself after the reservations (impossible: it is part of the prepared record that precedes launch). CCH136 has no such pre-check, so only CCH136 could pass via a baseline at finalize.
Stop conditions hit: "Option C needs a change to a persisted receipt/return format"; "the baseline cannot be taken before the child start" from host.mjs because the reservations happen inside `launchHeldCriticFamilyRoute`; "spec contradicts itself or the code" (CCH137 pre-check vs. unchanged `protectedBefore`).
