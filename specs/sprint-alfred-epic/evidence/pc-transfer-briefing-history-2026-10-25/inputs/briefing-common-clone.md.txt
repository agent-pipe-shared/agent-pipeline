# Common rules for clone-based build agents (2026-10-22) — part of every briefing that points here

## Where you work
- ONLY inside your own git clone `scratch/clones/<name>` (named in your briefing), cloned from the main checkout's HEAD of branch feat/sprint-alfred. Run EVERY command from the main checkout's working directory with clone-relative paths (`node --test scratch/clones/<name>/...`, `git -C scratch/clones/<name> ...`): the closed shell grammar refuses `cd`. Helper scripts you write go under `scratch/` of the MAIN checkout (gitignored, never committed). Never modify the main checkout's tracked files.
- Read `scratch/clones/<name>/templates/prompts/agent-obligations.md` first (closed shell grammar, protected test paths, commit rules). The clone has no git identity: pass `-c user.name=... -c user.email=...` copied from `git config user.name` / `git config user.email` read in the main checkout; change no config.
- Heavy suites run ONE AT A TIME (parallel runs collide on the registry); use a TMPDIR OUTSIDE every git repository for suites that sign / spawn openssl. Other agents and a long counted pin run share this machine: a timeout that appears only under load must be re-run alone before you call it red.

## Protected paths — never commit them
The pre-commit hook refuses these; you must NOT use `--no-verify`: `plugins/pipeline-core/hooks/guard-*.mjs` (and their `.test.mjs`), `plugins/pipeline-core/lib/guard/*`, `plugins/pipeline-core/scripts/pipeline-state.mjs`, `plugins/pipeline-core/hooks/guard-git.test.mjs`, `harness/verify-suites.json`, `docs/product-capability-inventory.json`, every path in `NEVER_LIFTABLE_KERNEL_PATHS` of `plugins/pipeline-core/lib/guard-maintenance-window.mjs` (kernel list, including `session-authority-registry.mjs`, `worktree-lifecycle.mjs`, `passive-read-policy.mjs`, `project-onboarding-v3.mjs`; a NEW first-party module imported by a kernel path becomes a kernel path itself, GMWKC01, and must be named in `docs/guard-maintenance-window-threat-model.md`, GMWKC03 — prefer putting new logic into an existing module; if a new module is unavoidable, deliver the kernel-list line and the threat-model entry in the protected diff). For any protected change: make it in the clone's working tree so you can measure it, then deliver the change as ONE unified diff `scratch/agent-out/<name>-protected.diff` in the MAIN checkout (relative to the repo root, `git apply`-able with -p1; produce the text with `git -C scratch/clones/<name> diff -- <paths>` and write it with the Write tool or a node helper) plus `scratch/agent-out/<name>-protected-notes.md` (what changed and why, measured results, exact commit message proposal). Verify the diff with `git apply --check scratch/agent-out/<name>-protected.diff` from the main checkout (read-only). Commit in the clone only unprotected files. A test that is green only with the protected diff applied is still committed (it documents the contract) — say so.
- A PIN or test file under a protected prefix that you only ADD or change is part of the protected diff, not of a clone commit.

## Quality rules
- RED first: every behaviour change gets a case that fails on the unchanged code for the intended reason (a fixture or import failure is not the intended RED), then GREEN. QG-04: never weaken, skip or delete an existing examiner; a necessary change to an existing assertion needs a bounded written justification (cite the PO decision) in the commit message and in your report, and goes into its own commit (or its own hunk of the protected diff, with the justification in the notes).
- Spec and PRD files are never changed. No signing, no override ceremonies, no network, no push / reset / stash / checkout / rebase. No machine-specific absolute paths, no secrets in files or commits. Language of every repo artifact: English.
- Commit by explicit pathspec only (`git add -- <path>` then `git commit -F <message file> -- <paths>`), message files under the clone's `scratch/commit-msg/`, Conventional Commits, small atomic commits as each piece is green. The final trailer block is exactly two lines: `AI-Assisted: true` and `Dispatch: <TASK_ID> (goldfish)` (TASK_ID in your briefing). Before your final report run `node --test scratch/clones/<name>/harness/scripts/check-consumer-safe-paths.test.mjs` if you touched anything under `plugins/pipeline-core/`, and `node plugins/pipeline-core/scripts/architecture-boundary-check.mjs` style checks only if you can run them against the clone (report new line-bound violations; do not raise ratchets yourself).
- Roles/status: when you finish, say "implementation complete in clone; independent Critic read, operator commit of the protected parts and PO acceptance pending" — never "done".

## Stop conditions
More than 2 failed attempts at the same problem; the task needs a design decision the briefing does not make (report the options, do not guess); more than the stated number of protected files; a suite that is red BEFORE your change for an unrelated reason (record it, do not fix it); tool budget at 80% (commit what is green, write the report).

## Report (max 35 lines)
Commits in the clone (SHA + one line each); per DoD check the exact command, exit code and counts; protected diff path + file list + `git apply --check` result; decisions you took and why; open items. Evidence pointers only, no log dumps.
