# w314 — One narrow command moves repositoryMode from local-only to remote-tracked, and the commit hook admits exactly that change (candidate 22 follow-up)

Delta on the candidate 22 follow-up chain (clone base 8627df377, two commits: the pinned tests first, then the change). Closest accepted criterion: AC-108 (PRD and Spec unchanged). Built by a Goldfish in a clone; delivered as a held patch the PO applies. Finding: CGR-19 of the Claude greenfield report (`repositoryMode` is written once at onboarding and a project that says `local-only` is pushed; the only route was a signed guard override). PO decision of 2026-11-09: one narrow, agent-executable command for `local-only` to `remote-tracked`, only with a configured remote; every other direction stays on the signed route. This slice is explicitly allowed to change the commit-hook source `scripts/pre-commit-hook-install.mjs` (PO decision of 2026-11-09).

## What

1. **`scripts/repository-mode-promote.mjs` (new), run as `--root <root> --to remote-tracked`.**
   - Writes both calibration twins (`project/pipeline.json`, `.claude/pipeline.json`, each when present) by a byte-level replace of the single token `"repositoryMode": "local-only"` to `"remote-tracked"` (the whitespace between key and value is captured and kept). The bytes are handled as latin1 (one character per byte), so CRLF, a BOM, the indent and the key order cannot move. Exactly one literal token per file is required; the re-parsed result must equal the old value with only that field changed (`JSON.stringify` of the parse, key order included); the document must be valid UTF-8 JSON holding an object.
   - The twins are compared after normalising that token (byte comparison of the promoted-or-already-promoted images), so a half-applied state resumes (only the twin that still says `local-only` is written) and a rerun reports `unchanged`, exit 0.
   - Typed refusals, exit 1, each naming the route that remains: `RMP-TARGET-UNSUPPORTED` (any `--to` but `remote-tracked`, hence also the reverse direction and `host-managed` as a target), `RMP-HOST-MANAGED`, `RMP-MODE-INVALID` (absent, another type, another string), `RMP-CALIBRATION-INVALID`, `RMP-CALIBRATION-UNSAFE` (symlink, non-file, empty or over 1 MiB), `RMP-NO-CALIBRATION`, `RMP-TOKEN-NOT-ONE` (zero or several literal tokens, an escaped key spelling), `RMP-TWIN-DRIFT`, `RMP-NO-REMOTE` (`git remote` lists nothing; checked only when a write is needed), `RMP-PREIMAGE-CHANGED`, `RMP-WRITE-FAILED`. Usage errors exit 2 with `RMP-USAGE` (each flag once, no extra argument, root an existing directory).
   - Atomic write: a temporary file in the same directory (exclusive create, the original file mode), fsync, rename; all preimages are re-read and compared byte for byte immediately before the first write; a readback after the writes. One JSON line is printed with `status` (`promoted` or `unchanged`), `written` and `paths` (the twins that differ from HEAD, the paths to commit; all present twins when HEAD cannot be diffed).
   - The pure rule is exported as `promoteRepositoryModeBytes(bytes)` and is what the hook uses (one rule, no second copy).
2. **`scripts/pre-commit-hook-install.mjs`: stateless admission next to the calibration-verify transition.** New `repositoryModePromotionPaths(projectRoot, paths)` adds the staged twins to the existing `sanctionedVerifyPaths` set (the `continue` for GS-10 and GS-11 does the rest) only when: every staged path is a calibration twin; every existing twin (present in HEAD or in the working tree) is staged; a remote is configured; and, per twin, the staged blob equals the writer's byte rule applied to the HEAD blob, with the same git file mode. No journal, no capability, no store, no new refusal text. Any other staged path, another field, whitespace, the reverse direction, `host-managed`, one of two twins, no remote, an unreadable input or an unloadable rule module leaves today's GS-10 and GS-11 refusal. The hook body is a template literal; the new code uses string concatenation and doubled backslashes only.
3. **`scripts/push-prepare.mjs`: `repositoryModeNotice` names the exact command** (`node <plugin-root>/scripts/repository-mode-promote.mjs --root <project-root> --to remote-tracked`), says the pre-commit hook admits exactly that change without a signature, and keeps the signed guard-override route for every other change. The notice is still advice (ready does not move, nothing is written or refused).
4. **Tests (written first and run red against the original code before any production edit):**
   - `scripts/repository-mode-promote.test.mjs` (new, 20 cases): CRLF plus BOM plus 4-space indent kept byte for byte; one JSON line; rerun `unchanged`; half-applied resume; single existing twin; twelve refusal rows (host-managed in either twin, absent, invalid, wrong type, unparsable, no calibration, no remote, twin drift by field and by line ending, duplicate key, escaped key spelling) each with exit 1, the typed code, the named route and the files untouched; every other target and the reverse direction; usage errors exit 2; the preimage race (seam `deps.beforeWrite`); the pure byte rule (nested key, invalid UTF-8).
   - `scripts/pre-commit-hook-install.test.mjs` (five cases added, real `git commit` through the installed hook): the positive goes through the REAL writer on CRLF 4-space twins and asserts the committed bytes differ by the value token only; negatives: another field alongside, only one of the two twins staged, a whitespace change on top, an unrelated file staged with the twins, no remote, the reverse direction, `host-managed` to `remote-tracked`. Each negative asserts today's refusal text and that HEAD did not move.
   - `scripts/push-prepare.test.mjs`: the CGR-19 pins restated in place (below).

## Measured seams (not re-derived from the briefing; read from the clone)

- `lib/architecture-adoption-authority.mjs` `adoptionSnapshot()` hashes the RAW bytes of `project/pipeline.json` into `profileSha256` (and binds `pipeline.user.yaml` and the architecture map). The only caller that passes `requireCurrent: true` is `scripts/architecture-adoption.mjs` line 343 (the call that records an adoption decision from a signed request). **Meaning:** a promotion changes those bytes, so an adoption request that was created BEFORE the promotion and not yet recorded fails with `ADOPTION-AUTHORITY-INPUT-CHANGED` and must be requested and signed again; a decision already recorded is not re-verified by that call (no other caller of `requireCurrent: true` exists in the plugin, scripts or harness; later readers of recorded decisions were not traced). This is the same effect any calibration edit has; promote before starting an adoption request, or request it again afterwards. Nothing in this slice changes that code.
- `lib/project-authority.mjs` lines 177 to 187 report `PA-CALIBRATION-DRIFT` when the twins' sha256 differ, which is why the command writes both twins and the hook admits only the pair together.
- `scripts/repository-freshness.mjs` `declaredRepositoryMode()` is the one reader of the field; `local-only` returns before the upstream check, so promoting can only make the freshness check stricter.
- The writer-commit capability (`writerCommitAdmission`) excludes every gate-strength path by design and is untouched; the admission here is the hook's own stateless comparison.
- Plan and design approval do not bind the calibration bytes (`observeCurrentPlanApprovalForCalibration`); `v3-bootstrap-authority.mjs` hashes none. Nothing else needed a change.
