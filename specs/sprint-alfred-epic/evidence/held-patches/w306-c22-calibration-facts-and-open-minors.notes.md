# w306 — Rigor inputs, effort claims, open minors and evidence commits stay honest and cheap (candidate 22)

Delta on the candidate 22 chain (clone base 6fa9369d0). Closest accepted criterion: AC-108 (PRD and Spec unchanged). Built by a Goldfish in a clone that carries the chain; delivered as a held patch (two commits). Targeted delivery green; batch Critic, Full Verify and PO acceptance stay pending.

## Why

Four findings of the Claude greenfield report: CGR-16 (minimum rigor derived from ignorance), CGR-20 (effort contradiction), CGR-22 (open minors land nowhere without a backlog), CGR-13 (evidence commits dominate the history).

## What it changes (all under plugins/pipeline-core/)

1. CGR-16 rigor inputs (`scripts/rigor-floor.mjs`, `lib/rigor-lifecycle.mjs`)
   - Measured on a fixture that looks like an onboarded greenfield (state file, a plan naming paths, one new untracked source file; real `collectRigorJournalEntry`): five of the eleven inputs ended unknown or unavailable and each became an `UNAVAILABLE_OR_UNKNOWN_INPUT:<name>` trigger: `protectedIdentity`, `architectureProfile`, `fitnessOutcomes`, `interruptionLineage`, `diffStats`. On a bare fixture without a state file the plan paths were unknown too (a fixture artifact, not a product finding: the collector already supplies `plannedPaths` from the plan once the state file exists).
   - Answerable, now supplied: (a) `protectedIdentity` was NEVER available: the resolver returns the shipped baseline revision as the decimal string `"1"` (its schema says type string), the accepted input requires an integer, so a resolvable identity was always read as unknown. The collector now converts a plain positive decimal string; anything else stays unknown. (b) `diffStats` was unknown whenever an untracked file existed, which is every greenfield change. The untracked files' lines are now counted from the files (newline bytes plus one for an unterminated last line, so LF and CRLF count alike; at most 256 files, 1 MiB each, no binary file, no link, nothing outside the root); any file that cannot be counted exactly leaves the count unknown.
   - Still unknown by design: `architectureProfile` and `fitnessOutcomes` need the architecture model, baseline and map of a calibrated project (same reason as CGR-17: fitness `unavailable` without calibration); `interruptionLineage` needs an established interruption-store snapshot, and an absent store is not an observed "zero".
   - Readout: new `rigorReadout(derivation)` splits the escalation codes into real `triggers` and `unknownInputs` (names). The text output of `rigor-floor.mjs` prints `triggers:` and `unknown inputs (not triggers):` on separate lines. The JSON form stays the schema-bound derivation (`schemas/pipeline.rigor-derivation.v1.json` forbids extra keys); a consumer calls `rigorReadout(result)`.
   - Unchanged on purpose: escalating on an unavailable input (fail-safe), and every byte `deriveMinimumRigor` returns. `validateRigorHistory` recomputes each stored row with the current code and compares canonically, so a change to the derivation output would invalidate every existing journal row.
2. CGR-20 effort (`scripts/critic-dispatch-preflight.mjs`)
   - Measured where each value comes from: `config/runner-profiles-v3.json` duties (`critic_normal` Claude effort medium, `critic_high_risk` Claude effort max, evidence kind `dispatch-receipt`); `agents/critic.md` frontmatter `effort: max`; the Critic prompt template line "Requested route: {{MODEL_ID}} at {{EFFORT}}" (`templates/prompts/critic-review.md`); the project calibration is a separate value this code never reads. Nothing at preflight observes the applied effort.
   - The printed MP-07 rationale line used to say the duty "is opus at effort max" (a fact). It now says the duty "requests opus at effort <registry value>" and adds: the applied effort is not observed by this packet; report the requested effort as requested, and name an applied effort only where a dispatch receipt shows it. The line still carries "Rationale (MP-07)", architecture or security and the one batch, so the dispatch policy admits it unchanged (tested). The calibration is not overwritten.
3. CGR-22 open minors (new `lib/open-minors.mjs`, test `lib/open-minors.test.mjs`)
   - Measured places: the Critic lineage record keeps only a digest and a status per finding (no text); the PO residual acceptance is private (git common directory, not readable from a fresh clone); no backlog exists in a project without one. The one tracked, human-readable place every project has is its handover (`project/pipeline.json` `handover`, default `docs/state.md`). Chosen: one managed block under "## Open minor findings" there. No new store.
   - API: `minorsFromVerdictFindings` (minor findings only, ids `CRF-<packet>-<n>` equal to the consumed-finding ids), `upsertOpenMinors` (pure; merges by id, idempotent, accepted is never reopened, keeps LF or CRLF, text outside the block untouched, a marker inside a finding text cannot break the block), `readOpenMinors`, `openMinorsCloseLine`, and two thin file wrappers `recordOpenMinors` / `summarizeOpenMinors` (repository-relative path only, no link, temp file then rename). Accepted minors stay listed as `[accepted by <label>, <date>]` after the close.
   - NOT wired, by instruction (the close files belong to parallel work): the Elephant wires two calls. (a) Where a Critic round or the close has a consumed verdict with minor findings: `recordOpenMinors({ root, handoverPath, entries: minorsFromVerdictFindings({ featureId, packetId, findings }) })`, and `{...entry, status: "accepted", acceptedBy, acceptedAt}` when the PO accepts residuals. (b) In the close summary: `openMinorsCloseLine(summarizeOpenMinors({ root, handoverPath }), handoverPath)`. The close already adds the handover path to its one close commit (w303), so the block lands in that commit without a new commit.
4. CGR-13 evidence commits (measurement only; no code)
   - Evidence-only commits come from: the dispatch record of every Goldfish dispatch (host commit, bound by the `Dispatch:` trailer and the record's changed-file coverage), the diagnostic-evidence registration, the Critic lineage registration, the registered delta request, the tracked Critic export, the Critic addenda (already ONE commit for all records of a close) and the close commit.
   - Bound, therefore left: each registration verb names its own "ONE evidence-only commit" and the admission accepts only that form (`register-feature-package.mjs`); the lineage of round N must be committed BEFORE the next correction commit, and the next verb reads HEAD as its registration commit (the output of one step is the input digest of the next, so two steps cannot share a commit); the transport check needs HEAD reachable from the candidate through evidence-only commits only, and chooses the candidate as the newest commit that is not evidence-only; host dispatch commits are verified one per record. Bundling any of these needs a change to the host commit contract or to a candidate binding, which this task forbids (stop condition 5).
   - Not measured: the 23 of 39 split of the report run (only the anonymised row was available), and whether a Critic export and a lineage registration may share one commit (the code says "registrations, or the tracked export", not both in one).
