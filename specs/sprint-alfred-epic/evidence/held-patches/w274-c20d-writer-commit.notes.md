## What the patch changes

Measured in the Antigravity greenfield TabletApp_agy_070_3 (P2, C2): right after the PO's signed plan approval, and again at close, the pre-commit hook refused the Pipeline's own State, lifecycle and audit-bundle outputs and the PO had to sign three extra human-guard overrides (two expired overnight).

1. **New `lib/writer-commit-capability.mjs`: the shared mechanism and the stable entry point.**
   `armWriterCommitCapability({ rootDir, writer, rerun, files: [{ path, sha256 }] })` records, after a successful write, the exact paths and sha256 digests the writer wrote in a record store `<git common dir>/agent-pipeline/writer-commit/` (HMAC-SHA256, key file in the same store, atomic writes, hardened private directory). It re-hashes every file first: bytes that are not the ones named throw `WC-BYTES` with `.heal` = the rerun of the writer, and nothing is armed. It stages nothing. It never arms a gate-strength path (`gateStrengthRuleFor`) or a path of the shipped protected baseline (hooks, guard libraries, the baseline data, the sanctioned writer's own source): those come back in `excluded`. Returns `{ status: "armed" | "not-needed", id, paths, protectedPaths, excluded, message, steps }`, where `steps` is the exact commit (`git add -- <paths>`, `git commit -m "chore(pipeline): commit the <writer> output" -- <paths>`).
   Also exported: `withWriterCommitCapability({ rootDir, writer, rerun }, fn)` (snapshot, run the writer's `fn` returning an exit code, arm what changed on success only, print the next step on stderr, never change the exit code), `captureWorktree` / `armWrittenSince` (the same in two steps, used per stage by finish-feature) and `formatWriterCommitNextStep`.
   **For the sibling dispatch C20D-P3-ONE-SHOT-CLOSE:** call `armWriterCommitCapability` with the exact files a step wrote (or bracket a step with `captureWorktree` + `armWrittenSince`); records from several steps aggregate naturally because each entry is bound per `(path, sha256)`, and the commit may name all their paths at once.
2. **`lib/protected-test-paths.mjs` (the hook side, next to the G20-55 admission).** `writerCommitAdmission(rootDir, relPath)` returns, for one STAGED path: `null` (no writer armed it, or any fault), `{ admitted: true }` (the staged blob hashes to an armed digest and the entry is unspent), `{ admitted: false, stale: { path, writer, rerun } }` (armed with other bytes) or `{ admitted: false, spent: true, ... }`. `writerCommitConsume` marks the used entries. Binding is per path and bytes: no index tree, so unprotected files staged beside the writer's bytes do not matter; an extra protected path, one changed byte or a path the writer never wrote stays a finding. Expiry is by bytes, never by a clock (no `expiresAt` anywhere): an entry used at HEAD X is admitted again only while HEAD is still X (a commit-msg failure and retry is not stranded) and is spent once its commit exists; an unrelated commit in between does not strand it.
3. **`scripts/pre-commit-hook-install.mjs` (the generated hook).** Inside the finding loop, right after the G20-55 closed-continuity admission, a staged path with an unspent matching entry is admitted; the entries are consumed only when the whole commit passes (no findings left, or the existing commit-scope override admits the rest). A stale or spent entry adds `PB-WRITER-COMMIT-STALE: <path> ... repair: rerun the writer: <rerun>` to the old refusal, which is otherwise unchanged. No new import call site (the two functions come from the already imported `protected-test-paths.mjs`).
4. **Wired writers.** `scripts/pipeline-state.mjs`: `run` is now a thin wrapper (`WRITER_COMMIT_COMMANDS` = `approve-plan`, `close-feature`) around the unchanged body, which is renamed `runPipelineState`; `scripts/finish-feature.mjs` brackets every stage that writes (start, checkpoint, prepared transition or its replay, and the State close), returns `writerCommit` (`status`, union `paths`, per-stage `stages`, `message`, `steps`) and prints the commit on stderr in the CLI. stdout stays the writer's own JSON in both.
5. **Kernel closure.** `pipeline-state.mjs` (a kernel path) now statically imports the new module, so `lib/guard-maintenance-window.mjs` lists it in `NEVER_LIFTABLE_KERNEL_PATHS` and `docs/guard-maintenance-window-threat-model.md` names it (GMWKC01, GMWKC03).
6. **Tests (QG-04: no existing assertion weakened; no existing test pinned the old refusal for these writers, so none needed restating).** New cases carry a `G20-66` comment: `scripts/pre-commit-hook-install.test.mjs` (4 cases through the real installed hook and a real `git commit`: exact bytes pass with no override and print the next step; plus an unprotected file passes, plus one more protected path is refused with its rule id; a changed byte is refused as stale naming the writer rerun and without a capability the old refusal stands; an unrelated commit between write and commit does not strand it), `scripts/d3-signed-reconcile-commit.test.mjs` (5 lib-level cases: arm and admit, `WC-BYTES`, stale and spent, gate-strength/baseline exclusion, the wrapper for `approve-plan` and `close-feature` and a failed writer arming nothing), `scripts/finish-feature.test.mjs` (1 case: every stage that writes arms exactly its bytes, the result carries the one commit, a changed byte is stale).

## Not changed

- `armReconcileCommitCapability` and its call site: left untouched (the briefing allows it). It binds the index tree through the human-guard-override store; the new mechanism does not use that store, so no new audit kind or auth verb exists (check-auth-gate-inventory-drift stays green) and unprotected staged files cannot change its verdict.
- `commit-pipeline-owned.mjs` and `pipeline-owned-files.mjs`: not touched; the printed next step is a plain two-line commit.
- Other writers (`configure-verify`, `set-phase`, the feature-package reconcile, the result bootstrap) are not wired: the briefing names approve-plan, close-feature and finish-feature.
- The printed `git commit -m` carries only the conventional subject; the GIT-03 provenance trailers (`AI-Assisted: true`, one `Dispatch:`) are the caller's, as for every other agent commit.

## Not proven

- No real Antigravity, Codex or Windows greenfield run; the hook cases run on this platform only. The record store uses the same hardened private-directory creator as the hook's other state.
- Which exact files the real approve-plan and close-feature write in a consumer project was not enumerated: the wrapper arms whatever the successful run changed in the working tree (tracked-dirty or untracked, not ignored), minus the excluded classes. A file the writer wrote that is ignored by git is not committable anyway.
- A protected path the hook exempts by another route (a signed maintenance window, a consumed override, first appearance) is simply not a finding; the capability stays unspent for it.
- The security model is the same custody as the human-guard-override store (a key file under the git common directory); it is an attribution of the writer's output, not a signature.
