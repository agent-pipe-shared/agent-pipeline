**Order.** The patch is a delta on the integrated 30j tree (the clone int30j: the 30i chain plus every 30j lane, including w30j12 with `signingConfirmationCard` and `signingCeremonyCard`). It does NOT apply to the real checkout before that chain; applied after it, `git apply --check` is clean (measured on the int30j clone: exit 0). An exit 1 against the real repository before the chain is expected. The check test therefore asserts only that the patch is non-empty and touches only the briefed files. `lib/human-guard-override.mjs` is a protected plugin source file: the PO applies and commits this chain.

**Criterion.** AC-112 is the closest existing accepted criterion; it does not name this route, and the PRD and the Spec are unchanged. The Critic is suspended for candidates of this repository (PO 2026-11-16) and no Full Verify runs: this change is verified by tests only; no review was made, and none is claimed.

## What it adds

- `lib/human-guard-override.mjs`: the describer (`describeHumanGuardOverrideSelectionCore`, so both `describeHumanGuardOverrideSelection` and `describeHumanGuardOverrideSignatureRequest`) returns a new key `cardFacts` next to its display lines: `{ toolName, commandClass, expiresAt, pathCount }`, taken from `planned`, the plan `readIndexedDisclosurePlan` already validated against its original request, selection and intent. A value of the wrong type is left out of the object. The four display lines, `materialArtifact`, `requestBinding` and `fullReviewMaterial` are untouched; nothing is read, written or stored additionally.
- `scripts/po-human-approval.mjs`: `signingConfirmationCard` gets one more branch. When the request has no schema (the digest-only route has no request file) and the resolved description carries a `cardFacts` object, the same `guard-override` card is built from those four keys (read key by key, never from display text). The card module itself validates every fact (bounded single line, positive safe integer) and omits a part that is absent or malformed. The call site in `sign-intent` is textually unchanged, so the existing structural case that pins the card in front of the unchanged `disclosureLines` stays green.
- A GMW (maintenance-window) description, an unresolved digest, a record without `cardFacts` and a record with a non-object `cardFacts` get no card, exactly as before.

## Why it is safe

- The disclosure index keeps its closed key list (`schema, root, intentSha256, requestSha256, planSha256, selectionSha256, reasonSha256, authorSourceRoot, expiresAt`); the facts come from the indexed plan the resolver already validates. A new case reads the index file and pins the key list.
- Every digest, subject, plan and proof byte, every display line, the review-material file (`publishSigningReviewMaterial` writes only `lines` and `fullReviewMaterial`, so the extra record key never reaches a stored byte), the passphrase and key handling and the confirmation frame are unchanged. No stored status, record shape or gate is added or changed.
