# w227 — a stop waits for the registry lock a sibling hook still holds before it reads its pending state

- Found by: Windows dispatch B on 19f (peer, 2026-11-05): the Goldfish ran 46.7 s and succeeded, but its SubagentStop host commit failed with `NGHF-PENDING-UNAVAILABLE`, reason `NGHS-PENDING-MISSING: registry-lock-held`. The pending state existed (the reserve phase had written it); the stop read it through the registry while a sibling hook held the lock and `readNativeGoldfishPending` turned the first held lock into "missing". The delivery was recovered by hand with `goldfish-host-commit-recover` (plan and apply, commit landed).
- Change: `readNativeGoldfishPending` (native-goldfish-host-state.mjs) reads under the existing bounded `retryWhileSessionAuthorityLockHeld`, budget `NATIVE_GOLDFISH_STOP_LOCK_WAIT_MS` = 90 s (inside the 300 s SubagentStop hook timeout; one lock cycle takes 60 to 100 s on Windows). The terminal preparation that follows in the finalizer waited 5 s; it now uses the same constant. A lock still held after the budget answers exactly as before (same code, same reason); any other fault (for example ENOENT) is not retried. The read and the clock are injectable (`read`, `lockWait`) for the test.
- Not known: which process held the lock at 17:09:25Z (no registry natives appear in the trace between the lines around it); the peer had run a heal against a dead lock owner shortly before. The change does not need the holder: it only stops a transient lock from being read as "missing".
- Test: case `D177-stop-pending-read-waits-for-a-held-registry-lock` (two held reads then success; a lock held past the budget keeps its reason; ENOENT is read once; the budget lies inside the hook timeout).
