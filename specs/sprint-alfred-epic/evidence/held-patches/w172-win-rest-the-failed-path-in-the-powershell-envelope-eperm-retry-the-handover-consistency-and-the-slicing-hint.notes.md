# w172 - the rest of the native Windows items: failed path in the PowerShell envelope, EPERM retry, handover consistency, slicing hint, launch contention (candidate 19c, Q10 ps1 half, W3, W6, E4)

Built by a Goldfish in a clone (`scratch/agent-out/s-win2`) at the repository state plus the held patches w166 and w168. **Apply order: w166, then w168, then this patch** (it edits files w168 changed; against the real checkout alone it does not apply, `apply --check` on a tree carrying w168 exits 0). Criterion binding: AC-108 is the closest existing accepted criterion; the PRD and the Spec are unchanged.

## What it changes

- **Q10 ps1 half.** `lib/windows-owned-authority-native.ps1`: `Refuse(code, path)` remembers the path it was given (`FailedPath`) at the five `WIN-AUTH-OPEN` sites, and the failure envelope carries it as an optional fifth key `path` (only for `WIN-AUTH-OPEN`, at most 4096 characters). `lib/windows-owned-authority-backend.mjs`: the envelope is still accepted with exactly `ok, code, committed`, and now also with exactly `ok, code, committed, path` when the path is a string of 1 to 4096 characters without control characters; anything else (unknown key, non-string, control character, oversized) is `WIN-AUTH-NATIVE-OUTPUT` as before. The error carries `failedPath`; `lastWindowsAuthorityFailedPath()` returns the path of the most recent native failure in the process. `HELPER_SHA256` is re-pinned to the new helper bytes (`sha256sum` of the LF file, the way the existing P4 pin checks it). `describeWindowsAuthorityRefusal` takes `failedPath` and prints it (with the preview and apply command) in preference to the readiness probe's path; a path containing a quote or a control character is never printed as a command. `hooks/guard-dispatch.mjs` reads the envelope path before the probe runs its own native calls and hands it over.
- **W3.** `scripts/security-readiness/probe-retry.mjs` (new): `runProbeRetryingEperm` repeats a probe once, after one injected pause, when the first run failed with the execution-environment status (EPERM, and EACCES, which `runProbe` does not tell apart); a second failure is reported exactly as before. The three readiness probes (gitleaks, osv-scanner, semgrep) call it.
- **W6.** `scripts/pipeline-state.mjs`: `update-public-handover` now also calls the new exported `syncPublicCurrentState`. It leads the `## Current state` section with `**Last updated:** YYYY-MM-DD` (a label the bootstrap facts already read as the handover date) and the same `**Lifecycle phase:**` marker the Next action block carries, and rewrites the generated sentence "Feature `id` is active in <phase>" for the same feature. Everything else is byte for byte; a handover without that section is not touched; a second run on the same day changes nothing. The JSON result gains `currentState` (`updated`, `current` or `absent`); the exit code rule is unchanged.
- **E4.** `hooks/native-slicing.mjs`: `slicingNudge(platform)`; on `win32` the hint states the sequential rule (one Goldfish launch at a time) instead of offering parallel dispatch; the three emitters use it (`options.platform` injected). `lib/windows-authority-readiness.mjs`: `prepareWithWindowsContentionRetry` retries a launch preparation that was refused with `WIN-AUTH-OPEN` on Windows while the readiness probe finds every folder readable (at most 3 attempts, injected pause), then returns the refusal with `contention: true` and a repair text that states the sequential rule and names the one command that waits for the first launch (`session-authority-repair.mjs wait --root <root> --timeout 120`, no `icacls` advice). A folder fault, another platform, another reason or a probe that cannot judge returns the first result unchanged. `guard-dispatch.mjs` runs the native host preparation through it.
- Registration: `plugins/pipeline-core/scripts/win-authority-rest.test.mjs` (new, 21 cases) in `harness/verify-suites.json` and as `verify-phase:harness/scripts/verify.mjs:win-authority-rest-tests` in `docs/product-capability-inventory.json`. The inventory also gets the missing entry for the w168 suite (`win-authority-readiness-and-preflight-tests`), registered in the suite list by w168 but not in the inventory.

## Not changed / not proven (read this before accepting)

- **Nothing ran on native Windows.** The ps1 change is not executed here (no PowerShell host); the C# change is mechanical (an optional parameter and a static field) but is unproven until a Windows run. The helper source changed, so the per-user native type cache rebuilds once.
- **The registry concurrency is a launch-level retry, not a registry change.** Whether the first launch really holds the file that causes `WIN-AUTH-OPEN` for the second, and whether a 400 ms pause twice is enough, is not known without Windows. The slicing hint therefore says "sequential" on Windows; parallel launches there stay unsupported by text, and the retry only softens the failure. `lib/session-authority-registry.mjs` and `lib/session-requester-bridge.mjs` are untouched.
- `hooks/guard-slicing.mjs` emits its own two "Slicing default" lines (serial run, TodoWrite batch); it is outside the named files and is not made platform-aware here.
- The adapters under `scripts/security-adapters/` are untouched: their spawn paths already classify EPERM as `execution_environment`; the retry sits in the readiness probes the briefing named (the reported failure).
- The `EPERM` retry cannot tell EPERM from EACCES (`runProbe` reports both as `execution_environment`); both are retried once.
- `reader-inputs/product-capability-inventory.json` is derived and is not regenerated here.
- No Full Verify; independent Critic review not run for this slice.
