# w171 — the pre-push hook template and the security completeness gate take the shared freshness verdict, and the carry-forward is on (candidate 19, D4b/E3 rest)

Delta on w162 (the chain through w162 must be applied first; `git apply --check` of this patch against a checkout without w162 fails by design). Built in a clone that carries w162 as its base commit. **This patch widens what a push accepts by default.** It is the build of the amendment of 2026-11-04 of `docs/adr/draft-authority-carry-forward-and-signed-reconcile-commit.md` and of the PO decision of the same day (the carry-forward is active by default, the safeguards of the ADR stay). The criterion binding is AC-108, the closest existing accepted criterion; the PRD and the Spec are unchanged.

## What it changes

- `lib/security-completeness-gate.mjs`: the commit comparison of the v2 envelope takes the verdict from `evidenceFreshnessFailureCodes`. Two optional parameters: `carryForward(evidenceCommit)` (a carried answer that names the tree of the evidence commit makes the envelope fresh, and `input.tree` is then compared with THAT tree, because the tree of a later evidence-only commit differs by construction; `!tree` still always fails) and `withCodes` (appends the stable code and the carry refusal to the commit-mismatch failure). Both default to off, so the failure text and the exact-commit meaning of every other caller (close, PR, release, clean-candidate run) and of the existing exact-string pins are unchanged.
- `scripts/pre-push-hook-install.mjs` (template of the managed hook): loads `evidence-freshness-codes.mjs` and `evidence-carry-forward-reader.mjs` by dynamic import (the same `join(PLUGIN_LIB_DIR, ...)` spelling as the other shared modules) once at module load, so `checkEvidenceFreshness` stays synchronous with the same three-argument call; a load fault fails closed with a message of its own. The helper takes the verdict from the shared function, keeps its messages and adds the stable code. A new optional fourth argument asks the carry-forward (`kind`) and collects the readback (`carried`). The v2 gate call passes `carryForward` and `withCodes`. The hook log entry of an allowed push carries an additive `carriedForward` field naming the record, the evidence commit and the passed-over commits. The pure helper's behaviour without the fourth argument is exact-commit only, as before. The installer file is part of the runtime snapshot digest, so an installed hook reports `updateRequired` and refreshes through the existing version-bound refresh; `INSTALLER_VERSION` is not changed.
- `hooks/guard-push.mjs`: the stable code is appended to the three evidence freshness messages and, for a stale record, the carry refusal reason (`[EF-STALE-COMMIT; carry-forward refused: PRODUCT-PATH-CHANGED]`). The v1 Security candidate binding (`candidate.commit`, `candidate.tree`) is the fourth hand-written comparison the briefing did not name: a Security record carried from commit A to B always failed it. A carried record is now bound to the commit and the tree it was produced for (`evidenceCommit`, `evidenceTree` of the reader's decision); an uncarried record is exact as before. The v2 gate call passes `carryForward` and `withCodes`.
- `lib/evidence-carry-forward-reader.mjs`: a carried decision also names `evidenceTree` (`git rev-parse <evidence commit>^{tree}`; any fault is a refusal). The decision of the default reader is remembered per process for `(repository, kind, evidence commit, candidate commit)`, because one push decision asks the same question up to three times and the secret scan is the costly part; an injected decision or scan is never cached. Header comment: active by default.
- `lib/evidence-freshness-codes.mjs`: `freshnessCodeSuffix(code, carryRefusal)`, the one place that spells the code next to a message.
- `scripts/push-prepare.mjs`: the readback of a carried record names the passed-over commits (`passed over <sha8>, ...`); the comment says active, not opt-in.
- `lib/push-gate-real-decision-carry.test.mjs` (new, registered in `harness/verify-suites.json` and the capability inventory): a git fixture with Verify and Security records (v1 and v2) bound to commit A; the real `hooks/guard-push.mjs` (spawned with the tool call) and the real pre-push hook template (rendered and spawned with the ref update on stdin) are asked. Accepted: evidence-only commits. Refused with `EF-STALE-COMMIT` and the carry reason: a product-file commit (`PRODUCT-PATH-CHANGED`), a change of `project/guard-config.json` (a gate-consumed file outside the set, `PRODUCT-PATH-CHANGED`), a secret scan finding or an unavailable scanner (`SECRET-SCAN-FINDING`, `SECRET-SCAN-UNAVAILABLE`; Verify stays carried), and a record bound to a commit that is not an ancestor (`NOT-AN-ANCESTOR`). Only the scanner binary is a stand-in (a shell script through `PIPELINE_GITLEAKS_PATH`). Also pinned: the hook log names the passed-over commits and the push-prepare readback names them.
- Docs: `docs/push-release-flow.md` describes the freshness of the push gate with the carry-forward; the ADR is Accepted with the decision line of 2026-11-04, and its `.json` digest is refreshed.

## Why it is bounded

- The ADR safeguards are all still in the decision (`lib/evidence-carry-forward.mjs`, unchanged by this patch): the closed evidence set, the product tree hash equality, the ancestor check, a clean secret scan of the passed-over commits for Security (unavailable or a finding is a refusal), and fail closed on any error. The set is not widened; Critic rounds are not carried.
- There was no runtime opt-in gate in w162 to remove: guard-push and push-prepare called the reader unconditionally; "opt-in" meant the apply script block and the comments. Active by default therefore means the block is no longer optional and the rest of the push path (v1 binding, v2 gate, hook template) now honours the same decision.
- A refused carry changes nothing: the record is stale for HEAD exactly as before, now with the reason next to the code.

## Deviations and judgement calls

- The briefing names two remaining hand-written comparisons; the v1 Security candidate binding of guard-push was a third that had to follow the carry for a Security record to be accepted at all, so it is changed.
- `lib/security-completeness-gate.mjs` appends the code only when its caller asks (`withCodes`): `lib/security-completeness-gate.test.mjs` pins the exact failure strings with `deepStrictEqual`.
- `scripts/push-gate-satisfiability.mjs` is not changed: it already classifies by the code and keeps the prose fallback; the new messages do not alter that.
- The hook template does not check the Verify push-boundary (it never did); the carry is the only addition there. The release-promotion envelope is not added to the hook.

## Not proven / not changed

- No Full Verify and no independent Critic review (suspended by the PO); this slice is a batch item for the Coordinator.
- The real gitleaks binary was not used by the new test (a stand-in script decides clean, finding or unavailable); the reader's real-binary cases are those of `evidence-carry-forward.test.mjs`.
- The installed hook was exercised by rendering the template against the plugin lib directory, not through `applyInstall` and the runtime snapshot; the snapshot copies `lib/` and `scripts/`, which hold both new imports, and the existing snapshot cases pin the digest.
- `lib/evidence-carry-forward.mjs` is unchanged: the decision does not yet store `productTreeSha256` in the record (it recomputes it from the git objects).
