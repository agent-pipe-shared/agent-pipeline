## Why

Analysis A6/C7: the ready gate kept a hand-maintained mirror (`PROJECT_ONBOARDING_CONTROLLING_NON_READY_STATUSES`, 33 literals) of the statuses the producer returns. A status the mirror lacked reached the gate as `PORG-INVALID-OBSERVATION` instead of `PORG-NOT-READY` (it happened for three statuses). A static extraction of the producer's literals was tried and fails (a status is computed at some call sites: the app-server trio, the repository failure table, the runtime-initialization ternary), so none is used; the check sits at the one place every status passes through.

## What it changes

- `lib/project-onboarding-v3.mjs`: exports the closed list `PROJECT_ONBOARDING_LIFECYCLE_STATUSES` (`ready` plus the 33 controlling statuses, frozen, same names and order as before) and `requireProjectOnboardingLifecycleStatus(status)`, which returns a listed status unchanged and throws for any other (string or not). The shared result builder `lifecycleResult` now calls it for `status` (the builder is also exported as `buildProjectOnboardingLifecycleResult`, the test seam). The four returns of `inspectProjectOnboardingV3` that build their envelope by spreading the base keys (`enrollment-history-recovery-required` twice, `enrollment-retirement-required`, `intake-required`, `enrollment-activation-required`) bypass the builder, so they call the same check inline (key order untouched). The module-load shape probe that reads the base key list used the status `shape-probe`; it now uses `ready` (the keys do not depend on the status).
- The refusal text names the repair: add the status to `PROJECT_ONBOARDING_LIFECYCLE_STATUSES` in the producer file and run `node --test plugins/pipeline-core/lib/project-onboarding-ready-gate.test.mjs`.
- `lib/project-onboarding-ready-gate.mjs`: `PROJECT_ONBOARDING_CONTROLLING_NON_READY_STATUSES` is now derived from the producer's list (every status but `ready`) instead of retyped. The export keeps its name, its 33 members and its order (checked against the old literal list by a one-off comparison: identical), because `lib/guard/constants.mjs` and several other suites import it. The gate's own fail-closed branch (a status outside the list is `PORG-INVALID-OBSERVATION`) is untouched. A new status added to the producer list now blocks at the gate without a second edit.
- No stored status, no record shape, no digest or key byte, no gate decision changes: every status keeps its meaning, the envelope keys and their order are asserted equal to the base key list for every listed status.

## Item 7 of C30-24 (Critic addenda under the ignored `/evidence/`): decided, NOT changed

The addendum path is `evidence/dispatch-critic-addendum-<task>.json` (`criticDispositionAddendumPath`), beside `evidence/dispatch-record-<task>.json` and the evidence file it binds; onboarding seeds the anchored rule `/evidence/` into a `.gitignore` it creates. Measured in a real Git repository with that rule (probe in `scratch`, not delivered): `git check-ignore` matches the addendum path; `git status --porcelain` does not list it while it is untracked; plain `git add -- <path>` is refused (exit 1, "paths are ignored"); `git add -f -- <path>` stages it, the commit succeeds, and from then on the file is tracked, shows later modifications in `git status` and appears in `git ls-files`. So the `git add -f` the close prints works end to end, and the same convention is printed by four other writers (the session finalizer, the package registration, the feature finish).

Neither candidate fix is deliverable inside this slice, and each hits a stop condition of the briefing:

1. Moving the addendum to a tracked location: the path is pinned in `lib/critic-course-admission.mjs` (the `ADDENDUM_PATH` regex), `lib/review-admission-read.mjs` (`CRITIC_ADDENDUM_PATTERN`), `lib/administration-documentation-paths.mjs`, `scripts/dispatch-record-write.mjs` (`criticDispositionAddendumPath` at the write) and `scripts/close-coordinator.mjs`; the validator also requires the sibling dispatch record and the evidence file under `evidence/`. None is in the write list, and existing closed features carry addenda at the old path (immutable artifacts).
2. Narrowing the ignore rule: `REQUIRED_PROJECT_IGNORE_PATTERNS` is derived from the seed's `/` lines, so editing `/evidence/` changes what an already onboarded project with its own `.gitignore` is asked for; Git also cannot re-include a file under an excluded directory. This is the briefing's explicit stop ("the fix would change what an already onboarded project ignores").

What stays open for a decision (not a defect of the force-add itself): between the write of an addendum and its evidence-only commit the files are invisible to `git status`; the close names the commit step in its stop (`CLOSE-CRITIC-ADDENDA-WRITTEN`).
