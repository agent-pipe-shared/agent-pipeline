# w30i4 — feature package registration can record the discarded predecessor of a successor (`--supersedes <feature-id>`) (candidate 30i, C30I-S3, queue C30-12)

Applies AFTER the 30h chain plus the skill split, the agent fields and the bound-session advance (the clone `base6`): the patch is the delta `0fb8a98db9f7..HEAD` of a clone that already holds all of them, because it edits files those slices touched. It does not apply to a checkout without them (`apply --check` on `base6`: exit 0; on the real repository before the chain: expected to fail). Criterion binding: AC-108 is the closest existing accepted criterion (a fresh bounded attempt under its unchanged text). The PRD and the Spec are unchanged. The Critic is suspended for candidates of this repository (PO decision 2026-11-16; consumer sessions still run Critic courses), so this change is verified by tests only.

## Why

C30F-G4 admits the first full review of the successor of a discarded feature when the successor's manifest declares the predecessor (`supersedes`), but no writer set it: `registerFeaturePackage` always wrote `supersedes: null`, and an approved manifest cannot be edited afterwards. Every successor therefore depended on `--successor-of` being remembered at every review round (C30F-G4B), and a later round on another machine without the retained course was refused.

## What it changes

- `lib/feature-package-registration.mjs`: `registerFeaturePackage` takes an optional `supersedes`. Absent or null: the manifest literal is `supersedes: null` exactly as before (bytes and digest unchanged). Given: the manifest carries it, after a validation that precedes every read of the tree and every write (the registration stays transactional; a refusal leaves nothing behind):
  - `FPR-SUPERSEDES-PATTERN`: the id must match the course admission's `FEATURE_ID` (now exported, not copied) AND this module's own `SAFE_ID`, the grammar the topology validator enforces on `supersedes` (`FTP-SUPERSEDES`); a wider id would be written and then rolled back as `FPR-VALIDATION-FAILED`.
  - `FPR-SUPERSEDES-SELF`: the feature's own id.
  - `FPR-SUPERSEDES-NOT-DISCARDED`: the State must record the predecessor as discarded. The notion is the course admission's own: its State filter was moved unchanged into the exported pure function `discardedFeatureIdsOfState(state)`, which `discardedFeatureIds(root)` now calls, so there is one definition. The repair sentence names the discard-feature route and registering without the flag.
  - An existing manifest of this feature: same value is the same no-op as today (`already-registered`, or the re-approval rebuild); another value is `FPR-SUPERSEDES-CONFLICT`; the flag on a manifest holding `supersedes: null` is `FPR-SUPERSEDES-LATE`, whose repair names `--successor-of <feature id of the discarded predecessor>` at review time (the supported route for an already registered successor). Nothing is written in either case.
  - Re-approval rebuild (`supersededRegistrations`): it required `manifest.supersedes === null`; it now requires `manifest.supersedes === <the flag or null>`. Without the flag a manifest that holds a relation is still refused `FPR-MANIFEST-CONFLICT` as today (never rebuilt with the relation silently dropped); with the same flag the rebuild carries the relation; null never becomes a value.
  - `choices.supersedes` describes the input in the registration result.
- `lib/critic-course-admission.mjs`: `FEATURE_ID` exported; `discardedFeatureIdsOfState` split out (behaviour of the admission unchanged; `--successor-of`, the first full round, impactAmbiguous and every round rule are untouched).
- `scripts/register-feature-package.mjs`: the shape `--root <root> --supersedes <id>` (exactly four arguments, `--stage` still last), the usage strings and the help text (one paragraph).
- `skills/critic-review/references/coordinator-course.md`: one sentence naming the flag and `--successor-of` for an already registered feature.
- `harness/config/verify-case-completion-augmentations.v1.json`: the policy row of `critic-course-admission-tests` lists the two new ids CCA102 and CCA103.
- No schema id, no digest of an existing manifest or course changes; `supersedes` keeps its meaning for alias descriptors (rename, split): the writer only writes a predecessor the State records as discarded.

## Tests (existing registered suites only; no new test file, no registration change)

The two admission cases were written after the implementation and were not run against the original code; case (b) is the control that shows the trap the flag removes.

## Not changed / not proven

- The envelope reader is a stub with the real reader's contract in the readback and admission cases (named seam). The real reader resolves the manifest through `validateFeaturePackage`, which the cases run on the written manifest; the only other readers of `supersedes` are the course admission and the topology validator (checked by search). The real approve-plan route plus the flag end to end was not run.
- A predecessor whose id the admission grammar admits but the manifest topology refuses (uppercase, `.`, `_`) cannot be written by this flag (`FPR-SUPERSEDES-PATTERN`); such a successor still names the predecessor at review time with `--successor-of`. Widening the manifest topology is outside this slice.
- The skills that describe the plain registration verb (`pipeline-start/references/implementation-continuation.md`, `happy-path.md`) and `design-course.md` are outside the write list and carry no sentence; the help text and `coordinator-course.md` do.
- `lib/pins/critic-course-consumer-chain-walk.test.mjs` is not changed (its fixtures write manifests by hand); the files `lib/feature-package-registration.test.mjs` and `scripts/register-feature-package.test.mjs` named in the briefing do not exist, and a new test file needs a registration in the protected `harness/verify-suites.json`, so the cases live in the two existing registered suites.
- A later registration of a successor whose predecessor is discarded afterwards is not supported (the flag requires the State record first); the Critic course, `--successor-of` and every review round rule are untouched.
- The full Verify run was not made; case counts change by ten (readback suite) and two (admission suite) after applying (inventory refresh).
