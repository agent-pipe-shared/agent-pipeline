# w318 — The onboarding can set the commit author it asks for, and runtime initialization names its action (candidate 23)

Delta on the candidate 23 integration state (clone base 7ecd5f42ebf, one change commit on top: tests first, then the change). Closest accepted criterion: AC-108 (PRD and Spec unchanged). Built by a Goldfish in a clone; delivered as a held patch that the PO applies (`lib/guard/*` and `lib/human-guard-override.mjs` are kernel paths).

## What

1. **`lib/guard/command-catalogue.mjs`: `isAuthorIdentityConfigCommand(command, root)`.** True only for exactly four parsed words: `git config user.name|user.email <one value>`. No flag of any kind (so no `--global`, `--system`, `--local`, `--file`, `--get`, `--unset`), no other key, no second value, no leading `-` or `~`, no `$`, backtick, backslash or glob character in the value, not blank, at most `AUTHOR_IDENTITY_FIELD_MAX_BYTES` (the bound the onboarding applies to the answer). Chains, `;`, pipes and redirects never parse into four words (the grammar rejects them).
2. **`lib/guard/lifecycle-gate.mjs`: the admission.** Only for a session-intent `PORG-NOT-READY` whose status is exactly `bootstrap-binding-required`, only for the Bash tool, after the existing scratch lane: `verdict(0)` for that predicate. Every other status keeps refusing the same commands with `GUARD-LIFECYCLE-NOT-READY` (asserted for every controlling status).
3. **`lib/guard/command-catalogue.mjs`: `observedRuntimeInitializationCommand(root, dependencies)`** re-observes the onboarding exactly as `observedOnboardingCommandMatch()` does (same `inspectProjectOnboardingV3` call shape) and renders `observed.nextAction` with `renderProjectOnboardingAction`. It returns null unless schema, status `runtime-initialization-required`, root and intent agree and the action is a non-mutating command; an unavailable or malformed observation prints nothing and the refusal stands as before. The command is never composed in text: the producer's own `nextAction` (`plan-runtime ... --root <root> --runner <runner> --intent session`) is what is printed.
4. **`lib/guard/lifecycle-gate.mjs`: the hint.** At `runtime-initialization-required` the refusal gains one line, `Next onboarding action (run exactly this): <command>`, through the existing `nearMissHint` argument of `blocked()`.
5. **`lib/human-guard-override.mjs`: the transport for Codex and Antigravity.** Both runners print the transported HGO recovery text (cause, allow-listed fixed guidance, the fixed reason) instead of the guard's own text, and that transport drops every dynamic line, so the Claude hint alone would not have reached them. `lifecycleRecoveryGuidance` now also carries exactly one line, for exactly that status, if it has the exact shape `Next onboarding action (run exactly this): node <...>project-onboarding-v3.mjs plan-runtime --root <word>` with optional `--runner (claude|codex|antigravity)` and `--intent session`, each word plain or single-quoted as `shellWord()` renders it, at most 2048 bytes. Anything else (another status, a second such line, a control character, another verb, `;`, an unknown executable) is dropped as before. The prefix constant is exported once and used by the guard and the transport.

## Why this route (author identity)

The driver deliberately never sets `user.name`/`user.email` (an identity is a claim about a human; see `project-onboarding-v3-author-identity.mjs`), and the standing rule (`skills/pipeline-start/SKILL.md`) is to apply it in this repository's local config immediately before the first commit, a moment only the agent knows. A driver verb would also need its own sanctioned-command admission, so it is not less surface. The skill text and `references/resume-hint.md` already say what the guard now admits, so neither is changed (the skill stays inside its 24 KiB budget untouched).

## Not changed (and why)

- `SKILL.md`, `references/resume-hint.md`, `collectAuthorIdentityAction` guidance: they already say `git config user.name "<name>"` / `user.email "<email>"`, local only, immediately before the first commit; the guard now matches the text.
- The fixed reason `Technical repair is required before retrying; repeating the same inspection alone cannot change readiness.` stays word for word: the Codex and Antigravity suites pin it for every status. At `runtime-initialization-required` the next-action line is printed in front of it.
- PowerShell: a PowerShell call never reaches the readiness gate (`evaluate.mjs` returns `powerShellScopeVerdict` first), so it is not refused by readiness and this slice does not touch that existing asymmetry.
- No value is ever defaulted or invented; the Critic preimage list and every file it covers; `harness/verify-suites.json`, the case registry and the inventory (no new test file; cases are in registered suites).
- The other lifecycle statuses and one-turn refusals the agent recovers from itself (out of scope by PO direction of 2026-11-09).
