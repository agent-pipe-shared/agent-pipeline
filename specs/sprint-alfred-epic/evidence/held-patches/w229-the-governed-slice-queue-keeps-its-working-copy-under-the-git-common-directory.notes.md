# w229 — the governed slice queue keeps its working copy under the Git common directory; the tracked file is only the handover copy (candidate 19)

Applies AFTER the held patch w225 to w228: it edits the same files (the patch is the delta `228b124f..HEAD` of the slice clone built on top of that chain). Against the real checkout alone it does not apply. Order: w225 to w228, then w229.
Source binding: AC-108 is the closest existing accepted criterion for this work; the PRD and the Spec are unchanged (a fresh bounded attempt under the unchanged Spec text).

## What it does

- New `lib/slice-queue-location.mjs` owns the location. From the repository root and the plan directory it returns the working path under the Git common directory (`<common dir>/<control dir>/slice-queues/<plan dir slug>-<12 hex of the plan dir digest>.json`,
  directory mode 0700, files 0600; a linked worktree resolves to the same file, because the common directory is asked of `git rev-parse --git-common-dir`, never joined by hand) and the repo-relative handover path. Outside a Git repository the working path IS the handover path (legacy behaviour, no sidecar).
- `resolveGovernedItemQueue` returns `path` (still the handover path, so every pending state and `delivery.queuePath` keeps validating), `workingPath`, `source` (`working` or `handover`), `handoverConflict`, and `sha256` = the digest of the bytes actually read.
- Read rule (reads never write): working copy present -> read it; absent -> the handover bytes byte-identical (never re-serialised, so the `queueSha256` of an in-flight pending state does not drift); both absent -> `SQ-DELIVERY-COURSE-ABSENT` as before.
- Sidecar `<name>.sync.json` beside the working copy: digest of the handover copy last imported or exported and digest of the working copy at that moment. Handover differs from the record while the working copy equals its record -> the handover copy wins (another machine pushed) and its bytes are read.
  Both changed, or no sidecar and both differ -> the working copy wins and the result carries `handoverConflict: true`.
- Writers (`prepareGovernedItemQueue`, `rollbackGovernedItemQueue`, `cancelUnstartedGovernedItemSlice` including its orphan-row branch, the scope amendment, and `slice-queue.mjs` add/defer/hold/depend/cancel) publish the new bytes as the working copy by temp file beside it + rename, after the compare-and-swap on the bytes they read. That is the "materialise": the first write of a handover-only repository creates the working copy; a refused mutation creates nothing.
  A rollback restores the exact prior working bytes, or removes the working copy and its sidecar when there was none. The legacy `.slice-queue-legacy-<digest>.json` backup and every temp file land beside the working copy.
- `slice-queue.mjs import --take-handover` replaces the working copy with the handover bytes. It refuses with a runnable repair (`cancel <slice> --started ...`) when a slice that still holds a live reservation is not in the handover copy. `validate` and `report` print `source` and `handoverConflict` (with the repair text when true).
- push-prepare exports at the start of its report, next to the fold: the working copy is written to the handover path and exactly that path is committed with the fold's trailer pair, only when the tree is otherwise clean and no recorded approval is outstanding for the current HEAD (the fold's gate); a conflict or an unchanged handover copy is left alone. The sidecar is updated afterwards. The git hooks and guard-push gain no refusal.
- `close-coordinator.mjs` (`assertCourseCriticEvidence`) and `audit-index.mjs` read the course through the shared reader. audit-index keeps the tracked handover path in `sources`: the digest in the index is the digest of that file, so it equals the digest of the course that was read once push-prepare exported it, and says `missing` when no handover copy exists yet; no new source kind and no `expectedSha256` for the course.
- Kernel listing: the new module is imported by `native-goldfish-host-state.mjs`, a never-liftable kernel file, so it is in `NEVER_LIFTABLE_KERNEL_PATHS` and named in the maintenance-window threat model (kernel closure suite run).

## Not changed / not proven

- `PIPELINE_FANOUT_CONFIG.queuePath` (guard-dispatch, stop-fanout, post-compact-reground) stays an operator-set path; nothing in the plugin sets it from the governed path.
- The three expressions naming `specs/<feature>/slice-queue.json` (pipeline-owned-files, verify-evidence-producer, dispatch-authorship-verify) are kept: they now describe the handover copy.
- The queue schema is not changed; a handover copy is never re-serialised when it seeds.
- `.gitignore` of this repository still ignores `specs/*/slice-queue.json` (PO decision 2026-10-17, machine-local queue state). The export commits that path exactly as the fold commits the State file, so in this repository `git add` refuses an ignored path and the export reports it did not commit. A project that does not ignore the path commits it. Reconciling the ignore line with this design is a coordinator decision (the file is outside this slice's scope).
- The baseline special case for `row.path === state.delivery.queuePath` stays for pending states from older builds, with a comment saying so.
- No full Verify run, no independent Critic review, no Windows run. The new file is read and written with plain `node:fs` only; it adds one `git rev-parse --git-common-dir` per process and no PowerShell observation. Its cost on Windows is not measured.
