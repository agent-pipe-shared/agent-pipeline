## How the course and its feature id are derived (no new field)
Every registered lineage record carries `request.packetId`; the records of one course live in one package's `specs/<featureId>/lifecycle.json` (candidate-evidence rows). `defaultReadCourseHistory` lists `specs/*` at the repository HEAD, calls `resolveRegisteredCriticCourseHistory({ repoRoot, featureId, candidateCommit: HEAD })` per directory (errors skipped, at most 256 directories, result cached per root+HEAD+packet) and takes the history that contains a record whose `request.packetId` equals the addendum's `criticPacketId`. The feature id is the path segment; it need not equal the closing feature. HEAD, not the review candidate, is read because the lineage record of the last round is registered in a commit after that round's candidate. The course is the whole retained chain of that package (the resolver already enforces one parent chain via `validateCriticReviewHistory`). Open question for the PO/Critic: `resolveRegisteredCriticCourseHistory` registers only `pipeline.critic-review-lineage.v1` rows (v2 rows are skipped there); a v2-only course is therefore read as "no course" and the finding falls back to the single-receipt text (refuses, never accepts).
