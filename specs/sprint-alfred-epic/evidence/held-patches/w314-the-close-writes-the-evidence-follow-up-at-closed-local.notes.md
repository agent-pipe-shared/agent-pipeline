## What it adds

- `lib/audit-proof-collection.mjs`: `prepareCloseAuditFollowUp({ root, featureId, approvedCommit, common })`. For `approvedCommit` = HEAD at closed-local it finds the feature's bundle, collects the final Verify and Security records the close recorded (`collectFollowUpEvidence`, unchanged) and calls `writeAuditProofFollowUp` with no proofs and no attributions. It returns `no-bundle`, `nothing-to-carry`, `already-followed-up` or `written` like its sibling `prepareAuditProofFollowUp`; bad input is `no-bundle`.
- `scripts/finish-feature.mjs`: the closed-local branch (phase `closed-local` only; a rerun in a later phase leaves it to the push's follow-up) calls it and returns a `followUp` field next to `pushEvidence`: `{ status, bundleDir, files?, commit? }`. `commit` is `{ paths, excluded, capability, message, steps }` from the same `writerCommitSteps` route the close commit uses, derived from what git reports uncommitted under `<bundle>/proofs`, so a rerun before the commit names it again. The close writes files only; the commit stays the caller's step. When a commit is pending the result also carries `next`: commit first, then run pushEvidence: the final Verify at HEAD runs AFTER that commit (the commit moves HEAD). A failure of the writer is `{ status: "unavailable", code }`, never a stop. The shared status-and-arm code of `commitFacts` became `commitOf(pathspecs, message)`; `commitFacts` output is unchanged.
- `lib/security-close-status.mjs`: the constant `CLOSE_FOLLOWUP_SENTENCE` ("reach the audit bundle only with the evidence follow-up of the next push; until then ... holds no security evidence") is now false and is replaced by `closeFollowUpSentence(status)`, which states what the close did (written or pending commit, nothing left to add, no bundle, could not be written). `finish-feature.mjs` prints it as the last sentence of the closed-local message (not at all in a later phase).
- Tests (all in existing registered files): `scripts/finish-feature.test.mjs` two new cases (written, verified, byte-identical manifest/README/artifacts, evidence sha256 equal to the private copies, commit steps printed, rerun before the commit says `already-followed-up` and names the commit again, after the commit `nothing-to-carry`, a later `prepareAuditProofFollowUp` carries no duplicate; no bundle and no recorded final record write nothing); `lib/audit-bundle.test.mjs` one new case for the lib function (including approved commit = candidate itself and bad input). The fixture helper `packageFixture` got an optional `candidate` parameter (default unchanged).
- Failing first: both new finish-feature cases were run RED before any production edit (`TypeError: Cannot read properties of undefined (reading 'status')`, no `followUp` field), then GREEN after.

## Measured risks (the two the recon note left open)

- (a) `git merge-base --is-ancestor` accepts the candidate itself: PROVEN by the lib case where the bundle commit, the recorded `candidateOid` and `approvedCommit` are the same commit (status `written`), and by the finish-feature fixture where HEAD equals the recorded candidate.
- (b) Is `audit-bundles/**` protected here: measured with `protectedTestPathRuleFor` and `gateStrengthRuleFor` against `audit-bundles/<feature>/<oid>/proofs/follow-up.json`, `.../001-final-verify.json` and `.../manifest.json` in the clone with this repository's guard config: no rule and no gate for any of them. So the commit needs no armed capability here. The step still calls `armWriterCommitCapability` like the close commit does: a project whose config protects those paths gets the capability armed by the writer itself (`commit.capability` is its id) and the printed steps are the same plain `git add` / `git commit -F` ones; nothing is printed that could fail for want of an arming command.
