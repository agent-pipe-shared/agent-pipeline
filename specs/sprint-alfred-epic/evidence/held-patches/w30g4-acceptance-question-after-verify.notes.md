## What it changes

- **`finish-feature.mjs`, order of the close stages.** The `ONESHOT-ACCEPTANCE-REQUIRED` stop moved from before the leftover rollback and `verify-candidate` to after the Verify, its registration, the package moves and the Critic/Verify lifecycle receipt, immediately before `acceptance-record`. A red or dirty Verify therefore stops with `ONESHOT-VERIFY-RED` and the human is never asked. A recorded acceptance for this candidate (`readAcceptanceRecord`) and an answer given with `--human-acceptance` are still taken before the rollback (the rollback removes an uncommitted record file) and still skip the question; the record is written after the Verify as before.
- **The stop is after writes and says so.** Its repair names what is in the tree (the passing Verify evidence and the package moved to `completed`, uncommitted), says not to commit it, and says the rerun with the answer discards those outputs (stage `discard-own-leftovers`) and runs the Verify again on the same candidate. The question text (`acceptanceQuestion`, new optional `verifyPassed`, English and German) says the candidate Verify has passed.
- **Option 2 chosen (the rerun repeats the Verify), not option 1 (reuse the passing evidence).** Reason: the leftover rollback already exists for exactly this tree (CFC-2) and deletes the evidence file; the real producer writes its output with `flag: "wx"` and a Critic/Verify lifecycle receipt per packet, so reusing an uncommitted evidence file would mean trusting a file and an earlier receipt, close to the Critic-bound Verify path this slice must not touch. Cost: the Verify runs twice per close. The producer allows reuse of suite receipts of the same candidate (`receiptReuse: "allowed"`); how much that saves was NOT measured, so no saving is claimed.
- **The rollback moved up, before the decline.** The decline branch is unchanged and stays before the Verify (the decline needs no Verify result, is never blocked by a slow or flaky one, and the existing contract "a decline runs no Verify" stays true). Because the asking call now leaves its Verify evidence and package move uncommitted, the rollback runs before the decline branch so the decline commit does not carry them and the package record is back at its pre-Verify state (`implementing`). `ONESHOT-ACCEPTANCE-NOT-YES` stays where it was, before the rollback: it checks only the words given and this call writes nothing for it (text now says "by this call").
- **Messages and docs.** The decline message no longer says "Nothing was verified" (an earlier call's Verify existed and was discarded); the usage text says the first call runs the Verify and, only when it passed, asks. `skills/close-feature/SKILL.md` and `skills/pipeline-start/references/happy-path.md` say the same in the same order: Verify first, then the question; the question stop is after writes; the rerun repeats the Verify.

## Deviations from the briefing

1. The decline and the `ONESHOT-ACCEPTANCE-NOT-YES` check were NOT moved behind the Verify; only the question was. Reasons above (cheap, never blocked by a red Verify, existing cases like "a decline runs no Verify" keep their meaning, the NOT-YES check writes nothing). The briefing's wish that the decline path is recoverable after a green Verify is met by the rollback moved up (tested: the decline commit holds no Verify leftovers, the tree is clean after it, the next close reaches the Result bootstrap).
2. The patch base (see above).

3. Beyond the briefing, on measured evidence: the leftover rollback is relaxed for a decline only. A decline after the question with a foreign dirty path in the tree skipped the rollback (it needs a tree of only own outputs), and the decline commit then carried the asking call's `verify-candidate.json` (measured RED: `.claude/pipeline-state.json, human-decline-*.md, verify-candidate.json`). With `--human-decline` the rollback now discards exactly the own-output paths and never the foreign one; for every other call the rule is unchanged.
