# w30i9 — the attended signature confirmation opens with a plain-language card (C30I-S5, queue C30-20)

**Order.** The patch is a delta on the integrated tree that already holds the 30i slices S1A to S7, S4 and the analysis (the clone base8). It does NOT apply to the real checkout before that chain; applied after it, `git apply --check` is clean (measured on the base8 clone). The check test therefore asserts only that the patch is non-empty and touches only the briefed files.

**Criterion.** AC-112 is the closest existing accepted criterion; the PRD and the Spec are unchanged. The Critic is suspended for candidates of this repository (PO 2026-11-16): this change is verified by tests only; no review was made, and none is claimed.

## What it adds

- `lib/critical-action-approval-card.mjs` (new, pure): `criticalActionApprovalCard({ kind, candidate, expiresAt, featureId, subject, language })` returns the card as lines, ending in a fixed delimiter line (`-----`). Six labelled parts per kind: what you are signing, why you are asked now, what it allows and until when, what it does not allow, if you decline, how to read the lines below. English and German, selected by the `humanFacingLanguage` the confirmation already resolves (any other value is English); names, paths, ids and hashes are untranslated data. The expiry is rendered in UTC with fixed month names next to the stored ISO time, so it reads the same on every machine.
- `scripts/po-human-approval.mjs`: the `authorize-critical` branch passes the card as the leading entries of the summary lines it already gives `requireExplicitConfirmation`. Nothing else in that file changes; `requireExplicitConfirmation`, `composeDisclosureLines` and `printDisclosureOnly` are untouched.
- All twelve kinds `authorize-critical` accepts (`CRITICAL_COMMAND_KINDS`) have a card: push, deploy, publication, feature-package-reconcile, release-preflight, interruption-promotion, accept-residual-critic-findings, acknowledge-caller-authored-critic, spec-addendum, acknowledge-gate-definition-changes, acknowledge-maintenance-red-check, replace-verify-command. A test pins the card table to that list. Ids are cited only where the repository ties one to the kind (GIT-05 and ADR-0061 for push, ADR-0061 for deploy, ADR-0061/ADR-0075 for publication, ADR-0056 follow-up for the package reconcile, ADR-0064, AC-6/N12, D190, C21B, ADR-0095, ADR-0096, ADR-0097, ADR-0100).
- Facts come only from what the request already holds: the kind, candidate commit and tree, the stored expiry, the feature id and the subject preimage (when `--subject` or a kind builder supplied one). A preimage field is stated only when it is a single-line string (or a list of them); a fact that is missing or malformed is left out, never guessed. No new read, git call, network call or input.

## What a decline really does (stated in the card, verified against the code)

A reply other than `approve` makes `requireExplicitConfirmation` throw "approval cancelled: explicit confirmation was not given". Before the prompt the command has already written the unsigned request into the approval directory; no signature, intent file or proof is written, and the next run overwrites the request. The card says exactly that. It does NOT say that "the agent is told" anything: this command tells the agent nothing, so the briefing's phrase was not carried over (the human sees the error; whoever runs the next step sees that no proof exists).

## Not changed / not proven

- **Registration.** The new test file `lib/critical-action-approval-card.test.mjs` is not run by Verify until the Coordinator registers it in `harness/verify-suites.json` (protected). The same criterion is pinned by the seven registered cases in `po-human-approval.test.mjs`. No case-completion row exists for `po-human-approval.test.mjs`, so `verify-case-completion-augmentations.v1.json` is unchanged.
- **Push facts the request does not hold.** The plugin-built push command passes only `--subject-sha256`, not `--subject` (`docs/push-release-flow.md`): the real push confirmation therefore holds no remote and no destination ref, and no commit or file counts are ever in the request. The card says only that the confirmation does not show the remote or the destination ref (they are bound inside the subject digest) and states them when a `--subject` preimage carries them. Showing them for the real push needs the push command builder to pass the preimage (`authorizeCriticalPushCommand` in `scripts/po-human-approval.mjs` and its `pipeline-state.mjs` callers) or a new read; the counts need a git call. Both are outside this slice (no new read, no schema change) and are open for a follow-up decision.
- **The other ceremonies.** The human guard override (`prepare-authorization` / `emit-signature-digest` / `authorize-by-signature`) and the design approval do not use this confirmation: they reach the PO through `sign-intent`, which shares `requireExplicitConfirmation` and `printDisclosureOnly` but builds its own lines with `compactSigningDisclosure` and the recorded request. Their output is unchanged by this patch; a card for them is a separate change. `approve-push` prints no confirmation of its own: its ceremony is `authorize-critical --kind push`, which now carries the card.
- `docs/po-human-approval.md` and `docs/push-release-flow.md` describe the confirmation lines; the card is not described there (outside the write list).
- The exact card wording was not read by a human; German wording is unreviewed by a native reader. The full Verify run was not made.
