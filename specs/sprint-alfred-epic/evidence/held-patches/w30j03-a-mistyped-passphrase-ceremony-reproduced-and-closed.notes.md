## What was reproduced (step 1, test first)

A ceremony is two stores: the records in `.git/agent-pipeline/chat-gate-ceremonies` and a member of the session-authority registry. Every record write precedes the member write, and each group of writes runs inside one registry boundary (the registry lock). The new cases in `lib/chat-gate-ceremony.test.mjs` end a REAL ceremony (a child process, SIGKILL) at each named point and ask what the next ceremony start does and what a plain registry read does. The kill points are injected without any production change: the registry's own method-stage observer for the member-side points, an interception of `fs.linkSync` / `fs.unlinkSync` for the record-side points, and a faked attended terminal whose first read of fd 0 ends the process for the prompt point.

By cases, S6 covers every window in which the ceremony recorded its owner and that process is gone (P2 to P6 and the prompt). It does not cover (a) a ceremony that recorded no owner, in the member-behind windows P2 to P4 (every ceremony of a build before S6 is such a ceremony; whether the PO's Windows incident hit this window is not shown), (b) the leftover temporary file of a record write, (c) P1. Journey coverage of the C30-21 wish: the typo inside a living process and the three passphrase attempts were already covered by the S6 cases (not repeated); the ended-process journeys are the table above, covered; a reload or second action after the repair is the "next start works and a second retirement pass finds nothing" assertion.

## What changed (step 2, only the uncovered windows, all in `lib/chat-gate-ceremony.mjs`)

- **The prefix rule.** When the member's source facts are an exact PREFIX of the record facts, the member stands at the phase of that prefix, association and kinds agree and it is not the member of an operation this process still runs, `reconcile` reads the member at the record's phase instead of refusing `chat:member-source-drift`. Why nothing owns it: the member is written after the records inside the same registry boundary, so a member behind its records, seen by a reader that holds the boundary, was left by a writer that ended inside its boundary; the ceremony body (the prompt) starts only after that boundary, so no body runs. A member AHEAD of its records, non-prefix facts and a changed association refuse exactly as before; the first two are pinned by new "stays refused" cases, the association check is the unchanged first test of `reconcile` and cannot be built from outside.
- **The next boundary step catches it up.** The retirement of an ended ceremony (S6) now also treats a ceremony with NO owner record as ended when its member is provably behind its records (the member is read through the registry's own member inspection, which the prefix rule lets pass); it finishes the ceremony as `cancelled` through the same advance and release S6 used. A ceremony whose member agrees with its records and that recorded no owner is still never retired on a guess (a live owner in another process may still run it); the next start also works there, as it did before.
- **The temporary file.** The exact temporary name `writePrivateFileNoReplaceAtomic` gives a record (`<id>.<phase>.json.<pid>.<16 hex>.tmp`) is no longer read as a record by the inventory. It is not trusted and not deleted (it stays where it is); every other unexpected name is still refused as a record.
- **What the relaxation lets the registry do on its own.** The registry's existing entry heal (`entryHeal` / `healDrift`) re-baselines a producer whose namespace changed outside the registry unless a BOUND member of it is armed or running, and retains the prior producer record in a marker first. Before this patch a lagging ceremony member made that producer's strict `reconcile` throw, so the heal skipped it; now it passes, so the heal may re-baseline the ceremony producer for such a ceremony too. That is the heal's existing, marker-retaining behaviour for this namespace, not a new repair path; the retirement then closes the member through the registry's own advance and release.
- Restated (QG-04) `scripts/po-human-approval.test.mjs` case "a half-way ceremony whose owner was never recorded is not retired on a guess": its premise state was a member BEHIND its records, which is now closed on purpose. It now uses the state the analysis keeps refusing (member AHEAD of its records, no owner record), which still produces the "no owner recorded" repair text. The behind-state case lives in `lib/chat-gate-ceremony.test.mjs`.

Request schema, intent digest, proof format, key handling, the owner-record schema and every record shape are byte-identical. No stored status was added. Nothing is deleted by the new paths.

## Not changed / not proven

- **P1** stays refused. Its member is keyed by the binding digest and no record exists, so it cannot be tied to the owner file (keyed by the ceremony id) without a new stored field, which the slice rules forbid. The refusal names the runnable repair (`routine-repair.mjs run move-aside --no-goldfish-running ...`); the window is the gap between two adjacent writes inside one boundary, not the typed passphrase. A reorder of the writes (record first) would remove it but changes the ceremony's write order, so it is not done here.
- **A plain registry read before any new ceremony start** still refuses for a half-way ceremony: P1 by this module's `reconcile` (`chat:member-without-source`), P2 to P4 by the registry's stored baseline comparison (`chat-gate:namespace-drift`, which the entry heal clears inside a boundary but a lock-free read does not run), P5 by `registry-lock-held` (the writer died inside its boundary and the lock is retired only by the next boundary entry). Those cases exist as `todo` cases so the gap stays visible; the fix needs `session-authority-registry.mjs`, outside this slice's write list. The next ceremony start repairs the state.
- **A record file killed between its link and the removal of its temporary file** (two links, `PB-FILE: private file must be a mode-0600 single-link regular file`) is refused with no repair named; it lives in `private-boundary.mjs` and the inventory's strict file check, outside the write list. Also not changed: the CLI's retire path does not name a repair for refusals raised before the reserve step (`chat:record-canonical` was one; the tmp filter removes that cause, not the missing text).
- The first run of the PO's Windows failure, which ended without its failure line, is not explained, and Windows was not exercised (the kill points use SIGKILL and a Linux fs interception; the cases skip on Windows).
- Briefing inconsistency, reported: the DoD line for the check test says "the patch applies to the real HEAD", while the coordinator facts (and this slice's chain) say it must not be applied to the real checkout; the check test follows the coordinator facts.
