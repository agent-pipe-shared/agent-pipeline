# w224 — a consumption answers absent when no capability file is an armed one for the tool

- Found by: first Windows measurement of the installed 19e (`0.7.0+claude.20261105060619.eb4e31a`), joint session. A refused Bash command (`GUARD-REDIRECT-UNAPPROVED`) still took 102.4 s and 189 PowerShell starts; the phase `hgo-start` came only at 83.9 s, so the cost lies in the consumption attempt before the denial is recorded (the registry progress marks were the lock cycle: `registry:141` read, `registry:380` read-source, `registry:565`/`156` inspect, `registry:169` publish).
- Cause: w219 answers `absent` before the registry boundary only when the capabilities directory holds no `*.json` file. A used capability stays on disk with `status: consumed`. The Windows store holds exactly one such file (first `status` value `consumed`), so the shortcut never fired. The same holds for this Linux clone (dozens of consumed files). w219's own test only covered an empty directory.
- Change: `consumeHumanGuardOverrideCore` reads the capability files plainly before the boundary and answers `absent` when every file parses as an object and none is `status: "armed"` with `toolName` equal to the call's tool. The consumption itself already skips such files (`continue`) before any lock, audit row or drift computation, so the returned status is identical; only the cost and the `skippedInvalidRecords` diagnostic for MAC-invalid files differ. Anything else (unparseable file, an armed capability for the tool, a fault other than ENOENT) goes on to the boundary exactly as before.
- Protected file: `plugins/pipeline-core/lib/human-guard-override.mjs`, hence the PO applies it. Test: a new case in `human-guard-override.test.mjs` (consumed and foreign-tool files answer absent without the boundary; an armed file for the tool and an unparseable file enter it).
- Verified in the work clone: new and w219 cases, neighbour suites (guard-testpath-override, capability-scan, disjoint, codex-pretool-guard) green; in the full human-guard-override suite only `Q9 (D55)` fails with `domain-ancestor-unsafe`, which fails identically on the previous chain clone (environment: scratch TMPDIR), not related.
- Not covered: the 61 s before `prepare-start` of a dispatch (second Windows result) is a different path; it is read from the trace when the peer's repeat lands.
