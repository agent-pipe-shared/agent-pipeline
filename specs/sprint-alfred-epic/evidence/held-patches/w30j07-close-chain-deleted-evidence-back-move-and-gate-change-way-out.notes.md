## What the patch changes

1. Item 9, the deleted or modified tracked file (`scripts/commit-pipeline-owned.mjs`). A tracked evidence file that the agent deleted shows as ` D` and is a foreign change, so `CPO-FOREIGN-CHANGES` refused with a plain sentence and no route. The refusal now carries a derived `repair` (and ends its `reason` with it), built from the porcelain codes by the new exported `foreignChangesRepair`: for a deleted file, put the ORIGINAL bytes back with `git restore -- <paths>` (HEAD holds them; if HEAD no longer does, `git log --oneline --all -- <path>` names the commit and `git restore --source=<commit> -- <path>` brings it back); for a file under `specs/<feature>/evidence/` it adds that a registered digest is fixed (`FPR-VERIFY-IMMUTABLE`), so no new run replaces it, and that if the original bytes are gone for good the route is the course reader's own text (a new feature of rigor 1 and the PO's `discard-feature`, the same `courseEvidenceGapText` the manifest refusal already uses). For a modified tracked file (the reported case: `acceptance.md`) it says copy the file outside the work tree first, then `git restore`, and for `specs/<feature>/acceptance.md` that the close writes the record again on the identical rerun. A staged change gets `git restore --source=HEAD --staged --worktree`. The push-approval record stays excluded (push-prepare folds it; no restore is offered). The `CPO-MANIFEST-EVIDENCE` text for a COMMITTED manifest that lists a gone file gains one sentence: if Git held the file once, `git log --oneline --all -- <path>` names the commit that held the bytes and `git restore --source=<commit> -- <path>` puts them back. The 30h uncommitted-manifest recovery is unchanged. Exit codes and what is committed are unchanged; `repair` is a new optional key of the printed refusal only (the one-shot already follows a receipt `repair`).
   `scripts/finish-feature.mjs`: the ordered clean-tree route names `CPO-FOREIGN-CHANGES` beside `CPO-MANIFEST-EVIDENCE` as a refusal whose result carries the repair; the bootstrap commit stop already printed any receipt `repair` and now prints the new one.
2. Item 10, `CLOSE-GATE-CHANGE-UNPROVEN` (`lib/gate-definition-changes.mjs`, `scripts/close-coordinator.mjs`, `scripts/finish-feature.mjs`). The new exported `gateChangeWayOutText({ restorePaths })` is derived text: the change is committed history, history is never rewritten and a revert is a new change that needs its own proof, so the acknowledgement (`approve-gate-change-acknowledgement`, which the repair already names with its exact command) is the one way the close passes with it; and the order hint stays: calibration changes belong before the feature starts or in their own block, never while a close is running. The coordinator's refusal appends it. The one-shot stop appends it on a clean and on a dirty tree; when a gate-definition file is only MODIFIED in the work tree (tracked, uncommitted: it is not in the range the PO signs, so no signature can cover it) the stop names it and the exact step (copy it outside the work tree, then `git restore -- <path>`; or its own commit, which becomes one more unproven change in the same list). The ordered route and the signing command are unchanged and still come first.
3. C6 (`scripts/finish-feature.mjs`). The back-move to `implementing` that only the decline call made is now the closure `packageBackToCorrection`, used by the decline (unchanged: a failure there is never a stop and is reported in `packageBack`) and by EVERY one-shot run that enters the evidence stages (`resumeLifecycleId === null || requalify`, no `--human-decline`) while State proves a correction round (no Result bound and a `declined-acceptance` retirement on record): a package record that still says `verifying` or `completed` is moved at the TOP of that block, before the packet, SBOM, Critic-standing, earlier-findings, bootstrap and Verify stops, so none of them can leave the lag standing. The move writes the (uncommitted) package manifest, so the call is entered once more, like the Result bootstrap re-entry (`deps.packageMovedBack`), and every stop of that run starts with a note: which record moved, that it is written but not committed (the owned commit the stop names commits it), and that its "nothing was written" counts from the move on; the result carries `packageBack`. The planner and the State writer stay the authority (they admit `completed -> implementing` only with `correctionRoundFeatureId`, proven from State); the one-shot adds no stored status and does not touch the transition table. Idempotent: a record already `implementing` (or any other state) is left alone, and the second run moves nothing. A refused move is a typed stop `package-correction-round` ("nothing was written": it is refused before any write) naming the typed refusal, the read-only `feature-package-plan ... --next-state implementing` command and the identical rerun, which retries it. `recordLag` stays what it was, a derived read; it no longer outlives the next run. A resumed close past the prepared stages (the lifecycle id given, no requalify) does not enter the block and is not touched.
   E2-16 settled by test: before the change a rerun did NOT retry the move. With the new test case against the original code, a package at `completed` or `verifying` with a retired Result produced no `feature-package-plan` call (moves `[]`); the requalify moves after the bootstrap carried the record forward from `completed` through `verifying` instead.
