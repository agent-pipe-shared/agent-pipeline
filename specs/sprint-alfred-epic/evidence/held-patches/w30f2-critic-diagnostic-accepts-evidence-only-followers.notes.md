# w30f2 — the Critic diagnostic can be produced after evidence-only follower commits (candidate 30f, C30F-G2)

Applies AFTER the 30e chain: the patch is the delta `20793081fe..HEAD` of a clone that already holds the 30e chain, because it edits the same files. It does not apply to a checkout without that chain (`apply --check` on the 30e clone: exit 0; on the real repository before the chain: expected to fail). Criterion binding: AC-108 is the closest existing accepted criterion (a fresh bounded attempt under its unchanged text). The PRD and the Spec are unchanged.

## What it changes

- Order trap closed. `produceCriticDiagnostic` (`critic-diagnostic-producer.mjs`) admitted only `HEAD == candidate`; any evidence, export or lineage commit after the correction commit made it refuse `CDI-DIRTY-CANDIDATE`, and the repair was a detached clean checkout. It now also admits a HEAD that is a descendant of the candidate when every commit between them is evidence-only, no change touches the bound spec or a bound guardrail, and the tracked tree equals HEAD. `HEAD == candidate` and a clean tree behave as before.
- The classifier is reused, not copied. `critic-course-admission.mjs` factors the per-commit decision of `classifyRegisteredEvidenceOnlyCommits` into `registeredEvidenceOnlyCommit` (same functions, same order) and adds `classifyEvidenceOnlyFollowers({ repoRoot, featureId, candidateCommit, headCommit })`. It admits a manifest registration (`evidenceOnlyCommit`), the export of a consumed review (`criticExportOnlyCommit`) and a disposition addendum (`criticAddendumOnlyCommit`). It does NOT admit the carry's close commit (it may change the Spec and documents under `specs/<id>/` and `docs/`; a test showed it would let a Spec edit through) or the administration/documentation pass-over.
- The diagnostic is unchanged: every field, and the candidate (not HEAD) stays the bound identity. The capture log header, written by `capture-evidence.mjs` (outside this scope), names the HEAD the command ran at, so with a follower it names the follower. This was the one consumer that re-derived "HEAD == candidate" from the capture: `validateCaptureHeader` in `critic-diagnostic-evidence.mjs` required `head == candidate.commit`. It now also accepts a header whose head has the tree the header names and is an evidence-only follower of the candidate (the same classifier, the feature taken from the diagnostic's spec path). Anything else is refused `CDI-DIGEST` as before.
- No import cycle: the evidence module is a leaf that `critic-course-admission.mjs` imports, and a static import back made the preflight suite fail to load (a TDZ error in a distant module). The evidence module therefore exposes `installEvidenceOnlyFollowerClassifier`, which `critic-course-admission.mjs` calls when it loads. Where that module is not loaded, no follower is admitted and the capture must name the candidate, exactly as today (fails closed). The producer, the preflight, the registrar (`feature-package-registration.mjs`) and the controlled-dispatch observers import it. NOT verified: `critic-diagnostic-packet.mjs` imports only the leaf; whether every dispatch-path entry that reaches it (`critic-packet-preflight.mjs`, `critic-claude-host.mjs`, `codex-critic-packet-host.mjs`, `critic-generic-batch.mjs`, `critic-export-policy.mjs`) has course admission loaded was not settled. Where it is not, a follower-produced diagnostic is refused `CDI-DIGEST` there (fails closed); if so, that entry needs one import of `critic-course-admission.mjs`, a file outside this scope.
- The classifier's own check of a registered diagnostic (`evidenceOnlyCommit`) passes the new option `exactCaptureHead: true`, so what counts as evidence-only does not widen and the classifier cannot call itself through a log made at a later head.
- Texts. The producer refusal now says which of four causes applies (a commit that is not evidence-only, a HEAD that is not a descendant, a tree that differs from HEAD, or a spec path outside `specs/<feature-id>/`) and keeps the clean-checkout repair; three preflight texts no longer say HEAD must be the candidate.

## Tests (existing files only, no registration change)

- `critic-diagnostic-evidence.test.mjs`: (a) producer behind two evidence-only followers binds the candidate and validates; (b) a follower that changes a source path, a spec text, a protected path or a guardrail is refused, also behind an evidence-only follower, and nothing is written; (c) a sibling history and a dirty tree behind a follower are refused; (d) a capture header naming a non-follower head is refused `CDI-DIGEST` while the produced log stays accepted. The C30d case is restated (QG-04): the needle "BEFORE any evidence, export or lineage commit" became "BEFORE any commit that is not evidence-only" plus the new no-feature reason, because that is exactly what changed.
- `critic-dispatch-preflight.test.mjs`: the preflight judges a follower-produced diagnostic as one made at the candidate, and refuses a capture naming another head. One pinned text restated (QG-04) for the changed sentence.
- `critic-course-admission.test.mjs`: one end-to-end case (`C30F-G2 a diagnostic produced behind an evidence-only follower is registered and admitted ...`): topology candidate, one registered evidence follower, the producer at the follower HEAD bound to the candidate, the real `addCriticDiagnosticEvidence` registrar, one registration commit, then `readCriticCourseAdmission` is not `CCA-DETERMINISTIC-UNAVAILABLE` and its digest equals the exact-commit digest (no carry entry).
- `critic-dispatch-preflight.test.mjs` also runs the registered flow through `preflightCriticDispatch` with a course context (packet-ready, candidate bound).
- Derived files: the new cases shift positional case ids (for example the preflight case became CDPF024) and two exports are new (`classifyEvidenceOnlyFollowers`, `installEvidenceOnlyFollowerClassifier`); the coordinator's inventory/ledger refresh after applying is needed.
- Test-first honesty: only the four evidence cases were run RED before the first production edit (4 of 28 failed). The admission and preflight cases were written after the implementation.

## Not changed / not proven

- `capture-evidence.mjs`, `feature-package-registration.mjs` (its `FPR-DELTA-NO-DIAGNOSTIC` text and the producer help text still say the diagnostic can be produced only while HEAD is the candidate) and `register-feature-package.mjs --help`: outside the scope, stale wording only, to be aligned in a later slice.
- A registration commit that follows a follower-produced diagnostic has the candidate as its diagnostic's candidate but another parent; the v1 classifier `evidenceOnlyCommit` (course counters) keeps requiring candidate == parent, so such a commit is not budget-neutral there. The v2 admission path (`evidenceCommitV2` with the D51 carry) does not require it. A second production at a HEAD behind that registration is therefore refused; not proven end to end.
- An export or lineage follower, the motivating case, has no producer case here (it needs a consumed receipt in the private packet store); only the registration follower is covered end to end. Journey coverage for the export follower: not covered.
- The producer's net check that no follower changes the bound spec or a bound guardrail (`touches-bound-source`) is defence in depth behind the classifier; no test reaches that branch on its own.
- The preflight case lost its forged-head assertion while being repaired; the forged header is covered by evidence case (d).
- The feature id is derived from the spec path (`specs/<id>/...`); a spec elsewhere has no classifiable follower and keeps the old refusal.
- The full Verify run was not made.
