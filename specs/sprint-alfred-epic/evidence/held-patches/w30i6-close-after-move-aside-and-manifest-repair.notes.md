# w30i6 — a close resumed after a move-aside keeps its owner-route resume and writes its close request; every stale-digest refusal names the sanctioned route (candidate 30i, C30I-S7, queue C30-22)

Applies AFTER the 30h chain plus the skill split, the agent fields, the bound-session advance and the registration `--supersedes` (the clone `base7`): the patch is the delta `0909956b1aca..HEAD` of a clone that already holds all of them, because it edits files those slices touched. It does not apply to a checkout without them (`apply --check` on `base7`: exit 0; on the real repository before the chain: expected to fail). Criterion binding: AC-110 is the closest existing accepted criterion (a fresh bounded attempt under its unchanged text). The PRD and the Spec are unchanged. The Critic is suspended for candidates of this repository (PO decision 2026-11-16; consumer sessions still run Critic courses), so this change is verified by tests only.

## Why

A PO-run `session-authority-repair.mjs move-aside` (forced by another defect, slice C30I-S6) retains the whole session-authority registry, catalogue included, under `session-authority-abandoned/<stamp>-<id>-repair-move-aside` and leaves an open Close lifecycle. Two things then had no way on:

1. `finish-feature.mjs` decided "owner route" from the existence of `session-authority/catalogue.json`. With the catalogue gone the close ran in DIRECT mode; the resume (`--resume-lifecycle-id`) evaluated `firstPassUnfinished` only when the owner route was required, so `close-request.json` was never written and the coordinator stopped `CLOSE-PATH-MISSING` with no repair. A run WITHOUT the resume id did not adopt the open lifecycle either and started a second close.
2. A manifest whose `acceptance`/`result` entries still bind the registration-time bytes (the committed files are newer) was refused `FPR-MANIFEST-CONFLICT` / `FTP-ARTIFACT-2/3: digest does not bind file bytes` with text that named no repair ("it is never amended").

## What it changes

### (b) the resume after a move-aside (`scripts/finish-feature.mjs`)

- New `ownerRouteMovedAside` (catalogue absent AND an aside whose name ends `-repair-move-aside` exists under `session-authority-abandoned`) and `ownerRouteResume = ownerRouteRequired || ownerRouteMovedAside`. `ownerRouteResume` replaces `ownerRouteRequired` in exactly the two RESUME decisions: adopting `onlyOpenLifecycle()` when no `--resume-lifecycle-id` is given, and `requalify` when `firstPassUnfinished()` (audit request or, with Continuity, close request missing) and `coordinatorStillBeforePrepared()`.
- The ROUTE selection is untouched: the Result bootstrap, retire and close-block branches still test `ownerRouteRequired`, because without a catalogue the real owner route refuses `COR-NO-CATALOGUE` ("run it on the direct route"). So after the move-aside the State entries run directly and the lifecycle is continued, never restarted (no second `plan-start`).
- Decision (adopt rather than refuse): the refusal alternative has no runnable step. `session-authority-repair.mjs` only reports the catalogue `absent` and nothing agent-runnable restores it; the owner route itself refuses without it. Adopting on the direct route is what the pre-move-aside close did for the same lifecycle.
- Why the signal is the retained aside and not "an open lifecycle plus a missing request": the existing direct fixtures (a resume at `checkpointed` with no audit request, "a resumed close never asks") are exactly that state in a repository that never had an owner route, and they must keep their behaviour byte for byte. A repository without such an aside is unchanged (case S7-3 pins it). A catalogue removed by other means (no aside) is not covered: it keeps today's behaviour.

### (a) every stale-digest refusal names the route

- `lib/feature-package-topology.mjs`: new export `featurePackageDigestRoute(root, manifestPath)`; read-only, `null` when no entry is stale. The finding strings are NOT changed (`pipeline-state.mjs` compares `FTP-ARTIFACT-<n>: digest does not bind file bytes` exactly, `DIGEST_FINDING_RE` and the close coordinator anchor on it): the text rides in the refusal reason. It names per stale entry: label, path, class, mutability, the bound digest and the digest of the bytes; says the manifest is never edited by hand and that, if the file as it is now is the intended content, the manifest is the stale side (otherwise restore the bytes that hash to the bound digest). Then the route by what the code decides, not by a blanket claim:
  - `mutable` entry: `pipeline-state.mjs feature-package-rebind-mutable --root <root> --manifest <manifest>` (the existing explicit agent-run verb of PHX-WP-MUTABLE-ARTIFACT-AUTOREBIND; no signature).
  - `immutable` or `append-only` entry: the `feature-package-reconcile` ceremony, which needs the PO's own signature in an attended terminal, never the agent's. The plan digest and the signing command are bound to HEAD and computed by the owner of the critical-action request (`continuity-result-bootstrap-plan` calls `planFeaturePackageReconcile` and renders it through `reconcileSigningRoute`, which is not exported and lives outside the write list), so the text names that read-only command, tells the agent to hand the PO exactly its `signatureCommand` line and to run the printed `reconcileCommand` afterwards, and notes that a plan whose `preview.requiredAuthority` is `"agent"` (Result entry only, G20-38) needs no signature. It does not re-derive the subject digest in a second place.
- `lib/feature-package-registration.mjs`: the helper `withDigestRoute(root, manifestPath, reason)` is applied at the six `FPR-MANIFEST-CONFLICT` "it is never amended" refusals (review unit, diagnostic evidence, Verify evidence, spec addendum, lineage, delta request) and at the "a manifest exists but is invalid; it is never overwritten" refusal of the registration (the reported refusal). Any other invalidity keeps its text exactly (case S7-3).
- `scripts/close-coordinator.mjs`: the `CLOSE-PACKAGE` refusal for a digest-only inconsistent package appends the same route (its existing sentence is kept; `pipeline-state-result-bootstrap.test.mjs` still matches it).

## Not changed / not proven

- No schema id, digest, reconcile ceremony, binding or approval scope changed; no new way to rebind a digest. `feature-package-rebind-mutable` already existed and only touches `mutable` entries.
- Deviation from the briefing's wording: it asks for "the PO-signed reconcile request command with its arguments filled" for immutable/append-only entries. The signing command and the plan digest need HEAD, the plan and Spec paths from State and the plan preview; re-deriving them in the topology/registration libs would be a second copy of `reconcileSigningRoute` (outside the write list). The text therefore names the owning read-only command and the sentence that the PO signs in an attended terminal; it fills what the code knows (feature id, manifest, entries, both digests, root). For a feature without Continuity authority `continuity-result-bootstrap-plan` prints no plan: that case still has only the generic route.
- The plan verb `pipeline-state.mjs feature-package-plan` rejects `invalid-current-package` with the bare finding (`pipeline-state.mjs` is outside the write list): a close stopped there (`ONESHOT-PACKAGE-PLAN`) does not get the route text. The one-shot's own `ONESHOT-REGISTER-FAILED` stop carries the registrar's output, which now holds it.
- A direct resume with the audit request missing and no move-aside keeps `ONESHOT-RESUME-REQUEST-MISSING` (its repair, a rerun without the resume id, is unchanged).
- The real `session-authority-repair.mjs move-aside` followed by the real close was not run end to end; the move-aside state is built in the fixture from the directory name the registry writes (`-repair-move-aside`). The full Verify and the case-count inventory refresh (new cases: finish-feature +4, readback +3, close-coordinator +1, topology block +1) were not run here.
