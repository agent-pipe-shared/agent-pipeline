# w225 — a started cancel of a slice whose queue row is gone re-creates the row as cancelled

- Found by: joint Windows session on 19e. The peer restored the queue file (`git restore`) after a probe dispatch: slice `gf-probe-1` had a native dispatch state (reservation) but no queue row. `inspect` named `slice-queue cancel --started`; that answered `SQ-NOT-FOUND` and named `routine-repair run heal` then `move-aside`; heal answered healed but deferred (member armed), move-aside was refused `RR-OUTSIDE-LIST` (an open item reservation is not on its closed list). No runnable end (PO rule: every refusal needs one).
- Change (`cancelUnstartedGovernedItemSlice`, `native-goldfish-host-state.mjs`): with `--started` (the caller's word that no Goldfish runs for it) and a native pending state that names the slice, the missing row is re-created as a CANCELLED row from the dispatch state alone (id, item id, write scope, criterion id, base commit; basic delivery binding; tier/commitMode/loadClass as a new slice gets them), validated with `validateSliceQueue` and written through the same compare-and-swap writer as every governed queue write. The reservation then settles through the one existing definition (`settledItemSlices`: a cancelled row of the governed queue). It never uses the current plan approval (it may be stale). Without `--started`, or for a slice no dispatch state names, nothing is written; the refusal text now names the started cancel (not heal/move-aside).
- Test: NGHS37 extended (row removed -> plain cancel refuses with the started-cancel repair and no routine-repair text; a new slice over the same scope is refused; started cancel re-creates the row; a second call says already cancelled; the new slice is admitted). Suite 69/69.
- Security note for the Critic: the release rests on the caller's `--started` assertion exactly as the ordinary started cancel does (its write scope is then no longer protected); the re-created row is a tracked, visible trace. Protected file: `native-goldfish-host-state.mjs`.
