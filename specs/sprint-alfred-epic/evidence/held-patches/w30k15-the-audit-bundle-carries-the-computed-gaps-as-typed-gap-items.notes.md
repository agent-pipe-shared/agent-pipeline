## Risk measured: FCA-OUTPUT-COLLISION for a close resumed across the upgrade

`planFeatureCloseAudit` compares the evidence block of an existing bundle with the new plan (`same(prior.evidence, bundlePlan.evidence)`). The new case builds three plans from the close-shaped input: without the key, with an empty list, with one gap. The block with an empty list is byte-identical to the block without the key (canonical JSON equal), so a close with no gap (a signed plan approval, no override capability) is never refused by this change. The block with one gap differs, so a close that built its bundle before the upgrade, has a chat plan approval or an override capability on the machine, and is planned again after the upgrade, is refused `FCA-OUTPUT-COLLISION` with the existing text ("Preserve it; inspect and use a distinct explicit output"); that is the one existing repair route and it deletes nothing. The executor is handed `plan.audit.options` (read at the call site, not exercised on a stored plan across the upgrade), so an in-flight prepared phase is expected to keep the options it was planned with; this was not measured. The real comparison was not run on a full close fixture: it was measured at the level of the compared block, and `lib/feature-close-audit-preflight.test.mjs` (7 cases) stays green.

## Not changed / not proven

- No stored status, record shape, digest or key byte, gate, signature, approval, push approval, Critic evidence or security scan changed; the verifier has no new branch; no existing case was weakened or removed.
- An override gap names the kind once, whatever the age of the capability: a capability does name the commit it was signed at (`signedCandidate.commit`), but an override covers edits made after that commit and before the close candidate, so narrowing would need an ancestry check per capability against the candidate; not built (smallest change), and the trace lists every capability of the machine too. A project that ever used an override therefore carries that gap in every new bundle on that machine. The same dependence means `FCA-OUTPUT-COLLISION` can hit any re-plan after the machine's capability store changed (a capability added or its mode changed between two plans of the same close), not only a re-plan across the upgrade.
- Not enumerated, as the plan says: model exception, onboarding consent (no gap, no item; the README now says so), the approval trace itself (D4), an expected-versus-carried line (D3), a legacy plan approval without a design record (`PLAN-PROOF-NOT-RETAINED` of the trace).
- Deviation from the plan's wording: the README paragraph is static text, not derived from `EVIDENCE_ITEMS` and `TRACE_NOT_ENUMERATED` (importing the trace into the bundle module was not worth an import for one paragraph). It is also conditional: it says a close-built bundle names the two gaps and that a bundle built another way (the CLI route) names none, so the README and the guide never claim a silent omission cannot happen.
- The coordinator hand-over has no usable unit seam (the audit route needs a registered package and a Critic/Verify lifecycle, and the existing audit-lifecycle suite has no plan-approval or override fixture, so it does not reach the gap path); it is pinned at the source in `close-coordinator.test.mjs` and its behaviour is pinned through `auditApprovalGaps` plus `planAuditBundle`. A full close run was not performed.
