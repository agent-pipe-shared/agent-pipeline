# w30i5 — a mistyped passphrase (or any failed signing) leaves no block: retype inside the run, an abandoned ceremony is retired, every refusal names a runnable repair (candidate 30i, C30I-S6, queue C30-21)

Applies AFTER the 30h chain plus the skill split, the agent fields, the bound-session advance and the registration `--supersedes` (the clone `base7`): the patch is the delta `0909956b1aca..HEAD` of a clone that already holds all of them, because it edits files those slices touched. It does not apply to a checkout without them (`apply --check` on `base7`: exit 0; on the real repository before the chain: expected to fail). Criterion binding: AC-109 is the closest existing accepted criterion (a fresh bounded attempt under its unchanged text). The PRD and the Spec are unchanged. The Critic is suspended for candidates of this repository (PO decision 2026-11-16), so this change is verified by tests only.

## Why (what the reproduction showed)

The PO's report (Windows, attended terminal): a wrong passphrase in `authorize-critical`, then two reruns that answered only `PO-HUMAN-APPROVAL-FAILED: chat:member-source-drift`, then a PO-run move-aside. Reproduced on Linux with an injected spawn and a child process that is killed at the signing step:

1. A signing step that fails INSIDE a living process already ends cleanly (terminal record `cancelled`, member advanced and released, the next entry works): that case is green on the original code and stays as a regression case. The hypothesis of an in-process bug is therefore not confirmed.
2. A process that ENDS between two record writes leaves the ceremony half-way. The exact PO symptom is reproduced: records say `terminal-observed` while the registry member still says `running` (or the member was never released) and every later start refuses `chat:member-source-drift` (RED on the original: `SessionAuthorityError: chat:member-source-drift`). The window is inherent: records and the registry member are two stores, written one after the other, and nothing recorded who the owner process was.
3. The refusal carried no repair on screen: the registry attaches `error.repair`, the CLI printed only `error.message`.
4. The agent-runnable route did not take it: `routine-repair run move-aside` refused `RR-OUTSIDE-LIST`, because the read refusal names its producer by a short prefix (`chat:`) while the producer is `chat-gate`, so the finding was not classified as a reconcile-refused producer.
5. The PO's move-aside removed `session-authority/catalogue.json`; the one-shot close (`finish-feature`) decides its owner-route mode from that file, so the later close silently ran on the direct route (the close side is slice C30I-S7).

## What it changes

- `lib/chat-gate-ceremony.mjs`: each ceremony records its owner process once, in the registry's own lock-owner identity (`sessionAuthorityLockOwner`), in a separate private directory `.git/agent-pipeline/chat-gate-ceremony-owners/<id>.json` (a new file next to, never inside, the closed ceremony records: no record schema, id or existing record changes). New `retireAbandonedChatGateCeremonies({repository, boundary})`: for a ceremony short of its terminal record, or whose registry member lags the records or was not released, and whose owner the registry's own judge (`judgeSessionAuthorityLockOwner`) proves dead, it publishes the missing `running`/`terminal-observed(cancelled)` records and advances and releases the member through the ordinary `advanceSessionAuthorityMember` and `releaseSessionAuthorityMember`. A ceremony of this process, one with a live or unjudgeable owner and one with NO recorded owner is kept and named, never retired. A ceremony start runs it before it reserves its member and prints one line (`Retired N earlier PO ceremony(ies) left half-way by a process that has ended`). When a `chat:` refusal remains, `error.repair` names `routine-repair.mjs run move-aside --no-goldfish-running --root <root> --reason "<why>"` and the reason (for example, no owner recorded).
- `lib/session-authority-registry.mjs`: one new export `recoverAbandonedSessionAuthorityMember` (the member of a binding read without the strict reconcile, which is the very check a half-way ceremony fails, so `recoverSessionAuthorityMember` cannot serve it; it only mints the in-process handle, every advance/release check is the ordinary one).
- `scripts/po-human-approval.mjs`: `formatHumanApprovalFailure` prints the failure line and, on a second line, `Repair: <repair>` when the refusal carries one (before, dropped). Part (4), done because it needs no change of the proof, request, key handling or any record: for a passphrase-protected key the signing spawn is retried up to three times inside the same run; every attempt is the SAME spawn over the same already confirmed intent file, the confirmation is asked once, nothing is written between attempts (a stderr notice only), and after the third refusal the run ends with one line (`openssl failed with exit code N after 3 passphrase attempts; nothing was signed or recorded: run the same command again to retype the passphrase`). A process that did not run (no exit code) and an unprotected key are not retried and keep their text.
- `lib/routine-repair.mjs`: the read refusal's prefix matches a reconcile-refused producer by its id or its first segment (`chat` matches `chat-gate`), so `move-aside` admits exactly that finding with the same checks as the others (heal first, then move-aside only when still refused; `--no-goldfish-running`; the closed list is not widened).
- `scripts/session-authority-repair.mjs`: `heal` runs the retirement inside the boundary before the ordinary heal (agent-runnable, also through `routine-repair run heal`) and reports `chatGateCeremonies {retired, kept}` when there is something to say; a refusal of the retirement itself is reported and the heal continues. Catalogue decision for `move-aside`: it must move the whole registry (its records may be what does not read), so the catalogue cannot be kept; when a Close lifecycle exists (`agent-pipeline/publication-close` not empty) the registry is rebuilt fresh in the same call from what remains and the output says `registryRebuilt {status}` (or why it could not, with the note that the registry stays catalogue-less until the next governed dispatch). With no Close lifecycle nothing changes (SAR04 still asserts the registry is absent after a move-aside). The rebuild is a conservative trigger (any lifecycle directory); a rebuilt registry is a valid fresh one, so a false positive costs nothing.
- `harness/config/verify-case-completion-augmentations.v1.json`: SAR22 added to the policy row of `session-authority-repair-tests`.

## Tests (existing registered suites only)

- `scripts/po-human-approval.test.mjs`: eight `C30I-S6` cases (a fixture repository with an initialized registry; injected spawn; a child process killed at the signing step): a failed signing ends cleanly and the next entry works; retype inside the run (3 attempts, one confirmation, no leftover file); three refusals end with one line and a rerun needs no repair; the printed failure carries the repair; two abandoned-process variants (member and records agree; member lags the records) are retired by the next start with the note and the next entry succeeds; a ceremony with no recorded owner is not retired and the refusal names the exact command; a ceremony running in this process is never cancelled by a nested start. The `CEREMONY_OWNED_PRIVATE_STATE` filter of the setup snapshots now lists the owner directory (same kind of wrapper-owned state; a key-directory store would still be caught). Whole file run alone: 227/227.
- `lib/routine-repair.test.mjs`: one case (the chat-gate refusal is classified reconcile-refused; the prefix is a match, not a wildcard). Whole file run alone: 50/50 including that case.
- `scripts/session-authority-repair.test.mjs`: SAR22 (move-aside rebuilds the catalogue while a Close lifecycle exists; the old registry stays retained); SAR04 unchanged and green.
- `lib/chat-gate-ceremony.test.mjs` 7/7 and `scripts/po-human-approval.signing-handoff.test.mjs` 6/6 (no case added there).
- Test-first: the `C30I-S6` cases were run RED against the original production code before the first production edit (7 of 8 failed, among them `chat:member-source-drift` for the lagging variant; the nested-start guard case and the in-process failure case passed on the original by construction); GREEN afterwards. The routine-repair case and SAR22 were written after the implementation.

## Not changed / not proven

- Windows was not exercised: the reproduction is platform-neutral (injected spawn, SIGKILL child) but the PO's exact first run (why that process ended without printing its failure line) is not explained; the owner liveness on Windows rests on the registry's existing win32 judge (pid plus process start).
- A half-way ceremony that predates this change has no owner record and is never retired on a guess: its refusal now names `routine-repair run move-aside --no-goldfish-running`, which this patch admits. A registry member with no records at all (a process ended between reserving the member and writing the first record) stays `chat:member-without-source` with the same named repair; it cannot be finished because the records cannot be rebuilt.
- After a move-aside with a Close lifecycle the rebuilt registry may carry a legacy running member for a pre-change ceremony; a start does not refuse on it, the owner-less one is kept and named.
- `heal` wiring (`chatGateCeremonies` in the output) is covered by the ceremony cases only through the start path; no separate heal case was added. `scripts/routine-repair.mjs` and `session-authority-repair.mjs` header comments were not updated.
- Not run: the full Verify, the other suites that import `chat-gate-ceremony.mjs` (`human-guard-override`, `pipeline-state`, the guard suites) after this change.
