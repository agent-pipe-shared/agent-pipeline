## RECON: where the three suspected gaps stand

1. The Elephant's bootstrap after a reload. `planMandatoryHookRefresh` (`scripts/pipeline-start-preflight.mjs`) turns a `ready` readback with a stale mandatory hook into `hook-refresh-required` with ONE typed, mutating `nextAction` (`refresh-mandatory-hooks.mjs --root <root>`, expected readback `pipeline.mandatory-hook-refresh.v1` `ready`); the start skill and `references/onboarding-recovery.md` already say the Elephant executes it once and reruns the preflight. The existing pin `bootstrap-should-refresh-hooks-when-the-plugin-updated.test.mjs` (P1/P2) covers all-stale, single-stale, the two-hop (missing beside stale) and Goldfish/Critic unaffected. Closed.
2. A session that did not run the bootstrap again after a reload. The hook's own refusal (`renderSnapshotStaleCheck`, `lib/hook-currentness.mjs`) already names the one command in the refresh script's own spelling and says "run it once, then repeat the refused command; bypassing this hook ... is forbidden" (30g, `repair-map.test.mjs` C30G-D3 A and the AC-179 cases of `git-hook-runtime-snapshots-go-stale-after-plugin-changes.test.mjs`, including the installed-hook run "refusal -> printed command -> the next commit passes"). The guard's command catalogue admits the refresh script for an agent as exact argv (`--root <root>`) for the loaded plugin's own script (read from `lib/guard/command-catalogue.mjs`; no test drove the guard with the printed command here). Closed for the refusal text.
3. A staleness the preflight does not detect (READ FROM CODE, not established by a test). The preflight reads staleness from the install planners against the LOADED plugin tree (`checkCloneProvisioning`, `staleMandatoryHookSnapshots`); the hook compares its snapshot with the library directory recorded at render time. For the reload case both are digest comparisons of the same tree, so they should agree; where they could differ is listed under "Not proven".
4. Which status the wait sits in. The queue row (C30-15 row 4) and the 30g notes (w30g3, "nothing is auto-run") place the observed `HOOK-SNAPSHOT-STALE` at the Elephant's own commit after a stamp, i.e. a session whose bootstrap ran BEFORE the reload (the refusal path, item 2), and say the preflight already carries the `hook-refresh-required` action on a `ready` readback (item 1). Neither names a soft bootstrap status as the place of the wait. The one edge left is the soft `plugin-refresh-required`, whose causes are a version mismatch, an ambiguous registry identity and a failed self-application attestation; `planMandatoryHookRefresh` returns those unchanged (`baseStatus !== "ready"`). A version-mismatch-only soft status has no failed attestation reading, so "attestation is good" alone does not decide it; whether it should get the refresh is an OPEN decision this patch does not make (see Open decision). `plugin-attestation-required` keeps its closed human recovery.
