# w30f2c — a diagnostic made behind evidence-only follower commits is honoured by the packet consumers (candidate 30f, C30F-G2C)

Applies AFTER the 30e chain AND the held patch w30f2 (C30F-G2): the patch is the delta `da8492193..HEAD` of a clone that already holds both, because it edits the same files. It does not apply to a checkout without them (`apply --check` on the clone holding the 30e chain plus C30F-G2: exit 0; on the 30e clone without C30F-G2 and on the real repository before the chain: expected to fail). Criterion binding: AC-108 is the closest existing accepted criterion (a fresh bounded attempt under its unchanged text). The PRD and the Spec are unchanged.

## What it changes

- Load order (finding 1). The packet module `critic-diagnostic-packet.mjs` still imports only the leaf and gets NO import of `critic-course-admission.mjs` (a measured TDZ chain through `runtime-projection-v3`). `scripts/critic-packet-preflight.mjs` now starts with one explicit side-effect import of `../lib/critic-course-admission.mjs`, placed before every import that reaches the packet module, so loading the preflight installs the follower classifier. Every consumer reaches diagnostic validation through the preflight (`inspectCandidatePacket`, `claimCandidatePacket`, `recordCandidateResult` and the other revalidating verbs), and `critic-claude-host.mjs` and `codex-critic-packet-host.mjs` import the preflight, so one entry import covers all three entry scripts. Measured: the classifier was ALREADY installed in each of the three entries through the transitive import graph (the preflight reaches course admission through `check-critic-skip-coverage` and `review-admission-read`); the explicit import makes that a stated contract instead of an accident of the graph. No TDZ in any of the three child-process loads.
- `lib/critic-export-policy.mjs` does not validate a diagnostic: it imports only `validateDiagnosticBundleShape` and `diagnosticReviewerReferences` (shape and reference projection). It needs no classifier and was not changed.
- Disposable checkout (finding 2). `inspectCandidatePacket` and every other verb revalidate the diagnostic bundle inside the packet's disposable checkout, which holds the candidate commit only, so the follower HEAD named in the capture header does not exist there. `validateCriticDiagnostic` takes a new optional `followerRoot`; the tree check of the header's HEAD and the follower classifier run there, everything else (source digests of the spec and guardrails at the CANDIDATE, the artifacts, the header identity) still runs against the checkout. `revalidateDiagnosticBundle` passes it through, and `revalidateCandidate` names the repository that prepared the packet: the Git common directory, four levels above the checkout (`<common>/agent-pipeline/critic-packets/<id>/checkout`). Nothing else is read from it. A directory that is not that repository makes the tree check or the classifier fail, which refuses (CDI-DIGEST, then CPP-DIAGNOSTIC): fail closed. No new classifier rule, no widening of "evidence-only"; the diagnostic still binds the candidate; a non-evidence follower, a non-descendant HEAD, a forged header and a log changed after capture stay refused.

## Tests (existing files only, no registration change)

- `critic-diagnostic-evidence.test.mjs`: the three C30F-G2B child-process cases are kept and committed. Case (a) is RESTATED (QG-04): as written it required the packet module ALONE to install the classifier, which is the rejected obvious fix; it is now one case per consumer entry (preflight, claude host, codex host) proving in a fresh child process that loading the entry and then validating through the packet module accepts a follower diagnostic, plus one case that the packet module alone keeps the fail-closed contract. Case (c) now loads the preflight entry first, so the forged non-evidence header is refused for the right reason, not merely because no classifier is installed.
- `critic-packet-preflight.test.mjs`: two new cases on a real git fixture with a feature manifest: a follower-produced diagnostic is prepared (the packet binds the candidate; the checkout provably lacks the follower commit) and inspected; and a forged header naming a source commit, a header naming an unknown commit and a log changed after prepare are each refused CPP-DIAGNOSTIC. The corpus pin 18 became 20 (the assertion and the four counts of the self-probe case).
- `critic-diagnostic-evidence.test.mjs` also holds one in-process case for the new input `followerRoot`, in a second repository that holds only the candidate (`init` plus `fetch` of the candidate): the follower is accepted with `followerRoot` set to the host repository, also when it is its Git common directory; refused CDI-DIGEST with no `followerRoot`, with `followerRoot` set to the candidate-only repository, with a header naming a non-evidence descendant together with that commit's own tree, with a header naming a sibling of the candidate together with its own tree, and with the follower's head but another tree. Not covered: a host run with a follower diagnostic.

The follower classifier it relies on is the one C30F-G2 tests.
- `followerRoot` is derived from the packet's recorded checkout path (canonical layout). A packet prepared with a different layout would fail the follower check closed rather than widen anything.
