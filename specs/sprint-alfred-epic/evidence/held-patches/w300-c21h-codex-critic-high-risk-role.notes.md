# w300 — Codex projects carry a second native Critic role, `critic-high-risk`, so a high-effort review keeps its Source return (candidate 21h, finding CGF-03)

Delta on the candidate 21h chain (clone base ac727af4d). Closest accepted criterion: AC-108 (PRD and Spec unchanged). Built by a Goldfish in a clone that carries the chain; delivered as a held patch.

## Why

Every Codex Critic round went out as `spawn_agent` with `agent_type: "default"` and model and `reasoning_effort` set on the call, because the projected role `critic` carries one fixed effort. `issueCriticSourceReturn` accepted only the agent type `critic`, so such a round never got a Source return and was recorded as `caller-authored-fallback`, which then needed a separate human acknowledgement at the close (CGF-03, CGF-20). PO decision 2026-11-09: a second projected Codex role.

## What it changes (all under plugins/pipeline-core/)

- `lib/runtime-projection-v3.mjs`: `CODEX_CUSTOM_AGENT_METADATA["critic-high-risk"]`, with the SAME developer instructions as `critic` (one shared constant, not a copy). The frozen V2 kernel does not enumerate the new file, so it follows the consult-advisor pattern: `projectValidatedIntent` adds every `codex-custom-agent-v3` manifest target the kernel did not return, projected from the baseline when the file exists and from the role seed when it does not; `readRuntimeProjectionV3Baselines` reads the new path (absent-safe).
- `config/runtime-projection-v3-owned-keys.json`: new target `.codex/agents/critic-high-risk.toml`, owned keys `model` and `model_reasoning_effort`, cell `{kind: duty, dutyId: critic_high_risk}`. No `decision` field: no decision number exists for this role, and a hand-edited value is still re-projected (the plan only lists a decision conflict for targets that carry one).
- Effort and model: the existing seed leaves `model` and `model_reasoning_effort` empty and the projector fills them from `routing.duties[<dutyId>].codex` of the validated `pipeline.user` intent, whose Core-owned default is `runner-profiles-v3.json` `duties.critic_high_risk.codex`. The new role therefore ends up with model `gpt-6-sol` and effort `max` (`critic` keeps `critic_normal`: `gpt-6-sol`, `medium`). The briefing said "high"; the coordinator settled that the role takes the registered value, `max`. No new configuration key.
- `lib/critic-source-return.mjs`: the stop hook treats `critic-high-risk` exactly like `critic` (also with the `pipeline-core:` prefix); every other agent type, `default` included, stays `not-applicable`.
- Every list that named `critic.toml`: `lib/runner-profile-migration-v3.mjs` (the classifier, legacy and slim seed tables), `lib/project-onboarding-v3.mjs` (`freshBaselines`), `lib/project-pipeline-footprint.mjs`, `lib/governance-scope.mjs`, `lib/guard-devplan-policy.mjs` (`GENERATED_CODEX_PROJECTION_PATHS`), `lib/codex-host-layout.mjs` (`CODEX_PROJECT_AGENT_PROFILES`, kept sorted), `lib/project-uninstall.fixture.mjs`; `scripts/project-reset.mjs` is manifest-driven and only a comment changed.
- Launch instruction: `skills/pipeline-start/references/happy-path.md` (Critic path, the line after `session-critic-finalizer.mjs admit`) and the `dispatch-critic` step of the critic runbook, which is generated: the text lives in `lib/runbook-paths.mjs`, and `runbooks/critic-path.v1.json` and `runbooks/index.v1.json` were regenerated by `generate-runbook.mjs` (no hand edit; `--check` is the drift test). A Codex Critic that needs a higher effort uses `agent_type: "critic-high-risk"`, never `default`.

## An existing project whose `.codex/agents/` lacks the new file (measured, no new manual step)

- The owned-key manifest drives every consumer, so a missing owned file is handled exactly like any other: the plain migration plan names it as a baseline fault (`declared runtime baseline is missing`), and `validateV3BootstrapAuthority` refuses with `v3_plan_not_noop` until the existing route runs; the onboarding lifecycle plans with `initializeMissingRuntimeForSlimV3` and reaches `runtime-initialization-required` then `plan-runtime`; that plan carries the file as a first-time target (before: absent), and the existing activation writes it. This is why the new path is in all three seed tables: without the slim seed a Claude-only project would have thrown on the missing `.codex` baseline.
- Proven in `project-onboarding-v3.test.mjs` (extended portable-seed case): delete the new file after the runtime initialization, the initialization plan changes exactly that path, activation restores it byte-identical.

- Runtime projection V2 files and tests (retired schema).
- The repository's own tracked `.codex/agents/*.toml` source role files (outside plugins/pipeline-core); the runner-profile-migration-v3 case count stays 61 (its case ids are pinned in harness config outside the patch scope), so the new assertions sit inside existing cases or in suites without that registry.
- No Claude or Antigravity behaviour changes: the new target is projected only where Codex targets already are.
