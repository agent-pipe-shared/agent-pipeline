# w317 — A read-only search is no push attempt, and a refused read offers no override (candidate 23)

Delta on the candidate 23 integration state (clone base 7ecd5f42ebf, one change commit on top: tests first, then the change). Closest accepted criterion: AC-108 (PRD and Spec unchanged). Built by a Goldfish in a clone; delivered as a held patch that the PO applies (`hooks/guard-push.mjs`, `lib/guard/evaluate.mjs` and `lib/guard/grammar-denials.mjs` are kernel paths, `NEVER_LIFTABLE_KERNEL_PATHS`).

## What

1. **`hooks/guard-push.mjs`: a second-stage proof for a read-only search (part 1).** `commandIsGitPush` stays as broad as it was (the Q12 option-B marker rule is untouched, `lib/git-cmd.mjs` is not edited). After the existing `provenNonPushMarkerCandidate` stage, the new `provenReadOnlySearch(cmd, projectDir)` admits a candidate only when ALL of these hold, each decided by the shared closed shell grammar and no parser of the guard's own:
   - the whole command is admitted by `isReadOnlyDiagnosticCommand` (so the flags, the paths, the bounded pipelines, the `&&` bound and the trailing `2>/dev/null` are exactly what a plain read already gets);
   - every `&&` part (`splitTopLevelAndChain`) parses with `parseGuardCommand`, which refuses an active `$` or backtick even inside double quotes, and a `;`, `&`, parenthesis or unterminated quote anywhere;
   - the first segment of every part is `rg` or `grep`, and every other segment of a pipeline is `rg`, `grep`, `head` or `tail`.
   Then no word of the command is an executable other than those four, so a `git` word anywhere in it is an argument, i.e. data, and no push can run. The reproductions `rg -n "git-guard GIT-03.{0,700}" docs/state.md` and `rg -n "(git -C|worktree)" docs` (and the single-quote, grep, pipe and `&&` spellings) now pass the guard with no output. The refusal text for every other candidate is unchanged.
2. **`lib/guard/evaluate.mjs` + `lib/guard/grammar-denials.mjs`: no override for a refused read (part 3).** `GUARD-READ-SCOPE-OUTSIDE-ROOT` is printed only for a command the grammar admits in every respect except that a read target lies outside the project root (the three classifiers `isOutsideRootReadOnlyAndChain`, `isOutsideRootBoundedDiagnosticRead`, `isOutsideRootSingleCommandRead`). For that code the refusal no longer asks the human-override planner for a route: no plan command, no "Human override available", no "No human override route is offered". `READ_SCOPE_DENIAL_REMEDY` gets one line that says a read needs no human override and names what is admitted (shell reads inside the project root and of the plugin's own files, the native Read tool for one exact file elsewhere). A mutating command (`GUARD-CROSS-REPO-MUTATION`) keeps its override text; it never goes through this code.
3. **Tests.** New file `hooks/guard-push-read-search.test.mjs` (9 allowed spellings, 8 refused ones, the marker refusal kept) and three new cases at the end of `hooks/guard-lifecycle-ready.test.mjs`: the read refusal prints no override while a mutation keeps it (rows: `cat` and `rg` of a credential-named outside file, `cat` of a dot-dot spelling; a piped, chained or `2>/dev/null` read of a credential-named outside file keeps its operator/redirect/parse code on the base and is not outside-root classified, so it is not asserted); the two part-2 characterizations (green on the base).

## Why part 1 is safe

- Admission needs the shared grammar's yes for the whole text first, so nothing the grammar refuses (a redirect other than `2>/dev/null`, `tee`, `rg --pre`, `-R`, a recursive tree with a secret name) becomes admitted.
- The tokenizer (`parseGuardCommand`) marks a token as expanding when it holds an unquoted `$`, or a `$` or backtick inside double quotes, and refuses such a token unless it is exactly `$PWD`; a single-quoted `$(git push)` is literal and stays data. So a substitution the shell would run is never inside a proven command.
- The executable of every segment is checked by name, so `rg x | git push`, `rg x && git push`, `rg x ; git push` and a bare `git push` are not proven (the last two never even parse). The tests pin each, plus `rg x $(git push origin HEAD)`, `rg "$(git push)" .` and the backtick form.
- It cannot widen a push: a command that is a push is not made of rg/grep/head/tail executables.

## Decisions taken inside the briefing

- The proof sits in `guard-push.mjs`, next to the existing second-stage proof, and not in `lib/git-cmd.mjs`: `git-cmd.mjs` has no imports and is the shared classifier of the Codex and Antigravity guards, which only use it to decide whether to run `guard-push.mjs`; the final decision is `guard-push.mjs`'s on every runner, so one edit covers all three. Importing the shell grammar into the classifier would add a kernel edge to a pure module.
- `head` and `tail` are allowed only as non-first pipeline segments because the grammar admits `rg ... | head -N`; `cat` is not (the briefing names rg and grep).
