# w310 — A scanner finding is discounted only inside a digest field of a Pipeline schema file (candidate 22 follow-up)

Delta on the candidate 22 follow-up chain (clone base 8627df377, two commits). Closest accepted criterion: AC-108 (PRD and Spec unchanged). Built by a Goldfish in a clone; delivered as a held patch. Finding: CGF-06 of the Codex greenfield report (generated Pipeline files carry digests under key-shaped field names; the secret scanner read them as credentials). PO decision: wire the existing classifier narrowly into the gitleaks adapter; no rule-file change.

## What

1. **`lib/generated-artefact-schema.mjs` and its test (copied, not rewritten).** Taken byte for byte from the held patch w308 (blob ids `ba221cd90` and `41ecb0aa2` match the patch header; the module holds a literal byte-order mark in one regex, so it was extracted by script, not retyped).
2. **`scripts/security-adapters/gitleaks.mjs`.** After the exact-match `.gitleaksignore` suppression has produced the retained findings, a finding is dropped only when ALL hold: its rule is `generic-api-key` or `sentry-access-token` (the two rules measured to read these digests; the config's own ledger allowlist names the same pair); it is a one-line finding whose `Secret` is a bare lower-case hex digest (32..64); its file is one physical, regular, in-root file of at most 4 MiB that `classifyGeneratedArtefact` accepts (`pipeline-generated`); and exactly one string field that the classifier lists as a digest field holds that digest on the finding's own line. The field is located from the finding, not from the file: a small position-aware reader of the (already valid) JSON yields every object-property string with the classifier's path syntax and its line; candidates are the fields on `StartLine` whose value equals `Secret`; when two fields on one line hold the same digest (compact one-line JSON) the finding's match text must name the key, else it stays. Anything unreadable, missing, outside the root, oversized, non-JSON, without a Pipeline schema id, with a non-digest value, with a digest embedded in a longer string, in a key, in an array element, or on another line stays a finding. CRLF, a byte-order mark and the absolute path gitleaks reports (normalised by the existing path step) are handled; the whole path is platform neutral.
3. **Accounting, additive.** `run()` returns `discounted: { policy: "pipeline.gitleaks-generated-digest-field.v1", findingCount }` next to the existing `ignored` block. `scripts/security-scan.mjs`: `scannerEntry` copies it into the v1 scanner entry (as it already does for `ignored`); `formatScannerLine` appends ` -- discounted: N finding(s) in digest fields of generated Pipeline files (<policy>)` only when N > 0, so every existing printed line is unchanged. The capability contract text names the exception.
4. **Tests (in the existing adapter suite `gitleaks.test.mjs`, 10 new cases, written first and run red against the original code; the red run covered the first 8, all failing, because the `discounted` block did not exist).** Positive: absolute and relative finding paths, CRLF + byte-order mark, compact one-line JSON with the key named in the match text. Negative, each with injected findings: a key-shaped non-digest value (and an upper-case digest, and a digest with a suffix) in a schema file; a digest in a file with no schema, a foreign schema, a malformed schema id, a top-level array; a digest in a field the classifier does not list (embedded, as a key, as an array element, reported on another line); a missing, non-JSON, oversized, directory, outside-the-root or non-string path; another rule on the same field; a mixed report. One case runs the real scan runner with a fixture gitleaks and checks the v1 entry, the printed line, and that the v2 evidence is still built and judged. One case runs the REAL gitleaks binary on the measured names (`idempotencyKey`, `scopeKey`, `reuseKeySha256`, `courseKey`): the Pipeline schema files (pretty with CRLF and a byte-order mark, and compact) leave no finding and are counted, the same content under a foreign schema still trips the scanner.

## Why

- A path-wide ignore, a rule-file change, or a discount keyed on "a digest exists in the file" would hide a real credential next to a digest. The exception follows the finding to one field of a file whose own schema is verifiable.
- Nothing disappears silently: the count has its own policy id and is printed.

## Not changed (and why)

- `.gitleaks.toml` and `config/security/gitleaks-default.toml`: pinned byte-equal, untouched.
- `.gitleaksignore` handling, the near-miss diagnostic, and the exact-match order: unchanged (the exact authority is tried first; the exception only sees what it left).
- The v2 evidence (`coverage.ignored` is a string array in a closed schema; the evaluator, the fixture matrix and the v2 writer need no change and their suites stay green). The count is in the v1 scanner entry and on the printed line, not in the v2 envelope.
- The Critic preimage files and every guard file: untouched. `harness/verify-suites.json`, the case-completion registry and the inventory: outside this patch.

## Restated in place (QG-04, nothing weakened)

- Three existing adapter cases copy the adapter alone into a synthetic plugin tree; the adapter now imports its sibling `lib/generated-artefact-schema.mjs` (every installed plugin ships it). Each fixture now also copies that one file; their assertions are unchanged (helper `copyGeneratedArtefactClassifier`, with a comment).
- The real-binary case "wires the repo's .gitleaks.toml" used a control copy that carried a Pipeline schema id and exactly the digests this exception now discounts, so its "control still trips" assertion would have measured the wrong layer. The control copy now carries a foreign schema id and is otherwise identical (with a comment); all its assertions are unchanged, and the Pipeline-schema copy is pinned by the new cases.

## Not proven / open

- `lib/generated-artefact-schema.test.mjs` is new and needs registration in `harness/verify-suites.json`. Neither `scripts/security-adapters/gitleaks.test.mjs` nor `scripts/security-scan.test.mjs` is named in `harness/verify-suites.json` (searched by file name); whether another mechanism runs them was not established, so their registration is unverified (Coordinator). `gitleaks.test.mjs` gained cases, so any case-count registry and the inventory need the usual rebaseline. The architecture map may need the new `lib` module assigned.
- The two-equal-digests-on-one-line disambiguation by the match text was proven with injected findings only; the real-binary case used distinct digests per field, so the real tool's match shape for that case is unexercised (a mismatch blocks, the safe direction).
- Real gitleaks line behaviour was exercised for the four measured key names on pretty CRLF input with a byte-order mark and on compact one-line input only; a gitleaks version that reports a multi-line match or another line for a digest field would block (safe direction), not discount.
- The rule limit (`generic-api-key`, `sentry-access-token`) is an additional narrowing of the briefed condition; another rule that reads a digest field would stay blocking until a measured case names it.
- Duplicate property names in one JSON object are located by line; the classifier sees the last value. A digest on a shadowed occurrence is discounted only when the final value (the classifier's view) is a digest field too, so a non-digest final value is never excused.
- The full Verify, an independent Critic review and PO acceptance are pending (Coordinator).
