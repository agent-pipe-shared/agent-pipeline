# w181-lb5 — onboarding leaves a draft in the EL-19 scope, bound projects migrate, every state has a repair (candidate 19c, late-binding build step 5) — CHECKPOINT, see "Not changed / not proven"

Delta on w180 (the clone base is the repository state plus the delivered held patch w180, because both edit the same files). **Apply order: w180 first, then this patch.** `git apply --check` against the repository alone is expected to fail until w180 is applied; against the repository plus w180 it exits 0 (checked in a chain clone).

Criterion binding: AC-108 is the closest existing accepted criterion; this is a fresh bounded attempt under its unchanged Spec text. The PRD and the Spec are unchanged. Design source: `docs/adr/draft-late-binding-of-prd-and-spec-at-the-approval.md` and the PO decisions of 2026-11-04 (marker `sealed: false`, one prepared plan and one signature, bound-but-unapproved projects stay locked while `reopen-design` is always executable, no state is a deadlock).

## What it changes

- **One shared scope predicate.** `lib/authority-seal-reader.mjs` exports `inSealScope(profile)` (`profile !== "mini"`, the EL-19 scope as the seal plan already approximated it from the package profile). `buildSealPlan`, `prepare-seal` (`scripts/pipeline-state.mjs`, which carried an inline copy) and the onboarding bind all read it from there. The reader module is already a kernel pin; no new module was added.
- **Bind trigger by scope (`lib/onboarding-continuity.mjs`).** The promotion / coordinator bind (`bootstrap-bind-apply`, `kickoff promote`) writes `continuity.authority` through `promotionAuthority(profile, authority)`: a profile in the scope leaves the unsealed draft (`sealed: false`, paths only, `result: null`); `mini` keeps today's bind of the digests byte for byte. The digests of the promotion time stay in the promotion plan (`plan.authority`) and in the private history entry (`prdSha256`, `specSha256`, `designInputSha256`) as provenance. The four checks that compared the promoted state's digests (plan validation, both replays, the cleanup-recovery candidate) now go through `promotionBinds(...)`: for a scope profile the state must be the draft of exactly that path, for `mini` the sealed shape with the same digest; a draft never matches a digest promotion and vice versa. The kickoff seed (revision 0/1, profile not yet known) is untouched.
- **Migration is the reader and the exits only.** No State write migrates a project. `pipeline-state.mjs inspect` gets one read-only key `sealSituation` (`pipeline.seal-situation.v1`): `situation` is `none | draft | bound-unapproved | sealed` (`invalid` for an unreadable authority shape), `plan.status` describes `scratch/seal-plan.json` (`none | current | presented | stale | drifted | unreadable | orphaned | documents-missing`), `next` is the typed next command (`submit-plan` before the submission, then `prepare-seal`, `present-plan`, `approve-plan`; none for a sealed package) and `exits` always lists `reopen-design --by <name>` (a draft also lists `prepare-seal`). A bound and plan-approved project is `sealed` and unchanged; a bound but not approved project is `bound-unapproved`, stays locked as before, and the readback names `reopen-design`. The guard tripwire text that refuses a direct edit of a bound document already names `reopen-design --by <name>`; the test pins it through the readback, the text was not rewritten.
- **Every state has a repair (walk of the state machine, `lib/authority-seal-plan.test.mjs` LB5-4 to LB5-11, real State fixtures):** draft without plan (`submit-plan`, then `prepare-seal`), draft with a prepared plan (`present-plan`, `approve-plan`; `reopen-design` voids the plan), stale plan (`prepare-seal`), PRD/Spec edited after the plan (`prepare-seal`, drift named), unreadable or orphaned plan file on a draft (`prepare-seal` replaces it), sealed (nothing; `reopen-design` as before), bound-unapproved (`reopen-design`, then `submit-plan` re-binds as before), plan file on a sealed package (`prepare-seal` retires the stray file, State untouched; the command still answers `PSP-ALREADY-SEALED`). `writeSealPlanFile` no longer refuses a link or multi-link plan file: it replaces it by name with the atomic rename and never writes through it (only a directory at that path is refused). For each case the repair command is checked against the lifecycle guard admission (`sanctionedPipelineStateArgs`), and the next command is run to prove the state it leaves works.
- **Happy path and runbooks.** `skills/pipeline-start/references/happy-path.md` and `lib/runbook-paths.mjs` (the plan runbook is generated: `runbooks/plan-path.v1.json`, `runbooks/index.v1.json`, regenerated only through `scripts/generate-runbook.mjs`) now say: in the PRD release scope the design package is a draft, review it, `prepare-seal`, present the plan, the one signature seals; `reopen-design` is executable in every state. New runbook step `prepare-seal` (closed catalogue shape).
- **Follow-up of w180 (design-input provenance).** `lib/onboarding-continuity.test.mjs` LB5-3 exercises `readPromotionDesignInputCapture` against a real private promotion history (kickoff-only history and no history read `absent`, the promoted history `present` with the real digest, an altered design input `drift`).
- Onboarding cases LB5-1 (draft written, history keeps the digests, replay, reconstruct, PRD edit in the draft stays valid) and LB5-2 (mini binds the digests byte for byte); the case counter pin of the corpus moved 324 -> 327.

- No new module and no new suite: nothing was added to `harness/verify-suites.json`, the capability inventory, `NEVER_LIFTABLE_KERNEL_PATHS` or the threat model.
- The kickoff seed bind (revision 0/1, profile unknown) is unchanged; the recovery candidate compares `entry.planPath`/`entry.specPath` with the draft paths (a promotion whose PRD path differs from its plan path would report no candidate).
- Exact-command exits: `exits[].command` of the readback carries the absolute path of the running script; the placeholder `<name>` stays.

## Elephant completion on the 19c chain (2026-11-04)

The dispatch ended at its tool budget; the Elephant ran the suites the Goldfish had not run, in the slice clone built on the chain with w180, and added what they found. The suite figures below were measured in that slice clone, whose chain lacked w179; the `...rebased.patch` is the same change cherry-picked onto the chain with w179 and w180 (the script applies it after w180). The figures are re-measured on the integrated clone by the Full Verify.

- **Defect found by the onboarding suite (not by the Goldfish's cases):** the COORDINATOR-sourced bootstrap bind (`buildCoordinatorSourcedPromotionPlan`, the route the greenfield onboarding takes) built its continuity through `initialContinuity` with the bound digests and bypassed `promotionAuthority`, so 14 bootstrap-bind cases (OBC267 to OBC299) failed with `promotion continuity postimage is invalid`.
