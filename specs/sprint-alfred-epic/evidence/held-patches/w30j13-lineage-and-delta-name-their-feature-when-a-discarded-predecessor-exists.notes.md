# w30j13 — the lineage and delta verbs name their feature when a discarded predecessor is retained (candidate 30j, C30J-J13)

Applies AFTER the integrated 30i tree (the clone base9): the patch is the delta `69ac3798…..HEAD` on that tree, so `git apply --check` against the plain repository HEAD is expected to fail and against the integrated 30i tree to pass (printed `exit 0`).
Criterion binding: AC-112 is the closest existing accepted criterion; the PRD and the Spec are unchanged. The Critic is suspended by the PO for candidates of this repository and no Full Verify ran: this change is verified by tests only.

## Defect (verified in code, reproduced RED first)

A consumer feature had a DISCARDED predecessor whose registration is retained (manifest and Critic review unit both present). The review ran and was consumed, yet
`register-feature-package.mjs --root <root> --add-review-lineage --packet <id>` stopped `FPR-LINEAGE-FEATURE-AMBIGUOUS`: `addCriticReviewLineage` counted every `specs/<id>` with a manifest and a review unit and demanded exactly one.
The delta verb (`addCriticDeltaRequest`) had the same rule (`FPR-DELTA-FEATURE`), and the finalizer writes the lineage through the same function, so its automatic lineage write came back `not-written`.
RED: the new case J13-1 failed with exactly `FPR-LINEAGE-FEATURE-AMBIGUOUS ... (feature-a, feature-b)` against the unchanged code; the delta cases J13-4/5 failed with `FPR-DELTA-FEATURE` before the delta change.

## What it changes (all in `lib/feature-package-registration.mjs`, `scripts/register-feature-package.mjs`, `scripts/register-feature-package-readback.test.mjs`)

- Lineage: with ONE candidate feature nothing changed (same code, same refusals). With several, every candidate runs the SAME derivation as before (identity, consumed-claim binding, history, compile). The binding is the consumed course claim: the compile compares the claim's `courseSourceSha256`/`courseDecisionSha256` with the course of THAT feature, so only the feature whose course the packet belongs to compiles. Exactly one such feature is chosen; an idempotent replay (the lineage of this packet already registered) counts as a match, so a repeated call answers `already-registered` with no second record and no change of the manifest.
- Zero or two matches: `FPR-LINEAGE-FEATURE-AMBIGUOUS` whose text lists each feature with its own refusal code and names the full command with `--feature <id>` per feature.
- Selector `--feature <id>` (CLI, trailing; lineage and delta forms only; combines with `--stage` and `--confirm-full-round`; every other composition is `FPR-ARGS`): validated. Unknown id: `FPR-LINEAGE-FEATURE-SELECTOR` / `FPR-DELTA-FEATURE-SELECTOR`. Lineage selector that the claim does not bind while another feature is bound: `FPR-LINEAGE-FEATURE-SELECTOR-CONTRADICTS`, naming the bound feature and the rerun command; nothing is written. A bound selector proceeds like the derived choice.
- Delta (no packet exists there; the binding is the registered lineage tail): with several features the features the State records as discarded (`discardedFeatures`, the PO's recorded decision; the CLI passes the State it already read) are left out and the rest decides. Derived, never stored. The S3 successor relation (`supersedes` in the successor's manifest) is a second evidence only and alone retires nothing: with `supersedes` but no State record the verb refuses `FPR-DELTA-FEATURE`. The chosen feature must still hold a registered lineage (`FPR-DELTA-NO-LINEAGE`), so a selector naming a feature without a round is refused; a selector naming a feature the State records as discarded is refused `FPR-DELTA-FEATURE-DISCARDED` (a predecessor may well hold its own rounds) and the refusal names the successor's command. If leaving the discarded features out does not leave exactly one: `FPR-DELTA-FEATURE` naming `--add-delta-request <input.json> --feature <id>` per feature.
- Usage line and `--help` carry `[--feature <feature id>]`; the substrings `--add-review-lineage --packet <packetId>` and `--add-delta-request <input.json>` stay intact (pinned elsewhere).
