## What the patch changes

1. New exported `preflightCriticDispatchWithAdmitRequest(input, deps)` in `scripts/critic-dispatch-preflight.mjs`; the command line prints it instead of the coverage result. It adds, to a `packet-ready` exact-range result only:
   - `admitRequest`: the complete closed request for `session-critic-finalizer.mjs admit`. `schema` is v2 for a feature package (with `review.courseContext` = the course context the preflight ran with, so admit reproduces the same preflight) and v3 otherwise (with `review.genericBatchRef`). `review.base` is the base the CALLER gave (for an effective full round the course base, not the reported genesis), `candidate`, `specPath`, `guardrailPaths`, `evidencePaths` come from `dispatch.reviewerInput`, `priorCriticEvidencePath` from `coordinatorOnly.priorCriticEvidence`, `correctionInputBindings` only when a bindings file was given. `projectId` is the calibration project name lower-cased (`project/pipeline.json`, then `.claude/pipeline.json`), `packetId` is 16 random bytes as 32 hex, `trigger` is the applied Critic row (`criticRequired.appliedRow`) of the matched dispatch record when it is T1, T2 or T3 (the triggers admit has), else `T1` (the strictest row, what admit itself defaults to; it selects the high-risk Critic duty, so it cannot lower a check); the next-step text says which of the two it is. `taskId` is the given `--task-id` (already admission-checked) or the one task id the review admission accepts.
   - Everything only the caller owns is an explicit typed placeholder `<FILL path: hint>`: `sessionId` (the id of the fresh Critic session, unknown before launch), the six `route.*` fields (the preflight does not select a runner), `verdictPath`, `event`, `projectId` when no calibration names one, `taskId` when unresolved, and `review.genericBatchRef.*` (printed by `register-batch`).
   - `admitCommand`: argv `node ${PIPELINE_PLUGIN_ROOT}/scripts/session-critic-finalizer.mjs admit --root <root> --request scratch/session-critic-finalization-request.json`.
   - `nextStep`: write `admitRequest` verbatim to that file, fill only the listed placeholders, run `admitCommand`; for a non-feature review it names `register-batch`; for an Opus route it points at `criticDispatchPromptLines`.
   - `taskIdResolution` (only when unresolved): `{ status: "unresolved", candidateTaskIds, reason }`; the reason names `--task-id` and the candidate ids (the matching ones when several match, else the Critic-required records that could apply). The result never refuses for this: it stays packet-ready with a `taskId` placeholder.
   - `criticDispatchPromptLines` (only when the registered Critic route resolves to an Opus model): a `Batch scope (MP-07): the reviewed range <base12>..<candidate12> (<n> changed files in <m> top-level paths), one batch.` line and a `Rationale (MP-07): ... critical architecture or security review of this one batch only.` line, in the shape `lib/dispatch-policy.mjs` admits unchanged. The route is `duty.critic_high_risk` (the duty `trigger: T1` selects) read from the registered V3 registry for the runner (`codex` when a Codex session id is in the environment, else `claude`); a selector that does not name Opus (and any unavailable cell) carries no lines.
2. `lib/session-critic-finalizer-read.mjs` (the read half, no write API): `ADMIT_REQUEST_PLACEHOLDER`, `admitRequestPlaceholderPaths`, `describeOpenPlaceholders`. `scripts/session-critic-finalizer.mjs` `validateCliRequest` (admit and finalize) now refuses a request that still holds a placeholder with `SCF-REQUEST-PLACEHOLDER` and a detail naming the open fields (siblings written `route.*`), before the generic shape check.
3. Why a wrapper and not the library result: the finalizer binds `sha256(canonical(preflightCriticDispatch(...)))` at admit and again at finalize (`SCF-PRELAUNCH-BINDING`), so a fresh `packetId` inside the library result would change that digest on every call. The library result and the coverage entry point (`preflightCriticDispatchWithCoverage`) are byte-identical to before; a test pins both.
4. Tests, added to existing registered suites (no new file): `scripts/critic-dispatch-preflight.test.mjs` (3 cases: the printed admit fields and the unchanged library result; `--task-id` given, zero and several targets; the Opus lines pass `dispatchFindings` unchanged with a control that the same prompt without them is refused, plus a non-Opus registry and the Codex route carry none), `scripts/session-critic-finalizer.test.mjs` (2 cases: a generic-batch request and a feature-package request, each refused by name while placeholders are open and admitted by the real CLI once only the placeholders are filled).

## Not changed

- The skill, agent, role, template and protocol texts (pinned): the next-step text lives in the printed result, not in them; the skill still describes the request by hand, which stays correct.
- `observe-critic-preflight.mjs` (the explicit collection controller) keeps the library producer as its port and so prints the library result without the admit fields; switching its port would put the fresh packet id into a path whose bytes are pinned as "the exact direct-CLI protocol".
- `CLI_HELP` of the finalizer is unchanged (a `--help` pin lists the keys); the placeholder refusal carries its own text.
- A current-artifact review scope gets no admit request (admit takes an exact range only and fails `SCF-RANGE` for it).
- `signedQualityImportAnchor` requests are not generated.
- No packet, file or state is created: the coordinator writes the request file itself.

## Not proven

- No live greenfield run of the Critic chain through a real Claude coordinator with the printed request; the admit step is exercised through the real CLI entry (`runSessionCriticFinalizerCli`) on fixture repositories.
- The trigger is read from the matched record's applied row only for T1 to T3 (admit has no T4 or T5 trigger); with no matched record, or a T4 record, it is the strict default `T1`, which the coordinator may change (T1 and T2 select the high-risk Critic duty, T0 and T3 the normal one; both are Opus on the registered Claude route).
- The Opus detection reads the registered default cell; a project whose session selects another model for the Critic duty is not observed here (no runner probe, by design).
- `describeOpenPlaceholders` keeps the refusal inside the 200-character CLI detail for the placeholders the printer emits; a hand-made request with many unrelated placeholders may be cut.
