# w30j12 — the plain-language card also opens the guard-override and design-approval signing confirmation (C30J-J12, queue C30-20 gap)

**Order.** The patch is a delta on the integrated 30i tree (the clone base9), which already holds the w30i9 card module (`lib/critical-action-approval-card.mjs`, `criticalActionApprovalCard`). It does NOT apply to the real checkout before that chain; applied after it, `git apply --check` is clean (measured on the base9 clone: exit 0). An exit 1 against the real repository before the chain is expected. The check test therefore asserts only that the patch is non-empty and touches only the briefed files.

**Criterion.** AC-112 is the closest existing accepted criterion; the PRD and the Spec are unchanged. The Critic is suspended for candidates of this repository (PO 2026-11-16) and no Full Verify runs: this change is verified by tests only; no review was made, and none is claimed.

## What it adds

- `lib/critical-action-approval-card.mjs`: `signingCeremonyCard({ kind, facts, language })` and `CEREMONY_CARD_KINDS` (`guard-override`, `design-approval`), in a table of their own. `CARD_KINDS` and the twelve `authorize-critical` kinds are untouched (the existing unit case that pins the table to the command's kind list stays green). Same six labelled parts, same labels, same end line (`-----`), English and German by the `humanFacingLanguage` the confirmation already resolves.
- `scripts/po-human-approval.mjs`: the exported pure helper `signingConfirmationCard({ requestSchema, request, record, language })` and one call-site change in the `sign-intent` branch. `disclosureLines = compactSigningDisclosure({ intentSha256, record, materialArtifact })` is textually unchanged; a new `confirmationLines = [...card, ...disclosureLines]` is what `printDisclosureOnly` (passphrase-protected key) and `requireExplicitConfirmation` (typed token) now receive. The evidence lines and hashes after the card are therefore byte-identical; the request schema, the intent digests, the review-material file and the proofs are not touched, and `compactSigningDisclosure`, `composeDisclosureLines` and the frame are unchanged. The `authorize-critical` and ceremony-start regions of the file are not touched (another dispatch edits them).
- Facts, only from what the ceremony already holds, no new read, git call or schema change:
  - **guard-override** (request schema `pipeline.human-guard-override-signature-digest.v1`): the tool name, the command class, the signed absolute expiry and the number of eligible paths, from `record.fullReviewMaterial` (the structured plan the signature request already resolved to). Raw paths and the denying guard's rationale are NOT repeated in the card; they stay in the redacting evidence lines below it. Sentence sources: arming only after `authorize-by-signature`, the byte-identical retry and consumption on first use (`consumeHumanGuardOverrideCore` sets `status: "consumed"`), the expiry check at consumption.
  - **design-approval** (`pipeline.design-approval-request.v1`): feature id, PRD path, Spec path, companion count, review-round count, verdict and open-finding count, and the candidate commit, from the validated request (`binding`, `approvalIntent.value.candidate`). The request holds no expiry, so the card says "the request carries no expiry" and what the approval is bound to (exactly these sources, reviews and commit) instead of inventing a time. What it releases is stated from the existing line and ADR-0085: the signed decision goes to `approve-plan`, which must consume it independently; when the verdict is `open-findings` the card states the open-finding count and that signing accepts them knowingly (the same fact `describeOpenReviewFindings` already prints).
  - A fact that is absent or malformed is left out (a count must be a positive safe integer; a string must be one bounded line); a missing guard-override expiry prints "This confirmation does not show the expiry."
- **Decline.** `sign-intent` with a passphrase-protected key asks for no typed token, so the decline part says what is true on both routes: nothing is signed and no proof is written unless the human confirms (or enters the passphrase); the request file stays in `scratch/` without a signature and grants nothing. It does not repeat the `authorize-critical` sentences about the approval directory and being overwritten by the next run (false here), and promises no message to the agent.

No live signing run with a real key and a terminal was made (`not verifiable` here). The full Verify run was not made. `docs/po-human-approval.md` does not describe the card (outside the write list).
