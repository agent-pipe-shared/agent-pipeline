# w238 notes: the registry checks each object once, heals once, keeps source digests and prunes settled members

Slice C19I-W238-REGISTRY, closest accepted criterion AC-108 (PRD and Spec unchanged), PO decision 2026-11-06 (options document `native-checks-options-2026-11-05.md`: O7, O8, O3 (ii), O9, open question 4). Held patch `w238-...patch` (delta on candidate 19h, `79899694d`); it changes `plugins/pipeline-core/lib/session-authority-registry.mjs` and adds `source-digest-memo.mjs` and `session-authority-registry-fewer-checks.test.mjs` (all under `plugins/pipeline-core/lib/`). The native backend, the domain owner, the host state, the hooks and the finalizer are untouched; the registry lock protocol (acquire, ownership re-read, release, the 1.5 s wait) and the publish compare-and-swap are untouched.

All five changes are built. Nothing is left out.

## The platform seam (prerequisite for every count)

What changes: `session-authority-registry.mjs` decided every Windows branch by `process.platform`. It now asks `isWin()`, which is `process.platform` unless a test says otherwise through `setSessionAuthorityRegistryTestSeam({platform, sourceDigestMemoFile, onPlanningBaseline})` (a new export; only an explicit import sets it; setting it also forgets the per-process memos as a new process would). The already-injectable `platform=process.platform` parameters of `sessionAuthorityLockOwner` and `judgeSessionAuthorityLockOwner` are unchanged. With the seam at `win32` and the backend's own `setWindowsOwnedAuthorityBackendTestSeam({platform:'win32', spawn})`, the registry's native branches run on Linux; the new test file's fake spawn emulates the helper (inspect, read, read-source, publish, remove, create-directory) over the real file system, so reads return real record bytes and facts move when a file changes.

## O7 no second inspect of a file read in the same boundary

What changes: `registryClosure` skips the native `inspect` of a file that already has a native witness in the current boundary (`hasNativeWitness`, the witness map of registry lines 98-105). Unknown files have no witness and are still inspected (then refused as `unknown-registry-entry`). Directories are still inspected.
What is given up: only the later time point of a file the same boundary already observed (the options document's O7 give-up). The witness map is also seeded by the lock at entry and by `nativePublish`, so the lock and a record published in this boundary are skipped too; both were natively observed in this boundary.
Native calls: in the test (emulated Windows, backend memo off) a boundary entry used to make one file `inspect` per walked file (catalogue, 12 producer records, members, releases, certificates, the lock); now 0. A stray unindexed file is inspected exactly once.
Case: `C19I-W238-1`. Checks: it asserts zero file inspects after an entry and exactly one (the stray) after planting an unknown file.

## O8 entry heal once per process or on drift

What changes: the migrate/heal at boundary entry is `entryHeal(repo)`. The migration of a catalogue bound to other participant sources (one catalogue read) still runs on every entry. The heal (a full `stateRead` plus the closure walk) runs once per process per repository (`entryHealed`), is retried while it fails, and runs again after a `stateRead` of this process met a namespace drift (`driftFault` clears the repository's mark). `healSessionAuthorityDrift` (the repair verb) is unconditional.
What is given up: an ordinary drift met after the first entry of a process (another process changed a producer namespace meanwhile) is no longer healed silently at the next entry of the same process; the callback's own `stateRead` raises the same `namespace-drift` refusal with its repair command, and the following entry heals. Hooks are short processes, so the first entry of each hook still heals as before. This is the availability change the options document states, not a detection change. What a `stateRead` verifies is unchanged.
Native calls: second entry in one process makes under a third of the first entry's read and inspect calls (test asserts `second * 3 < first`).
Case: `C19I-W238-2`. Not proven: the drift-met-then-heal-again path (the `driftFault` clear) has no dedicated case.

## O3 (ii) persisted source digests keyed on file identity

What changes: new module `plugins/pipeline-core/lib/source-digest-memo.mjs`. `installedSourceSha256` consults it (Windows only, and only on the real lstat/read path, so injected readers in existing tests stay exact) before the native `read-source`: a persisted digest answers only while the file's lstat identity tuple (dev, ino, mode, nlink, size, mtimeNs, ctimeNs, birthtimeNs) equals the stored one; any change re-reads, and the digest is remembered only if the identity is the same after the read. Storage: `%LOCALAPPDATA%/agent-pipeline/authority-source-digest-memo.v1.json`, the directory the backend's observation memo uses (same absolute/normalised `LOCALAPPDATA` rule). Same discipline as the backend memo: closed schema, at most 256 entries and 1 MiB, each entry validated on load (absolute path, 8-part numeric identity, 64-hex digest), atomic rename after merging what another process wrote, every fault is "no persisted answer".
What is given up: a hit trusts the lstat identity instead of re-reading the file, and a forged memo file would be trusted (same trust the options document records for O3; the file is in the user's own application-data directory). A persisted hit also skips the native witness of that source path; nothing else observes source files inside a boundary, so no drift comparison is lost.
Native calls: a source file costs one `read-source` once across processes (test: cold 1, same process 1, new process 0, changed bytes 1, changed mtime only 1).
Cases: `C19I-W238-3` (module: hit/miss by identity, malformed/foreign/oversized/relative/non-hex/extra-key files ignored, entry bound), `C19I-W238-4` (registry: the counts above).

## O9 an override refusal compares only its own producer

What changes: `executeSourceOwnedSessionAuthorityPlanning` reads the baseline (`planningBaseline`: readBaseline, legacy operations, reconcile) of the override producer only, three times (before, after, before the compare-and-swap), instead of all 12 producers three times (36 reads become 3). Still compared for all 12: the strict `stateRead` at the start (it reconciles every producer against its recorded baseline), the catalogue and every producer record reference after the writer ran (`planning-registry-effects`), every retained member (`planning-member-effects`), the closure. For the override producer: all of its own checks (`planning-preexisting-drift`, `planning-authority-operation-effects`, source preimage, namespace root drift, retained member source effects, `planning-unintended-hgo-effects`, postread agreement, journals, final drift).
What moves later / is given up: `planning-foreign-producer-effects` (another producer's namespace contents changed during the planning window) and the legacy-operation comparison of the other 11 producers inside the window. A foreign write during the window is no longer refused at the refusal; the other producer's next `stateRead` reconcile raises `namespace-drift` for it (healed when nothing of that producer is armed or running). `planning-unintended-hgo-effects` does not move: it only ever compared the override producer's own facts. `planning-preexisting-drift` for a foreign producer was already covered by the strict `stateRead` (it now surfaces as that producer's `namespace-drift`).
Native calls: on Windows the other 11 producers' namespace reads (the bulk of the refusal's natives) disappear from the three planning reads; the test counts baseline reads through the seam's `onPlanningBaseline` probe: producer set is exactly `human-guard-override`, at most 3 reads.
Case: `C19I-W238-6`. Honest note: the production edit for O9 was made before its case was written (the case was then run green; its pre-change failure is by construction: the probe and the 12-to-1 reduction did not exist); every other case was written and run red first.

## Prune of settled members (open question 4)

What changes: `pruneSettledMembers` (internal; called at the end of `releaseSessionAuthorityMember` with the state already in memory, soft: a refusal prunes nothing and never fails the release) and `pruneSettledSessionAuthorityMembers({boundary, keep})` (exported verb for a held boundary). For the `native-goldfish` producer, members that are `released` and carry a release record are settled. The newest `SESSION_AUTHORITY_SETTLED_MEMBERS_KEPT` (16, by `updatedAt`, then generation) stay indexed; older ones are retained, not deleted: their member and release files are moved byte for byte under `agent-pipeline/session-authority-abandoned/<stamp>-<hex>-settled-members/` with a `prune.json` marker holding the prior producer record, and leave the producer index (and so the closure walk and every `stateRead`). Order: reconcile check with the smaller member set (must keep the same baseline), marker, file moves (rolled back if a move fails), producer + catalogue publication, certificate refresh. Unreleased members are never touched.
How "settled" maps: the registry cannot see the host-state words integrated-by-commit / cancelled / superseded. It sees `released`, which every terminal release produces (the native producer's reconcile already treats a released member's operation as `terminal-observed`, and tolerates a terminal operation with no member record). A slice settled by commit evidence or by supersession whose member was never released is therefore not pruned. Whether `cancel --started` releases its member (so cancelled slices are covered) was not verified here.
What is given up / risks: (1) `nativeConcurrentPlan` (host state) skips pending states with no member and so loses the foreign-commit proof of a pruned member; only a commit that landed after the current slice's base commit and belongs to a slice settled more than 16 releases ago can be affected (it would surface as `native-concurrent-unowned-head`). (2) `readNativeReservedItemScopes` (host state) treats a pruned binding as not released, but it also skips settled slices through the queue, so a pruned slice that is still unsettled in the queue is the only exposure. (3) For an old session target whose released members are all pruned, a snapshot status moves from `cleared` to `absent`. (4) A crash between the file moves and the producer publication leaves unindexed member files (the closure fails `unknown-registry-entry`, repaired by the existing heal/move-aside route); the same window exists today between publishing a member and indexing it.
(5) The hook's `soft` only softens the baseline-keeping reconcile check: a fault in the marker write, a rename that cannot be rolled back, or the producer publication after the release already succeeded is thrown to the caller (a release that succeeded on disk reports failure; a publication failure after the moves leaves records the producer still indexes but that are not at their path, repairable with the existing move-aside route). Dormant until 17 released native-goldfish members exist. Fix shape if the PO wants it: widen the soft catch to everything after the early returns, or keep prune as the explicit verb and a heal step only.
Native calls: the closure walk reads two files per settled member in every `stateRead`; with 21 settled members seeded the walk reads at least 10 fewer records after pruning 5 (test asserts `after <= before - 2*5`). The measured repository's 27 settled reservations would drop to 16.
Case: `C19I-W238-5`. Not proven: the hook inside `releaseSessionAuthorityMember` is not driven by a case (it needs a full native reserve/release cycle); only the exported verb is. The existing suites that do release native members still pass (see report).
