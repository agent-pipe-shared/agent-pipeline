## What the patch changes

Since 20d the one-shot close commits `audit-bundles/<feature>/<candidate>/` (with `proofs/`) in the close commit. The push approval signs the commit that carries the bundle and the release approval comes later, so neither proof can sit inside it. This patch adds them afterwards as NEW files only (PO tile 2026-11-08), runner-neutral:

1. **`lib/audit-proof-collection.mjs`: `writeAuditProofFollowUp` and `prepareAuditProofFollowUp`.** Adds `proofs/NNN-<kind>.json` (numbering continues after the manifest's own proofs, `wx`, bytes = the same public proof bytes the bundle uses) and ONE list `proofs/follow-up.json` (`schema, candidate, approvedCommit, proofs[{kind,path,sha256,intentSha256}], attributions[{kind,mode,approvedAt}]`). `manifest.json` and `README.md` are never touched. The release step finds the feature's bundle (named after the package candidate, an ancestor of the approved commit; the latest if several), takes the push proof from the private store by `forCommit` (public proof object only, never a key), the release proof from the `--proof` file of the same run, and carries a chat or waiver approval as an ATTRIBUTION record (kind, mode, time), never as a proof. No bundle, nothing to carry, or a second run is a typed status (`no-bundle`, `nothing-to-carry`, `already-followed-up`), never a refusal.
2. **`lib/audit-bundle.mjs`: the verifier learns the follow-up.** `audit-bundle.mjs verify` also checks `proofs/follow-up.json` when present: shape, candidate equal to the manifest's, no path collision with the manifest's proofs, then the same bytes / intent / Ed25519 checks as for manifest proofs (`AB-FOLLOWUP`, `AB-DIGEST`, `AB-PROOF-INTENT`, `AB-PROOF-SIGNATURE`). A bundle without the file verifies exactly as before. `proofFindings` now takes the entry list.
3. **`scripts/release-preflight-cli.mjs`: `recordAuditProofFollowUp`.** After a ready release approval it runs the step above, arms the writer commit capability (G20-66, `armWriterCommitCapability`) for exactly the written files and returns the commit step. `nextActions` becomes: tag, commit step, `git push origin HEAD:refs/heads/main`, tag push (unchanged when there is no bundle). The output carries `auditProofFollowUp`.
4. **`lib/critical-action-authorization.mjs`: `authorizeAuditProofFollowUp`; `hooks/guard-push.mjs` uses it.** The guard admits the branch push of exactly ONE commit on top of the release-approved commit P without a second approval when ALL hold: consumer-shaped project, destination `refs/heads/main`; the commit has exactly one parent P; P has the recorded release approval and the annotated release tag at P (`authorizeRecordedReleaseTag`, the tag push's own check) and a recorded push approval for this remote and destination; P is the published tip `refs/remotes/<remote>/main`; the commit's diff ADDS only regular files (mode 100644, no rename, no change of an existing file) named `audit-bundles/<feature>/<C>/proofs/NNN-<kind>.json` or `.../proofs/follow-up.json` of ONE bundle whose `manifest.json` exists at P with `candidate.commit` C an ancestor of P; exactly one list; every blob at most 16 KiB, a public proof object (five fields, no private key, verifying Ed25519 signature) or the list, the list's paths and digests equal to the added files, and every carried proof EQUALS what the private store recorded for that approval (push: the recorded signed intent; release: a signature-mode approval). In `guard-push.mjs` the `refs/heads/main` publication boundary is not the deciding check for that one commit; the decision is taken after publication mode, the deploy adapters and the manifest gate, with the uncommitted-evidence check and the anonymous-public range check kept. Anything else falls through to the full gate unchanged. The tag push at P is untouched (G20-42b); "together with the tag" is two single-refspec pushes because `parsePushBinding` binds exactly one refspec.
5. **`docs/push-release-flow.md`** (consumer release section, step 4) names the step.
6. **Tests (QG-04: no assertion weakened; two restated in place with a comment).** New cases carry a `C20E-AP` comment: `hooks/guard-push-release-tag-ancestry.test.mjs` (10: admitted follow-up; other path; changed manifest; no release approval; no tag; two commits; private key; unpublished parent; tag push unaffected; a validly self-signed but unrecorded push proof; each refusal also asserts its typed code), `lib/audit-bundle.test.mjs` (4: new files only and the bundle verifies before and after; tampered bytes / intent / signature / candidate; attribution record and invalid proof; bundle discovery from the store), `scripts/release-preflight-cli.test.mjs` (1), `scripts/close-path-e2e.test.mjs` (restated: the consumer walk now has the release add the attribution record to its closed bundle, commits the printed step, the guard refuses the same commit with a stray file and admits the evidence-only one on all three runner identities, the bundle verifies before and after; the old `HEAD == record candidate` assertion now compares the approved commit because HEAD moved).

Not weaker: the only checks the follow-up commit skips are the push approval and the Verify / security evidence that are bound to the earlier commit and cannot be met by a commit that adds no code; the replacement is an exact structural and content check of what is added plus the earlier commit's own approvals. For every other content the full gate is unchanged (the stop condition did not fire).
