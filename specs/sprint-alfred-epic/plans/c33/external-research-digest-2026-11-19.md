# External research digest: file and module bounds for agent-assisted development

Collected 2026-11-19 by the Elephant (web search and page fetches; the pipeline's governed agent roles have no web tools). It is INPUT for the analysis, not a conclusion. Every claim is marked by how it was obtained:

- **[opened]** the page was fetched and read (the figures below are from it; the fetch tool summarises a page with a small model, so a figure is "as reported by the fetch", to be re-checked before it is quoted in a decision record);
- **[search only]** only a search result summary was seen; the primary page was NOT opened; do not rely on it without opening it;
- **[secondary]** a blog or summary of a primary source.

## 1. Opened sources

| # | Source | Date | Kind | What it supports | Caveat |
| --- | --- | --- | --- | --- | --- |
| S1 | Anthropic, "Set up Claude Code in a monorepo or large codebase" (code.claude.com/docs/en/large-codebases) [opened] | current docs | vendor guidance | As a codebase grows, defaults "can fill the context window with instructions and file reads unrelated to the task, costing tokens and degrading Claude's performance". Recommends scoping to the part a task touches: layered per-directory instruction files (root = repository-wide rules only, one per package or subsystem), starting the agent in a subdirectory, `Read` deny rules for generated and vendored code, language-server code intelligence instead of scanning, sparse worktrees, per-directory skills, a plugin when layering stops scaling. States that a single root instruction file either grows to cover every subsystem or stays too generic. | Vendor guidance, not a measurement. Gives no file-size or module-size number. |
| S2 | Anthropic, "How Claude Code works in large codebases" (claude.com/blog) [opened] | current | vendor blog | The agent navigates by traversing, reading and searching, not by an index; "works best when Claude has enough starting context to know where to look". Easier: lean layered instruction files, starting in subdirectories, per-subdirectory test and lint commands, symbol-level search. Harder: vague searches across very large codebases that can exhaust the context before work begins, compiled monorepos with deep cross-directory dependencies. Suggests a markdown codebase map at the root for repos with hundreds of top-level folders, layered across subdirectory files. Mentions multi-million-line monorepos. | Gives no token or file counts. |
| S3 | Liu et al., "Lost in the Middle: How Language Models Use Long Contexts", TACL 2024 (arXiv 2307.03172) [opened: abstract page only] | 2023 / 2024 | peer-reviewed | Performance is highest when relevant information is at the beginning or end of the input and degrades significantly in the middle, also for explicitly long-context models. | 2023-era models; tasks are multi-document QA and key-value retrieval, not code. Exact figures were not on the fetched page. |
| S4 | Chroma, "Context Rot: How Increasing Input Tokens Impacts LLM Performance" (trychroma.com/research/context-rot) [opened] | 2025-07-14 | vendor research report | 18 models (Anthropic, OpenAI, Google, Alibaba families) on needle-in-a-haystack variants, a conversational-memory task (306 prompts, about 113k tokens full vs about 300 tokens focused) and repeated words: performance becomes less reliable as input grows even on simple tasks; focused prompts clearly beat full ones; distractors hurt more with length; authors say how information is presented matters more than whether it fits. | Vendor report; the authors state the mechanism is unexplained and that length is entangled with difficulty; synthetic tasks, not code. No single degradation rate given. |
| S5 | Cao, Yin, Dhingra, Zhou, "Coding Agents are Effective Long-Context Processors" (arXiv 2603.20432) [opened, HTML] | 2026-03 | preprint | Ablation on BrowseComp-Plus with one coding agent: the same corpus (about 100k documents, about 750M tokens) stored as a folder of files vs one single file: 89.0 vs 83.0 with no retriever, 90.0 vs 86.0 with an embedding retriever, 82.0 vs 82.0 with BM25 (a tie). With a folder layout the agent did "coordinate-based reading" (`sed` calls 4.48 vs 0.61); with one file it fell into repeated search loops (`rg` calls 31.05 vs 18.46). Adding retrievers did not consistently help. | 100-example subset; one agent and one benchmark; the authors say the mechanism is inferred from command counts and "remains an open question". About documents, not source code. It is the nearest evidence that file granularity changes agent behaviour, and it shows a benefit of many files over one giant file, not a benefit of 1000 over 3000 lines. |
| S6 | Chatlatanagulchai et al., "Agent READMEs: An Empirical Study of Context Files for Agentic Coding" (arXiv 2511.12884) [opened, first half] | 2025-11 | preprint | 2,303 context files from 1,925 repositories (922 CLAUDE.md, 694 AGENTS.md, 687 Copilot instructions): median length 485 / 335.5 / 535 words, hard to read, 59 to 67 percent edited in several commits, content mostly testing (75.9 percent), implementation details (70.8), architecture (68.1). | Describes instruction files; explicitly does NOT measure the effect of file size on agent performance. |
| S7 | Tahir and Xiao, "Does class size matter? An in-depth assessment of the effect of class size in software defect prediction" (arXiv 2106.04687, EMSE 2021) [opened, first 100k characters] | 2021 | peer-reviewed | 23 Java systems, 11,444 classes, about 2.5M lines, 6,603 defects, 7 OO metrics: size mediates the metric-defect relationship consistently only for coupling between objects (13 of 23 systems); results vary by system; the authors conclude size should be controlled only when evidence shows it matters, tested per system. This contradicts the earlier advice to always control for size. | Java only; 6 proprietary systems; log LOC the only mediator; threats to validity were not read. It is about defect prediction, not about agent suitability. |
| S8 | ESLint, `max-lines` rule (eslint.org/docs/latest/rules/max-lines) [opened] | current | tool documentation | Default `max` is 300 lines; options `skipBlankLines`, `skipComments`; rationale: "Large files tend to do a lot of things and can make it hard following what's going"; "Recommendations usually range from 100 to 500 lines." | A linter default, not an empirical result. The search result summary says the rule is off unless enabled; the fetched page did not state it. |
| S9 | Shopify Engineering, "A Packwerk retrospective" [opened] | undated in the fetch | experience report | A large Rails monolith organised into "a couple dozen buckets" of components built from "thousands of files" and "millions of lines of code"; enforced boundaries by static analysis with todo files for tolerated violations; the todo files grew faster than people could fix them; isolating the base layer with zero violations and zero dependencies was a "resounding success"; domain-based components produced "monstrously large" todo files; the static check could not see runtime dependencies (a package with zero violations could still fail at runtime); "running code, more than any metric, will always be the best indicator of real progress". | One company; no package count or ideal package size is stated; the article does not say what is best for an AI agent. |
| S10 | Martin Fowler's site, "Linking Modular Architecture to Development Teams" [opened] | undated | experience report | Modules are formed along domain seams and each is owned by a small team ("two pizza" team); "Keeping tight control of the bounded context is as important as defining the domains themselves". | Gives no module-size rule and no module count. The cycle-time and reuse figures in it are inconsistent with its own headline claims (17 to 10.3 days is about 39 percent less, the summary says 60 percent), so do not quote its numbers. |

## 2. Seen only in search results (NOT opened; open before relying)

- **Hatton, "Reexamining the Fault Density-Component Size Connection", IEEE Software 1997** [search only, secondary summaries]: claims a U-shaped relation between component size and fault density with medium-sized components best (the "Goldilocks conjecture"); one secondary reading gives about 200 to 400 logical lines (about 400 to 800 physical), not confirmed against the paper; the claim is contested (re-analyses found no relation, and a mathematical-artifact explanation has been proposed).
- **El Emam, Benlarbi, Goel, Rai, "The confounding effect of class size on the validity of object-oriented metrics", IEEE TSE 2001** [search only]: argued class size strongly confounds metric validation; later work (S7) found the effect depends on the system.
- **Skelton and Pais, Team Topologies** [search only]: size a software boundary to the cognitive load of the team that owns it; team size about 9 (maybe up to 15); no number of modules is given.
- **SonarSource, "Cognitive Complexity" white paper** [search only]: argues for a method-level understandability measure instead of cyclomatic complexity; an independent paper (arXiv 2007.12520) argues its validation is incomplete.
- **Leads reported by a search summary that were not verified** [secondary]: a claim that code-repair accuracy "drops sharply between 32K and 256K tokens on LongCodeBench"; a finding that LLM-written context files lower agent success by 0.5 to 2 percent while developer-written ones raise it by about 4 percent; a two-agent ablation finding no measurable effect of context strategy on correctness.

## 3. What this evidence does and does not support (the Elephant's reading, to be challenged)

Established enough to design on:
1. Agents degrade as irrelevant context grows, and what matters is how much task-relevant, focused context the agent gets, not a line count as such (S1, S2, S4, S3).
2. Vendor guidance for large codebases is to scope the agent to the part a task touches, with layered, lean instruction files and a map, and not to rely on reading everything (S1, S2).
3. Very large single files are bad for agents (repeated search loops, coordinate-based reading becomes the only way in), and splitting into addressable units helped in one ablation (S5).

Not supported by anything opened:
- Any specific per-file line limit for agents (1000, 500, 300 or other). The only numbers are linter defaults and recommendations (ESLint 300 default, "100 to 500" recommended) and an unverified secondary reading of Hatton. There is no study that measures agent success against file length in lines.
- Any specific module size or module count for large systems. The sources give principles (domain seams, team cognitive load, tight boundary control) and scale examples (a couple dozen component groups, millions of lines), not numbers per module.
- That more, smaller files help an agent beyond some point. S5 compares one giant file with a folder, not 1000 against 300 lines; the opposite risk (more navigation, more imports, more tool calls) is plausible but not measured in anything opened.

Contested: a universal optimal component size (Hatton) and the confounding effect of size on defect metrics (El Emam vs Tahir and Xiao).

## 4. Facts measured in this repository on 2026-11-19 (stamped candidate 31c plus candidate 32 clone)

- `plugins/pipeline-core/scripts/architecture-boundary-check.mjs`: `DEFAULT_LINE_BOUND = 1000`, rule `over-line-bound` is a blocking finding; the policy file `architecture/boundary-policy.json` may set `lineBound` and carries 103 `over-line-bound` exceptions.
- `plugins/pipeline-core/scripts/architecture-fitness.mjs`: an advisory size report with `DEFAULT_MAX_FILE_LINES = 500` and `DEFAULT_MAX_MODULE_LINES = 2500` (overridable by `sizeBudgets` in `architecture/fitness-model.json`); never an outcome, finding or part of the overall status. So the product carries TWO different file-size numbers (1000 blocking, 500 advisory) and a module budget of 2500 lines, which is far below the size of any real business module and was evidently set for small examples.
- The map: `architecture/map/pipeline-core.md` is 75,441 bytes in one concept file (one Read of it in this session returned a 27,975-token page against a 25,000-token cap, so it cannot be read in one call); `harness.md` 5,361, `schemas.md` 3,934, `governance.md` 1,838, `backlog.md` 868, `index.md` 1,916 bytes; the generated `overview.html` is 2,208,596 bytes (derived, not meant to be read by an agent). The map index lists every module and the concept files are read per module, which does not scale if one module concept file lists 130 public contracts and more than 100 verification entry points.
- The Pipeline's own source (candidate 32 clone, plugin, harness and top-level scripts, without tests): 1160 files, 374,000 lines, 64 files over 1000 lines holding 139,000 lines, 14 over 2000, 4 over 5000 (largest 16,030); 5 modules, one of which (`pipeline-core`) owns about 1030 files; 38 `lib/` files import from `scripts/`; nine folder pairs import each other.
- An agent dispatch gets one module's paths as its write scope (the Goldfish briefing); the map and the module concept file are the context cost of entering a module.

## 5. Questions the analysis must answer (from the PO, 2026-11-19)

1. Is a single numeric file limit the right instrument, and if so which number or range, for which kinds of file (entry point, library, test, generated, data), enforced or only reported?
2. What module size and module count does the product need to support for a large business system (a CRM with many bounded contexts, 0.5 to 2 million lines), and how does an agent get exactly one module as context (map read cost, concept file size, interface-only views)?
3. Does the product, as implemented (blocking 1000-line rule, 500-line and 2500-line advisory budgets, one concept file per module, module write scope per dispatch), support that, and what has to change?
4. What are the defaults the product should ship, which must be configurable, and what should be only reported?
