## 3. Candidate 33: first the bounds, then the remediation (PO decision 2026-11-19)

**The Pipeline does not meet the module and size rules it imposes on projects** (backlog item `backlog/items/2026-11-19-the-pipeline-does-not-meet-the-module-and-size-rules-it-imposes-on-projects.md`). Measured on candidate 32: 64 of 1160 hand-written source files over 1000 lines holding 37 percent of the code, 14 over 2000, 4 over 5000 (largest 16,030 lines), 103 size exceptions, one module `pipeline-core` of about 1030 files, 38 `lib/` files importing from `scripts/`, nine mutually importing folder pairs; the boundary check reports 125 findings on candidate 32 after its exemptions (181 on 31c). Re-measure with `node scripts/arch-measure-summary.mjs .` and `node scripts/arch-measure-size.mjs .`.

**PO's order:** FIRST verify the bounds themselves, only then optimise. Whether 1000 lines per file and the current module cut are right for agents and for real large projects (a CRM with many bounded contexts, hundreds of thousands to millions of lines) is not verified: a very low bound may create too many files, imports and navigation steps. The map is a scaling problem too: `architecture/map/pipeline-core.md` is 75 KB in one concept file and cannot be read in one call. The product carries two file numbers (blocking 1000 in `architecture-boundary-check.mjs` `DEFAULT_LINE_BOUND`, advisory 500 in `architecture-fitness.mjs` `DEFAULT_MAX_FILE_LINES`) and an advisory module budget of 2500 lines (`DEFAULT_MAX_MODULE_LINES`).

**PO's central risk for any rebuild:** it must never create new drift or new status problems; user repositories must not end in states that block themselves or each other ("auf keinen Fall neue Drifts und neue Stati-Probleme"). The Fable plan has to be built around that: the migration of everything that binds the module id `pipeline-core` (`architecture/fitness-model.json`, `architecture/boundary-policy.json`, ADR sidecars with module applicability such as `docs/adr/0009-session-hygiene-lifecycle.json`, `project/architecture-decisions.compiled.json`, map concept files, baseline, generated overview, adoption state), what an older plugin version sees of a newer repository, additive and read-compatible changes only. Splitting the module map is NOT a small item and therefore not part of candidate 32.

## 5. Standing PO rules (distilled from the first machine's local memory; the new machine has its own)

- Chat with the PO in German; repository artifacts stay English. Private consumer project names and the PO's machine paths never go into the repository.
- Parallel work is the absolute standard for everything: independent work goes into parallel dispatches wherever the dependencies allow; code writers only with verified worktree isolation (`git worktree list` right after the launch). Serial needs a stated reason.
- The Elephant is the lead developer: small items (stage-0 fast path, ADR-0101) the Elephant builds itself, large ones go to Goldfish (`pipeline-core:goldfish-*` agent types with the `goldfish-task.md` briefing, never general-purpose with a hand-written briefing). The PO only signs where a signature is technically required; no operator command lists.
- Never fully blocking: every refusal needs a repair the agent or the PO can actually run; a refused operation leaves no state behind.
- Never replace a feature to turn a test green (QG-04: restate or fix the test, keep the good logic). Build all scope fully, no cautious "only up to" defaults; the greenfield test judges.
- The Critic is suspended (no Critic round for candidates unless the PO asks); Full Verify only after install and on the PO's word; report both as "not run", never "done". "Done" is only PO-accepted work.
- Stamp and push candidates only on the PO's call; protected plugin-source commits are made by the PO as human operator when no sanctioned agent route exists; `--by` and any operator label are never invented.
- Heavy suites run one at a time (parallel runs collide on the registry and a direct `node --test` leaves `TMPDIR` at `/tmp`); heal only with no Goldfish in flight; the PO is often away: do not wait on questions, collect them.
- Reusable helpers belong in `scripts/` with a header and a row in `docs/operating-tools.md`; `scratch/` is untracked and the PO works on two machines.
