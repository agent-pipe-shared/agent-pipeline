- **GREP-PUSH (Ruling 81), a decision with a default.** guard-push treats `(`, `)`, `{`, `$` and backtick after a
  git word as a possible hidden push. This is option B, accepted false positives, by your earlier decision. It costs
  calls whenever a commit or `git grep` carries such characters, for example the `(goldfish)` trailer.
  - Default: keep option B with no relaxation. Relief stays procedural (`git commit -F <file>`, `rg` instead of
    `git grep`). The refusal text names those two shapes; that is a tranche-2 message change.
  - Alternative: exempt markers for clearly non-push subcommands. That is a security trade, because
    `git commit -m "$(git push …)"` would then need another guard layer.

- **TR-S2 script exemption (Ruling 90 F2), a decision with a default.** The execution-lane classifier reads the
  content of every script a command runs, and the test files themselves contain credential-shaped fixture strings.
  Once wired, it would therefore refuse `node --test` on its own test file and on `po-human-approval.test.mjs`.
  - **Default:** an `exemptScripts` list, filled from the test files registered in `harness/verify-suites.json`. Their
    content is not scanned, but the command line still is. The registry can only change in a signed tranche, so the
    exemption is exactly as strong as the registry.
  - **Alternative:** no exemption. All test fixtures avoid literal credential spellings and build them at runtime
    instead. That is weaker (a pure convention) and touches many tests.

- **Concurrent-session warning on native Windows (Ruling 117), a decision with a default.** Off Linux the Pipeline
  cannot tell whether another session in the same repository is still alive, so the "second live session" warning
  never fires on your PC.
  - **Default:** a spawn-free check for 0.7.0. The pid still exists and the boot time matches → "probably live" →
    the warning fires and says "probably". A reused pid can give a false warning, which is acceptable for an advisory.
  - **Alternative:** accept the limitation in 0.7.0 and document it.

- **Encrypted PO key and the onboarding test cells (Ruling 132), a decision with a default.** Once a PO key must be
  passphrase-protected, `setup --existing-key` asks for the passphrase through OpenSSL in the terminal. That is the
  intended attended step. Two onboarding-init test cells drive this step as a chain of two CLI processes, and no test
  seam can pass a passphrase across that chain.
  - **Default (already dispatched):** those two cells call the same code in-process, with the test seam supplying the
    passphrase. A separate pin proves that the spawned CLI path, which has no terminal, fails closed rather than
    hanging or signing. Production gets no passphrase source.
  - **Alternative:** a production passphrase source for tests (an environment variable or a flag). That is a security
    trade, because the same route would then exist outside tests.

- **Empty trust anchors in signature mode (security posture, needs your decision).** A repository with no pinned PO key
  accepts any self-made key at the implementation boundary: the "any well-formed key may sign" default. A signed design
  approval is then proof of self-consistency, not of you. This repository has pinned anchors, so nothing is affected
  here. Backlog: `backlog/items/2026-10-09-empty-trust-anchors-admit-any-self-made-key-at-the-design-approval-boundary.md`.
  - **Recommendation:** in signature mode, the boundary refuses an empty anchor set with a typed code and names the
    setup command. This first needs a check that onboarding always pins the key before the boundary, so a fresh
    repository is not locked out.
  - **Alternative:** keep the posture for 0.7.0 and document it as a limitation.

- **D0: an existing, insufficiently protected `.git/agent-pipeline` directory on Windows (Ruling 141, decision with a
  default).** On Windows, several components create this directory with inherited permissions. Some components refuse
  it later, so existing checkouts would fail as soon as the creators are hardened.
  - **Default (being implemented):** repair in place when the directory belongs to the current Windows user, with a
    visible note. Refuse when it belongs to anyone else.
  - **Alternative:** always refuse, with a repair command for you.

- **D1: a repository on a drive whose filesystem keeps no Unix permission bits (WSL on `/mnt/<drive>`; Ruling 156,
  decision with a default, candidate blocker).** Measured: under WSL on this repository's own drive, a directory created
  private reads as open to everyone and `chmod` has no effect, so the private-state root is refused every time and the
  governance store cannot be used from WSL.
  - **Default (being implemented):** accept the directory there with a visible typed advisory
    (`PB-ROOT-MODE-UNRECORDED`), never claiming it is private; the real protection is the Windows permission set on the
    underlying folder.
  - **Alternative:** refuse, with instructions to enable the WSL `metadata` mount option (one line in `/etc/wsl.conf`,
    then `wsl --shutdown`).

- **A guard fix landed in the wrong commit (Rulings 146, 153, 155; acknowledgement with a default).** The cross-volume
  fix for the maintenance-window scope check is correct, and two independent reviews found no code defect in it. It sits
  in commit `e51844ab8`, under another task's trailer and next to an unrelated feature, because two parallel tasks edited
  the same file. The reviewer's verdict is FAIL on provenance only: a revert of that feature commit would silently undo
  the security fix.
  - **Default:** keep history as it is (rewriting it is forbidden). A binding revert note is recorded in Ruling 153 and
    goes into the candidate handover. The process gap is closed by the write-set rule and the per-hunk check before
    every commit.
  - **Alternative:** add a dedicated commit that re-states the fix with its own trailer. That fixes the provenance trail
    but not the revert hazard.
