# CYB-7 — provenance + artifact integrity (feature spec)

> **Status: IMPLEMENTATION, PO-authorized 2026-08-01.** Translates issue #45 (fetched
> verbatim via `gh issue view 45`, 2026-07-25) into checkable form. Phase III,
> depends on CYB-1 (catalog) and CYB-3/SBOM subject links. Not dispatched.

## 1. Problem (condensed)

A clean scan + release manifest don't prove which source/dependencies/
builder/commands/outputs produced a released artifact — mutable actions/
images/dependencies can change build behavior, builder identity/isolation is
unknown, rebuilds aren't comparable, SBOMs/scan evidence may bind to source
while shipped bytes differ, signatures can be mistaken for provenance with an
ambiguous subject. Outcome: candidate-to-artifact provenance, immutable
digests, policy-governed attestations aligned with SLSA provenance concepts —
**without claiming an unproven SLSA level** (PRD deviation D-class, per spec.md
"honest reproducibility... no unproven SLSA claims").

## 2. Core invariants (verbatim from #45, already checkable)

1. Source candidate, build invocation, artifact subjects have unambiguous
   immutable identities.
2. Provenance generated by the build boundary, never retroactively authored
   by the artifact.
3. Every artifact reference carries a cryptographic digest.
4. Builder/dependency/action/container identities pinned or explicitly
   qualified.
5. Signatures/attestations via external key boundary; no private signing key
   enters the repository.
6. Unknown/unverifiable provenance cannot be called verified.
7. External services are optional adapters, not core authority.

## 4. Reproducibility graded states (from #45 §6, verbatim)

`not-assessed | non-reproducible-expected | repeatable-in-same-builder |
reproducible-in-independent-builder | hermetic-evidence-available | mismatch |
unverifiable`. Critical assurance profiles (CYB-1's `critical` level) may
require a second build or independent verification.

## 5. Scope carried (from #45 §1-§7, mapped to spec.md's CYB-7 summary)

Subject model (source/build/artifact, multi-package aware) · `provenance.v1`
envelope · digest enforcement at produce/promote/readback (AC8's three
boundaries) · release-manifest machine companion (L6) · reference local
builder for the plugin package itself (concrete, not abstract — this repo's
own plugin package is the proving ground) · signing/attestation via external
key boundary **with a working local-test-key sign/verify path** (AC12 — the
PRD's own emphasis that this must actually execute, not stay design-only) ·
graded reproducibility states (§4).

## 6. Non-goals (verbatim from #45)

Requiring bit-for-bit reproducibility for every technology; treating a
signature as proof of secure content; committing signing keys; replacing SBOM/
vulnerability-evidence/release approval; mandating one registry/builder/
attestation service.
