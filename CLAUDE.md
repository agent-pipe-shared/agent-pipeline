# CLAUDE.md — Agent-Pipeline

Central, versioned Operating Model for agentic development across the PO's projects (<PROJECT_A>, <PROJECT_B>, <PROJECT_C>, future ones). This file governs work **in this repo**. Per [ADR-0015](docs/adr/0015-self-application.md), the Pipeline's own working model applies to the Pipeline repo itself — there is no separate meta-ruleset for "building the Pipeline" versus "working under the Pipeline."

## Session bootstrap (mandatory, every session)

1. **Read `docs/state.md` first.** It is the single canonical handover file ([ADR-0012](docs/adr/0012-handover-canonicalization.md)) — current phase, the decision register, open items, next steps. It wins on conflict with anything below.
2. **Run the bootstrap protocol:** [`harness/session-bootstrap.md`](harness/session-bootstrap.md) (full spec; executable form: `/pipeline-core:pipeline-start`, shipped in `plugins/pipeline-core`). It checks ruleset staleness, project calibration, handover freshness, and verify-gate availability, and ends in a mandatory confirmation line — no work starts before that line is printed.
3. **Elephant sessions additionally:** set and verify model/effort per [`policies/model-policy.md`](policies/model-policy.md) (MP-01), confirm `CLAUDE_CODE_SUBAGENT_MODEL` is unset (MP-04).
4. Role definitions live in [`roles/`](roles/) (`elephant.md`, `goldfish.md`, `critic.md`); [`docs/operating-model.md`](docs/operating-model.md) — *Roles and boundaries* — remains authoritative on conflict.

## Hard rules

- **Read-only toward the three project repos** (<PROJECT_A>, <PROJECT_B>, <PROJECT_C>) for the duration of Sprint 0: `git fetch/pull/clone` and reading only, never a write — until an explicitly approved Phase-4 migration changes this per project.
- **Push policy (revised 2026-08-06, PO decision — supersedes the standing approval [ADR-0017] recorded for this repo):** the push gate is `approval: required`. Every push needs an approval recorded against the exact candidate commit (`pipeline-state.mjs approve-push`). **How a human clears it is one setting**, `gates.push_approval` in `pipeline.user.yaml` ([ADR-0056](docs/adr/0056-push-approval-mode.md)): `signature` (default, and this repo's value) demands a detached Ed25519 proof with the private key outside the repository; `chat` lets the human clear it in-session, still commit-bound and still labelled in the record, but an attribution record rather than proof. Anything unreadable or unrecognised resolves to `signature`. What stays forbidden is enforced by the guard union, not by asking: never force-push, never rewrite history, never delete protected branches/tags, never skip hooks. Project repos keep their own calibration rules (GIT-05). **Full step-by-step flow, layer by layer, exact commands, who runs each one:** [`docs/push-release-flow.md`](docs/push-release-flow.md) — read it once per session rather than rediscovering the layers live.
- **Conventional Commits; small, atomic commits** — one concern per commit, per work package.
- **No secrets, tokens, or machine-specific absolute paths** in docs, prompts, or commits — this repo runs on two machines with different local paths. Reference paths repo-relative.
- **Language per [ADR-0011](docs/adr/0011-language-policy.md):** this Public Core is English-canonical, including agent-facing artifacts, public human-facing documentation, backlog items, reviews, and commit messages. German is permitted only as an explicitly marked, bounded reader aid in public user documentation; a private overlay may configure its own operator-facing language. Mixed cases follow the target-scope rule.
- **Bilingual-doc skip convention:** in bilingual docs, the authoritative content is the ENGLISH above the marker line; everything below the marker `<!-- DE-REFERENCE-BELOW | agents: skip everything below this line; it is a full German reference translation (redundant, wastes context). The authoritative content is the English above. Convention: CLAUDE.md (Language). -->` is a full German reference translation that agents MUST NOT read (redundant; wastes context). Humans may read it.
- **Model discipline:** every dispatch (Goldfish/Critic briefing) names its model explicitly in the "Dispatch-Metadaten" field ([`docs/operating-model.md` §2, "Dispatch briefing fields"](docs/operating-model.md#dispatch-briefing-fields)) — the implement-tier model by default, the design-tier (higher-capability) model only with a stated rationale (MP-05/MP-07). Subagents otherwise silently inherit the session's model; that silent inheritance is the failure mode this rule closes. Naming the model correctly in the dispatch TEXT is not sufficient by itself: a target subagent definition's own frontmatter `model:` pin overrides it, so an actual escalation needs the tool-layer `model` parameter on the dispatch call (`policies/model-policy.md` MP-29).
- **Dispatch from the template, never freehand.** A Critic dispatch is built by filling [`templates/prompts/critic-review.md`](templates/prompts/critic-review.md); a Goldfish dispatch by filling `goldfish-task.md`. Hand-writing one is the failure mode, not a shortcut: the template already forbids what a hand-written briefing reliably smuggles in — a claims-to-verify list, a hunt list, an "expected" aside, an implementor characterization. It says so in those exact words (`critic-review.md` §2), and a 2026-08-06 dispatch that was written freehand carried all of it anyway, replacing the Critic's own contractual search surface ([`roles/critic.md`](roles/critic.md) §46/§103) with the Elephant's hypotheses. A review that only looks where you told it to look is not a second pair of eyes. Evidence reaches it as **artifact paths**, not as commands to re-run — re-executing suites the Elephant already ran spends the Critic's budget on being a second CI instead of on reading code. **This applies identically to a Workflow-tool `agent()` dispatch:** its prompt string is built from the SAME template (`goldfish-task.md` / `critic-review.md`), never reproduced from memory, PLUS the Workflow-specific additive requirements — the `pipeline-core:` `agentType` prefix, a stated tool-call budget, the worktree self-heal block where isolation is used — documented in [`plugins/pipeline-core/skills/pipeline-start/references/workflow-dispatch.md`](plugins/pipeline-core/skills/pipeline-start/references/workflow-dispatch.md). Hand-building a Workflow prompt from memory is the identical freehand failure reached via a different mechanism — confirmed 2026-08-18 (NVA-WFDISP-1): an Elephant hand-built two Workflow `agent()` prompts this way in the same session.
- **Persist immediately; never rely on chat history.** Decisions, state changes, and insights go into files as they happen — a session is a cache on the persisted artifact, not the record of truth (`docs/operating-model.md` — *Evidence, review and recovery*).
- **Never report "done" while any check is still open.** A completion report, handover status row, or PO-facing summary may only use unqualified "done" for PO-accepted work (`docs/operating-model.md` §10 Glossary: Implementation complete vs. PO-accepted). While verify, independent Critic review, a manual/browser check, or explicit PO acceptance remains outstanding, name it explicitly by category ("implementation complete, PO acceptance pending" is not "done"; `roles/goldfish.md` §6 GF-09, `templates/handover.md`'s 🔵 marker). A push may still happen on explicit PO request with documented pending items, but the report must never describe it as fully accepted (2026-08-18, greenfield happy-path finding P1-6: a result was reported done although browser verification and an independent Critic review were both still missing).
- **Re-verify an inherited "still open"/"still needed" claim before dispatching work on it.** Before briefing a dispatch to address a backlog item or piece of work characterized as "still open" by an earlier survey, session, or another agent's report, re-read that item's own current Triage/status text and check `git log` for the area — trusting the inherited characterization without a fresh live check produced three separate stale-claim incidents in one 2026-08-18 session block (methodological, not one-off).
- **Self-application:** this repo's own checkpoint deliverables get an independent Critic review (fresh context, structured findings, [ADR-0014](docs/adr/0014-critic-contract.md)) BEFORE the PO's gate — the same contract the Pipeline imposes on the projects it governs.
- **No tree mutation while a HEAD/tree-bound PO command is outstanding.** Once you hand the PO a terminal command whose validity is bound to an exact HEAD or working-tree state (a push-approval or human-guard-override signature step, `guard-human-override.mjs plan`/`prepare-authorization`/`emit-signature-digest`/`authorize-by-signature`, anything reading `repository.head`/`statusSha256`), do not commit, `git stash`, or otherwise change the tracked or untracked tree until that command returns — including files you'd normally write immediately (docs/state.md, memory, scratch notes). Confirmed costly 2026-08-18: an Elephant edited `docs/state.md` and created a new file between handing over a `plan`/`prepare-authorization` result and the PO's `authorize-by-signature` call; both changed the bound `statusSha256`, triggering `HGO-DRIFT` and burning a live PO passphrase entry for nothing. Hold any such note in `scratch/` (or just in the turn's own text) and persist it for real only after the outstanding command returns.
- **A `guard-testpath.mjs` denial's admission failure has TWO known causes, and they render identically — measure which one before re-spending a PO ceremony.** Cause 2 is an expired window on a LEGACY capability, armed before commit `87a94007` fixed arming: both `authorize-by-signature` and chat-mode `authorize` now refuse to arm a capability past its own plan window in the first place, checked at both routes before the capability is built. A capability armed BEFORE that fix can still exist on disk, still self-reporting `{"status":"armed"}` for a window that has already closed; only `consumeHumanGuardOverride()` catches those (`human-guard-override.mjs` line 3359), and the retry then fails looking exactly like a first denial. Confirmed live 2026-08-28: a capability recorded `authorizedAt` 10:03:47Z against `expiresAt` 09:47:32Z, and the PO's signature was burned — that capability predated the fix. **Diagnose by running `plan` on both the original and the newly seeded request and comparing `toolInputSha256`: identical digests rule cause 1 out and point at the window** (`backlog/items/2026-08-28-an-expired-override-is-armed-instead-of-refused.md`). Practical consequence for the dispatcher: seed a ceremony only when the PO can sign immediately, and consume the signature the moment it arrives — never interleave other work, including writing a briefing, between seeding and consuming. Cause 1, a byte-identity mismatch, is not a code defect: `consumeHumanGuardOverride()` matches an armed capability against the retried tool call by `toolInputSha256` (`sha(canonical(toolInput))`, human-guard-override.mjs), computed from the RAW tool_input payload — not a semantic diff. Any difference between the exact tool call that produced the original denial and the one retried after the PO signs (a re-derived `old_string`/`new_string`, a different absolute path spelling, an optional field like `replace_all` present in one call and not the other) silently fails the match and falls through to an unarmed-looking denial, with no diagnostic surfaced anywhere — confirmed empirically 2026-08-18 (two live OT09 ceremony attempts failed this way; a controlled repro reproduced the exact mismatch, and a ceremony built from a request seeded by the ACTUAL intended retry consumed cleanly). **Before starting a live ceremony:** attempt the intended edit once (it will be denied — this is safe, no mutation happens, PreToolUse blocks pre-execution) to seed a fresh request in `.git/agent-pipeline/human-guard-overrides/requests/` carrying that exact call's `toolInputSha256`; build `plan`/`prepare-authorization`/`emit-signature-digest` FROM that same request-sha256; after the PO signs and `authorize-by-signature` arms the capability, retry with the IDENTICAL Edit call used to seed the request (same tool call, not a reconstruction) — do not let other turns or edits happen in between. A single Edit call can only cover one contiguous text region; multiple non-adjacent changes to one protected file need either multiple ceremonies or one Edit whose `old_string` spans the full region between them.
- **A handover-rotation extraction pass (ADR-0066 Decision 6/7) may be done incrementally, scoped to the sections about to be rotated in one event — never required as an all-at-once pass over the whole file's history before any rotation can run.** This is a process rule, not a purely mechanical one: `handover-rotate.mjs`'s `--acknowledge-extraction-done` marker is schema v2 (`pipeline.handover-rotation-extraction-ack.v2`, ADR-0066 Decision 6 amendment, 2026-08-18 — an earlier repo-wide one-time-boolean schema v1 was replaced because it stopped gating future rotations after the first acknowledgment), tracking `{title, contentHash, acknowledgedAt}` per section: a rotation naming a section never acknowledged, or edited since its last acknowledgment (content-hash mismatch), is mechanically refused. What the tool still cannot verify is whether the acknowledgment itself reflected a genuine read — it can only confirm the named section's current bytes hash-match a prior `--acknowledge-extraction-done` call, not that anyone actually reviewed those bytes for embedded durable rules. The incremental discipline therefore stays a session-held responsibility layered on top of the mechanical gate, not replaced by it: before acknowledging (and thereby unblocking rotation of) a batch of sections, actually read them for embedded durable rules with no home yet (an ADR, a guardrail, this file); only acknowledge/rotate what was actually reviewed in that pass, oldest-first; never treat a passing hash-match as evidence that the content was reviewed rather than merely re-acknowledged unread.

## Environment note

If `git` is unexpectedly missing from a session's `PATH`, treat it as a stale shell environment, not a missing install. Probe availability and version locally with `command -v git` and `git --version`; never persist machine-specific installation paths or versions in this repository.

`isolation: "worktree"` (Agent tool or Workflow `agent()`) provisions a fresh worktree from the LOCAL `refs/remotes/origin/HEAD` symbolic ref's target — never from the current checkout's branch/HEAD. **Root cause confirmed 2026-08-18 by direct test**, not inferred: `git symbolic-ref refs/remotes/origin/HEAD` in this repo pointed at `origin/main` (stuck since the last real release, hundreds of commits behind the actual working branch); a fresh worktree landed exactly on `origin/main`'s tip. Repointing it locally (`git symbolic-ref refs/remotes/origin/HEAD refs/remotes/origin/<current-working-branch>`, a local-only, reversible ref change — no network, no push) immediately made the NEXT fresh worktree land on that branch's tip instead — but that tip is only as fresh as the last real push to it, still behind an unpushed local HEAD.

**The reliable fix is a self-heal step, not a stop — but only once the dispatch has confirmed it is actually inside its own worktree.** A worktree shares this repo's object database, so any locally-committed SHA (pushed or not) is already present in it: on a HEAD mismatch, self-heal via `git checkout --detach <exact-expected-sha>` is safe in a fresh, own worktree with no work of its own yet — confirmed live to move HEAD cleanly to the exact target with an empty `git status`, no network, no data loss. It is NOT safe in a shared checkout carrying live uncommitted work, which is exactly the case that fired 2026-08-25 (below). Every worktree-isolated dispatch briefing must therefore supply the expected worktree path (the path the dispatch was asked to be provisioned into) alongside the expected SHA, and the dispatch's mandatory first step is a **containment check performed BEFORE any `checkout --detach`**: compare its own `git rev-parse --show-toplevel` against that briefed expected worktree path. If they do not match, the dispatch is running in a shared checkout, not its own worktree — it STOPS and reports; it never runs `checkout --detach`. Only when they match does the existing remedy proceed exactly as before: check `git rev-parse HEAD` against the exact expected SHA; on mismatch, self-heal via `git checkout --detach <sha>`, re-verify, then proceed normally; only STOP if that checkout itself fails (the SHA is not a valid local object — a genuinely different problem).

**After launching any worktree-isolated dispatch, still run `git worktree list` immediately** to sanity-check the base before trusting the dispatch — and treat the result as load-bearing, not a formality. A result showing only the single main worktree entry means isolation was NOT actually granted for that dispatch: that is a hard stop for launching further worktree-isolated dispatches in the same session, not a note to move past. Instead, either serialize the remaining work through the shared tree (see the shared-tree rule in `plugins/pipeline-core/skills/pipeline-start/references/workflow-dispatch.md`) or re-brief it explicitly as a non-isolated, shared-tree dispatch with no self-heal block at all, rather than continuing to hand out a self-heal instruction whose own precondition (an actual own worktree) is false. Confirmed 2026-08-25: three Agent-tool dispatches briefed with `isolation: "worktree"` all landed directly in the dispatcher's own checkout — `git worktree list` showed a single entry, checked twice — and one retry dispatch's self-heal step then ran `git checkout --detach <sha>` against that shared checkout, detaching the Elephant's live HEAD mid-session and costing a large fraction of the session to recover.
