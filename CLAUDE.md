# CLAUDE.md — Agent-Pipeline

Central, versioned Operating Model for agentic development across the PO's projects (<PROJECT_A>, <PROJECT_B>, <PROJECT_C>, future ones). This file governs work **in this repo**. Per [ADR-0015](docs/adr/0015-self-application.md), the Pipeline's own working model applies to the Pipeline repo itself — there is no separate meta-ruleset for "building the Pipeline" versus "working under the Pipeline."

## Session bootstrap (mandatory, every session)

1. **Read `docs/state.md` first.** It is the single canonical handover file ([ADR-0012](docs/adr/0012-handover-canonicalization.md)) — current phase, the decision register, open items, next steps. It wins on conflict with anything below.
2. **Run the bootstrap protocol:** [`harness/session-bootstrap.md`](harness/session-bootstrap.md) (full spec; executable form: `/pipeline-core:pipeline-start`, shipped in `plugins/pipeline-core`). It checks ruleset staleness, project calibration, handover freshness, and verify-gate availability, and ends in a mandatory confirmation line — no work starts before that line is printed.
3. **Elephant sessions additionally:** set and verify model/effort per [`policies/model-policy.md`](policies/model-policy.md) (MP-01), confirm `CLAUDE_CODE_SUBAGENT_MODEL` is unset (MP-04).
4. Role definitions live in [`roles/`](roles/) (`elephant.md`, `goldfish.md`, `critic.md`); [`docs/operating-model.md`](docs/operating-model.md) — *Roles and boundaries* — remains authoritative on conflict.

## Hard rules

- **Read-only toward the three project repos** (<PROJECT_A>, <PROJECT_B>, <PROJECT_C>) for the duration of Sprint 0: `git fetch/pull/clone` and reading only, never a write — until an explicitly approved Phase-4 migration changes this per project.
- **Push policy (revised 2026-08-06, PO decision — supersedes the standing approval [ADR-0017] recorded for this repo):** the push gate is `approval: required`. Every push needs an approval recorded against the exact candidate commit (`pipeline-state.mjs approve-push`). **How a human clears it is one setting**, `gates.push_approval` in `pipeline.user.yaml` ([ADR-0056](docs/adr/0056-push-approval-mode.md)): `signature` (default, and this repo's value) demands a detached Ed25519 proof with the private key outside the repository; `chat` lets the human clear it in-session, still commit-bound and still labelled in the record, but an attribution record rather than proof. Anything unreadable or unrecognised resolves to `signature`. What stays forbidden is enforced by the guard union, not by asking: never force-push, never rewrite history, never delete protected branches/tags, never skip hooks. Project repos keep their own calibration rules (GIT-05). **Full step-by-step flow, layer by layer, exact commands, who runs each one:** [`docs/push-release-flow.md`](docs/push-release-flow.md) — read it once per session rather than rediscovering the layers live.
- **Conventional Commits; small, atomic commits** — one concern per commit, per work package.
- **No secrets, tokens, or machine-specific absolute paths** in docs, prompts, or commits — this repo runs on two machines with different local paths. Reference paths repo-relative.
- **Language per [ADR-0011](docs/adr/0011-language-policy.md):** this Public Core is English-canonical, including agent-facing artifacts, public human-facing documentation, backlog items, reviews, and commit messages. German is permitted only as an explicitly marked, bounded reader aid in public user documentation; a private overlay may configure its own operator-facing language. Mixed cases follow the target-scope rule.
- **Bilingual-doc skip convention:** in bilingual docs, the authoritative content is the ENGLISH above the marker line; everything below the marker `<!-- DE-REFERENCE-BELOW | agents: skip everything below this line; it is a full German reference translation (redundant, wastes context). The authoritative content is the English above. Convention: CLAUDE.md (Language). -->` is a full German reference translation that agents MUST NOT read (redundant; wastes context). Humans may read it.
- **Model discipline:** every dispatch (Goldfish/Critic briefing) names its model explicitly in the "Dispatch-Metadaten" field ([`docs/operating-model.md` §2, "Dispatch briefing fields"](docs/operating-model.md#dispatch-briefing-fields)) — the implement-tier model by default, the design-tier (higher-capability) model only with a stated rationale (MP-05/MP-07). Subagents otherwise silently inherit the session's model; that silent inheritance is the failure mode this rule closes. Naming the model correctly in the dispatch TEXT is not sufficient by itself: a target subagent definition's own frontmatter `model:` pin overrides it, so an actual escalation needs the tool-layer `model` parameter on the dispatch call (`policies/model-policy.md` MP-29).
- **Dispatch from the template, never freehand.** A Critic dispatch is built by filling [`templates/prompts/critic-review.md`](templates/prompts/critic-review.md); a Goldfish dispatch by filling `goldfish-task.md`. Hand-writing one is the failure mode, not a shortcut: the template already forbids what a hand-written briefing reliably smuggles in — a claims-to-verify list, a hunt list, an "expected" aside, an implementor characterization (`critic-review.md` §2; the Critic's own search surface is [`roles/critic.md`](roles/critic.md) §46/§103). Evidence reaches it as **artifact paths**, not as commands to re-run. **This applies identically to a Workflow-tool `agent()` dispatch:** the SAME template, never reproduced from memory, PLUS the `pipeline-core:` `agentType` prefix, a stated tool-call budget and the worktree self-heal block where isolation is used ([`workflow-dispatch.md`](plugins/pipeline-core/skills/pipeline-start/references/workflow-dispatch.md)).
- **Persist immediately; never rely on chat history.** Decisions, state changes, and insights go into files as they happen — a session is a cache on the persisted artifact, not the record of truth (`docs/operating-model.md` — *Evidence, review and recovery*).
- **Never report "done" while any check is still open.** A completion report, handover status row, or PO-facing summary may only use unqualified "done" for PO-accepted work (`docs/operating-model.md` §10 Glossary: Implementation complete vs. PO-accepted). While verify, independent Critic review, a manual/browser check, or explicit PO acceptance remains outstanding, name it explicitly by category ("implementation complete, PO acceptance pending" is not "done"; `roles/goldfish.md` §6 GF-09, `templates/handover.md`'s 🔵 marker). A push may still happen on explicit PO request with documented pending items, but the report must never describe it as fully accepted.
- **Re-verify an inherited "still open"/"still needed" claim before dispatching work on it.** Before briefing a dispatch to address a backlog item or piece of work characterized as "still open" by an earlier survey, session, or another agent's report, re-read that item's own current Triage/status text and check `git log` for the area.
- **Self-application:** this repo's own checkpoint deliverables get an independent Critic review (fresh context, structured findings, [ADR-0014](docs/adr/0014-critic-contract.md)) BEFORE the PO's gate — the same contract the Pipeline imposes on the projects it governs.
- **No tree mutation while a HEAD/tree-bound PO command is outstanding.** Once you hand the PO a terminal command whose validity is bound to an exact HEAD or working-tree state (a push-approval or human-guard-override signature step, `guard-human-override.mjs plan`/`prepare-authorization`/`emit-signature-digest`/`authorize-by-signature`, anything reading `repository.head`/`statusSha256`), do not commit, `git stash`, or otherwise change the tracked or untracked tree until that command returns — including files you'd normally write immediately (docs/state.md, memory, scratch notes); a changed bound `statusSha256` fails the ceremony with `HGO-DRIFT` and burns the PO's passphrase entry. Hold any such note in `scratch/` (or just in the turn's own text) and persist it for real only after the outstanding command returns.
- **A `guard-testpath.mjs` denial that survives a signed override has TWO known causes that render identically — measure which one before re-spending a PO ceremony.** Run `plan` on the original and the newly seeded request and compare `toolInputSha256`: identical digests point at an expired window on a LEGACY capability (armed before commit `87a94007`; `backlog/items/2026-08-28-an-expired-override-is-armed-instead-of-refused.md`), different ones at a byte-identity mismatch — the armed capability matches the retried call by `toolInputSha256` of the RAW tool_input, so a re-derived `old_string`, another path spelling or an extra optional field fails silently. **Before a live ceremony:** attempt the intended edit once (denied, no mutation) to seed a request carrying that exact call's `toolInputSha256`; build `plan`/`prepare-authorization`/`emit-signature-digest` FROM that request; seed only when the PO can sign immediately; once `authorize-by-signature` arms it, retry with the IDENTICAL tool call at once — nothing in between, not even a briefing. One Edit covers one contiguous region; non-adjacent changes to one protected file need several ceremonies or one Edit spanning the region.
- **A handover-rotation extraction pass (ADR-0066 Decision 6/7) may be done incrementally, scoped to the sections about to be rotated in one event — never required as an all-at-once pass over the whole file's history before any rotation can run.** The per-section `--acknowledge-extraction-done` marker of `handover-rotate.mjs` only proves a section's bytes match a prior acknowledgment, never that anyone read them: before acknowledging a batch, actually read those sections for embedded durable rules with no home yet (an ADR, a guardrail, this file); only acknowledge/rotate what was reviewed in that pass, oldest-first.
- **Reusable scripts never stay in `scratch/`.** A helper that will be used again (stamp, runner, rebaseline, remeasure) is committed under `scripts/` with a purpose and usage header and listed in `docs/operating-tools.md`; the PO works on two machines and `scratch/` is untracked.

## Environment note

If `git` is unexpectedly missing from a session's `PATH`, treat it as a stale shell environment, not a missing install. Probe availability and version locally with `command -v git` and `git --version`; never persist machine-specific installation paths or versions in this repository.

`isolation: "worktree"` (Agent tool or Workflow `agent()`) provisions a fresh worktree from the LOCAL `refs/remotes/origin/HEAD` symbolic ref's target — never from the current checkout's branch/HEAD; repointing that ref locally is a reversible fix, still only as fresh as the last push. Every worktree-isolated briefing therefore supplies the expected worktree path and the expected SHA, and the dispatch's mandatory first step is a **containment check BEFORE any `checkout --detach`**: compare `git rev-parse --show-toplevel` with that path. On a mismatch it is in a shared checkout — it STOPS and reports, never `checkout --detach`. Only on a match, and a HEAD that differs from the SHA, it self-heals with `git checkout --detach <sha>` (the object database is shared), re-verifies and proceeds; it stops only if that checkout fails.

**After launching any worktree-isolated dispatch, run `git worktree list` immediately** and treat it as load-bearing: a single main entry means isolation was NOT granted — a hard stop for further worktree-isolated dispatches this session. Serialize the rest through the shared tree (`plugins/pipeline-core/skills/pipeline-start/references/workflow-dispatch.md`) or re-brief it as a non-isolated dispatch with no self-heal block.
