# ADR-0100: configure-verify may replace the verify command, with one signature

> Agent-Pipeline · Sprint Alfred · 2026-11-14

**Status:** accepted (2026-11-13, PO tile 3 after the 28d test round, "configure-verify replaces, 1 signature", register D252). Built in candidate 29d. Not yet run on a consumer repository.

**Context source (PO tile, 2026-11-13, test round 28d, finding C6):** the PO chose the recommended option: during implementation `configure-verify` may replace the verify command; the new command runs once first; then one PO signature covers both mirror files; the Critic gets the provenance and no longer reports the commit as EL-01.

## Context

`configure-verify` writes the verify command into the two calibration mirrors (`project/pipeline.json`, `.claude/pipeline.json`) once, from the baseline-only seed. A second call with another command is refused ("refused calibration tiers (configured)"), and the guard refuses a hand edit of either mirror (gate-strength `GS-10`/`GS-11`).

In the 28d test round a consumer had to change its verify command (it failed on a newer Node). It took about ten steps: the guard refused four times and named `configure-verify`, which refused once configured; the Elephant then ran two signed human-guard overrides, one per mirror file, each with a proof wait that timed out after 570 s; and the Critic reported the two signed commits as a major (EL-01, the Elephant wrote a gate file).

## Decision

1. **An explicit replace route.** `pipeline-state.mjs configure-verify --verify-command <new> --replace` replaces a configured command during an implementing lifecycle. Without `--replace` the configured-tier refusal is unchanged. `--replace` is refused when the committed command is not configured, when it equals the new one, or when the new one names the evidence producer or the Verify adapter (the rule the consumer Verify check already applies).
2. **The new command runs once first, and must pass.** On a tree with no tracked change (untracked files are allowed, and must be left exactly as they were) the route runs the new command the way the consumer Verify check runs it (`shell: true`, in the project root, with a timeout). It records a private test-run receipt: the command's digest, HEAD and tree, the exit code, the duration and the output digest. The tree must still be clean afterwards. A non-zero exit, a timeout or a changed tree refuses (`CVR-TEST-RUN-RED`, `CVR-TEST-RUN-DRIFT`); nothing is signed. Taking the stricter reading of "test run first" is an open PO question (AFK tile T7).
3. **One signature over both post-images.** A new critical-action kind, `replace-verify-command`, in the `gates.human_approval` mode, fail-closed to `signature`. Its subject is built by one builder that the recording step and the signing terminal share: the feature id, the previous and the new command, the test-run receipt digest, and for each committed mirror its path, its committed bytes digest and the exact post-image digest. The candidate is the clean HEAD. One proof covers both files. In `chat` mode the record is chat-attributed and labelled, as for every critical kind.
4. **The write is exactly the signed bytes, and the commit takes the existing configure-verify transition.** With a verified, unconsumed proof the route writes both mirrors with the signed post-images and prepares the existing configure-verify commit transition with a `replacement` member (previous command, subject digest, proof digest). The transition accepts a configured previous command only with that member. The pre-commit hook admits the staged mirrors through the same transition check it already runs (no new union member). The commit route printed is the existing one, with the subject line `chore: replace project verification command`.
5. **The close sees it as proven, unlabelled when signed.** Amends ADR-0096 Decision 3: for `GS-10`/`GS-11` a configure-verify transition record that carries a `replacement` member and a signature proof is the proof kind `verify-replacement`, with no label; a chat-attributed one is labelled "chat-attributed, not signed". A first configuration keeps its label "confirmed via runner prompt, not signed". The record is device-local, as before; on another machine the change needs the ADR-0096 acknowledgement (its Decision 4).
6. **A replace between red and green repairs nothing.** Amends ADR-0097 Decision 4: the green receipt of a maintenance slice for `verify:configured` counts only when the calibrated verify command at the receipt's commit equals the one at the slice's base commit. A replaced command therefore never turns a red check green by itself.
7. **The Critic sees a sanctioned commit.** The Critic constructs its own input. The commit is a configure-verify transition commit with the standard message, made by the Pipeline's own writer after a signed approval, not a hand edit under an override. The proof list is not handed to the Critic (ADR-0014; ADR-0096 Decision 6); the audit bundle's `gate-changes` item lists the change with the proof kind `verify-replacement`. No Critic template changes.

## Consequences

- A verify command change during implementation is three steps: the replace call (test run, then the signing request), the PO's one signature, and the replace call again, then the printed commit.
- `po-human-approval.mjs` knows the kind (`prepare-critical`/`authorize-critical` without `--subject`; the subject is derived).
- The lifecycle guard needs no change (it does not list `pipeline-state.mjs` flags in the ready lane). Measured 2026-11-14 on the installed 29c guard: the replace call shape runs (the 29c script itself then refuses the unknown flag), and `git add -- project/pipeline.json .claude/pipeline.json` is admitted (the gate-strength shell lane admits `git add` by its allowlist). The pre-commit hook admits the staged mirrors through the transition check, and its "commit them alone" repair recognises a ready replacement too. The gate-strength refusal for `GS-10`/`GS-11` and the configured-tier refusal of `configure-verify` now name the `--replace` route, so an agent is no longer sent to two overrides for a verify-command change.
- The approval mode is bound into the PO-gate authority at plan approval: switching `gates.human_approval` after the plan was approved makes the transition refuse (`CVCT-AUTHORITY-STALE`), for this route as for a first configuration. The round-trip suite therefore runs the signature leg on a chat-approved fixture through a test seam (`forceStrictCriticalProof`, which can only force the strict proof path, never waive one); the proof, store, transition and readback it exercises are the production code.
- The commit hook and the close readback count a record's `replacement` member only when this device's store holds the approval of exactly that subject digest and proof digest; signed or unsigned therefore follows the stored approval, not the record's own mode word.
- Not covered: replacing `verifyImpact` commands; a replace outside the implementing lifecycle; the Critic template naming the proof kind (it would need a re-pin, a PO decision).
